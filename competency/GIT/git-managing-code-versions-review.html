Beginner HackerRank: Version Control Basics · Basic Commands · Gitignore

ตรงกับเกณฑ์ Beginner ข้อ “ใช้ version control tool เช่น Git จัดการ source code และติดตามการเปลี่ยนแปลง” และหัวข้อ Version Control Basics, Basic Commands กับ Gitignore ของ HackerRank Git (Basic)

เคสนี้เจอบ่อยมากในคนที่เพิ่งเริ่มใช้ Git แก้ไฟล์เสร็จแล้วสั่ง git commit -m "fix bug" Git ตอบกลับมาว่า no changes added to commit ทั้งที่ไฟล์ก็แก้จริง ปัญหาไม่ได้อยู่ที่ Git ไม่ทำงาน แต่ Git ไม่ได้ commit ไฟล์ที่เราแก้ มันจะ commit เฉพาะสิ่งที่ถูกเตรียมไว้ใน staging area เท่านั้น ถ้าเข้าใจจุดนี้ได้ คำสั่งพื้นฐานที่เหลือก็ตามมาเอง

Git เก็บอะไร และเก็บไว้ที่ไหน

Git เป็น distributed version control system แปลว่าทุกเครื่องที่ clone repository มาจะมี history ครบทั้งก้อน ไม่ได้ขอ history จาก server ทุกครั้งที่ดู log แบบระบบ centralized รุ่นเก่าอย่าง SVN ผลที่ตามมาคือ commit, ดู log, สร้าง branch ทำได้โดยไม่ต้องต่อเน็ต และ remote ก็เป็นแค่อีกสำเนาหนึ่งที่ทีมตกลงกันว่าเป็นจุดแลกเปลี่ยน

ในเครื่องเรา ไฟล์หนึ่งไฟล์เดินทางผ่านสามพื้นที่ ดูจากภาพด้านล่าง

พื้นที่คืออะไรคำสั่งที่ย้ายของเข้าพื้นที่นี้
Working treeไฟล์จริงบนดิสก์ที่เรากำลังแก้ใน editorแก้ไฟล์ด้วยมือ
Staging area (index)รายการสิ่งที่จะอยู่ใน commit ถัดไปgit add
Repository (.git)ฐานข้อมูล commit ทั้งหมดของ repogit commit

การมี staging area คั่นอยู่ทำให้เราเลือกได้ว่าจะเอาอะไรเข้า commit เช่น แก้ไว้สามไฟล์ แต่สองไฟล์เป็นงานเดียวกัน ก็ add เฉพาะสองไฟล์นั้นแล้ว commit แยกออกมา ถ้าอยากเลือกถึงระดับบรรทัดให้ใช้ git add -p

คำสั่งรอบแรกที่ต้องใช้ได้คล่อง

git init                          # สร้าง repo ใหม่ในโฟลเดอร์ปัจจุบัน
git clone <url>                   # ดึง repo ที่มีอยู่มาพร้อม history ทั้งหมด
git status                        # ไฟล์ไหนอยู่พื้นที่ไหน
git add src/app.js                # ส่งการเปลี่ยนแปลงของไฟล์นี้เข้า staging
git commit -m "fix: ตรวจค่าว่างก่อนคำนวณ"   # สร้าง commit จากสิ่งที่อยู่ใน staging
git log --oneline                 # ดู history แบบสั้น

git clone ทำมากกว่า git init อยู่สองอย่าง คือตั้ง remote ชื่อ origin ให้ชี้กลับไปยัง URL ที่ clone มา และ checkout branch เริ่มต้นให้พร้อมใช้งาน ชื่อ origin เป็นแค่ชื่อที่ตั้งตามธรรมเนียม จะเปลี่ยนเป็นอะไรก็ได้

diff มีสามแบบ และต้องรู้ว่าเทียบอะไรกับอะไร

คำสั่งเทียบใช้ตอนไหน
git diffworking tree กับ staging areaดูสิ่งที่แก้แล้วแต่ยังไม่ได้ add
git diff --stagedstaging area กับ commit ล่าสุด (HEAD)ตรวจก่อน commit ว่าอะไรจะเข้าไป
git diff HEADworking tree กับ HEADดูทุกอย่างที่เปลี่ยนจาก commit ล่าสุด ไม่สนว่า add หรือยัง

ลองดูโค้ดนี้ว่าผลลัพธ์จะเป็นอย่างไร

echo "v1" > a.txt
git add a.txt
echo "v2" > a.txt
git commit -m "add a"

commit ที่ได้เก็บ v1 ไม่ใช่ v2 เพราะ git add ถ่ายสำเนาเนื้อหา ณ ตอนที่สั่ง ไม่ได้จดว่า “ไฟล์นี้” แล้วไปอ่านใหม่ตอน commit หลัง commit เสร็จ git status จะแสดง a.txt เป็น modified เพราะ working tree ตอนนี้ต่างจาก commit แล้ว นี่เป็นเหตุผลที่ควรเช็ก git diff --staged ก่อน commit ทุกครั้ง

commit และ HEAD

commit คือ snapshot ของทั้งโปรเจกต์ ณ จุดหนึ่ง พร้อมชื่อผู้เขียน เวลา ข้อความ และตัวชี้ไปยัง commit ก่อนหน้า (parent) รหัสที่เห็นยาว ๆ เป็นผลคำนวณจากเนื้อหาของ commit ทั้งหมด ถ้าเนื้อหาหรือ parent ต่างไปแม้นิดเดียว รหัสก็เปลี่ยน ส่วน HEAD คือตัวชี้ว่าตอนนี้เราอยู่ตรงไหน ปกติมันชี้ต่อไปที่ branch ที่กำลังใช้ และ branch ก็ชี้ไปที่ commit ล่าสุดของมัน

ข้อความ commit ควรบอกว่า “ทำไม” ถึงแก้ ไม่ใช่แค่ “แก้อะไร” เพราะ diff บอกอยู่แล้วว่าแก้อะไร อีกหกเดือนข้างหน้าคนที่เปิด git blame อยากรู้เหตุผลมากกว่า

ตั้งค่าตัวตนและระดับของ config

git config --global user.email "somchai@example.com"
git config --list --show-origin     # ดูว่าแต่ละค่ามาจากไฟล์ไหน

Config มีสามระดับ คือ system (ทั้งเครื่อง), global (ของ user) และ local (เฉพาะ repo นั้น ที่ .git/config) ค่าที่ระดับแคบกว่าชนะระดับกว้างกว่า local ชนะ global ชนะ system เครื่องที่ใช้ทั้งงานและโปรเจกต์ส่วนตัวมักตั้ง email ระดับ global เป็นอีเมลหนึ่ง แล้วไป override ใน repo ที่ต่างกันด้วยคำสั่ง git config user.email ... ที่ไม่ใส่ --global

.gitignore ใช้กับไฟล์ที่ ยังไม่ถูก track เท่านั้น ถ้าไฟล์ถูก commit ไปแล้ว การเพิ่มชื่อไฟล์ลง .gitignore ไม่ทำให้ Git เลิกติดตาม ลองดูผลจริง

echo ".env" > .gitignore
echo "secret=2" >> .env
git status -s
#  M .env          ← ยังขึ้น modified เพราะ .env ถูก track อยู่ก่อนแล้ว
git rm --cached .env      # เลิก track แต่ไม่ลบไฟล์ในเครื่อง
git status -s
# D  .env          ← จะถูกลบออกจาก repo ใน commit ถัดไป
git check-ignore -v .env  # ถามว่า rule ไหนทำให้ไฟล์นี้ถูก ignore
ถ้าเคย commit secret ไปแล้วการ git rm --cached ลบไฟล์ออกจาก commit ถัดไปเท่านั้น ค่าเดิมยังอยู่ใน history ต้องถือว่า secret นั้นรั่วแล้วและเปลี่ยนค่าใหม่ เรื่องการล้าง history อยู่ในหัวข้อ 14

สามอย่างที่ทำให้ history รก คือ พิมพ์ git add . โดยไม่ดู git status ก่อนแล้วไฟล์ build หรือ log เข้ามาด้วย, commit ก้อนใหญ่ที่ผสมหลายเรื่อง จน revert เรื่องเดียวไม่ได้, และ commit ไฟล์ที่ไม่ควรมีใน repo อย่าง .env, node_modules/ ส่วน lock file อย่าง package-lock.json ควร commit เพราะช่วยให้ทุกคนได้ dependency เวอร์ชันเดียวกัน

HEAD และการอ้างอิง commit: ~ ^ @ {}

Beginner HackerRank: Basic Commands · Git Log

ตรงกับเกณฑ์ Beginner ข้อ “ใช้ Git จัดการ source code และติดตามการเปลี่ยนแปลง” โดยเน้นการอ้างถึง commit ด้วย HEAD และสัญลักษณ์ ~ ^ @ {} ที่ใช้ได้ในเกือบทุกคำสั่ง ตรงกับหัวข้อ Basic Commands และ Git Log ของ HackerRank Git (Basic)

คำสั่งอย่าง git reset --hard HEAD~2 หรือ git diff @{u} โผล่อยู่ในแทบทุกบทความเรื่อง Git แต่คนจำนวนมากแค่ copy ไปวาง พอเจอ merge commit ก็ชี้ผิดตัวโดยไม่รู้ว่าพลาดตรงไหน ส่วนนี้ไล่ตัวอ้างอิงเหล่านั้นทีละอัน ตั้งแต่ HEAD เองไปจนถึงเครื่องหมายแปลก ๆ ที่ต้องครอบ quote

HEAD คือตัวชี้ว่าตอนนี้เรายืนอยู่ตรงไหน

HEAD เป็นไฟล์เล็ก ๆ ชื่อ .git/HEAD ในสภาพปกติมันไม่ได้เก็บรหัส commit แต่เก็บชื่อ branch เช่น ref: refs/heads/main แล้ว branch ค่อยชี้ต่อไปยัง commit อีกที ลำดับจึงเป็น HEAD → branch → commit เวลา commit ใหม่ Git ขยับ branch ไปข้างหน้า HEAD ก็ตามไปเองเพราะชี้ผ่าน branch

มีอีกสถานะคือ detached HEAD ซึ่งไฟล์ HEAD เก็บรหัส commit ตรง ๆ ไม่ผ่าน branch เกิดตอน checkout commit เก่าหรือ tag ลองดูทั้งสองแบบ

cat .git/HEAD                     # ref: refs/heads/main
git symbolic-ref -q HEAD          # refs/heads/main (ถ้า detached จะไม่พิมพ์อะไรและ exit code ไม่เป็น 0)
git rev-parse HEAD                # รหัสเต็มของ commit ที่ HEAD ชี้อยู่
git checkout HEAD~2               # ไป commit เก่า สถานะกลายเป็น detached HEAD
git switch -c experiment          # ถ้าอยากเก็บงานที่ทำต่อจากตรงนี้ ให้สร้าง branch ก่อนสลับออก
commit ที่ทำตอน detached ไม่มี branch ถือไว้ถ้าสลับกลับ main ไปเลย commit เหล่านั้นไม่มีตัวชี้แล้ว ยังกู้ได้จาก reflog ชั่วระยะหนึ่ง แต่ไม่ควรพึ่งวิธีนั้น ให้สร้าง branch ไว้ก่อน

~ กับ ^ ต่างกันตรงที่ merge commit

ทั้งสองตัวใช้ “ถอยจาก commit หนึ่งไปหา parent” แต่ตีความตัวเลขไม่เหมือนกัน ~n คือถอยตามสาย parent แรก n ขั้น ส่วน ^n คือเลือก parent ตัวที่ n ของ commit นั้น ถ้า commit ไม่ใช่ merge มี parent เดียว สองแบบจึงให้ผลเหมือนกัน ความต่างโผล่เมื่อเจอ merge commit ซึ่งมีสอง parent ลองดูกราฟนี้

*   M   (HEAD)   parent 1 = E (สายที่เรายืนอยู่), parent 2 = D (สายที่ merge เข้ามา)
|\
| * D
| * C
* | E
|/
* B
* A
นิพจน์ชี้ไปที่อ่านว่า
HEAD~ หรือ HEAD^Eparent แรกของ M (~ เปล่ากับ ^ เปล่าคือ 1)
HEAD~2Bถอยสองขั้นตามสาย parent แรก (M → E → B)
HEAD^^ และ HEAD^1^1Bparent แรกของ parent แรก เท่ากับ HEAD~2
HEAD^2Dparent ตัวที่สองของ M คือสายที่ merge เข้ามา
HEAD^2~1Cไปที่ D ก่อน แล้วถอยตามสาย parent แรกอีกหนึ่งขั้น
HEAD~3AM → E → B → A
HEAD~1^2errorE มี parent เดียว จึงไม่มี parent ตัวที่สอง

ข้อที่คนพลาดบ่อยคือ HEAD~2 กับ HEAD^2 ดูคล้ายกันมากแต่คนละเรื่อง ตัวแรกคือถอยสองขั้น ตัวหลังคือ parent ตัวที่สอง ในกราฟข้างบนได้ B กับ D ตามลำดับ ส่วน HEAD~0 และ HEAD^0 คือ commit ปัจจุบัน ใช้บ่อยตอนต้องการ “commit” จากชื่อ tag ที่ชี้ไปยัง tag object

@ และ {} ไม่ได้เดินตาม parent

เครื่องหมาย @ เปล่า ๆ เป็นชื่อย่อของ HEAD จึงเขียน @~2 แทน HEAD~2 ได้ ส่วนวงเล็บปีกกาเป็นวิธีขอ “ตำแหน่งเก่า” หรือ “ปลายทางที่เกี่ยวข้อง” ซึ่งไม่ได้เดินตามสาย parent เลย

นิพจน์ความหมาย
HEAD@{1} หรือ @{1}ตำแหน่งของ HEAD เมื่อหนึ่งครั้งก่อน อ่านจาก reflog ในเครื่อง
main@{2}ตำแหน่งของ branch main เมื่อสองครั้งก่อน
@{yesterday}, @{2.days.ago}ตำแหน่งตามเวลา ใช้ได้เท่าที่ reflog ในเครื่องเก็บย้อนไปถึง
@{-1}branch ที่เพิ่ง checkout ก่อนอันปัจจุบัน และ git switch - คือทางลัดของการสลับกลับไป branch นั้น
@{u} หรือ @{upstream}upstream ของ branch ปัจจุบัน เช่น origin/main (ถ้ายังไม่ตั้ง upstream จะ error)
@{push}ปลายทางที่ git push จะส่งไป
HEAD^{tree}, HEAD^{commit}แปลง object ให้เป็นชนิดที่ต้องการ เช่น tree ของ commit นี้
v1.0^{}ลอก annotated tag ไปถึง object ที่มันชี้อยู่ ซึ่งปกติคือ commit
:/ข้อความcommit ล่าสุดที่ข้อความ commit ตรงกับ regex โดยค้นย้อนจากทุก ref

ลองดู reflog ของ repo ที่เพิ่ง merge แล้วถอยด้วย reset --hard HEAD~1 ตำแหน่งก่อนถอยยังอยู่ที่ HEAD@{1} ซึ่งเป็นสิ่งที่ใช้กู้งานได้

ba62270 HEAD@{0}: reset: moving to HEAD~1
ab6e8b4 HEAD@{1}: merge feat: Merge made by the 'ort' strategy.
ba62270 HEAD@{2}: commit: E

ข้อสังเกตจากผลข้างบน HEAD@{1} คือ merge commit ที่เพิ่งถูกถอยออก ซึ่ง ไม่ใช่ parent ของ HEAD ปัจจุบัน เลย ถ้าใช้ HEAD~1 แทนจะได้อีกอย่าง นี่คือเหตุผลที่ต้องแยกสองแบบนี้ให้ออก

ใช้จริงตอนไหน

git diff HEAD~3                   # เทียบ working tree กับ commit ก่อนหน้าสามขั้น
git show HEAD~2:src/app.js        # ดูไฟล์นั้น ณ commit ก่อนหน้าสองขั้น
git reset --soft HEAD~1           # ถอย commit ล่าสุด เก็บงานไว้ใน staging
git rebase -i HEAD~4              # จัดเรียง 4 commit ล่าสุด
git log @{u}..HEAD                # commit ในเครื่องที่ยังไม่ได้ push
git diff @{u}                     # ต่างจาก upstream อย่างไร
git reset --hard 'HEAD@{1}'       # กลับไปตำแหน่งก่อนหน้า (กู้จาก reflog)
git switch -                      # กลับ branch ก่อนหน้า
git rev-parse HEAD~2              # แปลงนิพจน์เป็นรหัส commit เต็ม ใช้ตรวจว่าชี้ถูกตัวไหม

ก่อนรันคำสั่งที่เขียนทับ เช่น reset --hard ให้พิมพ์ git rev-parse หรือ git log -1 กับนิพจน์เดียวกันดูก่อนสักครั้ง ถ้านิพจน์ชี้ผิดตัวจะเห็นทันทีโดยยังไม่เสียอะไร

ข้อควรระวังเรื่อง shell และ reflogเครื่องหมาย ^, {} และ @{ บาง shell ตีความเอง เช่น ^ เป็นอักขระ escape ใน cmd.exe และ @{ เป็นไวยากรณ์ hashtable ใน PowerShell ถ้าเจอข้อผิดพลาดแปลก ๆ ให้ครอบนิพจน์ด้วย quote เช่น 'HEAD@{1}' ไว้ก่อนเสมอ อีกเรื่องคือ reflog อยู่ในเครื่องเราเท่านั้น และหมดอายุตามค่า gc นิพจน์ @{n} กับ @{yesterday} จึงให้ผลต่างกันในแต่ละเครื่อง ส่งให้เพื่อนใช้ไม่ได้ ถ้าต้องอ้างให้คนอื่นใช้ ให้ใช้รหัส commit, tag หรือ branch แทน
จำสั้น ๆ~ นับขั้นตามสาย parent แรก, ^n เลือก parent ตัวที่ n, @ คือ HEAD และ @{...} ถามตำแหน่งเก่าหรือปลายทางที่ตั้งไว้ ไม่ได้เดินตาม parent

Branch, Merge และการแก้ Conflict

Beginner HackerRank: Branching · Merging

ตรงกับเกณฑ์ Beginner ข้อ “Commit, merge และ resolve code changes ใน shared repository” และหัวข้อ Branching, Merging, Git Log ของ HackerRank Git (Basic)

สองคนแก้ไฟล์ config.ini บรรทัดเดียวกันบนคนละ branch แล้วสั่ง merge Git ก็หยุดแล้วบอกว่า CONFLICT หลายคนตกใจตรงนี้ ทั้งที่จริงมันเป็นเหตุการณ์ปกติ Git แค่บอกว่ามันตัดสินใจแทนเราไม่ได้ ก่อนจะแก้ conflict เป็น ต้องเข้าใจก่อนว่า branch กับ merge ทำงานยังไง

Branch คือตัวชี้ ไม่ใช่การ copy โฟลเดอร์

branch เป็นไฟล์เล็ก ๆ ที่เก็บรหัส commit หนึ่งอัน การสร้าง branch ใหม่จึงแทบไม่มีต้นทุน ไม่ได้ copy ไฟล์ใด ๆ เมื่อ commit ใน branch ที่กำลังใช้อยู่ ตัวชี้ของ branch นั้นจะขยับไปยัง commit ใหม่ ส่วน branch อื่นอยู่ที่เดิม

git branch                        # ดูรายชื่อ branch (ตัวที่มี * คือที่ใช้อยู่)
git switch -c feature/login       # สร้างแล้วย้ายไปทันที (คำสั่งเก่าคือ git checkout -b)
git switch main                   # กลับไป main
git branch -d feature/login       # ลบ branch ที่ merge แล้ว

git switch และ git restore เพิ่มมาใน Git 2.23 เพื่อแยกหน้าที่ที่ git checkout ทำปนกันอยู่ ข้อสอบยังใช้ checkout อยู่มาก จึงควรอ่านออกทั้งสองแบบ

ตอนลบ branch มีสองแบบ -d จะปฏิเสธถ้า Git ไม่เห็นว่า commit ของ branch นั้นถูกรวมเข้าไปใน branch อื่นแล้ว ส่วน -D ลบเลยโดยไม่ถาม ใช้เมื่อมั่นใจว่าไม่ต้องการงานนั้นแล้ว

Merge สองแบบ: fast-forward กับ three-way

ถ้า main ไม่มี commit ใหม่เลยตั้งแต่แตก feature ออกไป Git แค่ขยับตัวชี้ของ main ไปข้างหน้าเท่านั้น เรียกว่า fast-forward ไม่เกิด commit ใหม่ แต่ถ้า main ขยับไปแล้ว Git ต้องรวมสามจุดเข้าด้วยกัน คือปลาย main, ปลาย feature และต้นทางร่วม (merge base) แล้วสร้าง merge commit ที่มี parent สองตัว

ลองดูผลจริงของ repo ที่ main กับ feature ต่างมี commit ของตัวเอง แล้วสั่ง git merge --no-ff feature

git log --oneline --graph
# *   fce3203 M: merge feature
# |\
# | * 7ea6093 C: feature
# * | 72c0430 D: main
# |/
# * c914097 B: add line2
# * 76509b4 A: init

บรรทัด |\ และ |/ คือจุดที่ history แตกกิ่งและกลับมารวมกัน ถ้าเห็น * เรียงตรงเป็นแนวเดียวแปลว่า history เป็นเส้นตรง

Conflict เกิดตอนไหน และแก้ตามลำดับยังไง

conflict เกิดเมื่อสอง branch แก้ บริเวณเดียวกัน ของไฟล์เดียวกันในแบบที่ไม่เหมือนกัน หรือฝั่งหนึ่งลบไฟล์ที่อีกฝั่งแก้ ถ้าแก้คนละบรรทัดที่ไม่ติดกัน Git รวมให้เองได้ ลองจำลองดู

git switch -c feature/a
sed -i 's/timeout=30/timeout=60/' config.ini && git commit -am "a: timeout 60"
git switch main
sed -i 's/timeout=30/timeout=45/' config.ini && git commit -am "main: timeout 45"
git merge feature/a
# CONFLICT (content): Merge conflict in config.ini
# Automatic merge failed; fix conflicts and then commit the result.
git status -s
# UU config.ini
cat config.ini
<<<<<<< HEAD
timeout=45
=======
timeout=60
>>>>>>> feature/a
retries=3

ส่วนระหว่าง <<<<<<< HEAD กับ ======= คือฝั่งเรา (branch ที่ merge เข้าไป) ส่วนระหว่าง ======= กับ >>>>>>> คือฝั่งที่ merge มา ขั้นตอนแก้คือ เปิดไฟล์แล้วตัดสินใจว่าค่าสุดท้ายควรเป็นอะไร (อาจเลือกฝั่งใดฝั่งหนึ่ง หรือผสมกัน) ลบ marker ทั้งสามชนิดออกให้หมด แล้ว git add config.ini จากนั้น git commit หรือ git merge --continue ถ้าเริ่มแล้วรู้สึกว่าไปผิดทาง สั่ง git merge --abort เพื่อกลับสู่สภาพก่อน merge ได้เลย

ก่อน commit ผล merge ให้ค้นหา marker ซ้ำอีกรอบลองรัน git diff --check หรือค้นคำว่า <<<<<<< ในโปรเจกต์ เพราะการ commit ไฟล์ที่ marker ยังค้างอยู่เป็นความพลาดที่เจอบ่อย และ conflict ที่แก้ถูกไวยากรณ์แต่ผิด logic ต้องพึ่ง test หลัง merge ถึงจะจับได้

สิ่งที่ควรดูใน log

git log --oneline --graph --all     # เห็นทุก branch เป็นกราฟ
git log main..feature               # commit ที่อยู่ใน feature แต่ยังไม่อยู่ใน main
git show HEAD~1                     # ดูรายละเอียด commit ก่อนหน้า HEAD

Remote, Push, Pull, Fork และ Pull Request

Beginner

ตรงกับเกณฑ์ Beginner ข้อ “Collaborate via shared repositories, pull requests และ code reviews บนแพลตฟอร์ม” และหัวข้อ Basic Commands (remote, push) ของ HackerRank Git (Basic)

เช้าวันจันทร์ สั่ง git push แล้วเจอ rejected ... (non-fast-forward) หรือ fetch first สาเหตุคือใน remote มี commit ที่เครื่องเราไม่มี เพื่อนร่วมทีม push ไปก่อนแล้ว Git ไม่ยอมให้เรา push ทับเพราะ history จะหาย ก่อนแก้ต้องรู้ว่าเครื่องเรากับ remote สื่อสารกันยังไง

Remote และ remote-tracking branch

remote คือชื่อเล่นของ URL (origin เป็นชื่อมาตรฐานที่ git clone ตั้งให้) ส่วน origin/main เป็น remote-tracking branch คือสำเนาในเครื่องเราที่จำว่า “ครั้งล่าสุดที่คุยกับ origin, main ของเขาอยู่ที่ commit ไหน” มันไม่อัปเดตเองตลอดเวลา จะขยับก็ต่อเมื่อเรา fetch หรือ pull หรือ push

คำสั่งทำอะไรแตะ working tree ไหม
git fetchดาวน์โหลด commit ใหม่และขยับ origin/*ไม่
git pullfetch แล้ว merge (หรือ rebase ถ้าตั้งค่าไว้) เข้า branch ปัจจุบันใช่
git pushส่ง commit ของ branch ปัจจุบันขึ้น remoteไม่

เมื่อไม่แน่ใจว่าเพื่อนแก้อะไรไว้บ้าง ให้ git fetch ก่อน แล้วดู git log main..origin/main ว่ามีอะไรเข้ามา จากนั้นค่อยตัดสินใจว่าจะ merge หรือ rebase

git push -u origin feature/login     # push ครั้งแรกและผูก upstream ให้ git push ครั้งต่อไปไม่ต้องระบุ
git fetch origin
git log --oneline main..origin/main  # ดูของใหม่ก่อนรวม
git pull --rebase                    # ถ้าทีมใช้ history เส้นตรง

เมื่อโดน rejected ทางแก้ที่ปลอดภัยคือดึงของใหม่มารวมกับงานเราก่อน (git pull หรือ git pull --rebase) แก้ conflict ถ้ามี แล้ว push ใหม่ ห้ามแก้ด้วย git push --force เพราะจะเขียนทับ commit ของเพื่อนที่เราไม่เคยเห็น

Fork, clone, branch ต่างกันยังไง

Clone คือสำเนา repo ลงเครื่อง ส่วน fork เป็นฟีเจอร์ของแพลตฟอร์ม (เช่น GitHub) ที่ copy ทั้ง repo ไปเป็นของบัญชีเรา ใช้เมื่อเราไม่มีสิทธิ์เขียนใน repo ต้นทาง เช่น ไปช่วย open source ขั้นตอนทั่วไปคือ fork แล้ว clone fork ของเรา ตั้ง remote ชื่อ upstream ชี้ไป repo ต้นทางเพื่อ fetch ของใหม่ แล้วเปิด pull request กลับไป ส่วน branch อยู่ใน repo เดียวกันและเหมาะกับทีมที่มีสิทธิ์เขียนอยู่แล้ว

Pull request และ code review

Pull request (GitLab เรียก merge request) ไม่ใช่ฟีเจอร์ของ Git แต่เป็นของแพลตฟอร์ม มันคือคำขอให้รวม branch หนึ่งเข้าอีก branch โดยมีที่ให้คนอื่นอ่าน diff คอมเมนต์ และให้ระบบ CI รัน test ก่อนรวม ลำดับงานโดยทั่วไปคือ

  1. แตก branch จาก main ที่อัปเดตล่าสุด ตั้งชื่อให้บอกงาน เช่น feature/payslip-export
  2. commit เป็นก้อนเล็กที่มีความหมายในตัวเอง แล้ว push ขึ้น remote
  3. เปิด PR เขียนคำอธิบายว่าแก้อะไรและทำไม ผูกกับ issue และบอกวิธีทดสอบ
  4. รอ CI ผ่านและให้ reviewer อ่าน แก้ตามคอมเมนต์โดย commit เพิ่มใน branch เดิม PR จะอัปเดตเอง
  5. เมื่อได้รับ approve ก็ merge แล้วลบ branch

ตอนกด merge บน GitHub มักมีสามตัวเลือก ได้แก่ merge commit (เก็บ commit ทั้งหมดและเพิ่ม merge commit), squash and merge (รวมทุก commit เป็นอันเดียว) และ rebase and merge (เล่น commit ซ้ำบนปลาย main แบบเส้นตรง) ทีมควรเลือกแบบเดียวกันและบอกไว้ในเอกสาร เพราะมีผลกับหน้าตา history ในระยะยาว

PR ที่ดีควรเล็กพอให้ reviewer อ่านจบในรอบเดียว ถ้าแก้หลายเรื่องปนกันคนรีวิวจะเริ่มอ่านผ่าน ๆ และพลาดจุดที่มีปัญหา ในมุมคนรีวิว ให้ดูว่า logic ถูกไหม มี test ไหม ชื่อสื่อความหมายไหม และมี secret หรือข้อมูลที่ไม่ควรหลุดเข้ามาหรือเปล่า

ถอยงานอย่างปลอดภัย: restore, amend, stash, mv, rm

Beginner HackerRank: Amend · Stash · Move/Remove

ตรงกับ HackerRank Git (Basic) หัวข้อ Move and Remove, Amend และ Stash และเกณฑ์ Beginner ข้อ commit และจัดการการเปลี่ยนแปลงใน repository

ทุกคนเคยพลาด commit ไปผิดข้อความ add ไฟล์ที่ไม่ควร add หรือแก้ไฟล์ค้างไว้ตอนหัวหน้าสั่งให้สลับไปแก้ bug ด่วน คำถามที่ควรถามตัวเองก่อนพิมพ์คำสั่งแก้คือ “คำสั่งนี้แตะพื้นที่ไหน และถ้าผิดกู้คืนได้ไหม” เพราะบางคำสั่งลบงานที่ยังไม่เคยอยู่ใน commit ซึ่ง Git กู้ให้ไม่ได้

ยกเลิกการเปลี่ยนแปลงตามพื้นที่

สถานการณ์คำสั่งกู้คืนได้ไหม
add ไฟล์เข้า staging ผิด อยากถอดออกแต่เก็บการแก้ไขไว้git restore --staged fileงานยังอยู่ใน working tree
ทิ้งการแก้ไขที่ยังไม่ได้ add กลับไปเหมือนตอน add/commit ล่าสุดgit restore fileไม่ได้ ถ้าไม่เคย add หรือ commit ไว้
แก้ข้อความหรือเพิ่มไฟล์ที่ลืมใน commit ล่าสุดgit commit --amendได้ผ่าน reflog
ลบไฟล์ที่ไม่ใช้แล้วgit rm fileได้ จากประวัติ commit ก่อนหน้า
เลิกติดตามไฟล์แต่เก็บไฟล์ไว้บนดิสก์git rm --cached fileไฟล์ยังอยู่ในเครื่อง
ย้ายหรือเปลี่ยนชื่อไฟล์git mv old newได้

คำสั่ง git checkout -- file ทำงานเหมือน git restore file ในโลกเก่า และ git reset HEAD file ทำงานเหมือน git restore --staged file สองบรรทัดนี้มักโผล่ในข้อสอบเพราะเป็นของเดิมที่คนยังใช้กันเยอะ

แก้ commit ล่าสุดด้วย amend

git commit -m "fix: typo in login"
# ลืม add ไฟล์ test
git add tests/login.test.js
git commit --amend --no-edit        # เอาไฟล์เข้า commit เดิม ไม่แก้ข้อความ
git commit --amend -m "fix: แก้คำผิดในหน้า login"   # แก้เฉพาะข้อความ

--amend ไม่ได้แก้ commit เดิมจริง ๆ แต่สร้าง commit ใหม่มาแทนที่ รหัสจึงเปลี่ยน ถ้า commit เดิมถูก push ไปแล้วและมีคนดึงไปใช้ การ amend แล้ว push ต้องใช้ force ซึ่งจะทำให้ history ของคนอื่นไม่ตรงกัน ใช้ amend เฉพาะกับ commit ที่ยังอยู่ในเครื่องเรา

stash เก็บงานค้างไว้ชั่วคราว

ลองนึกว่าเรากำลังแก้ฟีเจอร์ค้างอยู่ แล้วต้องสลับไปแก้ bug บน main Git จะไม่ให้ switch ถ้าไฟล์ที่แก้อยู่ชนกับ branch ปลายทาง ตรงนี้ git stash ช่วยได้ มันเก็บการแก้ไขที่ tracked ไว้ในกองชั่วคราว แล้วคืน working tree ให้สะอาด

git stash push -m "login form ค้างอยู่"     # เก็บงาน (ตั้งชื่อให้หาง่าย)
git stash push -u                           # รวมไฟล์ใหม่ที่ยังไม่ track ด้วย
git stash list                              # ดูของที่เก็บไว้
git stash pop                               # เอากลับมาแล้วลบออกจากกอง
git stash apply stash@{1}                   # เอากลับมาแต่ยังเก็บไว้ในกอง
git stash drop stash@{1}                    # ทิ้งรายการที่ไม่ต้องการ

ข้อควรระวังสองข้อ ข้อแรก git stash เฉย ๆ ไม่เก็บไฟล์ใหม่ที่ยังไม่ track (ต้องใส่ -u) ข้อสองคือ pop อาจเจอ conflict ได้ และถ้า conflict stash จะยังไม่ถูกลบ เพราะ Git ไม่อยากให้เสียของ

ก่อนใช้คำสั่งที่ทิ้งงาน ให้ลอง dry runเช่น git clean -n จะแสดงรายชื่อไฟล์ที่ untracked ซึ่งจะถูกลบ โดยยังไม่ลบจริง ต่อเมื่อพอใจค่อยสั่ง git clean -f (ใส่ -d สำหรับโฟลเดอร์ -x สำหรับไฟล์ที่ถูก ignore)

ทีมใหม่ถามว่า “เราควรใช้ branching strategy อะไร” คำตอบที่ถูกต้องคือขึ้นกับว่าทีมปล่อยงานบ่อยแค่ไหน มีกี่เวอร์ชันที่ต้องดูแลพร้อมกัน และทีมมีระบบ test อัตโนมัติมากน้อยเพียงใด ไม่มีแบบที่ดีที่สุดในทุกบริบท ระดับ Beginner ต้องรู้ว่าแต่ละแบบหน้าตาเป็นยังไง และรู้ว่าตัวเองต้องทำตามกฎของทีมอย่างไร

Git Flow

Git Flow เป็นโมเดลที่ Vincent Driessen เสนอไว้ มี branch หลักสองตัวที่อยู่ตลอด คือ main (เก็บโค้ดที่ปล่อยแล้ว แต่ละ commit คือเวอร์ชันหนึ่ง) กับ develop (รวมงานที่กำลังพัฒนาสำหรับรอบถัดไป) และมี branch ชั่วคราวสามชนิด

Branchแตกจากรวมกลับเข้าใช้ทำอะไร
feature/*developdevelopพัฒนาฟีเจอร์หนึ่งเรื่อง
release/*developmain และ developเตรียมปล่อย แก้ bug เล็กน้อย ปรับเลขเวอร์ชัน
hotfix/*mainmain และ developแก้ bug ด่วนบน production

Git Flow เหมาะกับงานที่ปล่อยเป็นรอบมีกำหนดการ เช่น แอปมือถือที่ต้องผ่านการรีวิวของ store หรือซอฟต์แวร์ที่ลูกค้าใช้หลายเวอร์ชันพร้อมกัน ข้อจำกัดคือมี branch ให้ดูแลเยอะ และ branch อายุยาวอย่าง develop ทำให้ conflict สะสมได้ ตัวผู้เสนอเองก็เคยเขียนไว้ว่าโมเดลนี้อาจไม่เหมาะกับงานที่ deploy ต่อเนื่อง

GitHub Flow และ Trunk-based

GitHub Flow ง่ายกว่ามาก มี main ที่ deploy ได้เสมอ แตก branch สั้น ๆ ออกมาทำงาน เปิด PR รีวิว merge เข้า main แล้ว deploy Trunk-based development ยิ่งเข้มกว่า คือทุกคน commit เข้า trunk (main) บ่อย ๆ หรือใช้ branch ที่มีอายุไม่กี่ชั่วโมงถึงไม่กี่วัน ฟีเจอร์ที่ยังไม่เสร็จซ่อนไว้หลัง feature flag แทนการแยก branch ยาว ๆ แบบนี้ได้ผลดีเมื่อมี test และ CI ที่ไว้ใจได้

ต้องมี CI/test ที่แข็งแรงแค่ไหนมีประโยชน์ แต่มี release branch รองรับจำเป็นจำเป็นมาก
เหมาะกับหลายเวอร์ชันพร้อมกัน, ปล่อยตามรอบเว็บแอปที่ deploy ได้ทุกวันทีมที่ integrate ถี่และมี automation เยอะ

ตั้งชื่อ branch และ commit ให้ทีมอ่านง่าย

ทีมส่วนใหญ่ใช้ prefix บอกชนิดงาน เช่น feature/, bugfix/, hotfix/, release/ ตามด้วยชื่อสั้นหรือเลข ticket เช่น feature/PAY-142-export-pdf ส่วนข้อความ commit หลายทีมใช้รูปแบบ Conventional Commits เช่น feat: add payslip export, fix: handle empty month เพราะอ่านง่ายและเครื่องมือเอาไปสร้าง changelog ต่อได้ ที่สำคัญกว่ารูปแบบคือทุกคนในทีมใช้แบบเดียวกัน

สิ่งที่ Beginner ต้องทำได้รู้ว่าจะแตก branch จากไหน ตั้งชื่อตามที่ทีมกำหนด เปิด PR เข้า branch ที่ถูกต้อง (ไม่ใช่ main เสมอไป ถ้าทีมใช้ develop) และไม่ push ตรงเข้า branch ที่ถูก protect

Workflow ขั้นสูง: feature, release, hotfix และ merge strategy

Intermediate HackerRank: Gitflow · Merging

ตรงกับเกณฑ์ Intermediate ข้อ “ออกแบบและใช้ workflow การ branch และ merge ขั้นสูง เช่น feature branch, release branch, hotfix” และหัวข้อ Gitflow ของ HackerRank Git (Intermediate)

แอปมือถือเวอร์ชัน 3.4 อยู่บน store แล้ว ทีมกำลังพัฒนา 3.5 ใน develop อยู่ แล้วมีรายงาน crash ที่แก้ได้ด้วยโค้ดสองบรรทัด ปัญหาคือถ้าแก้บน develop ก็จะพ่วงงานที่ยังไม่เสร็จของ 3.5 ไปด้วย ตรงนี้คือเหตุผลที่ Git Flow มี hotfix branch แยกออกมา โจทย์ระดับ Intermediate ไม่ได้ถามแค่ว่า branch มีกี่ชนิด แต่ถามว่า แตกจากไหน รวมกลับที่ไหน และต้อง tag ตอนไหน

รอบการปล่อยแบบ Git Flow ทีละขั้น

# 1) ตัด release branch จาก develop เมื่อฟีเจอร์ของรอบนี้ครบ
git switch develop && git pull
git switch -c release/3.5.0
#    ช่วงนี้แก้ได้เฉพาะ bug และเลขเวอร์ชัน ไม่เพิ่มฟีเจอร์ใหม่

# 2) พร้อมปล่อย: รวมเข้า main, tag, แล้วรวมกลับ develop
git switch main
git merge --no-ff release/3.5.0
git tag -a v3.5.0 -m "Release 3.5.0"
git switch develop
git merge --no-ff release/3.5.0
git branch -d release/3.5.0

# 3) hotfix บน production: แตกจาก main (ที่มี tag ล่าสุด)
git switch -c hotfix/3.5.1 v3.5.0
#    แก้ bug แล้ว commit
git switch main  && git merge --no-ff hotfix/3.5.1 && git tag -a v3.5.1 -m "Hotfix 3.5.1"
git switch develop && git merge --no-ff hotfix/3.5.1

สองจุดที่คนพลาดบ่อย จุดแรกคือลืมรวม release หรือ hotfix กลับเข้า develop ผลคือ bug ที่เพิ่งแก้หายกลับมาในรอบถัดไป จุดที่สองคือ tag ผิดที่ tag เวอร์ชันควรวางบน commit ที่ถูกปล่อยจริง ซึ่งอยู่บน main หลัง merge ถ้ามี release branch ค้างอยู่ตอนต้องแก้ hotfix ให้รวม hotfix เข้า release branch นั้นแทน develop เพราะ release branch จะรวมเข้า develop อยู่แล้ว

เครื่องมือ git flow ที่ใช้พิมพ์ git flow release start เป็นส่วนเสริมที่ติดตั้งแยก ไม่ได้มากับ Git เอง มันแค่รวมคำสั่งข้างบนเป็นชุด เข้าใจคำสั่งดิบก่อนจะช่วยให้รู้ว่าเครื่องมือกำลังทำอะไร

ตัวเลือกตอน merge: ff, no-ff และ squash

แบบผลต่อ historyข้อดีข้อจำกัด
ค่าเริ่มต้นถ้าทำ fast-forward ได้ก็ทำ ถ้าไม่ได้ก็สร้าง merge commitไม่ต้องเลือกหน้าตา history ไม่คงที่
--no-ffสร้าง merge commit เสมอ แม้ fast-forward ได้เห็นว่า feature ไหนรวมเข้ามาเมื่อไร revert ทั้ง feature ได้ด้วยการ revert merge commithistory มี merge commit เยอะ
--ff-onlyทำได้ต่อเมื่อ fast-forward ได้ ไม่งั้นล้มเหลวบังคับให้ rebase ก่อน history เป็นเส้นตรงต้อง rebase ให้ทันเมื่อ main ขยับ
--squashเอาการเปลี่ยนทั้งหมดมาไว้ใน staging ให้เรา commit เป็นอันเดียว ไม่มี parent เชื่อมกลับmain สะอาด หนึ่ง feature หนึ่ง commitเสียรายละเอียดรายก้อน และ Git ไม่รู้ว่า branch ถูก merge แล้ว

ข้อสุดท้ายนี้ทำให้งงได้ ลองดูผลจริงหลัง squash merge แล้วสั่งลบ branch

git merge --squash feat && git commit -m "squashed feat"
git branch -d feat
# error: the branch 'feat' is not fully merged.
# If you are sure you want to delete it, run 'git branch -D feat'

เหตุผลคือ -d ตรวจว่า commit ปลายของ feat เป็นบรรพบุรุษของ branch ที่ merge เข้าไปหรือไม่ แต่ squash สร้าง commit ใหม่ที่ไม่มี parent ชี้กลับไป feat ดังนั้น Git จึงมองว่ายังไม่ถูกรวม เมื่อมั่นใจแล้วว่าเนื้อหารวมไปครบ ก็ใช้ -D ได้ แพลตฟอร์มอย่าง GitHub มีปุ่มและการตั้งค่าให้ลบ branch หลัง merge ผ่าน PR ให้เองอยู่แล้ว

Branch อายุยาวและการ backport

ซอฟต์แวร์ที่ต้องรองรับหลายเวอร์ชัน เช่น 2.x กับ 3.x จะมี maintenance branch อย่าง release/2.x อยู่ยาว เมื่อแก้ bug บน main ที่ต้องนำไปใส่ 2.x ด้วย ทีมจะ cherry-pick commit นั้นไปยัง branch เก่า (เรียกว่า backport) ควรเขียน commit ให้แก้เรื่องเดียวและแยกจากงานอื่น เพราะ cherry-pick ใช้ได้ดีเฉพาะกับ commit ที่อยู่ลำพังได้ ดูรายละเอียดคำสั่งที่หัวข้อ 9

Rebase, history เป็นเส้นตรง และ conflict ที่ซับซ้อน

Intermediate HackerRank: Rebase

ตรงกับเกณฑ์ Intermediate ข้อ “Resolve complex merge conflicts และ rebase branch เพื่อรักษา linear history” และหัวข้อ Rebase ของ HackerRank Git (Intermediate) กับ Rebase Interactive ใน Advanced

ทีมตั้งกฎว่า main ต้องเป็นเส้นตรง ห้ามมี merge commit คุณเปิด PR ไว้สามวัน ระหว่างนั้น main ขยับไปห้า commit ปุ่ม merge ถูกล็อกเพราะ branch “ล้าหลัง” ทางออกคือ rebase และการ rebase เป็นเรื่องที่ต้องเข้าใจกลไกก่อนใช้ เพราะมันเปลี่ยน history จริง

Rebase ทำอะไรกับ commit

rebase หยิบ commit ของ branch เราที่ต่างจากปลายทางออกมา แล้ว สร้างใหม่ ทีละอันบนปลายของ branch เป้าหมาย commit ที่ได้มีเนื้อหาการเปลี่ยนแปลงเดียวกัน แต่ parent ต่างไป รหัสจึงเปลี่ยน ของเดิมยังอยู่ในฐานข้อมูลสักพักแต่ไม่มี branch ไหนชี้ถึงแล้ว

git switch feature/export
git fetch origin
git rebase origin/main        # เล่น commit ของ feature ซ้ำบนปลาย main ล่าสุด
git push --force-with-lease   # ต้อง force เพราะ commit รหัสเปลี่ยนแล้ว
กฎสำคัญ: ไม่ rebase commit ที่คนอื่นดึงไปใช้แล้วถ้าเรา rebase แล้ว push ทับ คนที่มี commit เดิมอยู่ในเครื่องจะเจอ history แยกจากเรา และอาจ push commit เก่ากลับขึ้นมาโดยไม่ตั้งใจ rebase เหมาะกับ branch ส่วนตัวที่ยังไม่มีใครต่อยอด

เรื่อง force push ให้เลือก --force-with-lease แทน --force มันจะปฏิเสธถ้า remote มี commit ที่เรายังไม่เคยเห็น ลองดูสถานการณ์ที่เพื่อน push เข้ามาระหว่างเรา rebase

git push --force-with-lease origin main
# ! [rejected]        main -> main (stale info)
# error: failed to push some refs to '../r.git'

ข้อควรรู้คือ ถ้ามีเครื่องมือเบื้องหลังที่ fetch ให้อัตโนมัติ (เช่น editor บางตัว) lease จะดูเหมือนถูกต้องทั้งที่เรายังไม่ได้อ่านของใหม่ Git 2.30 เพิ่ม --force-if-includes มาใช้คู่กันเพื่อเช็กว่า commit ที่ remote ถูกรวมเข้า local แล้วจริง

ทีมที่ชอบเส้นตรงมักใช้ git pull --rebase หรือตั้ง pull.rebase=true ส่วนทีมที่ต้องการเห็นว่าอะไรรวมเข้ามาเมื่อไรก็ใช้ merge ทั้งสองแบบใช้ได้ ข้อสำคัญคือตกลงกัน

rebase --onto: ย้ายท่อนของ branch

สมมติ topic2 แตกมาจาก topic1 แล้ว topic1 ถูกทิ้ง เราอยากเอาเฉพาะ commit ของ topic2 ไปไว้บน main

git rebase --onto main topic1 topic2
#            ^ ปลายทางใหม่  ^ ต้นทางเก่า (ไม่เอา)  ^ branch ที่ย้าย

อ่านว่า “เอา commit ที่อยู่หลัง topic1 จนถึงปลาย topic2 ไปวางบน main”

Interactive rebase: เก็บกวาด commit ก่อนเปิด PR

git rebase -i HEAD~4        # เปิดรายการ 4 commit ล่าสุดใน editor
คำสั่งในรายการผล

rewordเก็บการเปลี่ยนแปลง แต่หยุดให้แก้ข้อความ
editหยุดที่ commit นี้ให้แก้เนื้อหาหรือแบ่งเป็นหลาย commit แล้ว git rebase --continue

ลำดับของบรรทัดในไฟล์คือลำดับ commit ที่จะเล่นซ้ำ สลับบรรทัดก็เท่ากับ reorder เคล็ดที่ช่วยได้มากคือ git commit --fixup <sha> ตอนเจอข้อผิดพลาดของ commit เก่า แล้วค่อยรัน git rebase -i --autosquash ให้มันจัดเรียงและรวมให้เอง

conflict ระหว่าง rebase: ours กับ theirs สลับกัน

ตอน rebase Git เล่น commit ของเราซ้ำบนปลายของอีกฝั่ง ดังนั้น “ours” คือฝั่งที่เรากำลังวางทับ (เช่น main) และ “theirs” คือ commit ของเราที่กำลังถูกเล่นซ้ำ ตรงข้ามกับสัญชาตญาณและตรงข้ามกับตอน merge

git rebase main
# Could not apply a612ede... a: timeout 60
cat config.ini
# <<<<<<< HEAD              ← ฝั่ง main ที่เรา rebase ไปวางทับ
# timeout=45
# =======
# timeout=60
# >>>>>>> a612ede (a: timeout 60)   ← commit ของเราที่กำลังถูกเล่นซ้ำ
git checkout --ours config.ini      # ได้ timeout=45 (ของ main) ไม่ใช่ของเรา

แก้เสร็จแล้ว git add ตามด้วย git rebase --continue ถ้าอยากข้าม commit นี้ใช้ --skip ถ้าอยากกลับไปเริ่มใหม่ใช้ --abort

Conflict ซ้ำ ๆ และตัวช่วย

ถ้าต้อง rebase branch เดิมหลายรอบแล้วเจอ conflict ตัวเดิมทุกครั้ง ให้เปิด git config rerere.enabled true Git จะจำวิธีที่เราแก้ครั้งก่อนและใช้ซ้ำให้อัตโนมัติเมื่อเจอ conflict รูปเดิม และถ้าอ่าน marker ไม่ออก ลอง git config merge.conflictStyle zdiff3 (Git 2.35 ขึ้นไป) หรือ diff3 เพื่อให้แสดงเนื้อหา base ด้วย จะเห็นว่าแต่ละฝั่งแก้อะไรจากต้นฉบับ ส่วนการ rebase branch ที่มี merge commit อยู่ข้างใน ให้ใช้ --rebase-merges เพื่อคงโครงของ merge ไว้ ไม่งั้นจะถูกแบนเป็นเส้นตรง

ลูกค้าแจ้งว่า “เวอร์ชันที่ติดตั้งอยู่มี bug” ทีมต้องตอบได้ทันทีว่าเวอร์ชันนั้นคือ commit ไหน และเป็นโค้ดชุดเดียวกับที่ build ออกไปจริงหรือไม่ ถ้าไม่มี tag ก็ต้องไล่เดาจากวันที่ tag คือคำตอบของเรื่องนี้

Tag สามแบบ

แบบสร้างด้วยเก็บอะไรใช้เมื่อ
Lightweightgit tag v1.0แค่ชื่อชี้ไปที่ commitทำเครื่องหมายส่วนตัวชั่วคราว
Annotatedgit tag -a v1.0.0 -m "..."object ของ tag มีชื่อผู้สร้าง วันที่ ข้อความเวอร์ชันที่ปล่อยจริง
Signedgit tag -s v1.0.0 -m "..."annotated tag พร้อมลายเซ็น GPG หรือ SSHต้องพิสูจน์ว่าใครออก release

ลองดูความต่างจริง lightweight tag เป็นชนิด commit ตรง ๆ แต่ annotated tag เป็น object ชนิด tag ของมันเอง

git tag light
git tag -a v1.0.0 -m "release 1.0.0"
git cat-file -t light     # commit
git cat-file -t v1.0.0    # tag
git describe --tags       # v1.0.0  (บอกว่าห่างจาก tag ล่าสุดกี่ commit)

Tag ไม่ถูก push ไปเอง

การ git push ปกติส่งเฉพาะ commit ของ branch ที่ระบุ ไม่ส่ง tag ไปด้วย ต้องสั่งเพิ่มเอง

git push origin v1.0.0           # push tag เดียว
git push origin --tags           # push ทุก tag (รวม lightweight)
git push origin --follow-tags    # push เฉพาะ annotated tag ที่ชี้ถึง commit ที่กำลัง push
git tag -d v1.0.0                # ลบ tag ในเครื่อง
git push origin --delete v1.0.0  # ลบ tag บน remote

ผลที่ทดลองจริง คือหลัง git push origin main --follow-tags บน remote มีเฉพาะ annotated tag ส่วน lightweight tag ต้อง push ชื่อมันเองถึงจะขึ้น เพราะ --follow-tags ตั้งใจให้ส่งเฉพาะ tag ที่มีข้อมูลผู้สร้างและข้อความ

Semantic Versioning

รูปแบบ MAJOR.MINOR.PATCH ตามข้อกำหนดที่ semver.org มีความหมายว่า เพิ่ม MAJOR เมื่อมีการเปลี่ยนที่ทำให้ผู้ใช้เดิมพัง (breaking change) เพิ่ม MINOR เมื่อเพิ่มความสามารถแบบเข้ากันได้ และเพิ่ม PATCH เมื่อแก้ bug แบบเข้ากันได้ pre-release เขียนต่อท้ายด้วยขีด เช่น 2.0.0-rc.1 เวอร์ชันแบบนี้เหมาะกับ library และ API ที่ผู้ใช้ต้องรู้ว่าอัปเดตแล้วจะพังไหม ส่วนแอปที่ผู้ใช้ปลายทางไม่เห็นเลขอาจใช้ปฏิทิน (เช่น 2026.11) หรือเลข build ก็ได้ ขึ้นกับว่าใครเป็นผู้อ่านเลขนี้

ขั้นตอน release ที่ทำซ้ำได้

  1. ตกลง scope และ freeze ฟีเจอร์ของรอบนี้ ตัด release branch หรือเลือก commit บน main ที่จะปล่อย
  2. รัน test และ build จาก commit นั้น ถ้าต้องปล่อยหลายขั้นให้ใช้ tag แบบ release candidate เช่น v2.3.0-rc.1
  3. เมื่อผ่านแล้วสร้าง annotated tag บน commit เดียวกับที่ build ออกไป เช่น v2.3.0
  4. สร้าง changelog จาก git log v2.2.0..v2.3.0 --oneline หรือจาก Conventional Commits
  5. deploy artifact ที่ build จาก tag นั้น ไม่ build ใหม่จาก branch ที่อาจขยับไปแล้ว
  6. ถ้ามี bug ใน production แตก hotfix จาก tag แล้วออก v2.3.1 ไม่แก้ tag เดิม
อย่าย้าย tag ที่ปล่อยไปแล้วการลบแล้วสร้าง tag ชื่อเดิมให้ชี้ commit ใหม่ ทำให้เครื่องที่ดึง tag เก่าไว้แล้วไม่อัปเดต (Git ปกติไม่เขียนทับ tag ที่มีอยู่เมื่อ fetch) และทำให้ชื่อเวอร์ชันเดียวมีโค้ดสองแบบ ถ้าพลาดให้ออกเลข patch ใหม่ดีกว่า

ส่วน “tag กับ branch ต่างกันยังไง” คำตอบสั้นคือ branch ขยับตามทุก commit ใหม่ ส่วน tag ตั้งใจให้ชี้ที่เดิมตลอด ใช้เป็นหมุดอ้างอิงเวอร์ชันและเป็นจุดที่ย้อนกลับไป deploy ได้

reset, revert, cherry-pick, stash และ patch

Intermediate HackerRank: Reset · Stash/clean

ตรงกับเกณฑ์ Intermediate ข้อ “Use advanced commands for history manipulation, cherry-picking, stashing และ patch creation” และหัวข้อ Reset, Stash ของ HackerRank Git (Intermediate)

คำถามที่ทำให้คนสับสนที่สุดข้อหนึ่งคือ “อยากถอย commit ล่าสุดทิ้ง ต้องใช้ reset หรือ revert” คำตอบคือขึ้นกับว่า commit นั้น ถูก push ให้คนอื่นเห็นแล้วหรือยัง reset เปลี่ยน history ส่วน revert เพิ่ม history ใหม่ที่ล้างผลของอันเก่า

reset สามโหมด

git reset ย้ายตัวชี้ของ branch ปัจจุบัน แล้วตัดสินใจว่าจะอัปเดตพื้นที่อื่นตามไปด้วยแค่ไหน

โหมดHEAD/branchStaging areaWorking treeใช้เมื่อ
--softย้ายคงเดิมคงเดิมอยากรวม commit ล่าสุดหลายอันเป็นอันเดียว
--mixed (ค่าเริ่มต้น)ย้ายรีเซ็ตให้ตรง HEAD ใหม่คงเดิมถอน commit แต่เก็บการแก้ไขไว้ใน working tree
--hardย้ายรีเซ็ตถูกเขียนทับทิ้งทุกอย่างกลับไปที่ commit นั้น
git reset --soft  HEAD~1   # status: M  r.txt   (staged — พร้อม commit ใหม่)
git reset --mixed HEAD~1   # status:  M r.txt   (แก้อยู่ แต่ยังไม่ staged)
git reset --hard  HEAD~1   # status: สะอาด ไฟล์กลับไปเป็นของ commit เดิม

ผลที่ทดลองข้างบนแสดงว่ามีเฉพาะ --hard ที่เปลี่ยนเนื้อหาไฟล์จริง ๆ อย่า reset บน branch ที่แชร์กับคนอื่นแล้ว เพราะต้อง force push ตามมา

reflog: ตาข่ายกันตก

หลัง reset --hard commit ที่ “หาย” ยังอยู่ในฐานข้อมูล เพียงแต่ไม่มี branch ไหนชี้ถึง Git เก็บบันทึกการขยับของ HEAD ไว้ในเครื่องเราที่ reflog

git reflog
# 3801722 HEAD@{0}: reset: moving to HEAD~1
# 25115d7 HEAD@{1}: commit: r2 again2     ← commit ที่เพิ่งหายไป
git reset --hard HEAD@{1}                  # กลับไปที่ commit นั้น

reflog เป็นของแต่ละเครื่อง ไม่ถูก push และมีอายุจำกัด ค่าเริ่มต้นเก็บรายการที่ยังเข้าถึงได้ 90 วัน และรายการที่เข้าถึงไม่ได้ 30 วัน (ตั้งผ่าน gc.reflogExpire และ gc.reflogExpireUnreachable) ถ้าไม่เคย commit หรือ stash งานไว้เลย reflog ก็กู้ให้ไม่ได้

revert: ล้างผลของ commit ด้วย commit ใหม่

git revert 9fceb02             # สร้าง commit ใหม่ที่ตรงข้ามกับ 9fceb02
git revert HEAD~3..HEAD        # revert หลาย commit ทีละอัน
git revert -m 1 <merge-sha>    # revert merge commit ต้องบอกว่าเก็บ parent ที่ 1 (ฝั่ง main) ไว้

ถ้าลองสั่ง git revert กับ merge commit โดยไม่ใส่ -m จะได้ error ว่า is a merge but no -m option was given เพราะ Git ไม่รู้ว่าให้ถอยกลับไปทางสายไหน -m 1 แปลว่าถือ parent แรก (สายที่เรา merge เข้าไป) เป็นฝั่งหลัก และย้อนผลของฝั่งที่สอง จุดที่มือใหม่ไม่ค่อยรู้คือหลัง revert merge ไปแล้ว ถ้าอยากเอา branch นั้นกลับมารวมอีก การ merge ซ้ำจะไม่ได้เนื้อหาเดิมกลับมา เพราะ Git คิดว่ารวมไปแล้ว ต้อง revert ตัว revert นั้นก่อน

cherry-pick: เอา commit เดียวไปวางที่อื่น

git switch release/2.x
git cherry-pick -x 9fceb02     # -x เติมบรรทัด "(cherry picked from commit ...)" ให้ตามรอยได้
git cherry-pick A^..B          # ช่วง A ถึง B รวม A
git cherry-pick -m 1 <merge-sha>   # ถ้าเลือก merge commit ต้องบอก parent เหมือน revert

commit ที่ได้เป็นของใหม่ รหัสไม่ตรงกับต้นฉบับ ซึ่งแปลว่าถ้าภายหลัง merge สอง branch เข้าด้วยกัน Git ไม่รู้ว่าสองอันเป็นการเปลี่ยนเดียวกัน ส่วนใหญ่จะรวมได้เพราะเนื้อเหมือนกัน แต่ถ้าแต่ละฝั่งแก้ต่อจากนั้นก็อาจเกิด conflict ได้ ใช้ cherry-pick เมื่อต้องการแค่บาง commit เช่น backport bug fix หรือกู้ commit ที่ลงผิด branch

patch: ส่งการเปลี่ยนแปลงโดยไม่ผ่าน remote

คำสั่งสร้างรับด้วยเก็บ author และข้อความ commit
git diff > fix.patchdiff ธรรมดาgit apply fix.patchไม่เก็บ (ได้แค่เนื้อไฟล์ที่เปลี่ยน)
git format-patch -3ไฟล์ .patch หนึ่งไฟล์ต่อ commitgit am *.patchเก็บครบ

กรณีที่ใช้จริงคือส่ง fix ให้เครื่องที่เข้าถึง remote ไม่ได้ หรือโครงการที่รับ patch ทางอีเมล ถ้า git am ติดปัญหาให้แก้ แล้ว git am --continue หรือถอยด้วย git am --abort

stash ขั้นต่อไป

นอกจาก push / pop ที่รู้อยู่ ยังมี git stash push -p (เลือกเก็บทีละก้อน) git stash show -p stash@{0} (ดู diff ของที่เก็บไว้) และ git stash branch new-branch ที่สร้าง branch ใหม่จาก commit ที่ stash ถูกสร้าง แล้ว pop ให้ ซึ่งช่วยหนีปัญหา conflict ตอน pop บน branch ที่เปลี่ยนไปมากแล้ว

ค้นและตรวจ history: log, diff range, blame, grep

Intermediate HackerRank: Searching · Blame · Git Log

ตรงกับ HackerRank Git (Intermediate) หัวข้อ Searching และ Blame และเกณฑ์ Intermediate ข้อใช้คำสั่งขั้นสูงเพื่อสืบค้นและวิเคราะห์ history

มีคนถามว่า “ฟังก์ชัน calculateTax ถูกแก้เมื่อไร ใครแก้ แล้วแก้ทำไม” และต้องตอบก่อนประชุมอีกสิบนาที เครื่องมือค้นประวัติของ Git ทำให้ตอบได้โดยไม่ต้องเปิด GitHub UI และไม่ต้องไล่อ่าน commit ทีละอัน

log: กรองให้เหลือเฉพาะที่ต้องการ

git log --oneline --graph --decorate --all
git log --author="somchai" --since="2 weeks ago"
git log --grep="payslip"                  # ค้นในข้อความ commit
git log -S"calculateTax"                  # commit ที่ทำให้จำนวนที่พบคำนี้เปลี่ยน (เพิ่มหรือลบ)
git log -G"calculate(Tax|Vat)"        # commit ที่บรรทัดที่เพิ่มหรือลบตรงกับ regex
git log --follow -- src/tax.js            # ตามประวัติไฟล์ข้ามการ rename
git log -L :calculateTax:src/tax.js       # ประวัติเฉพาะฟังก์ชัน
git shortlog -sn                          # จำนวน commit ต่อคน

-S (เรียกว่า pickaxe) ตอบคำถามว่า “คำนี้โผล่หรือหายตอนไหน” ส่วน --grep ค้นข้อความที่คนเขียนไว้ ซึ่งต่างกันตรงที่ -S ดูเนื้อโค้ด ส่วน --grep ดูข้อความ commit

ช่วง commit: .. กับ ...

จุดนี้ข้อสอบชอบถาม เพราะต่างกันแค่จุดเดียว ในโครงที่ main และ feature ต่างมี commit ของตัวเองหลังแตกจากกัน

git log --oneline main..feature
# 7ea6093 C: feature                  ← อยู่ใน feature แต่ไม่อยู่ใน main
git log --oneline --left-right main...feature
# < 72c0430 D: main                   ← ที่ฝั่งเดียวของแต่ละสาย (symmetric difference)
# > 7ea6093 C: feature
git diff --name-only main...feature   # เปลี่ยนอะไรบ้างใน feature นับจากจุดแตกกิ่ง (ไม่รวมงานใหม่ของ main)
git diff --name-only main..feature    # เทียบปลายทั้งสอง รวมงานของ main ด้วยในรูปลบ

สรุปสั้น ๆ สำหรับ git log คือ A..B หมายถึงของใน B ที่ A ไม่มี ส่วน A...B คือของที่อยู่ฝั่งเดียว สำหรับ git diff ความหมายต่างออกไป A...B เทียบ merge-base ของสองฝั่งกับ B ซึ่งเป็นสิ่งที่ PR แสดง ส่วน A..B เท่ากับเทียบปลาย A กับปลาย B ตรง ๆ

blame, grep และ show

git blame -L 40,60 src/tax.js           # ใครแก้แต่ละบรรทัดล่าสุด เฉพาะช่วงที่สนใจ
git blame -w -C src/tax.js              # ไม่สนช่องว่าง และตามโค้ดที่ย้ายมาจากไฟล์อื่น
git config blame.ignoreRevsFile .git-blame-ignore-revs   # ข้าม commit จัด format ทั้งโปรเจกต์
git grep -n "TODO"                      # ค้นในไฟล์ที่ track ปัจจุบัน แสดงเลขบรรทัด
git grep --count "TODO"                 # นับจำนวนที่เจอต่อไฟล์
git grep "calculateTax" v2.1.0          # ค้นในเวอร์ชันเก่าโดยไม่ต้อง checkout
git show 9fceb02 --stat                 # ดูว่า commit นั้นแตะไฟล์ไหน

blame บอกว่า commit ล่าสุดที่แตะบรรทัดนั้น ซึ่งไม่ได้แปลว่าคนนั้นเป็นคนเขียนตรรกะเดิม ถ้ามี commit จัดรูปแบบทั้งโปรเจกต์ blame จะชี้ไปที่ commit นั้นหมด จึงต้องใช้ -w หรือไฟล์ ignore-revs ช่วย ส่วนวิธีค้นหา commit ที่ทำให้ bug เกิดด้วยการทดสอบอัตโนมัติ คือ git bisect อยู่ที่หัวข้อ 15

ทีมแปดคนเริ่มมีปัญหา มีคน push ตรงเข้า main ตอนดึก ๆ มีคน force push ทับงานของอีกคน และ PR ค้างรอรีวิวสามวันเพราะ reviewer อยู่คนละ time zone ปัญหาแบบนี้แก้ด้วยกฎกับสิทธิ์ที่ระบบบังคับใช้ได้จริง ไม่ใช่ด้วยการขอร้อง

จุดที่ต้องรู้คือ hook ฝั่ง client อยู่ใน .git/hooks ซึ่ง ไม่ถูก clone ตามมา และผู้ใช้ข้ามได้ด้วย git commit --no-verify ทีมจึงมักแชร์ hook ผ่านโฟลเดอร์ใน repo แล้วตั้ง core.hooksPath ให้ชี้ไป หรือใช้เครื่องมือจัดการ hook ส่วนกฎที่ห้ามหลุดจริง ๆ ต้องบังคับที่ฝั่ง server หรือใน CI เพราะ client hook เป็นแค่ตัวช่วยของผู้พัฒนา

สิทธิ์และการป้องกัน branch บนแพลตฟอร์ม

โครงสร้างภายในของ Git (Internals)

Advance HackerRank: Internals

ตรงกับ HackerRank Git (Advanced) หัวข้อ Git Internals (Objects, Plumbing Commands, git cat-file, Refs และ pack files) และเป็นพื้นฐานของเกณฑ์ Advance ทุกข้อ เพราะการแก้ history ใหญ่ ๆ ต้องรู้ว่าอะไรถูกเก็บและอะไรถูกชี้ถึง

เพื่อนร่วมทีมถามว่า “ทำไมเปลี่ยนชื่อไฟล์แล้ว Git ยังรู้ว่าเป็นไฟล์เดิม ทั้งที่ไม่มีคำสั่ง rename ใน history” หรือ “ทำไม commit ที่โดน reset --hard ยังกู้ได้” คำตอบทั้งสองอยู่ในวิธีที่ Git เก็บข้อมูล ซึ่งเรียบง่ายกว่าที่คิด Git คือฐานข้อมูลแบบ key-value ที่ key เป็น hash ของเนื้อหา และ branch กับ tag เป็นแค่ตัวชี้เข้าไปในฐานข้อมูลนั้น

Object สี่ชนิดใน object database

ทุกอย่างที่ Git เก็บเป็น object ที่มีชื่อเป็น hash ของเนื้อหา (ส่วนใหญ่ใช้ SHA-1 ส่วน SHA-256 เป็น object format ทางเลือกที่ต้องดูว่า Git เวอร์ชันและแพลตฟอร์มที่ใช้รองรับหรือไม่) เนื้อหาเหมือนกันก็ hash เหมือนกัน จึงเก็บครั้งเดียว

ชนิดเก็บอะไร
blobเนื้อหาของไฟล์ล้วน ๆ ไม่มีชื่อไฟล์
treeรายการของโฟลเดอร์ แต่ละรายการมีชื่อ, mode (เช่น 100644) และ hash ที่ชี้ไป blob หรือ tree ย่อย
commithash ของ tree ราก, parent (0, 1 หรือมากกว่า), author, committer, ข้อความ
tag (annotated)ชี้ไป object หนึ่งอัน พร้อมชื่อผู้สร้าง ข้อความ และลายเซ็นถ้ามี

ลองสร้างมือเปล่าเพื่อเห็นว่าไม่มีเวทมนตร์ ค่า hash ของข้อความ test content จะได้เหมือนกันทุกเครื่องเพราะคำนวณจากเนื้อหา

echo 'test content' | git hash-object -w --stdin
# d670460b4b4aece5915caf5c68d12f560a9fe3e4      ← -w คือเขียนลง object database ด้วย
git cat-file -t d670460b      # blob
git cat-file -p d670460b      # test content

git cat-file -p HEAD          # ดู commit ล่าสุด
# tree <sha ของ tree ราก>
# parent <sha ของ commit ก่อนหน้า>
# author Dev <dev@example.com> <timestamp> +0700
git ls-tree HEAD              # ดู tree: mode, ชนิด, hash, ชื่อ
# 100644 blob c0d0fb45...    app.txt

และเพื่อพิสูจน์ว่า git commit เป็นแค่การเรียกคำสั่งเล็ก ๆ ต่อกัน ลองสร้าง commit ด้วยคำสั่งระดับล่าง (plumbing) ทีละขั้นดู

H=$(echo 'hello' | git hash-object -w --stdin)           # 1) เขียน blob
git update-index --add --cacheinfo 100644,$H,hello.txt   # 2) ใส่ลง staging
T=$(git write-tree)                                      # 3) สร้าง tree จาก staging
C=$(echo "first by hand" | git commit-tree $T)           # 4) สร้าง commit ชี้ tree นั้น
git update-ref refs/heads/main $C                        # 5) ให้ branch ชี้ commit
git log --oneline
# f36ac19 first by hand

คำสั่งที่เราใช้ทุกวัน (commit, merge, checkout) เรียกว่า porcelain ส่วนคำสั่งระดับล่างข้างบนเรียกว่า plumbing เหมาะกับการเขียนสคริปต์เพราะผลลัพธ์คงที่กว่า

Refs: branch, tag และ HEAD เป็นแค่ไฟล์

branch ชื่อ main คือไฟล์ .git/refs/heads/main ที่ข้างในมีรหัส commit 40 ตัวอักษร (41 ไบต์รวมขึ้นบรรทัดใหม่) ส่วน .git/HEAD ปกติเป็น symbolic ref ที่เขียนว่า ref: refs/heads/main ถ้าเข้าสู่สภาวะ detached HEAD ไฟล์นี้จะเก็บรหัส commit ตรง ๆ เมื่อ repo มี ref จำนวนมาก Git จะรวมไว้ในไฟล์ packed-refs เพื่อประหยัดพื้นที่ คำสั่ง git update-ref และ git symbolic-ref เป็นวิธีที่ถูกต้องในการแก้ไฟล์เหล่านี้ ไม่ควรไปแก้ไฟล์ด้วยมือ

เมื่อรู้แบบนี้ก็เข้าใจได้ว่า ทำไมการสร้าง branch ถึงถูกมาก (เขียนไฟล์ 41 ไบต์) ทำไม reset --hard ไม่ได้ลบ commit (แค่เปลี่ยนค่าในไฟล์) และทำไม commit ที่ไม่มีใครชี้ถึงจึงกู้ได้ตราบที่ยังไม่ถูกเก็บกวาด

ทำไมเปลี่ยนชื่อไฟล์แล้ว Git ยังตามรอยได้

เพราะ Git ไม่ได้บันทึกการ rename แต่ละ commit เก็บ tree ทั้งก้อน ตอนเรา diff หรือ log Git เปรียบเทียบ tree สองฝั่งแล้วเดาว่า blob ที่หายไปกับ blob ที่โผล่ใหม่คือไฟล์เดียวกันหรือไม่ โดยดูความคล้ายของเนื้อหา (ค่าเริ่มต้นประมาณ 50%) นี่คือเหตุผลที่ rename พร้อมแก้เนื้อหาเยอะ ๆ ในคราวเดียวอาจถูกมองเป็น ลบแล้วสร้างใหม่ และทำให้ git log --follow ขาดช่วง คำแนะนำในการปฏิบัติคือ commit การย้ายไฟล์แยกจาก commit ที่แก้เนื้อหา

Loose object, packfile และการเก็บกวาด

object ใหม่ถูกเก็บเป็นไฟล์ลีบ (loose object) ที่ .git/objects/xx/yyyy... บีบอัดด้วย zlib เมื่อมีมากขึ้น Git จะรวมเป็น packfile (.git/objects/pack/*.pack) ที่เก็บ object หลายตัวไว้ในไฟล์เดียวและใช้ delta compression คือเก็บ object ที่คล้ายกันเป็น “ตัวเต็มหนึ่งตัวกับผลต่างของตัวอื่น” ซึ่งทำให้ repo ที่มี history ยาวแต่ละไฟล์เปลี่ยนเล็กน้อย ยังมีขนาดเล็ก การรวมนี้เกิดตอน git gc หรือตอน push/fetch

git count-objects -vH      # ดูจำนวน loose object, ขนาด, in-pack
git gc                     # รวมเป็น pack และเก็บกวาด
git fsck --lost-found      # หา object ที่ไม่มี ref ชี้ถึง (dangling)
git verify-pack -v .git/objects/pack/pack-*.idx | head

object ที่ไม่มี branch, tag, reflog หรือ object อื่นชี้ถึง เรียกว่า unreachable git gc จะลบทิ้งเมื่อเก่าเกินเกณฑ์ ค่าเริ่มต้นคือสองสัปดาห์ (gc.pruneExpire) ซึ่งเป็นช่วงเวลาที่เรายังกู้ได้ เช่น ด้วย git fsck --lost-found หลังจากพลาดโดยไม่เหลือ reflog

สถาปัตยกรรม repo: monorepo, submodule, subtree

Advance HackerRank: Submodules · Administration

ตรงกับเกณฑ์ Advance ข้อ “Architect repository structures สำหรับโครงการหลายทีมขนาดใหญ่ (monorepo, submodules, subtree)” และหัวข้อ Submodules ของ HackerRank Git (Intermediate)

องค์กรมีหกทีมที่ใช้ UI library, auth library และ API schema ร่วมกัน คำถามที่ถูกส่งมาถึงคนออกแบบคือ “แยก repo ต่อทีม หรือรวมเป็นอันเดียว แล้วของที่ใช้ร่วมกันจะอยู่ตรงไหน” ไม่มีคำตอบเดียวที่ถูกในทุกองค์กร สิ่งที่ต้องทำคือชั่งว่าต้นทุนแบบไหนที่ทีมนี้รับได้

Polyrepo กับ Monorepo

ด้านPolyrepo (หลาย repo)Monorepo (repo เดียว)
ขอบเขตความเป็นเจ้าของชัด ทีมคุมสิทธิ์และ release ของตัวเองต้องออกแบบเอง เช่น CODEOWNERS ตามโฟลเดอร์
แก้ของที่ใช้ร่วมกันและผู้ใช้ในคราวเดียวต้องแก้หลาย repo หลาย PR และประสานเวอร์ชันแก้ใน commit เดียว test ครอบคลุมทั้งชุด
การจัดการ dependency ภายในผ่านเวอร์ชันของ package ที่ปล่อยออกมาใช้โค้ดล่าสุดร่วมกันได้ แต่ต้องมีวินัยเรื่อง breaking change
ขนาดและความเร็วแต่ละ repo เล็ก clone เร็วโตเร็ว ต้องใช้เทคนิคช่วย (ด้านล่าง)
CIแยกต่อ repo เรียบง่ายต้องรันเฉพาะส่วนที่ได้รับผลกระทบ ไม่งั้นช้าและแพง
สิทธิ์การเข้าถึงตั้งต่อ repo ได้ละเอียดละเอียดระดับโฟลเดอร์ทำได้ยากกว่า ขึ้นกับแพลตฟอร์ม

ที่ตัดสินจริงมักเป็นปัจจัยเหล่านี้ ทีมแก้ข้ามขอบเขตบ่อยแค่ไหน ต้องการ atomic change ข้าม component ไหม ต้องปล่อยเวอร์ชันของแต่ละส่วนแยกกันหรือเปล่า และองค์กรมีเครื่องมือ build กับ CI ที่รองรับ monorepo อยู่แล้วหรือยัง

เทคนิคทำให้ repo ใหญ่ยังใช้งานได้

# clone แบบไม่ดึงเนื้อไฟล์ทั้งหมดมาก่อน (partial clone) และ checkout เฉพาะบางโฟลเดอร์
git clone --filter=blob:none --sparse https://example.com/org/monorepo.git
cd monorepo
git sparse-checkout set services/payslip libs/common

git clone --depth 1 <url>          # shallow clone: เอา history แค่ commit ล่าสุด (เหมาะกับ CI)
git worktree add ../hotfix-3.5 release/3.5   # checkout อีก branch ในโฟลเดอร์ใหม่ โดยไม่ clone ซ้ำ
git maintenance start              # ให้ Git ดูแล repo ใหญ่เบื้องหลัง (Git 2.29 ขึ้นไป)

partial clone ต้องให้ server รองรับด้วย ส่วน shallow clone มีข้อจำกัดในงานที่ต้องใช้ history เช่น git describe, git bisect, หรือการหา merge-base ในบางกรณี ไฟล์ไบนารีขนาดใหญ่ เช่น รูปดีไซน์ วิดีโอ ควรเก็บด้วย Git LFS ซึ่งเก็บเฉพาะ pointer ใน repo และเอาตัวไฟล์ไปไว้ที่เซิร์ฟเวอร์ LFS (ตั้งผ่าน git lfs track "*.psd" ที่เขียนกฎลง .gitattributes) แต่ต้องตรวจว่าแพลตฟอร์มรองรับและมีโควตาเท่าไร

Submodule: ชี้ไปที่ commit ของอีก repo

submodule ฝัง repo อื่นไว้ในโฟลเดอร์หนึ่งของ repo เรา (เรียกว่า superproject) แต่สิ่งที่ superproject บันทึกไม่ใช่เนื้อไฟล์ มันบันทึก รหัส commit ที่ต้องใช้ ของ repo ย่อย (ใน tree เป็น mode 160000) ส่วน URL เก็บใน .gitmodules ดังนั้นสองคนที่ checkout superproject ที่ commit เดียวกันจะได้โค้ดของ submodule เวอร์ชันเดียวกันเสมอ

git submodule add https://example.com/org/ui-kit.git libs/ui-kit
git commit -m "chore: add ui-kit submodule"

git clone --recurse-submodules <url>        # clone พร้อม submodule
git submodule update --init --recursive     # ถ้า clone มาแล้วลืม flag

git submodule update --remote libs/ui-kit   # ขยับ submodule ไปตาม branch ที่ track
git add libs/ui-kit && git commit -m "chore: bump ui-kit"   # ต้อง commit การขยับนี้ใน superproject เอง

กับดักที่เจอบ่อยมีสามอย่าง หนึ่ง เข้าไปแก้ในโฟลเดอร์ submodule แล้วพบว่าอยู่ใน detached HEAD เพราะ submodule ถูก checkout ที่ commit เฉพาะ ไม่ใช่ branch ต้องสลับไปที่ branch ก่อนทำงาน สอง commit ใน submodule แต่ลืม push ก่อน push superproject ทำให้คนอื่นเจอ error เพราะ commit ที่ superproject ชี้ไปไม่มีใน remote ของ submodule สาม CI ต้องมีสิทธิ์อ่าน repo ย่อยและต้องสั่ง init submodule ด้วย

Subtree: เอาเนื้อ repo อื่นมาไว้ในโฟลเดอร์ของเรา

git subtree รวมเนื้อหาและ history ของ repo อื่นเข้ามาเป็นโฟลเดอร์ปกติของ repo เรา คนที่ clone ไปได้ไฟล์ครบโดยไม่ต้องรู้ว่ามี repo อื่นอยู่เบื้องหลัง ไม่มี .gitmodules และไม่ต้องใช้ flag พิเศษ

git subtree add  --prefix=libs/ui-kit https://example.com/org/ui-kit.git main --squash
git subtree pull --prefix=libs/ui-kit https://example.com/org/ui-kit.git main --squash
git subtree push --prefix=libs/ui-kit https://example.com/org/ui-kit.git feature/fix-button

subtree เป็นคำสั่งในส่วน contrib ที่มากับ Git ส่วนใหญ่ ข้อจำกัดคือ history ของ repo ที่ผสมกันซับซ้อนขึ้น (โดยเฉพาะถ้าไม่ใช้ --squash) และการส่งการแก้ไขกลับขึ้นไปยัง repo ต้นทางต้องใช้ subtree push ซึ่งช้าลงเมื่อ history ยาว

เขียน history ใหม่ระดับ repo และงานดูแลระบบ

Advance HackerRank: Rewriting History · Administration

ตรงกับ HackerRank Git (Advanced) หัวข้อ Git Administration (git filter-branch, git fsck, git reflog, git gc) และ Rewriting History ส่วนเกณฑ์ Advance คือการดูแล repository ขนาดใหญ่และรับมือเหตุการณ์ที่ต้องแก้ history ระดับ repo

เช้าวันศุกร์มีข้อความเข้า Slack ว่า “ผม commit AWS key เข้า main เมื่อสามวันก่อน เพิ่งเห็น” ทีมต้องตัดสินใจเรื่องเร่งด่วนหลายอย่างพร้อมกัน และลำดับของสิ่งที่ทำสำคัญกว่าเครื่องมือที่ใช้ เรื่องนี้เป็นโจทย์ scenario ที่ออกสอบง่าย เพราะวัดทั้งความรู้ Git และความเข้าใจเรื่องความเสี่ยง

ลำดับของ secret leak runbook

  1. เพิกถอนหรือเปลี่ยน secret ทันที การแก้ history ไม่ทำให้ค่าที่รั่วไปแล้วปลอดภัย ใครที่ clone หรือ fork ไปแล้วยังมีค่าเดิมอยู่ ต้องถือว่ารั่ว
  2. ตรวจว่า secret ถูกใช้โดยใครบ้างช่วงที่ผ่านมา (log ของผู้ให้บริการ) และมี fork หรือ clone ที่เรารู้อยู่แล้วกี่ที่
  3. ตัดสินใจว่าต้องเขียน history ใหม่ไหม ถ้า repo เป็น private และ secret ถูกเพิกถอนแล้ว บางทีมเลือกไม่เขียนใหม่เพื่อไม่กระทบทุกคน ถ้าเป็น repo สาธารณะหรือมีข้อกำหนดด้านการตรวจสอบ มักต้องล้างออก
  4. ถ้าเขียนใหม่ ให้ทำบน clone สดแล้วใช้เครื่องมือที่เหมาะสม (หัวข้อถัดไป) จากนั้น force push ทุก branch และ tag ที่ได้รับผลกระทบ
  5. แจ้งทุกคนให้ re-clone หรือทำ rebase งานที่ค้างบน history ใหม่ และติดต่อผู้ให้บริการโฮสต์เพื่อล้างข้อมูลที่ถูก cache หรือค้างใน PR (ดูเอกสารของแพลตฟอร์มที่ใช้)
  6. ป้องกันซ้ำ เปิด secret scanning หรือ push protection ถ้าแพลตฟอร์มมี เพิ่ม pre-commit hook ตรวจ secret และเก็บ secret ไว้ในระบบจัดการ secret ไม่ใช่ในไฟล์

filter-branch กับ filter-repo

git filter-branch เป็นเครื่องมือเดิมที่ HackerRank Advanced ระบุไว้ แต่เอกสารทางการของ Git ระบุว่าปัญหาด้านความปลอดภัยและประสิทธิภาพของมันแก้แบบเข้ากันได้ย้อนหลังไม่ได้ จึงไม่แนะนำให้ใช้ และแนะนำเครื่องมืออย่าง git filter-repo แทน (ตัวนี้เป็นเครื่องมือแยกที่ต้องติดตั้งเอง ไม่ได้มากับ Git) ควรอ่านออกทั้งสองแบบเพราะข้อสอบและระบบเก่ายังอ้างถึง filter-branch

git clone --mirror https://example.com/org/app.git app-clean.git   # ทำงานบน clone สด
cd app-clean.git

git filter-repo --path config/secrets.yml --invert-paths   # ลบไฟล์นี้ออกจากทุก commit
git filter-repo --replace-text expressions.txt             # แทนข้อความตามรายการ เช่น token → ***REMOVED***
git filter-repo --strip-blobs-bigger-than 10M              # ตัดไฟล์ใหญ่เกิน 10 MB ออก
git filter-repo --subdirectory-filter services/payslip     # แยกโฟลเดอร์นี้เป็น repo ใหม่พร้อม history

ข้อควรรู้ของ filter-repo คือมันปฏิเสธรันบน clone ที่ไม่ใช่ “สด” เพื่อกันพลาด (ถ้าไม่ใส่ --force) และมันลบ remote origin ออกหลังเขียนเสร็จ เพื่อกัน push ผิดที่โดยไม่ตั้งใจ ต้องเพิ่ม remote กลับเอง ก่อนใช้งานจริงให้ลองกับสำเนาและอ่านเอกสารฉบับล่าสุดของเครื่องมือเพราะตัวเลือกและพฤติกรรมอาจเปลี่ยน

ผลกระทบของการเขียน history ใหม่

commit ตั้งแต่จุดที่แก้เป็นต้นไปจะได้รหัสใหม่ทั้งหมด เพราะรหัสของ commit รวม hash ของ parent เข้าไปด้วย ผลคือ tag เดิมต้องย้ายหรือสร้างใหม่ PR ที่เปิดอยู่ชี้ commit ที่ไม่มีแล้ว branch ของทุกคนที่แตกจาก history เดิมจะไม่ตรงกับของใหม่ การ force push เข้า branch ที่ถูก protect ต้องปิดการป้องกันชั่วคราวหรือใช้สิทธิ์ผู้ดูแล และแพลตฟอร์มบางแห่งมี ref พิเศษ (เช่น ของ PR) ที่ push ทับไม่ได้ ทำให้เนื้อหาเดิมยังเข้าถึงได้ผ่านทางนั้นจนกว่าผู้ให้บริการจะล้างให้ จึงต้องรีบเพิกถอน secret ตั้งแต่ขั้นแรก

คนที่มีงานค้างบน history เก่าแก้ได้ด้วยการ rebase เฉพาะ commit ของตัวเองไปวางบน history ใหม่ เช่น git rebase --onto origin/main <จุดแตกเดิม> my-branch หรือง่ายกว่านั้นคือ clone ใหม่แล้ว cherry-pick งานของตัวเองมา

ดูแลและเก็บกวาด repository

git fsck --full                    # ตรวจความสมบูรณ์ของ object database
git gc                             # รวมและบีบอัด object ลบของที่เกินกำหนด
git count-objects -vH              # ดูขนาดและจำนวน object

# ลบทิ้งจริงทันที (อันตราย: ตัดทางกู้คืนผ่าน reflog และ unreachable object)
git reflog expire --expire=now --all
git gc --prune=now --aggressive

สองบรรทัดสุดท้ายใช้หลังเขียน history ใหม่เพื่อให้ object เก่าที่มี secret หายไปจริงจากเครื่องนั้น อย่าใช้เป็นกิจวัตรบน repo ที่ใช้งานอยู่ เพราะตัดตาข่ายนิรภัยอย่าง reflog ทิ้ง

Merge strategy และ bisect ขั้นสูง

Advance HackerRank: Merge Strategies · bisect

ตรงกับ HackerRank Git (Advanced) หัวข้อ Merge Strategies (resolve, recursive, octopus, ours, subtree) และ Debugging ด้วย git bisect รวมถึงเกณฑ์ Advance เรื่องการ resolve conflict ที่ซับซ้อน

QA แจ้งว่าหน้าสรุปเงินเดือนคำนวณผิดตั้งแต่ release ล่าสุด แต่ระหว่าง v2.4.0 กับตอนนี้มี 180 commit และไม่มีใครรู้ว่าอันไหนทำพัง การไล่อ่านทีละ commit เป็นวิธีที่ช้าที่สุด Git มีเครื่องมือที่ใช้การค้นหาแบบแบ่งครึ่งทำให้เหลือไม่กี่รอบ และอีกเรื่องที่ควรรู้ลึกคือ “merge ทำงานยังไง และเลือก strategy ได้อย่างไร”

git bisect: ค้นหาแบบแบ่งครึ่ง

ถ้าเรารู้ว่า commit หนึ่งดีและอีกอันเสีย bisect จะ checkout commit ตรงกลางให้ทดสอบ แล้วตัดช่วงที่เหลือครึ่งหนึ่งทุกรอบ ประมาณ log₂(N) รอบ ดังนั้น 180 commit ใช้ราว 8 รอบ (2⁸ = 256 ≥ 180)

git bisect start
git bisect bad                    # commit ปัจจุบันมี bug
git bisect good v2.4.0            # เวอร์ชันนี้ยังดี
# Git checkout commit กลางให้ ทดสอบแล้วตอบ good หรือ bad ไปเรื่อย ๆ
git bisect run ./check-payslip.sh # หรือให้สคริปต์ตอบแทน
# <sha> is the first bad commit
git bisect reset                  # กลับมาที่ branch เดิม

สคริปต์ที่ใช้กับ bisect run สื่อสารผ่าน exit code

Exit codeความหมาย
0commit นี้ดี (good)
1 ถึง 127 ยกเว้น 125commit นี้เสีย (bad)
125ทดสอบไม่ได้ ให้ข้าม (skip) เช่น build ไม่ผ่านด้วยเหตุอื่น
128 ขึ้นไปยกเลิกการ bisect ทั้งหมด
#!/bin/sh
# check-payslip.sh
make build >/dev/null 2>&1 || exit 125    # build ไม่ผ่าน = ข้ามไป ไม่นับเป็น bad
./run-test payslip-total                  # test fail จะ exit ไม่ใช่ 0 = bad

ผลที่ลองรันกับ repo ตัวอย่างหกคอมมิต ที่ bug เริ่มจาก commit 4 คือ bisect รายงาน is the first bad commit ที่ commit 4 ถูกต้อง ข้อควรระวังคือ test ต้อง deterministic ไม่งั้น bisect จะชี้ผิดที่ และถ้า history มี merge เยอะ ให้ดูว่า Git รุ่นที่ใช้มีตัวเลือก --first-parent สำหรับ bisect หรือไม่ เพื่อไล่เฉพาะแนว main

จุดที่ต้องแยกให้ออกคือ -s (strategy) กับ -X (strategy option) ที่ชื่อ ours เหมือนกันแต่ความหมายต่างกันมาก ลองดูผลจริง ฝั่ง main แก้ line2 ฝั่ง theirs แก้ทั้ง line2 และ line11

git merge -X ours theirs     # เฉพาะจุดที่ conflict เลือกฝั่งเรา ส่วนที่ไม่ชนยังรับจากอีกฝั่ง
grep -E "line2|line11" f.txt
# line2-OURS
# line11-THEIRS          ← การแก้ line11 ของ theirs ถูกรับไว้

git merge -s ours theirs     # ทิ้งเนื้อหาของ theirs ทั้งหมด แต่บันทึกว่า merge แล้ว
# line2-OURS
# line11                 ← การแก้ line11 ของ theirs หายไป

strategy option ที่ใช้บ่อยมี -X theirs, -X patience (ช่วยเมื่อ diff จับบรรทัดผิดคู่), -X ignore-space-change, -X renormalize (ปัญหา line ending) และ -X subtree=<path> ควรใช้ -X ours/theirs อย่างระวัง เพราะมันเลือกให้โดยไม่ผ่านตาเรา อาจกลบการแก้ที่จำเป็นของอีกฝั่ง

นำทีม: workflow, toolchain, mentoring และเหตุการณ์ force push

Advance HackerRank: Interactive Rebase · Administration

ตรงกับเกณฑ์ Advance ข้อ “Mentor teams on Git best practices, workflow customization และ toolchain extensions” หัวข้อนี้เน้นการตัดสินใจและการสื่อสารกับทีม ซึ่งในข้อสอบมักเป็น scenario และ judgment

คนระดับนี้ถูกวัดว่าทำให้ทีมทำงานกับ Git ได้ดีขึ้นหรือไม่ ไม่ใช่แค่รู้คำสั่งเยอะ ทีมสิบสองคนมีพี่ที่ force push ทับงานคนอื่น น้องที่กลัว rebase จน branch อายุสามสัปดาห์ และ PR ที่ใหญ่เกินกว่าจะรีวิวได้ สิ่งที่ต้องตอบคือจะจัดระบบอย่างไรให้ทุกคนทำถูกโดยไม่ต้องจำกฎเอง

เลือก workflow จากบริบทของทีม ไม่ใช่จากความนิยม

คำถามที่ควรถามถ้าคำตอบเป็นมักโน้มไปทาง
ปล่อยบ่อยแค่ไหน และ deploy กลับได้เร็วไหมทุกวัน ย้อนกลับเร็วtrunk-based หรือ GitHub Flow
ต้องรองรับกี่เวอร์ชันพร้อมกันหลายเวอร์ชัน ลูกค้าอัปเดตเองrelease branch ต่อเวอร์ชัน และ backport
มีขั้นตอนรีวิวจากภายนอกก่อนปล่อยไหม (เช่น store, regulator)มี ใช้เวลาเป็นวันrelease branch เพื่อ freeze โค้ดระหว่างรอ
CI และ test เชื่อใจได้แค่ไหนยังไม่ครอบคลุมยังไม่เหมาะกับ merge เข้า trunk ถี่ ๆ ควรเพิ่ม test ก่อน
มีงาน compliance ที่ต้องมีหลักฐานผู้อนุมัติมีบังคับ PR, required review, signed commits

เมื่อเลือกแล้ว ให้เขียนลงเอกสารสั้น ๆ หนึ่งหน้าที่อยู่ใน repo (เช่น CONTRIBUTING.md) ตัวอย่างหัวข้อที่ควรมีดูตามนี้

Git working agreement (ตัวอย่าง)
- Branch: feature/<ticket>-<ชื่อสั้น>  อายุไม่เกิน 3 วันทำการ ถ้าเกินให้แตกงานย่อย
- Commit: Conventional Commits  (feat:, fix:, chore:, docs:)
- PR: ไม่เกินประมาณ 400 บรรทัดที่เปลี่ยน, ต้องมีคำอธิบายและวิธีทดสอบ
- Merge: squash and merge เข้า main, ห้าม push ตรง, ห้าม force push main/release/*
- Review: ตอบรอบแรกภายใน 1 วันทำการ, ต้องมี CODEOWNER ของโฟลเดอร์ที่แก้ approve
- Release: tag แบบ vMAJOR.MINOR.PATCH บน main, hotfix แตกจาก tag
- ถ้าพลาด: อย่า force push เอง ให้ถามใน #git-help ก่อน

ตัวเลขในตัวอย่าง (3 วัน, 400 บรรทัด) เป็นแค่ตัวอย่างประกอบ ให้ทีมตั้งค่าของตัวเองจากข้อมูลจริงของทีม

ให้เครื่องมือช่วยบังคับ ไม่ต้องพึ่งการจำ

  • Branch protection / rulesets และ required checks กันการ push ตรงและการ merge ที่ CI ยังไม่ผ่าน
  • Hook ฝั่ง client ที่แชร์ผ่าน repo (core.hooksPath หรือเครื่องมือจัดการ hook) สำหรับ format, lint, ตรวจข้อความ commit และกันการ commit secret แต่อย่าพึ่งเป็นด่านเดียว เพราะข้ามได้
  • CODEOWNERS ให้การรีวิวถึงคนที่ควรเห็น
  • Merge queue (ถ้าแพลตฟอร์มมี) ทดสอบ PR บนปลาย main ล่าสุดก่อน merge จริง ช่วยกัน main พังจาก PR ที่ผ่านตอนแยกกันแต่ชนกันเมื่อรวม
  • Bot อัปเดต dependency และ secret scanning เพื่อลดงานซ้ำและตรวจจับของที่หลุด
  • PR template และ issue template ให้ข้อมูลครบตั้งแต่รอบแรก

สอนทีมให้ใช้ Git เป็น

วิธีที่ได้ผลคือฝึกกับสถานการณ์จริงใน repo ทดลอง ไม่ใช่สไลด์ ตัวอย่าง lab ที่ใช้สอนได้ เช่น “ทำ reset --hard พลาดแล้วกู้ด้วย reflog”, “แก้ conflict ที่ rebase สามรอบ”, “ลง commit ผิด branch แล้วย้ายด้วย cherry-pick”, “รวม commit ที่ยุ่งเหยิงด้วย interactive rebase” ให้คนที่เพิ่งเข้าทีมจับคู่กับคนเก่าตอนทำ PR แรก และดู history ของ PR ในมุมที่ถามว่า “อีกหกเดือน คนที่มาอ่าน commit เหล่านี้จะเข้าใจไหม” เรื่องการวัดผล อย่าเพิ่งใช้ตัวชี้วัดที่ล่อให้เกมระบบ (เช่น จำนวน commit ต่อคน) ให้ดูสิ่งที่สะท้อนปัญหาจริง เช่น เวลาที่ PR รอรีวิว ขนาด PR และจำนวนครั้งที่ต้อง revert

นี่เป็นเหตุการณ์ที่ควรมีขั้นตอนไว้ก่อน เพราะตอนเกิดจริงทุกคนจะตกใจ

  1. หยุดไม่ให้ใคร pull หรือ push เพิ่ม และบอกทีมให้ อย่าลบ clone ในเครื่อง เพราะเครื่องที่มี commit เดิมคือแหล่งกู้คืน
  2. หา SHA ก่อนถูกเขียนทับ จาก audit log หรือหน้า activity ของแพลตฟอร์ม (ชื่อเมนูต่างกัน) หรือจาก clone ของใครสักคนที่ยังไม่ได้ fetch ใช้ git reflog show origin/main
  3. ยืนยันว่า commit นั้นยังอยู่ แล้วคืนค่าด้วย git push --force-with-lease=main:<sha-ปัจจุบัน> origin <sha-เดิม>:main เพื่อกันการเขียนทับซ้อน
  4. ให้ทุกคนตรวจ branch ของตัวเอง และเปิด branch protection ที่ห้าม force push หลังเหตุการณ์ พร้อมเขียนสรุปบทเรียนโดยไม่ตำหนิตัวบุคคล

บริษัทมี SVN ที่ใช้มาสิบสองปี มีโปรเจกต์ 40 ตัว ผู้ใช้ 150 คน และมีเครื่องมือ build ที่ผูกกับเลข revision คำสั่งคือ “ย้ายทั้งหมดไป Git ภายในไตรมาสนี้ โดยงานต้องไม่หยุด” ความเสี่ยงของงานนี้ไม่ได้อยู่ที่คำสั่งแปลง แต่อยู่ที่ข้อมูลที่หายเงียบ ๆ และคนที่ใช้งานไม่เป็นในวันแรก

แผนย้ายเป็นระยะ

  1. สำรวจ ขนาด repo จำนวน branch/tag ไฟล์ไบนารีใหญ่ ใครใช้ repo อะไร และใครพึ่ง revision number อยู่บ้าง (build script, ระบบ ticket, เอกสาร)
  2. ออกแบบการแมป trunk, branches, tags ของเดิมไปเป็น branch และ tag ของ Git รวมถึงชื่อผู้ใช้เดิมเป็นชื่อและอีเมลที่ถูกต้อง (authors mapping) ถ้าไม่ทำ commit จะผูกกับตัวตนที่ผิด
  3. ทดลองแปลงกับโปรเจกต์นำร่อง และตรวจผลด้วยวิธีที่ทำซ้ำได้
  4. ล้างและจัดการของใหญ่ ไฟล์ไบนารีใหญ่ย้ายไป Git LFS ข้อมูลลับที่เคยหลุดเอาออก ตัดสินใจว่าจะเก็บ history ครบหรือตัดบางส่วน
  5. เตรียมแวดล้อมใหม่ repo, สิทธิ์, branch protection, CI/CD ชี้ repo ใหม่, เอกสารและการฝึกอบรม
  6. Cutover ประกาศช่วง freeze ให้ระบบเดิมเป็นอ่านอย่างเดียว แปลงรอบสุดท้าย ตรวจ แล้วเปิดใช้ Git
  7. ช่วงหลังย้าย เก็บระบบเดิมแบบอ่านอย่างเดียวไว้ตามระยะที่ตกลง มีคนคอยตอบคำถามช่วงแรก และเตรียมแผนย้อนกลับในกรณีที่พบความเสียหายของข้อมูลก่อนที่ใครจะ commit งานใหม่ลง Git

ตรวจว่าการแปลงไม่ทำข้อมูลหาย

อย่าตัดสินว่า “เสร็จแล้ว” จากการที่คำสั่งแปลงไม่ error วิธีตรวจที่ใช้ได้จริงคือเทียบเนื้อไฟล์ที่จุดสำคัญ เช่น ทุก tag ที่เคยปล่อย

svn export -q https://svn.example.com/repo/tags/v2.0 /tmp/svn-v2
git archive --format=tar --prefix=git-v2/ v2.0 | tar -x -C /tmp
diff -r /tmp/svn-v2 /tmp/git-v2 && echo "tree ตรงกัน"

เมื่อต้องใช้ Git ในแอปพลิเคชัน

งานบางอย่าง เช่น เครื่องมือ CMS, bot ที่สร้าง PR, หรือระบบที่เก็บเอกสารเวอร์ชันไว้ใน Git ต้องเรียก Git จากโค้ด มีสองทาง คือเรียกโปรแกรม git เป็น process ย่อย กับใช้ไลบรารีอย่าง libgit2 (C พร้อม binding หลายภาษา), JGit (Java) หรือ go-git (Go) การเรียก git ได้พฤติกรรมครบเหมือนที่ใช้บนคอนโซลและแก้ปัญหาง่ายกว่า แต่ต้องมี Git ติดตั้งและต้องระวังการ parse ผลลัพธ์ ควรใช้ตัวเลือกที่ผลลัพธ์คงที่เช่น --porcelain หรือคำสั่ง plumbing ส่วนไลบรารีไม่ต้องสร้าง process และมี API เป็นของตัวเอง แต่ความสามารถอาจไม่เท่ากับ Git ตัวจริง (เช่น บางโปรโตคอลหรือ hook) ต้องเช็กเอกสารของไลบรารีนั้นก่อนเลือก

สถานการณ์

โจทย์ 1: เผลอ commit ลง main ทั้งที่ควรอยู่ใน branch ฟีเจอร์ และยังไม่ได้ push

เรื่องนี้เจอกันบ่อยมาก ข้อสำคัญคือต้องเก็บ commit ไว้ก่อนแล้วค่อยถอย main กลับ ถ้าถอยก่อนจะต้องไปงมหาใน reflog ทีหลัง

git branch fix/oops              # สร้างตัวชี้ใหม่ที่ commit ปัจจุบัน
git reset --hard origin/main     # ถอย main กลับให้ตรงกับ remote
git switch fix/oops              # ไปทำงานต่อบน branch ที่ถูกต้อง

ถ้าเปลี่ยนใจจะย้ายทีละ commit ใช้ git cherry-pick ก็ได้ แต่วิธีข้างบนเร็วกว่าเมื่อต้องย้ายหลาย commit ระวังอย่ารัน reset --hard ถ้ามีงานที่ยังไม่ commit ค้างอยู่ใน working tree เพราะส่วนนั้นจะหายและกู้ไม่ได้

โจทย์ 2: รัน git reset --hard HEAD~3 ไปแล้วรู้ตัวว่าพลาด จะกู้ commit กลับมาอย่างไร

commit ไม่ได้ถูกลบทันที ตัวชี้ของ branch แค่ขยับไปที่อื่น ให้ดู reflog หาตำแหน่งก่อนที่จะ reset

git reflog -5                    # หารายการที่ขึ้นว่า commit: ... ก่อน reset
git reset --hard 'HEAD@{1}'      # หรือใช้รหัส commit ที่เห็นใน reflog

ข้อจำกัดที่ต้องรู้คือ reflog อยู่ในเครื่องเท่านั้น และเก็บตามอายุที่ตั้งไว้ (ค่าเริ่มต้น 90 วันสำหรับรายการที่ยังเข้าถึงได้ และ 30 วันสำหรับที่เข้าถึงไม่ได้) ส่วนการแก้ไขที่ไม่เคย add หรือ commit ไม่อยู่ใน reflog เลย

โจทย์ 3: อยากส่ง PR แต่มี commit “wip” 4 อันที่ยังไม่ push ต้องการรวมเป็นอันเดียวที่อ่านง่าย 
git rebase -i HEAD~4             # เปิดรายการ commit ในเครื่องมือแก้ไข
# เก็บบรรทัดแรกเป็น pick แล้วเปลี่ยนบรรทัดที่เหลือเป็น fixup (ทิ้งข้อความ)
# หรือเป็น squash ถ้าอยากเขียนข้อความรวมใหม่
git log --oneline -3             # ตรวจผลก่อน push

ถ้า commit เหล่านี้ถูก push ไปแล้วและมีคนดึงไปใช้ อย่าทำวิธีนี้ เพราะต้อง force push ซึ่งทำให้ history ของคนอื่นไม่ตรงกัน ทางเลือกที่ปลอดภัยกว่าคือให้แพลตฟอร์มทำ squash ตอน merge PR

โจทย์ 4: ปล่อยเวอร์ชัน 2.3.0 ไปแล้วเจอ crash บน production ต้องออก 2.3.1 ตามแนว Git Flow 
git switch -c hotfix/2.3.1 v2.3.0      # แตกจากโค้ดที่อยู่บน production
# แก้ bug และ commit
git tag -a v2.3.1 -m "Hotfix 2.3.1"
git switch main
git merge --no-ff hotfix/2.3.1         # รวมเข้า main
git switch develop                     # หรือ release/* ถ้ามีรอบที่ยังเปิดอยู่
git merge --no-ff hotfix/2.3.1         # อย่าลืมรวมกลับ ไม่งั้น bug จะกลับมา
git push origin main develop v2.3.1    # tag ต้อง push เอง

จุดที่คนมักพลาดมี 3 จุด คือแตก hotfix จาก develop แทน main, ลืมรวมกลับเข้า develop และลืม push tag ถ้าทีมใช้ GitHub Flow หรือ trunk-based ก็ไม่ต้องมี hotfix branch แยก แค่แก้บน main แล้วปล่อยเวอร์ชันใหม่

โจทย์ 5: test เพิ่งเริ่มล้ม แต่มี commit ระหว่าง v1.4.0 กับตอนนี้อีก 200 อัน จะหา commit ที่ทำให้พังอย่างไร 
git bisect start HEAD v1.4.0           # bad คือ HEAD, good คือ v1.4.0
git bisect run ./run-tests.sh          # สคริปต์คืน 0 = good, 1-124 = bad, 125 = skip
git bisect reset                       # จบแล้วกลับมาที่ branch เดิม

200 commit ใช้ประมาณ 8 รอบ (log2 ของ 200) สคริปต์ต้องแยกกรณี build ไม่ผ่านด้วยเหตุอื่นออกมา ให้ exit 125 เพื่อข้าม ถ้าคืน 1 ทั้งหมดผลจะชี้ผิดที่

โจทย์ 6: เพื่อนแก้ conflict เดิมซ้ำทุกครั้งที่ rebase branch อายุยาวบน main ช่วยอะไรได้บ้าง 
git config rerere.enabled true         # จำวิธีแก้ conflict ไว้ใช้ซ้ำ
git rebase main                        # รอบถัดไปที่เจอรูปเดิม Git จะแก้ให้
git diff                               # ตรวจผลที่ rerere ใส่ให้ก่อนไปต่อ
git add -u && git rebase --continue

rerere ไม่ได้ตัดสินใจแทนเรา มันแค่ใช้ซ้ำสิ่งที่เคยตัดสินแล้ว จึงควรตรวจผลก่อนไปต่อเสมอ อีกทางที่ลดปัญหาได้ตรงกว่าคือ merge main เข้า branch ถี่ขึ้น หรือแตก PR ให้เล็กลง

โจทย์ 7: API key หลุดเข้า repo และ push ไปแล้ว 3 เดือนก่อน ต้องทำอะไรบ้าง ตามลำดับ
  1. เพิกถอนและออก key ใหม่ก่อน เพราะต้องถือว่า key นั้นรั่วแล้ว ตรวจ log ของผู้ให้บริการว่ามีการใช้ผิดปกติไหม
  2. ประเมินขอบเขตว่า key อยู่ใน commit ไหน branch ไหน และ fork หรือ clone ที่เราควบคุมไม่ได้มีหรือไม่
  3. ถ้าจะล้าง history ให้ทำใน clone ใหม่ด้วย git filter-repo (เอกสารของ Git แนะนำแทน filter-branch) เช่น git filter-repo --replace-text expressions.txt
  4. เพิ่ม remote กลับ (เครื่องมือลบ origin ให้โดยตั้งใจ) แล้ว force push หลังสำรอง repo เดิมและแจ้งทุกคน
  5. ให้ทุกคน clone ใหม่ หรือย้ายงานที่ค้างอยู่อย่างระวัง เพราะสำเนาเก่าพาข้อมูลลับกลับเข้ามาได้
  6. เพิ่ม secret scanning ที่ฝั่ง server หรือ CI เพื่อไม่ให้เกิดซ้ำ ไม่ควรพึ่ง hook ฝั่งเครื่องอย่างเดียวเพราะข้ามได้ด้วย --no-verify

ข้อ 1 สำคัญที่สุด เพราะข้อ 3 ถึง 5 ไม่ได้ทำให้สำเนาที่ถูกดึงไปก่อนแล้วหายไป ข้อมูลที่เคยหลุดต้องถือว่าหลุดแล้ว

โจทย์ 8: บริษัทมี 6 ทีม ใช้ไลบรารีร่วมกัน ต้องออกแบบโครงสร้าง repo (ลองเขียนก่อนเปิด)

ข้อนี้ไม่มีคำตอบเดียวที่ถูก คำตอบที่ดีต้องบอกข้อสมมติ ทางเลือก และสิ่งที่ต้องแลก ตัวอย่างโครงที่อธิบายได้ครบ

  1. ข้อสมมติ ทีมแก้ไลบรารีร่วมกันบ่อย ต้องการเปลี่ยนไลบรารีและผู้ใช้ใน PR เดียว มีเครื่องมือ build ที่รันเฉพาะส่วนที่เปลี่ยนได้
  2. ทางเลือก A: monorepo ได้ atomic change และเห็น dependency ชัด แต่ต้องมี CI แบบเลือกส่วนที่เปลี่ยน, CODEOWNERS ต่อโฟลเดอร์ และใช้ sparse-checkout หรือ partial clone เมื่อ repo โต
  3. ทางเลือก B: polyrepo ออกไลบรารีเป็น package พร้อมเวอร์ชัน แต่ละทีมอิสระ แลกกับการประสาน release และการอัปเกรดตามกัน
  4. ไฟล์ binary ใหญ่ ใช้ Git LFS ส่วน submodule เหมาะกับ dependency ที่ต้องล็อกเวอร์ชันและเปลี่ยนไม่บ่อย ส่วน subtree เหมาะเมื่อไม่อยากให้ผู้ใช้ต้องรู้ขั้นตอนพิเศษตอน clone
  5. กติกา branch protection บน main, required checks, signed commits ถ้ามีข้อกำหนดเรื่องที่มาของโค้ด และตกลงรูปแบบ commit เพื่อทำ changelog อัตโนมัติ

ถ้าอยากเลือกเพียงข้อเดียว ให้ดูว่าทีมแก้ข้ามกันบ่อยแค่ไหน ถ้าบ่อย monorepo คุ้ม ถ้าไม่บ่อยและต้องการความอิสระ polyrepo ง่ายกว่า
