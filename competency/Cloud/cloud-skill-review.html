วิธีใช้

ข้อเลือกข้อเดียว: กดตัวเลือกแล้วเห็นเฉลยทันที. ข้อที่มีป้าย เลือกหลายข้อ ให้ติ๊กทุกข้อที่คิดว่าถูก แล้วกด “ตรวจคำตอบ” ซึ่งจะถูกก็ต่อเมื่อครบและไม่มีข้อผิดปน. ตำแหน่งตัวเลือกสลับใหม่ทุกครั้งที่กด “ทำใหม่”. ตัวเลขราคาและตัวอย่างคำนวณเป็นค่าสมมุติเพื่อฝึกคิด ส่วนชื่อบริการและ limit ของ provider เปลี่ยนได้ ให้ตรวจกับเอกสารทางการก่อนนำไปอ้างในงานจริง.

1

Cloud models, service types และประโยชน์ที่ข้อสอบชอบถาม

Beginner

คำถามแรกที่ต้องตอบให้ได้คือ "cloud ต่างจากการเช่า server ธรรมดาตรงไหน?" นิยามที่ใช้อ้างอิงกันบ่อยคือของ NIST (SP 800-145) ซึ่งบอกว่า cloud ต้องมีลักษณะสำคัญ 5 อย่าง ได้แก่ on-demand self-service, broad network access, resource pooling, rapid elasticity และ measured service. ถ้าเช่า server รายเดือนแล้วต้องรอคนมา provision ให้ ก็ยังไม่ใช่ cloud ตามนิยามนี้.

ประโยชน์ของ cloud และสิ่งที่มักเข้าใจผิด

Scalability คือความสามารถในการรองรับโหลดที่เพิ่มขึ้น แยกเป็น vertical (เพิ่มขนาดเครื่อง) กับ horizontal (เพิ่มจำนวนเครื่อง). Elasticity คือการที่ระบบ "ขยายและหดเองตามโหลด" จึงจ่ายตามที่ใช้จริง ซึ่งเป็นที่มาของ cost efficiency แบบเปลี่ยนจาก CapEx (ซื้อเครื่องล่วงหน้า) เป็น OpEx (จ่ายตามการใช้). แต่ cloud ไม่ได้ถูกกว่าเสมอ. workload ที่โหลดคงที่ตลอด 24 ชั่วโมงและใช้เครื่องเต็มกำลัง อาจถูกกว่าเมื่อจองระยะยาวหรืออยู่บนเครื่องของตัวเอง ซึ่งจะลงรายละเอียดในหัวข้อ pricing.

App Engine: จุดที่ควรรู้ เพราะ skill definition ระบุไว้

Skill definition ระบุ App Engine ไว้ตรง ๆ ดังนั้นควรรู้ว่ามันมีสองแบบ. Standard environment รันโค้ดใน sandbox ของ runtime ที่ Google รองรับ เริ่ม instance ได้ในระดับวินาที และคิดเงินตาม instance hours. Flexible environment รัน application ใน Docker container บน Compute Engine VM เริ่มช้ากว่า (ระดับนาที) แต่ปรับ runtime ได้อิสระกว่า และคิดเงินตาม vCPU, memory และ disk ที่ใช้ (ตามเอกสารของ Google). ถ้างานต้องการ container ที่กำหนดเองทั้งหมดและไม่ผูกกับ runtime ของ App Engine ให้ดู Cloud Run ด้วย เพราะ Google มีเอกสารเปรียบเทียบและแนวทางย้ายจาก App Engine ไป Cloud Run ซึ่งรับ container image ได้ทุกภาษา.

ตัวอย่างโจทย์แนวนี้"ต้องการรันโค้ดโดยไม่อยากจัดการ server เลย และโหลดขึ้นลงแรงมาก" → นึกถึง serverless (Lambda / Functions / Cloud Run). "ต้องการควบคุม OS และติดตั้ง agent เอง" → VM. "ส่งโค้ดแล้วให้ platform จัดการ runtime" → PaaS.

บริการอื่นที่มีในทุกเจ้า: ไม่ใช่แค่ compute

นอกจาก compute, storage และ database แล้ว สามเจ้ายังมีหมวด networking (VPC / VNet), load balancing, CDN, secret/key management, IaC (CloudFormation, ARM/Bicep, Terraform ที่ใช้ได้ข้าม provider) และ observability. ตอนอ่านโจทย์ให้แปลงจากชื่อเฉพาะกลับเป็นหน้าที่ก่อน เช่น "S3" = object storage แล้วค่อยคิดต่อว่าโจทย์ถามเรื่องอะไร.

Containerization: Docker, image, registry และ Kubernetes เบื้องต้น

Beginner

ปัญหาที่ container แก้คือ "บนเครื่องผมรันได้นะ". Container แพ็กแอปพร้อม dependency (library, runtime, config ที่ต้องใช้) เป็น image เดียว ทำให้รันได้เหมือนกันทั้งบนเครื่อง dev, CI และ production. มันไม่ได้บรรจุ OS ทั้งตัว แต่แชร์ kernel ของ host ไว้ จึงเบากว่า virtual machine ที่มี guest OS ของตัวเอง.

คำศัพท์ที่ต้องแยกให้ออก

Image คือแพ็กเกจแบบอ่านอย่างเดียว (immutable) ที่สร้างจาก Dockerfile. Container คือ instance ที่กำลังรันของ image นั้น. Registry คือที่เก็บ image (Docker Hub, Amazon ECR, Azure Container Registry, Artifact Registry). Tag เช่น myapp:1.4.2 ใช้ระบุเวอร์ชัน. Dockerfile ด้านล่างเป็น multi-stage build ที่ใช้ได้จริงกับแอป Node.js ธรรมดา.

dockerfileFROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/package*.json ./
RUN npm ci --omit=dev
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

จุดที่ควรอธิบายได้: แยก stage เพื่อให้ image สุดท้ายไม่มี source และ dev dependency ติดไปด้วย (image เล็กลง และมีส่วนให้โจมตีน้อยลง). COPY package*.json มาก่อน COPY . . เพื่อให้ layer cache ของ npm ci ยังใช้ได้ตราบที่ dependency ไม่เปลี่ยน. USER node ทำให้ process ไม่รันด้วย root. EXPOSE เป็นแค่การบันทึกว่าแอปฟังพอร์ตไหน ไม่ได้เปิดพอร์ตให้ภายนอกเอง.

Container กับ cloud: ใช้งานผ่านอะไรได้บ้าง

รัน container บน VM เองก็ได้ แต่ในงานจริงมักใช้ orchestrator เพราะต้องมีเรื่อง scheduling, restart เมื่อล่ม, rolling update และ scale. Kubernetes เป็นตัวที่นิยมที่สุด. แนวคิดแกนกลางมีสามอย่าง: Pod (หน่วยเล็กสุดที่ schedule ได้ ภายในมี container หนึ่งตัวหรือมากกว่า), Deployment (บอกว่าต้องการ Pod กี่ตัวและอัปเดตอย่างไร), Service (endpoint คงที่ที่กระจาย traffic ไปยัง Pod ที่เปลี่ยนไปมา). ถ้าไม่อยากดูแล cluster เอง มีทางเลือกอย่าง Cloud Run, Fargate, Azure Container Apps ที่รัน container โดยไม่ต้องจัดการ node.

yamlapiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: api
          image: registry.example.com/orders-api:1.4.2
          ports:
            - containerPort: 3000
          readinessProbe:
            httpGet:
              path: /healthz
              port: 3000
          resources:
            requests: { cpu: "250m", memory: "256Mi" }
            limits:   { cpu: "500m", memory: "512Mi" }

selector.matchLabels ต้องตรงกับ template.metadata.labels ไม่เช่นนั้น Deployment จะสร้างไม่ผ่าน. readinessProbe บอกว่า Pod พร้อมรับ traffic เมื่อไร. requests คือค่าที่ scheduler ใช้จองทรัพยากร ส่วน limits คือเพดาน.

ข้อควรระวังContainer ไม่ได้ปลอดภัยเองโดยอัตโนมัติ. image ที่มี package เก่าที่มีช่องโหว่ หรือรันด้วย root หรือฝัง secret ไว้ใน layer ก็ยังเป็นความเสี่ยงเหมือนเดิม และ secret ที่ฝังใน layer จะอยู่ในประวัติของ image แม้ลบไฟล์ใน layer ถัดไป.

Region, Availability Zone, scalability และ elasticity ในทางปฏิบัติ

Beginner

Region คือพื้นที่ทางภูมิศาสตร์ที่ provider มี data center อยู่ (เช่น ap-southeast-1 ของ AWS ที่สิงคโปร์). ภายใน region มี Availability Zone (AZ) หลายแห่งที่แยกกันทางกายภาพ มีไฟและ network ของตัวเอง แต่เชื่อมกันด้วย latency ต่ำ. Azure และ GCP ก็ใช้แนวคิดเดียวกัน (Azure มี availability zones ใน region ที่รองรับ, GCP มี zones ใน region). ชื่อและจำนวนของแต่ละ region ให้ดูหน้า global infrastructure ของ provider เพราะเพิ่มขึ้นเรื่อย ๆ.

ถ้าวางทุกอย่างไว้ใน AZ เดียว แล้ว AZ นั้นมีปัญหา ระบบก็ล่มทั้งหมด. การกระจายไปหลาย AZ ใน region เดียวกันป้องกันความเสียหายระดับ data center. การกระจายไปหลาย region ป้องกันความเสียหายระดับ region และช่วยเรื่อง latency ของผู้ใช้ในแต่ละภูมิภาค แต่ต้องจัดการเรื่องการ replicate ข้อมูล, ค่าใช้จ่าย data transfer และ consistency เพิ่ม.

ทำอย่างไรเพิ่ม CPU/RAM ของเครื่องเดิมเพิ่มจำนวน instance แล้วกระจาย traffic
ข้อดีง่าย ไม่ต้องแก้แอปมากไม่มีเพดานเท่ากับเครื่องเดียว ทนต่อ instance ล่ม
ข้อจำกัดมีเพดานของขนาดเครื่อง มักต้อง restart และยังเป็น single point of failureแอปควรเป็น stateless หรือแยก state ออกไป (session, cache, database)

แอปที่เก็บ session ไว้ใน memory ของเครื่องตัวเองจะ scale out ได้ยาก เพราะ request ถัดไปของผู้ใช้เดียวกันอาจไปตกเครื่องอื่น. วิธีแก้ที่พบบ่อยคือย้าย session ไปไว้ใน Redis/Memcached แบบ managed หรือใช้ token ที่ client เก็บ (เช่น JWT) แต่ต้องดูว่ารองรับข้อกำหนดเรื่องการเพิกถอน (revoke) token ได้หรือไม่.

Elasticity และ auto scaling

Auto scaling ปรับจำนวน instance ตาม metric เช่น CPU utilization, request count หรือความยาวของ queue. ตัวอย่างนโยบายง่าย ๆ คือ "คง CPU เฉลี่ยไว้ราว 60%". สิ่งที่ต้องคิดเสมอคือ instance ใหม่ต้องใช้เวลาเริ่มต้น (warm-up) ดังนั้นถ้าคาดว่าโหลดจะพุ่งตามเวลา (เช่นเปิดขายตอนเที่ยง) การตั้ง scheduled scaling ล่วงหน้าไว้คู่กับ reactive scaling จะดีกว่าการรอให้ CPU พุ่งแล้วค่อยขยาย.

Latency, availability, durabilityคนมักใช้สลับกัน. Availability คือสัดส่วนเวลาที่บริการใช้งานได้. Durability คือโอกาสที่ข้อมูลจะไม่สูญหาย (เช่น object storage ที่ replicate ข้อมูลหลายแห่ง). Latency คือเวลาตอบสนอง. ระบบหนึ่งอาจ durable มากแต่ available ไม่สูงในช่วงที่ service มีปัญหา.

Cloud service interaction: อ่าน architecture diagram และ communication flow

Intermediate

ข้อสอบระดับนี้ไม่ถามว่า "S3 คืออะไร" แต่ให้ diagram มาหนึ่งใบแล้วถามว่า "request วิ่งผ่านอะไรบ้าง", "ถ้าชิ้นนี้ล่มแล้วส่วนไหนได้รับผลกระทบ", หรือ "ควรเพิ่มอะไรตรงไหน". วิธีอ่านที่ได้ผลคือไล่ตามเส้นทางของ request หนึ่งตัวตั้งแต่ client ไปจนถึง data store แล้วแยกให้ได้ว่าลูกศรไหนเป็น synchronous (ผู้เรียกต้องรอผล) และลูกศรไหนเป็น asynchronous (ส่งงานเข้า queue แล้วไปต่อ).

บทบาทของแต่ละชั้นใน diagram

CDN เก็บ static content ไว้ใกล้ผู้ใช้ ลด latency และลดโหลดที่ origin. Load balancer กระจาย request ไปยัง instance ที่ health check ผ่าน; ชนิด Layer 7 (HTTP) ตัดสินใจตาม path/header ได้ ส่วน Layer 4 (TCP) มักเรียบง่ายกว่าและมี overhead น้อยกว่า. API gateway รวมงานซ้ำ ๆ ไว้จุดเดียว เช่น authentication, rate limiting, request validation. Queue คั่นกลางระหว่างฝั่งที่ส่งงานกับฝั่งที่ทำงาน ทำให้สองฝั่งไม่ต้องเร็วเท่ากันและไม่ต้องออนไลน์พร้อมกัน. Cache ลดการยิง database ซ้ำสำหรับข้อมูลที่อ่านบ่อย แลกกับความเสี่ยงที่ข้อมูลจะเก่า (stale) จึงต้องกำหนด TTL และวิธี invalidate.

Sync หรือ async: เลือกอย่างไร

ถ้าผู้ใช้ต้องการผลลัพธ์ทันทีและงานสั้น (เช่นดูรายการสินค้า) ใช้ sync. ถ้างานหนักหรือช้า (เช่นออกใบเสร็จเป็น PDF, ส่งอีเมล, ประมวลผลรูป) ให้ตอบรับก่อนแล้วโยนเข้า queue ให้ worker ทำ. ผลข้างเคียงที่ต้องรับให้ได้คือผู้ใช้ไม่ได้ผลทันที (ต้องมี polling, webhook หรือ notification) และ queue ส่วนใหญ่ส่งข้อความแบบ at-least-once ซึ่งแปลว่า worker อาจได้รับข้อความเดิมซ้ำ จึงต้องทำให้ logic เป็น idempotent.

Networking ที่ต้องอ่านออก

Public subnet คือ subnet ที่มี route ไปยัง internet gateway. Private subnet ไม่มี route ขาเข้าจากอินเทอร์เน็ต ถ้าต้องออกไปข้างนอก (เช่น ดึง package) ใช้ NAT gateway หรือ service endpoint/private link. Security group (AWS) / NSG (Azure) ทำหน้าที่เหมือน firewall ระดับ instance โดยเป็น stateful ส่วน network ACL เป็นกฎระดับ subnet. ใน AWS security group ไม่มีกฎ deny; มีแต่ allow และค่าเริ่มต้นปฏิเสธทุกอย่างที่ไม่ได้ระบุ.

เทคนิคอ่านโจทย์ diagramถามตัวเองสามข้อ: (1) request path เดียวกันผ่านกี่ชั้น และชั้นไหนเป็น single point of failure (2) มี state เก็บอยู่ที่ไหน (3) ข้อมูลหรือ service ไหนเปิดสู่ public โดยไม่จำเป็น. สามข้อนี้ช่วยให้ไล่ประเด็นของโจทย์ diagram ได้ครบ.

Managed services และ pricing models: ประเมินตามรูปแบบการใช้งาน

Intermediate

Managed service คือบริการที่ provider ดูแลการติดตั้ง patch, backup, high availability และ scaling ให้ในระดับหนึ่ง เช่น RDS แทนการลง MySQL บน VM เอง. สิ่งที่คุณได้คือภาระ operation น้อยลง สิ่งที่แลกคือค่าบริการต่อหน่วยมักสูงกว่า, ปรับแต่งระดับ OS ไม่ได้, และผูกกับ feature ของ provider. ตัดสินใจโดยเทียบ "ต้นทุนของคนที่ต้องดูแล" กับ "ส่วนต่างราคา" ไม่ใช่ดูราคาต่อชั่วโมงอย่างเดียว.

สมมุติ instance หนึ่งราคา On-Demand 0.10 USD/ชั่วโมง และแบบจองระยะยาวคิดเป็น 0.06 USD/ชั่วโมงที่ต้องจ่ายตลอด 730 ชั่วโมงต่อเดือนไม่ว่าจะใช้หรือไม่. ถ้าเปิดเครื่องตลอดเดือน On-Demand = 73.00 USD และแบบจอง = 43.80 USD. แต่ถ้าเครื่องทำงานแค่ 40% ของเวลา (292 ชั่วโมง) On-Demand จะเหลือ 29.20 USD ส่วนแบบจองยังเป็น 43.80 USD. จุดคุ้มทุนคือ 0.06 / 0.10 = 60% ของเวลาในเดือน. ต่ำกว่านี้ On-Demand ถูกกว่า สูงกว่านี้การจองถูกกว่า.

ค่าใช้จ่ายที่มักถูกลืม

Data transfer ออกจาก cloud ไปอินเทอร์เน็ต (egress) และข้ามระหว่าง region/AZ มักคิดเงิน ส่วนขาเข้ามักไม่คิด (ตรวจเงื่อนไขของ provider แต่ละราย). Storage มีหลาย tier ตามความถี่ในการเข้าถึง และบาง tier คิดค่า retrieval และมีระยะเก็บขั้นต่ำ. Load balancer, NAT gateway, log ingestion และ snapshot คิดเงินแยก ซึ่งบ่อยครั้งแซงค่า compute ในระบบเล็ก. Lambda ตัวอย่าง: 1,000,000 ครั้ง ครั้งละ 200 ms ที่ memory 512 MB = 1,000,000 × 0.2 วินาที × 0.5 GB = 100,000 GB-second (เทียบกับ free tier ของ Lambda ที่ AWS ระบุไว้ 400,000 GB-second และ 1 ล้าน request ต่อเดือน).

Managed ไม่ได้แปลว่าไม่ต้องทำอะไรใน RDS คุณยังต้องเลือก instance size, ตั้ง backup retention, ออกแบบ index, ตั้ง security group และทดสอบ restore. Provider ดูแลตัว database engine และ host แต่ไม่รู้ว่า query ของคุณช้าเพราะอะไร.

Security best practices: IAM, encryption และการจัดการ secret

Intermediate

หลักใหญ่คือ least privilege ให้สิทธิ์เท่าที่งานต้องใช้และไม่เกินนั้น, defense in depth วางหลายชั้น ไม่พึ่งชั้นเดียว, และ shared responsibility ตามโมเดลที่ AWS ระบุว่า provider รับผิดชอบ security "of" the cloud ส่วนลูกค้ารับผิดชอบ security "in" the cloud ซึ่งขอบเขตขึ้นกับบริการที่เลือกใช้. ถ้าตั้ง S3 bucket เป็น public เอง นั่นเป็นความรับผิดชอบของคุณ ไม่ใช่ของ provider.

IAM: identity, role, policy

แยกให้ออกว่า user คือตัวตนระยะยาวของคนหรือระบบ (มี credential ถาวรได้), group คือชุดของ user ที่ใช้ policy ร่วมกัน, ส่วน role คือตัวตนที่ถูก "สวม" ชั่วคราวและได้รับ credential อายุสั้น เหมาะกับ EC2/Lambda/container ที่ต้องเรียกบริการอื่น เพราะไม่ต้องฝัง access key ลงในโค้ด. Policy ระบุว่าใครทำ action อะไรกับ resource ไหนภายใต้เงื่อนไขใด. กติกาประเมินสิทธิ์ที่ต้องจำ: ค่าเริ่มต้นคือ deny, ต้องมี explicit allow จึงจะทำได้, และ explicit deny ชนะ allow เสมอ.

Policy นี้อนุญาตอ่านเฉพาะ bucket acme-reports และ prefix finance/ และปฏิเสธทุกคำขอที่ไม่ใช้ TLS. สังเกตว่า s3:ListBucket อ้างกับ resource ระดับ bucket ส่วน s3:GetObject อ้างกับ object (/finance/*) ซึ่งเป็นจุดที่คนเขียน policy ผิดบ่อย. การใช้ "Action": "*" กับ "Resource": "*" คือตรงข้ามกับ least privilege.

Encryption

In transit ใช้ TLS ระหว่าง client กับ service และระหว่าง service ภายในที่ข้ามขอบเขตเครือข่าย. At rest เข้ารหัสข้อมูลที่เก็บไว้ (disk, object, database, backup). ส่วนใหญ่ใช้ envelope encryption: ข้อมูลถูกเข้ารหัสด้วย data key และ data key ถูกเข้ารหัสอีกชั้นด้วย key ใน KMS (AWS KMS / Azure Key Vault / Cloud KMS). ข้อดีคือ key หลักไม่ต้องออกจาก KMS และสั่ง rotate หรือเพิกถอนได้จากจุดเดียว. มีทั้ง provider-managed key (ง่ายกว่า) และ customer-managed key (คุมนโยบายและ audit ได้มากกว่า แต่ต้องดูแลเอง).

Secret และ network

อย่าฝัง password, API key หรือ connection string ลงใน source code, image layer หรือ commit. เก็บใน secret manager (Secrets Manager, Key Vault, Secret Manager) แล้วให้ workload ดึงด้วย role/managed identity. เปิด audit log (CloudTrail, Azure Activity Log, Cloud Audit Logs) เพื่อตอบคำถาม "ใครทำอะไรเมื่อไร". บังคับ MFA กับบัญชีที่มีสิทธิ์สูง และจำกัด root/owner account ให้ใช้เฉพาะงานที่จำเป็น.

อย่าสับสนEncryption ไม่ใช่ access control. ข้อมูลที่เข้ารหัสด้วย key ที่ทุกคนใน account ใช้ได้ ก็ยังถูกอ่านได้โดยคนที่มีสิทธิ์ใช้ key นั้น. ต้องคุมทั้งสิทธิ์ของข้อมูลและสิทธิ์ของ key.

SLA, ความพร้อมใช้งาน และการจัดแนวกับ compliance

Intermediate

สามคำนี้มักถูกใช้ปนกัน. SLI คือตัวชี้วัดที่วัดได้จริง (เช่นสัดส่วน request ที่สำเร็จ). SLO คือเป้าหมายภายในของทีมต่อ SLI นั้น (เช่น 99.95% ต่อเดือน). SLA คือข้อตกลงทางสัญญากับลูกค้า ที่มักระบุเงื่อนไขชดเชย (service credit) เมื่อ provider ทำไม่ถึงเป้า. SLA ของ provider ไม่ได้รับประกันว่าระบบของคุณจะไม่ล่ม แค่กำหนดผลชดเชยเมื่อบริการนั้น ๆ ต่ำกว่าเกณฑ์ และมักมีเงื่อนไขว่าต้องออกแบบตามที่ provider กำหนด (เช่นรันหลาย AZ).

Composite availability

ถ้า request ต้องผ่านหลาย component ต่อกันแบบอนุกรม (ขาดตัวใดตัวหนึ่งก็ล่ม) ให้คูณ availability เข้าด้วยกัน. สมมุติมี gateway 99.95% → function 99.95% → database 99.99% (ตัวเลขสมมุติเพื่อฝึกคำนวณ ไม่ใช่ SLA จริงของ provider ใด) ได้ประมาณ 0.9995 × 0.9995 × 0.9999 ≈ 0.9989 หรือ 99.89% ซึ่งต่ำกว่าตัวที่ต่ำสุดเสมอ. ในทางกลับกัน ถ้ามีสำเนาที่ทำงานแทนกันแบบขนาน (และล้มเหลวแยกอิสระ) availability รวม = 1 − (อัตราล้มเหลวของแต่ละตัวคูณกัน). สอง instance ที่ 99% ต่อกัน ได้ 1 − 0.01 × 0.01 = 99.99%. สมมติฐานว่า "ล้มเหลวอิสระต่อกัน" มักไม่จริงเมื่ออยู่ใน AZ หรือ region เดียวกัน จึงต้องกระจาย failure domain.

RTO, RPO และ DR

RPO (Recovery Point Objective) คือข้อมูลที่ยอมเสียได้นานแค่ไหน (เช่น 15 นาทีของธุรกรรม) จึงกำหนดความถี่ backup/replication. RTO (Recovery Time Objective) คือใช้เวลานานแค่ไหนกว่าระบบจะกลับมา จึงกำหนดว่าต้องมีระบบสำรองพร้อมรับมือระดับใด. กลยุทธ์ DR เรียงจากถูก-ช้าไปแพง-เร็ว: backup & restore → pilot light → warm standby → active-active (multi-site). เลือกจาก RTO/RPO ที่ธุรกิจยอมรับ ไม่ใช่เลือกแบบที่ดีที่สุดทางเทคนิคเสมอ.

จัดแนวกับ compliance

Provider มีรายงาน/ใบรับรองของตัวเอง (เช่น ISO/IEC 27001, SOC reports) ที่ลูกค้านำไปใช้เป็นหลักฐานส่วนที่ provider รับผิดชอบได้ แต่ส่วนที่เป็น "in the cloud" ลูกค้าต้องมีการควบคุมและหลักฐานเอง. ประเด็นที่ต้องดูเสมอมีสี่เรื่อง: data residency (ข้อมูลอยู่ใน region ที่กฎหมายหรือสัญญากำหนดหรือไม่), การจำแนกข้อมูลและการเข้ารหัส, audit log และระยะเก็บ, และการควบคุมสิทธิ์. สำหรับข้อมูลส่วนบุคคลในไทย ต้องพิจารณา พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA) ร่วมกับข้อกำหนดของอุตสาหกรรมนั้น ๆ; รายละเอียดทางกฎหมายควรปรึกษาผู้เชี่ยวชาญ ไม่ควรตัดสินจากสรุปในเอกสารติวนี้.

Cost ไม่ได้เป็นเส้นตรง

serverless ถูกมากเมื่อโหลดต่ำหรือเป็นช่วง ๆ แต่เมื่อโหลดสูงและต่อเนื่อง ต้นทุนต่อ request ที่คงที่จะแซงค่า instance ที่จองไว้. โค้ดข้างล่างใช้ราคา "สมมุติ" เพื่อหาจุดตัด (ไม่ใช่ราคาของ provider ใด).

pythonINSTANCE_PER_MONTH = 60.0          # instance 1 ตัว เปิดตลอดเดือน (USD)
PER_MILLION_REQUESTS = 0.20        # ค่า request ต่อ 1 ล้านครั้ง (USD)
PER_GB_SECOND = 0.0000166667       # ค่า duration ต่อ GB-second (USD)

def serverless_cost(requests, avg_ms, memory_gb):
    gb_seconds = requests * (avg_ms / 1000) * memory_gb
    return requests / 1_000_000 * PER_MILLION_REQUESTS + gb_seconds * PER_GB_SECOND

for monthly_requests in (1_000_000, 10_000_000, 40_000_000, 200_000_000):
    cost = serverless_cost(monthly_requests, avg_ms=120, memory_gb=0.5)
    cheaper = "serverless" if cost < INSTANCE_PER_MONTH else "instance"
    print(f"{monthly_requests:>12,} req/เดือน  serverless = {cost:8.2f} USD  -> ถูกกว่า: {cheaper}")

ผลที่ได้: 1 ล้านครั้ง = 1.20 USD, 10 ล้าน = 12.00, 40 ล้าน = 48.00 (ยังถูกกว่า instance 60), และ 200 ล้าน = 240.00 (แพงกว่า). จุดตัดอยู่ราว 50 ล้าน request ต่อเดือนภายใต้สมมติฐานนี้. ในงานจริงยังต้องบวกค่า API gateway, log, การรองรับ peak ที่ instance เดียวรับไม่ไหว และเวลาของคนดูแล ซึ่งทำให้จุดตัดเลื่อนไปได้ทั้งสองทาง.

Performance: latency มาจากไหน

ปัจจัยที่ทำให้ช้ามักไม่ใช่ CPU แต่เป็นระยะทาง (client ไป region), จำนวน network hop ระหว่าง service, การเรียก database แบบ N+1, cold start ของ function ที่ไม่มีการใช้งานมาสักพัก และ connection ที่ถูกเปิดใหม่ทุกครั้ง. ตัวช่วยที่ใช้บ่อย: CDN และ cache ใกล้ผู้ใช้, connection pooling/proxy หน้า database, provisioned concurrency หรือ min instances เพื่อลด cold start (แลกกับค่าจ่ายคงที่), read replica สำหรับ workload อ่านหนัก (แลกกับ replication lag), และการวาง compute กับ data ไว้ region เดียวกันเพื่อเลี่ยง cross-region latency และค่า transfer.

วิธีตอบ trade-off question(1) ระบุ requirement ที่เป็นตัวตัดสิน เช่น latency เป้าหมาย, ความถี่ของ peak, state (2) ตัดตัวเลือกที่ขัดกับข้อกำหนดบังคับก่อน เช่น compliance, timeout limit (3) เทียบที่เหลือด้วย cost/ops/scale (4) บอกสิ่งที่ยอมแลก. โครงสี่ข้อนี้ช่วยให้คำตอบแบบเขียนอธิบายครบประเด็น.

Cloud-native design: microservices, serverless และ event-driven

Advance

Cloud-native ไม่ได้แปลว่า "ย้ายไปอยู่บน cloud". มันคือการออกแบบให้ใช้ความสามารถของ cloud: ทุกอย่างแตกเป็นบริการเล็ก ๆ ที่ deploy แยกกัน, state ถูกแยกออกจาก compute, scale ตามโหลด, และยอมรับว่า "ความล้มเหลวเกิดขึ้นเป็นเรื่องปกติ". รูปแบบที่ใช้ร่วมกันบ่อยคือ microservices, serverless และ event-driven architecture.

Microservices: ได้อะไร เสียอะไร

แบ่งระบบตาม business capability (เช่น orders, inventory, payment) ให้แต่ละบริการมีข้อมูลของตัวเอง deploy และ scale แยกกันได้ ทีมทำงานคู่ขนานได้โดยไม่ชนกัน. สิ่งที่แลกคือความซับซ้อนแบบกระจาย: network call แทน function call, ธุรกรรมข้ามบริการไม่มี ACID ข้ามกัน, การ debug ต้องมี distributed tracing, และต้องมี platform (CI/CD, service discovery, observability) รองรับ. ทีมเล็กหรือโดเมนยังไม่นิ่ง มักเริ่มจาก modular monolith แล้วค่อยแยกบริการเมื่อเจอแรงกดดันจริง (เช่นส่วนหนึ่งต้อง scale ต่างจากส่วนอื่นมาก). การย้ายระบบเดิมแบบค่อยเป็นค่อยไปมีรูปแบบ strangler fig คือสร้างบริการใหม่ครอบทีละส่วนแล้วค่อย ๆ เบี่ยง traffic ออกจากระบบเก่า.

Event-driven: ใช้ event แทนการเรียกตรง

ข้อดีคือ producer กับ consumer แยกกันหลวม (loose coupling) ทั้งเรื่องเวลา เวอร์ชัน และการ scale. ข้อควรระวังคือพฤติกรรมของ message broker: ส่วนใหญ่รับประกัน at-least-once ไม่ใช่ exactly-once ดังนั้น consumer ต้อง idempotent, ลำดับข้อความอาจสลับกันถ้าไม่ได้ใช้ ordering key/FIFO, และต้องมี DLQ กับ alert เพื่อไม่ให้ข้อความที่พังหายเงียบ. ตัวอย่างโค้ดข้างล่างแสดง idempotent handler และ retry แบบ exponential backoff ที่มี jitter.

pythonimport random
import time

processed_ids = set()      # ใน production เก็บใน database/cache ที่ทุก worker เห็นร่วมกัน
balance = {"acc-1": 100}

def handle_message(message):
    """ถ้า message ซ้ำ (at-least-once delivery) ต้องไม่หักเงินซ้ำ"""
    if message["id"] in processed_ids:
        return "skip"
    balance[message["account"]] -= message["amount"]
    processed_ids.add(message["id"])
    return "applied"

def call_with_retry(fn, attempts=4, base_delay=0.1):
    for attempt in range(attempts):
        try:
            return fn()
        except ConnectionError:
            if attempt == attempts - 1:
                raise
            time.sleep(random.uniform(0, base_delay * 2 ** attempt))   # backoff + full jitter

msg = {"id": "evt-001", "account": "acc-1", "amount": 30}
print(handle_message(msg), handle_message(msg), balance)
# applied skip {'acc-1': 70}

โค้ดตัวอย่างนี้เก็บ processed_ids ไว้ใน memory เพื่ออธิบายหลักการเท่านั้น. ถ้ามีหลาย worker หรือ worker restart ต้องเก็บใน store ร่วม และควรตรวจกับการเขียนข้อมูลเป็น transaction เดียว (หรือใช้ unique constraint) เพื่อไม่ให้เกิดช่องว่างระหว่าง "หักเงิน" กับ "บันทึกว่าทำแล้ว". Jitter สำคัญเพราะถ้า client หลายตัว retry พร้อมกันที่ช่วงเวลาเดียวกัน จะกระแทก service ที่เพิ่งฟื้นซ้ำอีกรอบ.

รูปแบบที่ควรรู้จักชื่อและเหตุผล

Saga จัดการธุรกรรมที่ข้ามหลายบริการด้วยลำดับของ local transaction และ compensating action (เช่นชำระเงินแล้วสต็อกไม่พอ → สั่งคืนเงิน) แทนการใช้ distributed transaction. Transactional outbox เขียน event ลงตาราง outbox ใน transaction เดียวกับข้อมูลหลัก แล้วมี process แยกส่งออกไป broker ช่วยแก้ปัญหา "บันทึก DB สำเร็จแต่ publish ไม่สำเร็จ". Circuit breaker หยุดเรียก dependency ที่กำลังพัง (fail fast) แทนที่จะรอ timeout แล้วลากทั้งระบบล้ม. Bulkhead แยก resource pool ต่อ dependency เพื่อให้ตัวหนึ่งช้าแล้วไม่ดูด thread ของทั้งแอป. CQRS แยกโมเดลเขียนกับอ่านเมื่อสองฝั่งต้องการรูปแบบข้อมูลและ scale ต่างกัน แต่เพิ่มความซับซ้อนเรื่อง eventual consistency.

Serverless: ข้อจำกัดที่ต้องออกแบบรองรับ

Function ต้อง stateless (instance หนึ่งถูกสร้าง/ทิ้งได้ตลอด), มี execution timeout (Lambda ตั้งได้สูงสุด 15 นาที ตามเอกสาร AWS ณ ตอนเขียน — ตรวจ limit ปัจจุบันเสมอ), มี cold start และ concurrency limit ที่ถ้าเกินจะถูก throttle หรือไปกระทบ downstream (เช่น database connection หมด). งานยาวหรือต้องรอหลายขั้นตอนมักใช้ workflow orchestrator (Step Functions, Durable Functions, Workflows) แทนการเขียน function ใหญ่ตัวเดียว.

Hybrid และ multi-cloud: ความซ้ำซ้อนกับการควบคุม

Advance

คำถามที่ควรถามก่อนคือ "เราอยากได้อะไรจาก multi-cloud?" เหตุผลที่เจอบ่อยมีไม่กี่ข้อ: ลดความเสี่ยงจากการพึ่ง provider เดียว, ข้อบังคับด้าน regulation/data residency ที่ provider เดียวตอบไม่ครบ, ต้องการบริการเด่นของแต่ละเจ้า (best-of-breed), หรือสืบทอดมาจากการควบรวมกิจการ. ถ้าเป้าหมายคือ "ระบบไม่ล่ม" อย่างเดียว การทำ multi-AZ และ multi-region ใน provider เดียวมักให้ความทนทานระดับ region ด้วยต้นทุนและความซับซ้อนที่ต่ำกว่า multi-cloud. แต่ไม่ได้ป้องกันความเสี่ยงระดับ provider เช่นปัญหาบัญชี, control plane ล่มทั้งระบบ หรือประเด็นสัญญา.

ตัวเลือกและสิ่งที่ต้องแลก

แนวทางได้เสีย / ความเสี่ยง

Portability ทำได้ถึงระดับไหน

ชั้นที่ย้ายง่าย: container image, Kubernetes manifest, ภาษาโปรแกรม, open-source database (PostgreSQL, MySQL), และ Infrastructure as Code ที่ไม่ผูก provider (Terraform/OpenTofu แต่ resource ของแต่ละ provider ยังต่างกัน). ชั้นที่ย้ายยาก: managed service ที่มี API เฉพาะ (เช่น DynamoDB, Cosmos DB, Pub/Sub), IAM model, network primitive และข้อมูลปริมาณมาก. "Data gravity" คือข้อมูลก้อนใหญ่ดึงให้ compute และบริการอื่นมาอยู่ใกล้ ทั้งเพราะ latency และค่า egress ทำให้การย้ายข้อมูลกลายเป็นต้นทุนหลักของการเปลี่ยน provider.

การลด lock-in ไม่ใช่เรื่องขาว-ดำ. วิธีที่ใช้ได้จริงคือจำแนกว่า dependency ไหน "ผูกแล้วคุ้ม" (เช่นใช้ managed database ที่ประหยัดแรงดูแลมาก) กับอันไหนควรห่อด้วย abstraction layer ที่ย้ายได้ในราคาที่ยอมรับได้ แล้วเขียน exit plan คร่าว ๆ ไว้ว่าถ้าต้องย้ายจะใช้เวลาและเงินเท่าไร.

เครื่องมือ hybrid / multi-cloud ที่ provider เสนอ

แต่ละเจ้ามีผลิตภัณฑ์ที่ขยาย control plane ของตัวเองไปยัง on-premises หรือ cloud อื่น เช่น AWS Outposts, Azure Arc, และฝั่ง Google มีกลุ่มผลิตภัณฑ์ที่เคยชื่อ Anthos (ปัจจุบันจัดอยู่ใน GKE Enterprise / Google Distributed Cloud). ชื่อและขอบเขตเปลี่ยนบ่อย ให้ตรวจเอกสารปัจจุบัน และในข้อสอบเน้นเข้าใจ "เหตุผลที่มีผลิตภัณฑ์กลุ่มนี้" มากกว่าท่องชื่อ.

ข้อควรระวังเรื่อง redundancyสำเนาที่อยู่คนละ cloud แต่ใช้ identity provider, DNS หรือ pipeline deploy ตัวเดียวกัน ก็ยังมี single point of failure ที่ชั้นนั้น. ทำ failure mode analysis ว่าอะไรที่ใช้ร่วมกันของทั้งสองฝั่งบ้าง.

เชื่อม cloud กับ enterprise และ governance ด้วย framework

Advance

เมื่อองค์กรมี account/subscription เป็นสิบเป็นร้อย ปัญหาไม่ใช่ว่า deploy ได้หรือไม่ แต่คือ "ใครสร้างอะไรได้ ใครจ่าย ใครรับผิดชอบเมื่อพัง และพิสูจน์กับผู้ตรวจสอบได้อย่างไร". Governance คือชุดนโยบาย กระบวนการ และกลไกบังคับใช้ที่ตอบคำถามเหล่านี้โดยไม่ทำให้ทีมพัฒนาช้าลงจนเกินไป.

Landing zone และโครงสร้าง account

Landing zone คือโครงพื้นฐานที่จัดไว้ล่วงหน้าก่อนให้ทีมเริ่มใช้งาน: โครงสร้างการจัดกลุ่ม account (AWS Organizations, Azure management groups/subscriptions, Google Cloud organization/folders/projects), เครือข่ายกลาง, identity และ logging ส่วนกลาง, และ guardrail ที่ใช้กับทุก account. Guardrail แบบ preventive ขัดขวางไม่ให้ทำสิ่งต้องห้าม (เช่น AWS Service Control Policies, Azure Policy ในโหมด deny, Google Organization Policy) ส่วนแบบ detective ตรวจพบแล้วแจ้งเตือน (เช่น config rule, security posture tool). นโยบายควรเขียนเป็นโค้ด (policy as code) ใส่ version control และทดสอบเหมือนซอฟต์แวร์.

Identity, cost และ operation ที่ต้องเชื่อมกับองค์กร

Identity เชื่อมกับ identity provider ขององค์กรผ่าน SAML หรือ OIDC เพื่อให้ SSO และปิดสิทธิ์พร้อมกันเมื่อพนักงานลาออก ไม่สร้าง user แยกในแต่ละ cloud. Cost ใช้ tagging หรือ label มาตรฐานและโครงสร้าง account เพื่อทำ showback/chargeback ให้ทีมเห็นต้นทุนของตัวเอง ตั้ง budget และ alert, และทำ FinOps อย่างต่อเนื่อง (มองเห็น → ปรับให้เหมาะสม → ดำเนินงาน). Operation เชื่อม log และ alert เข้า SIEM/ระบบ monitoring กลาง และเชื่อม change management/ITSM ให้การเปลี่ยนแปลงผ่านกระบวนการที่องค์กรกำหนด โดยใช้ pipeline อัตโนมัติเป็นตัวบังคับ แทนการอนุมัติด้วยคนทุกครั้ง.

Cloud Adoption Framework (Azure)วางแผนระดับองค์กรตั้งแต่ strategy, plan, ready, adopt, govern, manageมุ่งที่ portfolio และ governance ขององค์กร ไม่ใช่ระบบเดียว (ชื่อช่วงอาจปรับตามเวอร์ชัน)
ISO/IEC 27001, COBIT และกรอบ compliance อื่นเมื่อต้องแสดงว่าการใช้ cloud อยู่ภายใต้ระบบบริหารความเสี่ยงขององค์กรมีมาตรการควบคุมและหลักฐาน (evidence) ที่ตรวจสอบได้

ข้อแตกต่างที่ควรแยกให้ออกคือ Well-Architected ตอบ "ระบบนี้ออกแบบดีหรือยัง" ในระดับ workload ส่วน Cloud Adoption Framework ตอบ "องค์กรควรเตรียม ย้าย และกำกับดูแลอย่างไร" ในระดับองค์กร ทั้งสองเสริมกัน. อีกประเด็นคือ pillar มี trade-off ระหว่างกัน เช่น เพิ่ม reliability ด้วย multi-region ทำให้ cost สูงขึ้น การตัดสินใจจึงต้องผูกกับ requirement ทางธุรกิจ.

การเชื่อมต่อระหว่างองค์กรกับ cloud

Site-to-site VPN ผ่านอินเทอร์เน็ตตั้งเร็ว ราคาต่ำ แต่ bandwidth และ latency ผันแปรตามเครือข่ายสาธารณะ. Dedicated connection (AWS Direct Connect, Azure ExpressRoute, Google Cloud Interconnect) ให้เส้นทางส่วนตัวที่ latency และ throughput คาดการณ์ได้ แต่ใช้เวลาติดตั้งและมีค่าใช้จ่ายสูงกว่า องค์กรจำนวนมากใช้ VPN เป็นเส้นสำรองของ dedicated connection.

รูปแบบคำตอบที่ดีข้อ governance ที่ให้เหตุผลเป็นขั้น: กำหนดนโยบาย → บังคับใช้อัตโนมัติ (guardrail / policy as code) → วัดผลและรายงาน (log, cost, compliance posture) → ปรับปรุงต่อเนื่อง. ตัวเลือกที่เป็น "ให้ทุกทีมตกลงกันเอง" หรือ "ให้คนกลางอนุมัติด้วยมือทุกคำขอ" มักไม่ขยายตัวและมักเป็นตัวเลือกที่ผิด.

แนว Deloitte / HackerRank: รูปแบบข้อสอบและชุดฝึกแบบ scenario

อ่านก่อน: ข้อมูลส่วนนี้จริงแค่ไหนDeloitte skills taxonomy ที่ใช้ภายในองค์กรไม่ได้เปิดเผยต่อสาธารณะ ผมจึงไม่มีข้อสอบหรือเกณฑ์ตัดสินจริงของ Deloitte มาให้. ข้อสอบในชุดนี้เขียนขึ้นให้ตรงกับนิยามทักษะ 3 ระดับที่คุณให้มา (Beginner / Intermediate / Advance) และใช้โจทย์แบบ scenario ในลักษณะงานให้คำปรึกษาด้าน cloud (เป็นการคาดการณ์แนวข้อสอบของผม ไม่ใช่ข้อมูลจริงจาก Deloitte). ส่วนฝั่ง HackerRank มีรูปแบบที่ตรวจสอบได้จากเอกสารของ HackerRank ตามด้านล่าง.

HackerRank มีอะไรสำหรับ cloud บ้าง

จากเอกสารของ HackerRank (knowledge base และ skills directory) ข้อสอบที่เกี่ยวกับ cloud ปรากฏในสามลักษณะ. แบบแรกคือ Multiple Choice ซึ่งตรวจอัตโนมัติ ใช้วัดความเข้าใจ concept เช่นประเภทบริการ, pricing, security. แบบที่สองคือ Cloud hands-on questions ที่ให้ผู้สอบเข้าใช้ AWS console หรือ Azure portal จริงด้วยบัญชีชั่วคราวที่ HackerRank จัดให้ แล้วให้ระบบตรวจอัตโนมัติจาก evaluation criteria ที่มีน้ำหนักต่อข้อ ไม่ใช่ดูแค่ว่ารันผ่านหรือไม่. แบบที่สามคือ DevOps / project-based ซึ่งให้ Linux environment หรือโปรเจกต์ที่มี IDE และตรวจจากผลลัพธ์ เช่นจำนวน unit test ที่ผ่าน. นอกจากนี้ยังมี Code Review และ Debugging ที่ให้ดูโค้ดหรือ config ที่มีปัญหา. สิ่งที่ข้อสอบจริงของแต่ละบริษัทเลือกใช้ขึ้นกับตำแหน่งและบริษัทนั้น ๆ.

ดังนั้นเตรียมสี่ทักษะ: (1) ตอบ MCQ แบบเลือกข้อเดียวและเลือกหลายข้อ (2) อ่าน config เช่น IAM policy JSON, Dockerfile, Kubernetes YAML แล้วบอกว่าผิดตรงไหน (3) คิด trade-off จาก scenario (4) ทำ lab ใน console ให้ถูกตาม requirement ภายในเวลา.

Checklist ฝึก hands-on (ทำบนบัญชีทดลองของตัวเองเท่านั้น)

โจทย์ lab ที่เจอได้บ่อยในรูปแบบ "ตั้งค่าให้ตรงเงื่อนไข": สร้าง bucket ที่ไม่ public, เปิด versioning และ encryption, สร้าง role ที่ให้อ่านได้เฉพาะ prefix เดียว, จำกัด security group ให้รับเฉพาะพอร์ตและ source ที่ระบุ, ตั้ง alarm ให้แจ้งเมื่อ metric เกินเกณฑ์. ตัวอย่างชุดคำสั่ง AWS CLI สำหรับข้อแรก (เปลี่ยนชื่อ bucket ให้ไม่ซ้ำ และดู flag ล่าสุดใน aws s3api help):

bash · AWS CLIBUCKET=my-unique-lab-bucket-12345
REGION=ap-southeast-1

aws s3api create-bucket --bucket "$BUCKET" --region "$REGION" \
  --create-bucket-configuration LocationConstraint="$REGION"

aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

aws s3api put-bucket-versioning --bucket "$BUCKET" \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption --bucket "$BUCKET" \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"aws:kms"}}]}'

อย่าลืมว่า bucket ใหม่ของ S3 ในปัจจุบันถูกเข้ารหัสด้วย SSE-S3 เป็นค่าเริ่มต้นอยู่แล้ว ข้อ lab ที่ระบุ "ใช้ KMS key" จึงต้องตั้งค่าเพิ่มตามนี้เพื่อให้ผ่านเกณฑ์. การอ่านโจทย์ให้ครบทุกเงื่อนไขสำคัญกว่าการพิมพ์คำสั่งเร็ว เพราะระบบตรวจให้คะแนนทีละ criteria.

เคล็ดลับเรื่องเวลาทำข้อ MCQ ที่มั่นใจก่อน, ข้อ scenario ให้ขีดฆ่าตัวเลือกที่ผิดเงื่อนไขตรง ๆ ก่อน (เช่น ผิด compliance, เกิน limit) แล้วค่อยเทียบที่เหลือ, และข้อเลือกหลายข้อให้ตรวจแต่ละตัวเลือกเป็น "จริง/เท็จ" แยกกัน เพราะหลายข้อสอบให้คะแนนเมื่อเลือกครบและไม่มีข้อผิดปน (ควรดูเงื่อนไขการให้คะแนนของแต่ละข้อสอบ).

ชุดฝึกด้านล่างผสม 3 ระดับ ติดป้ายระบุว่าเป็นแนวไหน. ข้อที่เป็น "เลือกหลายข้อ" จะมีป้ายและปุ่มตรวจคำตอบ ข้ออื่นเลือกแล้วเฉลยทันที.
