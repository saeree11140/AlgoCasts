Container, Image และ Registry ต่างกันอย่างไร

Beginner

Competency: อธิบายได้ว่า container คืออะไร ต่างจาก VM ยังไง และแยกคำว่า image, container, tag, digest, registry ออกจากกันได้

ปัญหาที่ container มาแก้

เคสคลาสสิกคือ “บนเครื่องผมรันได้นะ” แต่พอขึ้น server แล้วพัง สาเหตุมักไม่ใช่โค้ด แต่เป็นสิ่งแวดล้อมรอบ ๆ เช่น Node คนละ version, library ของระบบไม่ครบ หรือ config ไม่ตรงกัน Container แก้ปัญหานี้ด้วยการเอาแอปกับ dependency ที่ต้องใช้ มัดรวมเป็นแพ็กเกจเดียว แล้วรันมันในสภาพแวดล้อมที่ถูกแยกออกจากระบบอื่น

Container เป็นแค่ process ที่ถูกขังไว้

Container ไม่ใช่เครื่องจำลองทั้งเครื่อง มันคือ process ธรรมดาบน Linux ที่ถูกจัดให้เห็นโลกแคบกว่าปกติ ผ่านกลไกของ kernel สองตัวหลัก ตัวแรกคือ namespaces ที่ทำให้ process เห็นแค่ process list, network interface และ filesystem ของตัวเอง ตัวที่สองคือ cgroups ที่จำกัดว่าใช้ CPU, memory ได้เท่าไหร่ เพราะ container ทุกตัวใช้ kernel ของ host ร่วมกัน มันจึงสตาร์ตเร็วและกินทรัพยากรน้อยกว่า VM ที่ต้องมี OS พร้อม kernel ของตัวเองเต็มชุด

Virtual MachineApp + Library → Guest OS (มี kernel ของตัวเอง) → Hypervisor → Hardware
แยกขาดจากกันมากกว่า แต่หนักและสตาร์ตช้ากว่า
ContainerApp + Library → Container runtime → Host OS (kernel ร่วมกัน) → Hardware
เบาและเร็วกว่า แต่ isolation ขึ้นกับ kernel ตัวเดียวกัน
ข้อควรระวังContainer ไม่ใช่ security boundary แบบ VM ถ้า kernel ของ host มีช่องโหว่ หรือ container ถูกรันด้วยสิทธิ์สูงเกินไป ก็มีโอกาสหลุดออกมาที่ host ได้ ไว้เรื่องนี้ไปลงลึกในหัวข้อ Image Security

บน Mac และ Windows ที่ใช้ Docker Desktop จริง ๆ แล้ว Docker รัน Linux VM เล็ก ๆ อยู่เบื้องหลัง container ของเราก็รันอยู่ใน VM ตัวนั้น เลยทำให้เรื่อง performance ของ bind mount และ network บางเคสต่างจากบน Linux ตรง ๆ

Layer และ writable layer

ทุกคำสั่งที่เปลี่ยน filesystem ใน Dockerfile เช่น RUN, COPY จะสร้าง layer ใหม่ซ้อนขึ้นไป Layer เหล่านี้เป็น read-only และถูก cache กับแชร์ข้าม image ได้ ตอนสร้าง container Docker จะวาง writable layer บางๆ ไว้บนสุด ทุกอย่างที่แอปเขียนระหว่างรันจะลงที่ชั้นนี้ ซึ่งผูกอยู่กับ container ตัวนั้น

Writable layerเฉพาะ container นี้ หายเมื่อ docker rm
Layer: COPY . .read-only แชร์ได้
Layer: RUN npm ciread-only แชร์ได้
Base image: node:22-alpineread-only แชร์ได้

ลองรันดูสักรอบ

docker pull nginx:1.27
docker run -d --name web -p 8080:80 nginx:1.27
docker ps                      # ดู container ที่กำลังรัน
docker image ls                # ดู image ในเครื่อง
docker inspect --format '{{.Image}}' web
docker stop web && docker rm web

ถ้าอยากให้ production ไม่โดน “ของเปลี่ยนเงียบ ๆ” ให้อ้าง image ด้วย digest หรือใช้ tag ที่ระบุ version ชัดเจน และไม่แก้ทับ tag เดิม ส่วน latest เป็นแค่ชื่อ tag ธรรมดา ไม่ได้แปลว่าล่าสุดเสมอไป มันคือสิ่งที่คนที่ push กำหนดให้ชี้ไปที่ image ไหนก็ได้

จำไว้สอบContainer ใช้ kernel ร่วมกับ host (VM ไม่ใช่) • Container เป็น image + writable layer • Tag ย้ายได้ แต่ digest ไม่เปลี่ยน • กลไกที่ใช้แยกและจำกัด process คือ namespaces กับ cgroups

Dockerfile และการ build image

Beginner

Competency: เขียน Dockerfile สำหรับแอปจริงได้ เข้าใจ layer cache และรู้ว่า CMD, ENTRYPOINT, ARG, ENV ต่างกันอย่างไร

Dockerfile แรกของแอป Node.js

โจทย์ที่เจอบ่อยคือ “แพ็กแอป Express ตัวนี้เป็น image” ลองดู Dockerfile นี้ (ตัวอย่างประกอบ เลือก tag ให้ตรงกับ version ที่ทีมใช้จริง)

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

ทำไมต้อง copy package*.json แยกก่อน แล้วค่อย COPY . . เหตุผลคือ layer cache Docker จะ reuse layer เดิมตราบเท่าที่คำสั่งและไฟล์ที่เกี่ยวข้องไม่เปลี่ยน ถ้าเรา copy โค้ดทั้งก้อนก่อนแล้วค่อยติดตั้ง dependency ทุกครั้งที่แก้โค้ดแค่บรรทัดเดียว npm ci จะรันใหม่หมด แต่ถ้าแยกไว้ แก้โค้ดอย่างเดียว layer ของ dependency ยังใช้ cache ได้ หลักคือ ของที่เปลี่ยนน้อยไว้บน ของที่เปลี่ยนบ่อยไว้ล่าง

คำสั่งที่ต้องรู้ให้ชัด

คำสั่งทำอะไรจุดที่ต้องระวัง
FROMกำหนด base imageระบุ tag ที่ชัดเจน อย่าปล่อย latest
WORKDIRกำหนด directory ทำงานดีกว่าเขียน RUN cd ... && เพราะ cd ไม่มีผลข้าม layer
COPY / ADDคัดลอกไฟล์เข้า imageADD แตก tar และดึง URL ได้ ถ้าไม่ต้องการ ใช้ COPY
RUNรันคำสั่งตอน build แล้วเก็บผลเป็น layerรวมคำสั่งที่เกี่ยวข้องกัน เช่น update กับ install ไว้ใน RUN เดียว
ENVตั้ง environment variable ที่อยู่ทั้งตอน build และตอนรันค่าถูกเก็บใน image ใครดึง image ไปก็เห็น
ARGตัวแปรที่ส่งตอน build ผ่าน --build-argไม่อยู่ใน environment ตอนรัน แต่ยังเห็นได้ใน docker history จึงไม่ใช่ที่เก็บ secret
EXPOSEบันทึกว่าแอปฟัง port ไหนเป็นเอกสารเฉยๆ ไม่ได้เปิด port ให้ใครเข้า
CMDคำสั่งหรืออาร์กิวเมนต์เริ่มต้นตอนรันถูกแทนที่ได้ด้วยการต่อท้าย docker run image คำสั่งอื่น
ENTRYPOINTโปรแกรมหลักที่ container จะรันต้องใช้ --entrypoint ถึงจะเปลี่ยน ส่วนที่ต่อท้าย run จะกลายเป็น argument

CMD กับ ENTRYPOINT ใช้คู่กันอย่างไร

ถ้า image ตั้ง ENTRYPOINT ["python", "app.py"] และ CMD ["--port", "8000"] แล้วรัน docker run img จะได้ python app.py --port 8000 แต่ถ้ารัน docker run img --port 9000 ส่วน CMD จะถูกแทนที่ ได้ python app.py --port 9000 ENTRYPOINT เป็นตัวกำหนดว่า container นี้ “ทำหน้าที่อะไร” ส่วน CMD เป็นค่า default ที่ปรับได้

Exec form กับ shell form

เขียน CMD ["node", "server.js"] (exec form) กับ CMD node server.js (shell form) แล้วผลต่างกัน แบบหลังจะถูกห่อด้วย /bin/sh -c ทำให้ shell เป็น PID 1 ส่วน node เป็นลูก ตอนสั่ง docker stop สัญญาณ SIGTERM ไปถึง shell ซึ่งปกติไม่ส่งต่อให้ลูก แอปเลยไม่มีโอกาสปิดตัวอย่างสุภาพ ต้องรอครบเวลา timeout (ค่า default 10 วินาที) แล้วโดน SIGKILL แทน ถ้าไม่มีเหตุผลต้องใช้ shell feature ให้ใช้ exec form

ข้อผิดพลาดที่เจอบ่อย

อย่างแรกคือแยก RUN apt-get update กับ RUN apt-get install เป็นสองบรรทัด layer แรกถูก cache ไว้ตั้งแต่เมื่อหลายเดือนก่อน พอเพิ่ม package ใหม่ที่บรรทัดสอง Docker ใช้ index เก่าแล้วโหลดไม่เจอ วิธีแก้คือรวมไว้ใน RUN เดียว อย่างที่สองคือใช้ FROM node:latest วันนี้ build ผ่าน อีกสามเดือน base เปลี่ยน major version แล้ว build พัง โดยที่เราไม่ได้แก้อะไรเลย

# ไม่ดี: update ถูก cache แยกจาก install
RUN apt-get update
RUN apt-get install -y curl

# ดีกว่า: อยู่ใน layer เดียว และล้าง cache ของ apt
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
จำไว้สอบเรียง layer จากของที่เปลี่ยนน้อยไปมาก • EXPOSE ไม่ได้เปิด port • ARG อยู่แค่ตอน build ส่วน ENV อยู่ถึงตอนรัน • Exec form ทำให้ signal ไปถึงแอปโดยตรง

docker run, port, environment และ lifecycle

Beginner

Competency: รัน container พร้อม port, env, volume, restart policy และ resource limit ได้ รู้ว่า stop กับ kill ต่างกันอย่างไร

docker run ทำอะไรบ้างในคำสั่งเดียว

docker run คือ docker create ต่อด้วย docker start ถ้า image ยังไม่อยู่ในเครื่องก็ pull ให้ก่อน ลองดูตัวอย่างที่ใช้ flag ครบกลุ่มที่ข้อสอบชอบถาม

docker run -d --name api \
  -p 8080:3000 \
  -e NODE_ENV=production \
  --env-file ./api.env \
  -v api-data:/app/data \
  --restart unless-stopped \
  --memory 256m --cpus 0.5 \
  myorg/api:1.4.2
Flagหน้าที่หมายเหตุ
-dรันแบบ background (detached)ไม่ใส่ จะผูก terminal กับ container ตัวนั้น
-itเปิด stdin และ terminal แบบโต้ตอบใช้กับ shell หรือ REPL
--rmลบ container อัตโนมัติเมื่อหยุดเหมาะกับงานชั่วคราวหรือ debug
-p host:containerเปิด port จาก host เข้าไปหา container-p 8080:3000 คือ host 8080 ไป container 3000
-e / --env-fileส่ง environment variableค่าในคำสั่งไปอยู่ใน shell history ด้วย ของลับใช้ env-file หรือ secret แทน
-vmount volume หรือ bind mountรายละเอียดอยู่หัวข้อ Storage
--restartนโยบายสตาร์ตใหม่no, on-failure[:n], always, unless-stopped
--memory, --cpusจำกัด resource ผ่าน cgroupsใช้ memory เกินแล้วโดน OOM kill (exit 137)

Port mapping อ่านจากซ้ายไปขวา

ในรูป -p 8080:3000 เลขซ้ายคือ port บน host เลขขวาคือ port ในตัว container ผู้ใช้เปิด http://host:8080 แล้ว Docker ส่งต่อไปที่ port 3000 ของ container ถ้าไม่ระบุ IP ฝั่ง host จะ bind ที่ 0.0.0.0 ทุก interface อยากให้เข้าได้เฉพาะจากเครื่องเดียวกันให้เขียน -p 127.0.0.1:8080:3000 ส่วน EXPOSE ใน Dockerfile ไม่ได้ทำให้เกิดการ publish port แต่ถ้ารันด้วย -P (ตัวใหญ่) Docker จะ publish port ที่ EXPOSE ไว้ทั้งหมดไปยัง port สุ่มบน host

Lifecycle และคำสั่งที่ใช้บ่อย

docker ps -a                  # ทุก container รวมที่หยุดแล้ว
docker logs -f --tail 100 api # ตาม log
docker exec -it api sh        # เข้าไปใน container ที่รันอยู่
docker stop api               # SIGTERM แล้วรอ (default 10 วินาที) ค่อย SIGKILL
docker kill api               # SIGKILL ทันที (เปลี่ยน signal ได้ด้วย -s)
docker restart api
docker rm -f api              # ลบแม้ยังรันอยู่
docker cp api:/app/data/report.csv .

ข้อสังเกตเรื่อง PID 1 process แรกใน container ได้เป็น PID 1 และ Linux ปฏิบัติกับ PID 1 ต่างจาก process อื่นนิดหน่อย คือถ้าไม่ได้ลงทะเบียน handler ของ SIGTERM ไว้เอง สัญญาณนั้นจะถูกเมิน แอปส่วนใหญ่จึงควรจัดการ SIGTERM ให้เรียบร้อย หรือใช้ --init ให้ Docker ใส่ init process เล็กๆ มาคอยส่งต่อสัญญาณและเก็บ zombie process ให้

Resource limit และ restart policy

ถ้าไม่ตั้ง limit container จะใช้ memory ได้เท่าที่ host มี เครื่องที่รันหลาย container จึงโดน container ตัวเดียวกินจนหมดได้ เมื่อตั้ง --memory 256m แล้วแอปใช้เกิน kernel จะ kill process นั้น และ container ออกด้วย exit code 137 ส่วน --cpus 0.5 คือเพดานการใช้ CPU ไม่ใช่การจอง ตัว restart policy unless-stopped จะสตาร์ตใหม่เมื่อ Docker daemon ขึ้น เว้นแต่เราเป็นคนสั่ง stop ไว้เอง ต่างจาก always ที่จะสตาร์ตให้อีกครั้งเมื่อ daemon ขึ้นมาใหม่

เทคนิคสอบโจทย์ถาม “เข้า container ที่รันอยู่แล้ว” คำตอบคือ docker exec ส่วน docker run สร้าง container ใหม่เสมอ ถึงจะใช้ image เดียวกันก็ตาม

Docker Compose สำหรับหลาย container

Beginner

Competency: ประกอบหลาย service เช่น API กับ database ด้วยไฟล์เดียว และเข้าใจเรื่อง service name, healthcheck และ volume

ทำไมไม่รันด้วย docker run หลายคำสั่ง

แอปจริงมักมีมากกว่าหนึ่งชิ้น เช่น API, database, cache ถ้ารันแยกต้องสร้าง network, ใส่ env และเรียงลำดับเองทุกครั้ง Compose ให้เราประกาศทุกอย่างในไฟล์เดียวแล้วสั่ง docker compose up ได้เลย ปัจจุบันใช้ Compose v2 ที่เป็น plugin ของ Docker CLI (พิมพ์ docker compose ไม่มีขีด) ส่วน v1 แบบ docker-compose ถูกเลิกสนับสนุนไปแล้ว และไฟล์ไม่จำเป็นต้องมีบรรทัด version: อีก

services:
  api:
    build: .
    ports:
      - "8080:3000"
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
volumes:
  pgdata:

สามเรื่องที่ไฟล์นี้สอน

เรื่องแรก ชื่อ service คือ hostname Compose สร้าง network ให้โปรเจกต์โดยอัตโนมัติ และทุก service ใน network นั้นเรียกกันด้วยชื่อได้ จึงเขียน @db:5432 ได้โดยไม่ต้องรู้ IP การใช้ localhost ใน API จะวนกลับมาที่ container ของ API เอง ซึ่งเป็นความผิดพลาดที่เจอบ่อยที่สุดของมือใหม่

เรื่องที่สอง depends_on แบบสั้นรอแค่ให้ container ถูกสตาร์ต ไม่ได้รอให้ database พร้อมรับ connection Postgres ใช้เวลาเตรียมตัวอีกพักใหญ่ API ที่ต่อเร็วเกินไปจะ error ตอนเริ่ม เลยต้องมี healthcheck กับ condition: service_healthy ตามตัวอย่าง นอกจากนี้ตัวแอปเองก็ควรมี retry เผื่อ database หลุดระหว่างทางด้วย เพราะ production ไม่ได้มี Compose คอยรอให้

เรื่องที่สาม volume ชื่อ pgdata อยู่รอดจากการลบ container แต่ docker compose down -v จะลบ named volume ด้วย ข้อมูลหายหมด ถ้าไม่ใส่ -v volume จะยังอยู่

คำสั่งที่ใช้บ่อย

docker compose up -d --build    # build ใหม่แล้วรัน
docker compose ps
docker compose logs -f api
docker compose exec db psql -U app
docker compose config           # ดูไฟล์หลังแทนค่าตัวแปรแล้ว ใช้ตรวจ typo
docker compose down             # ลบ container + network (volume ยังอยู่)

มีอีกจุดที่ทำให้งงคือแก้โค้ดแล้ว docker compose up -d แต่ไม่เห็นการเปลี่ยนแปลง เพราะ Compose ใช้ image ที่ build ไว้แล้ว ต้องสั่ง --build เพื่อให้ build ใหม่ ส่วนเรื่อง env ให้ต่างกัน environment: ใส่ค่าตรง ๆ ในไฟล์ env_file: อ่านจากไฟล์ และไฟล์ .env ที่วางข้าง compose file ใช้แทนค่า ${VAR} ในตัว compose file เอง ไม่ได้ส่งเข้า container โดยอัตโนมัติ

จำไว้สอบชื่อ service ใช้เป็น hostname ได้ • depends_on แบบปกติไม่รอให้พร้อม ต้องมี condition: service_healthy • down -v ลบ named volume • ใช้ docker compose (v2)

Container Networking ขั้นสูง

Intermediate

Competency: เลือก network driver ให้เหมาะกับงาน แยก network ตามชั้นของระบบ และ debug ปัญหา connectivity ได้อย่างเป็นระบบ

Network driver แต่ละแบบเหมาะกับอะไร

Driverลักษณะใช้เมื่อ
bridge (default)network bridge ที่ Docker สร้างให้ container ที่ไม่ระบุอะไร ไม่มี DNS ตามชื่อ containerทดลองเร็ว ๆ ไม่ควรเป็นฐานของระบบจริง
user-defined bridgeสร้างเองด้วย docker network create มี DNS ในตัว (เรียกกันด้วยชื่อ) และแยกจาก network อื่นแอปหลาย container บน host เดียว
hostcontainer ใช้ network stack ของ host ตรง ๆ ไม่มี port mappingต้องการลด overhead หรือฟัง port จำนวนมาก แต่แลกกับการสูญเสียการแยก network
noneไม่มี network ภายนอก เหลือแค่ loopbackงานที่ไม่ควรออกเน็ตเลย เช่น batch ประมวลผลไฟล์
overlaynetwork ข้ามหลาย host (ใช้กับ Swarm)ต่อ container ข้ามเครื่อง ส่วนบน Kubernetes ใช้ CNI plugin แทน
macvlan / ipvlanให้ container ได้ IP จาก network ฝั่ง physical โดยตรงระบบเก่าที่ต้องการ IP ของตัวเองใน LAN

แยก network ตามชั้นของระบบ

แนวคิดที่ใช้บ่อยคือแยก network เป็น frontend กับ backend โดย proxy อยู่ frontend, API อยู่ทั้งสอง ส่วน database อยู่ backend เท่านั้น แบบนี้ proxy คุยกับ database ตรง ๆ ไม่ได้ ต่อให้ proxy ถูกเจาะ attacker ก็ต้องผ่าน API อีกชั้น เพิ่ม internal: true ให้ network ที่ไม่ควรออกอินเทอร์เน็ต container ใน network นั้นจะเรียกกันเองได้ แต่ออกข้างนอกไม่ได้

services:
  proxy:
    image: nginx:1.27
    ports: ["443:443"]
    networks: [frontend]
  api:
    image: myorg/api:1.4.2
    networks: [frontend, backend]
  db:
    image: postgres:16
    networks: [backend]
networks:
  frontend:
  backend:
    internal: true

Service discovery และ port

ใน user-defined network ตัว Docker มี DNS ภายในที่แปลงชื่อ container หรือ service เป็น IP ให้ และเรียกกันผ่าน container port ได้เลย เช่น api ต่อ db:5432 ไม่ต้อง publish port ของ db ออก host ถ้าไม่มีใครข้างนอกต้องเข้าถึงจริง ๆ การลดจำนวน port ที่ publish คือการลดพื้นที่ที่ถูกโจมตีโดยตรง ถ้าจำเป็นต้อง publish เช่นเพื่อ debug ให้ bind ที่ loopback เป็น -p 127.0.0.1:5432:5432

เรื่องที่คนมองข้ามDocker แก้ rule ของ iptables เองเพื่อทำ port publishing ทำให้ port ที่ publish อาจไม่ถูกกรองด้วย rule ของ ufw หรือ firewalld ที่เราตั้งไว้ตามที่คิด ถ้าต้องควบคุม ให้ bind ที่ IP เฉพาะ และดูเอกสารเรื่อง Docker กับ firewall ของ distro ที่ใช้ ผลจะขึ้นกับ version และ firewall backend ของเครื่อง

Debug connectivity ไล่จากล่างขึ้นบน

เมื่อ container A เรียก B ไม่ได้ ให้ไล่ตามนี้ ทั้งคู่อยู่ network เดียวกันหรือเปล่า ชื่อแปลงเป็น IP ได้ไหม port ฝั่ง B ฟังอยู่จริงไหม และมี policy ตัดหรือเปล่า เครื่องมือที่ช่วยได้คือ image อย่าง netshoot ที่มี curl, dig, tcpdump อยู่ครบ เอาไปเกาะ network namespace ของ container ที่มีปัญหาได้โดยไม่ต้องเพิ่มเครื่องมือใน image จริง

docker network ls
docker network inspect backend                 # ดู subnet และ container ที่ต่ออยู่
docker run --rm -it --network container:api nicolaka/netshoot
# ในเชลล์ของ netshoot (ใช้ network ร่วมกับ api):
nslookup db
curl -sv http://db:5432 --max-time 3
ss -ltn

เรื่อง host ของเครื่อง: ใน Docker Desktop เรียก host ได้ที่ host.docker.internal บน Linux ต้องเพิ่ม --add-host=host.docker.internal:host-gateway เอง

จำไว้สอบDNS ตามชื่อมีเฉพาะ user-defined network • ไม่ต้อง publish port ถ้าแค่ container คุยกัน • internal: true ตัดทางออกอินเทอร์เน็ต • --network container:X ใช้ network namespace ร่วมกับ X

Container Storage ขั้นสูง

Intermediate

Competency: เลือก volume, bind mount และ tmpfs ให้ถูกงาน จัดการสิทธิ์ไฟล์ และวางแผน backup ข้อมูลของ container

สามแบบของการ mount

แบบเก็บที่ไหนเหมาะกับข้อควรระวัง
Volumeพื้นที่ที่ Docker จัดการ (บน Linux อยู่ใต้ /var/lib/docker/volumes)ข้อมูลที่ต้องอยู่รอด เช่น databaseลบ volume ก็คือลบข้อมูล
Bind mountpath ที่เรากำหนดบน hostแชร์ source ตอน dev หรือ config ที่ host เป็นเจ้าของผูกกับโครงสร้างไฟล์และสิทธิ์ของ host
tmpfsmemory ของ hostข้อมูลชั่วคราวหรือลับที่ไม่ควรลงดิสก์หายเมื่อ container หยุด และกิน RAM

พฤติกรรมที่ข้อสอบชอบถาม: ถ้า mount named volume ที่ว่าง ทับ path ที่ image มีไฟล์อยู่แล้ว Docker จะคัดลอกเนื้อหาเดิมจาก image ลงใน volume ให้ตอนใช้ครั้งแรก แต่ถ้าเป็น bind mount เนื้อหาจาก host จะ บัง เนื้อหาเดิมใน image ไปเลย และถ้า path ฝั่ง host ว่าง ใน container ก็จะว่างด้วย

-v กับ --mount

ทั้งสองทำงานคล้ายกัน แต่ --mount เขียนยาวกว่าและชัดกว่า ข้อต่างที่ใช้จริงคือถ้า path ฝั่ง host ของ bind mount ไม่มีอยู่ -v จะสร้าง directory เปล่า (เจ้าของเป็น root) ขึ้นมาให้เงียบ ๆ ส่วน --mount จะ error ทันที ซึ่งปลอดภัยกว่าเพราะไม่ซ่อนความผิดพลาดจาก typo

docker run -d --name db \
  --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data \
  postgres:16

docker run -d --name web \
  --mount type=bind,src="$PWD/site",dst=/usr/share/nginx/html,readonly \
  nginx:1.27

docker run -d --read-only --tmpfs /tmp:rw,size=64m myorg/api:1.4.2

สิทธิ์ไฟล์ (UID/GID) คือสาเหตุของปัญหา volume ส่วนใหญ่

Linux เทียบสิทธิ์ด้วยเลข UID ไม่ใช่ชื่อ user ถ้าแอปใน container รันด้วย UID 10001 แต่ directory ที่ mount เป็นของ UID 1000 บน host ก็เขียนไม่ได้ แม้ชื่อ user จะดูเหมือนกัน แนวทางแก้มีสามทาง คือ chown directory ให้ตรงกับ UID ที่แอปใช้ ตั้ง --user ให้ตรงกับเจ้าของ directory หรือใช้ named volume ที่ Docker สร้างตอน image มี directory นั้นอยู่แล้วและตั้งเจ้าของไว้ใน Dockerfile

Backup และ restore volume

วิธีที่ใช้ได้กับทุก volume คือรัน container ชั่วคราวที่ mount ทั้ง volume และ directory สำหรับเก็บ backup แล้วใช้ tar

# backup
docker run --rm -v pgdata:/data:ro -v "$PWD":/backup alpine \
  tar czf /backup/pgdata.tgz -C /data .

# restore เข้า volume ใหม่
docker volume create pgdata_restore
docker run --rm -v pgdata_restore:/data -v "$PWD":/backup alpine \
  tar xzf /backup/pgdata.tgz -C /data

แต่สำหรับ database ที่กำลังรัน การ copy ไฟล์ดิบตอนที่มีการเขียนอยู่อาจได้ข้อมูลที่ไม่สอดคล้องกัน วิธีที่เชื่อถือได้กว่าคือใช้เครื่องมือของ database เอง เช่น pg_dump หรือ snapshot ที่ database รองรับ แล้วจึงเก็บไฟล์ที่ได้ ส่วน volume driver อื่น ๆ เช่น NFS ก็ตั้งได้ตอนสร้าง volume

docker volume create --driver local \
  --opt type=nfs --opt o=addr=10.0.0.5,rw \
  --opt device=:/exports/shared shared-data

เรื่อง storage driver และพื้นที่ดิสก์

ปกติ Docker บน Linux ใช้ overlay2 ซ้อน layer แบบ copy-on-write เมื่อแอปแก้ไฟล์ที่อยู่ใน layer ของ image ครั้งแรก Docker จะ copy ไฟล์ทั้งไฟล์ขึ้นมาไว้ใน writable layer ก่อน ทำให้การเขียนหนัก ๆ ผ่าน writable layer ช้ากว่า volume เหมาะแล้วที่ database และงานเขียนถี่จะใช้ volume ส่วน docker system df ใช้ดูว่า image, container, volume และ build cache กินพื้นที่เท่าไหร่

ฝั่ง Kubernetesแนวคิดเดียวกันถูกยกระดับเป็น PersistentVolume (PV), PersistentVolumeClaim (PVC) และ StorageClass แอปขอพื้นที่ผ่าน PVC แล้ว cluster จัดสรรให้ตาม StorageClass ส่วน access mode เช่น ReadWriteOnce (mount เขียนได้จาก node เดียว) กับ ReadWriteMany ขึ้นกับ storage backend ที่ใช้ ไม่ใช่ทุกตัวรองรับ

Security Policy ของ Container Image

Intermediate

Competency: ทำให้ image และการรันปลอดภัยขึ้นด้วยการลดสิทธิ์ ลดสิ่งที่ไม่จำเป็น จัดการ secret ถูกวิธี และรู้ว่านโยบายแต่ละข้อป้องกันอะไร

ถามก่อนว่ากำลังป้องกันอะไร

สมมติ attacker หาช่องโหว่ในแอปแล้วรันคำสั่งใน container ของเราได้ คำถามคือเขาทำอะไรต่อได้บ้าง ถ้า container รันด้วย root มี shell ครบ เขียนไฟล์ได้ทุกที่ และมี capability เยอะ เขาจะมีของให้เล่นมาก นโยบายความปลอดภัยของ image จึงคือการตัดทางเหล่านี้ทีละข้อ

Dockerfile ที่ใส่ policy พื้นฐานครบ

# syntax=docker/dockerfile:1
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build --chown=10001:10001 /app/dist ./dist
USER 10001:10001
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
CMD ["node", "dist/server.js"]

จุดที่ควรสังเกตมีสี่อย่าง ตัว build tool ทั้งหมดอยู่ใน stage แรกและไม่ติดไปกับ image สุดท้าย รันด้วย USER 10001:10001 เป็นเลขตรง ๆ ไม่ใช่ root ใช้ base ที่เล็กลงเพื่อให้มีของให้ถูกโจมตีน้อยลง และมี HEALTHCHECK ให้ Docker รู้ว่าแอปยังตอบสนองอยู่ (Kubernetes จะไม่ใช้ HEALTHCHECK ตัวนี้ แต่ใช้ probe ที่ตั้งใน manifest แทน)

ทำไมต้อง USER แบบตัวเลขถ้าใน Kubernetes ตั้ง runAsNonRoot: true แต่ image ใช้ชื่อ user เช่น USER appuser kubelet จะแจ้งว่าไม่สามารถยืนยันว่า user นั้นไม่ใช่ root ได้ (non-numeric user) และไม่สตาร์ต container ให้ ใช้ UID เป็นตัวเลขแก้ปัญหานี้ได้

ปรับที่ตอนรัน

docker run -d --name api \
  --read-only --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --pids-limit 200 --memory 256m \
  myorg/api:1.4.2

--cap-drop ALL ตัด Linux capability ทั้งหมด (เพิ่มกลับเฉพาะที่จำเป็นด้วย --cap-add) no-new-privileges กันไม่ให้ process ได้สิทธิ์เพิ่มผ่าน setuid binary --read-only ทำให้ root filesystem เขียนไม่ได้ ถ้าแอปจำเป็นต้องเขียนที่ไหน ให้เปิดเป็น tmpfs หรือ volume เฉพาะจุด และ Docker ใช้ default seccomp profile ที่บล็อก syscall อันตรายบางตัวอยู่แล้ว อย่าปิดมันด้วย --security-opt seccomp=unconfined โดยไม่มีเหตุผล

Secret อย่าให้ติดอยู่ใน layer

ถ้า COPY .env . เข้ามา แล้วค่อย RUN rm .env ใน layer ถัดไป ไฟล์ยังอยู่ใน layer ก่อนหน้า ใครได้ image ไปก็ docker save แตก layer ออกมาอ่านได้ หรือส่ง token ผ่าน ARG ก็เห็นใน history เช่นกัน ทางที่ถูกคือ BuildKit secret mount ซึ่งเปิดให้ใช้ได้เฉพาะระหว่างคำสั่ง RUN นั้นและไม่ถูกเขียนลง layer

# syntax=docker/dockerfile:1
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev

# ตอน build
docker build --secret id=npmrc,src=$HOME/.npmrc -t myorg/api:1.4.2 .

ส่วน secret ตอนรัน (เช่น database password) ควรมาจาก secret manager ของ platform หรือ Docker/Kubernetes secrets ที่ mount เป็นไฟล์หรือ env ตอน start ไม่ใช่ค่าที่ฝังใน image

สิ่งที่ไม่ควรทำ

สิ่งที่เจอทำไมเสี่ยงทางแก้
--privilegedให้เกือบทุก capability และเข้าถึง device ของ hostระบุ capability หรือ device ที่จำเป็นจริงเท่านั้น
mount /var/run/docker.sockผู้ที่คุม socket สั่ง Docker daemon ได้ ซึ่งเทียบเท่า root บน hostใช้ API ที่จำกัดสิทธิ์ หรือเครื่องมือ build ที่ไม่ต้องใช้ socket
ไม่มี USER (รัน root)RCE ในแอปได้สิทธิ์ root ใน container ทันทีสร้าง user ที่ไม่มีสิทธิ์พิเศษและระบุ UID
FROM image:latestbuild ซ้ำไม่ได้ ตรวจย้อนหลังไม่ได้ว่าใช้ตัวไหนระบุ tag ชัดเจน หรือ pin ด้วย digest
curl ... | sh ใน Dockerfileรันสคริปต์ที่ไม่ได้ตรวจสอบดาวน์โหลด ตรวจ checksum หรือ signature ก่อนใช้

การ pin ด้วย digest เช่น FROM node:22-alpine@sha256:... ทำให้ build ได้ base เดิมทุกครั้ง แต่ก็ต้องมีกระบวนการอัปเดต digest เป็นระยะ (เช่นใช้ Renovate หรือ Dependabot) ไม่งั้น base จะค้างอยู่กับช่องโหว่เก่าโดยที่ไม่มีใครรู้ตัว

Multi-stage build และ BuildKit

Intermediate

Competency: ลดขนาดและพื้นที่โจมตีของ image ด้วย multi-stage เร่ง build ด้วย cache และเลือก base image โดยรู้ trade-off

Multi-stage ทำไมถึงจำเป็น

แอปที่ต้องคอมไพล์ เช่น Go, Java, หรือ frontend ที่ build ด้วย webpack ต้องใช้ compiler และ dev dependency ตอน build แต่ไม่ต้องใช้ตอนรัน ถ้าเก็บทุกอย่างไว้ใน image เดียว ก็ได้ image ที่ใหญ่และมีเครื่องมือให้ attacker ใช้เยอะ Multi-stage แก้ด้วยการแยกเป็นหลาย FROM แล้วหยิบเฉพาะผลลัพธ์จาก stage ก่อนหน้าด้วย COPY --from= stage สุดท้ายเท่านั้นที่เป็น image ที่ถูกส่งออก

FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
ENTRYPOINT ["/server"]

ตัวอย่างนี้ใช้ distroless เป็น stage สุดท้าย ใน image ไม่มี shell และ package manager เลย ข้อดีคือพื้นที่โจมตีน้อยมาก ข้อเสียคือ debug ยากขึ้น เพราะ docker exec ... sh ใช้ไม่ได้ ต้องใช้ debug image ชั่วคราวหรือ ephemeral container ของ Kubernetes แทน ส่วน --target build ใช้ build ถึง stage ที่ต้องการเท่านั้น เหมาะกับการรัน test ใน CI

BuildKit และ cache

BuildKit เป็น builder เริ่มต้นของ Docker Engine ตั้งแต่ version 23.0 มันรัน stage ที่ไม่ขึ้นต่อกันพร้อมกันได้ และมีฟีเจอร์ที่ใช้ได้ผ่านบรรทัด # syntax=docker/dockerfile:1 อย่าง cache mount ที่เก็บ cache ของ package manager ไว้ข้าม build โดยไม่ติดไปใน layer

# syntax=docker/dockerfile:1
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]

ถ้าต้องการให้ image รันได้ทั้ง amd64 และ arm64 ใช้ docker buildx build --platform linux/amd64,linux/arm64 -t myorg/api:1.4.2 --push . ผลลัพธ์คือ manifest list ตัวเดียวที่ชี้ไป image ของแต่ละ platform พอ client pull Docker จะเลือกให้ตรงกับเครื่อง

เลือก base image ยังไง

Baseข้อดีข้อจำกัด
Debian/Ubuntu (full)เครื่องมือครบ debug ง่ายใหญ่ มี package มาก ทำให้มี CVE ที่ต้องตามมากขึ้น
-slimเล็กลงแต่ยังเป็น glibcต้องติดตั้ง package ที่ขาดเอง
Alpineเล็กมาก ใช้ musl libcbinary หรือ native module ที่คอมไพล์ไว้สำหรับ glibc อาจใช้ไม่ได้ หรือพฤติกรรมต่างกัน
Distroless / scratchมีเฉพาะสิ่งที่แอปต้องใช้ไม่มี shell ต้องวางแผน debug ล่วงหน้า และแอปต้อง static หรือมี runtime ที่ตรงกัน

เล็กอย่างเดียวไม่ใช่เป้าหมาย ต้องดูทั้งความเข้ากันได้ของ library การ debug และความสามารถของทีมในการดูแล ถ้าสงสัยว่าทำไม image ใหญ่ ใช้ docker history --no-trunc image ดูว่า layer ไหนหนัก และ .dockerignore ถูกตั้งหรือยัง

นำโครงการย้ายระบบเข้า Container (Migration)

Intermediate

Competency: วางแผนและนำทีมย้ายแอปเดิมเข้า container อย่างเป็นขั้นตอน คุมความเสี่ยง มีแผน rollback และรู้ว่าเมื่อไหร่ควรหยุดหรือถอย

เริ่มที่การประเมิน ไม่ใช่ที่ Dockerfile

โปรเจกต์ย้ายที่พังส่วนใหญ่พังเพราะประเมินแอปไม่ละเอียด ไม่ใช่เพราะเขียน Dockerfile ไม่เป็น ก่อนเขียนบรรทัดแรก ต้องรู้ว่าแอปแต่ละตัวพึ่งอะไร เก็บ state ที่ไหน config มาจากไหน ต้องเปิด port อะไร ต่อออกไปหาระบบไหนบ้าง และมีไฟล์ที่เขียนลงดิสก์เครื่องเดิมหรือเปล่า จากนั้นจัดกลุ่มเพื่อเลือกแนวทางของแต่ละตัว

แนวทางทำอะไรเหมาะกับ
Rehostแพ็กแอปเดิมเป็น container โดยแทบไม่แก้โค้ดแอปที่ stateless อยู่แล้ว ต้องการย้ายเร็ว
Replatformแก้บางส่วน เช่น ย้าย log ออก stdout เก็บ session ใน Redis ย้าย config ไป envแอปที่ผูกกับเครื่องเดิมอยู่บ้าง
Refactorแยกหรือเขียนใหม่บางส่วนส่วนที่มีเหตุผลทางธุรกิจชัดเจนพอจะลงทุน ไม่ควรทำไปพร้อมกับการย้ายถ้าไม่จำเป็น

แอปต้องพร้อมแค่ไหนก่อนย้าย

ใช้แนวคิดจาก Twelve-Factor เป็นเช็กลิสต์ได้ ข้อที่กระทบการย้ายมากที่สุดคือ config มาจาก environment ไม่ฝังในโค้ดหรือ image, process เป็น stateless (session กับไฟล์อัปโหลดอยู่นอกตัว container), log ออก stdout/stderr, และแอปปิดตัวอย่างสุภาพได้เมื่อได้รับ SIGTERM เพราะ container ถูก stop กับสร้างใหม่บ่อยกว่าเครื่อง VM มาก

const server = app.listen(3000);

process.on('SIGTERM', () => {
  console.log('SIGTERM received, closing server');
  server.close(() => process.exit(0));      // หยุดรับ request ใหม่ รอตัวที่ค้างให้จบ
  setTimeout(() => process.exit(1), 8000).unref();  // กันค้างเกินเวลา
});

เวลารอนี้ต้องสั้นกว่า grace period ของ platform ด้วย Docker ให้ 10 วินาทีโดยค่า default ส่วน Kubernetes ให้ terminationGracePeriodSeconds 30 วินาทีโดย default ถ้าแอปใช้เวลาปิดตัวนานกว่านั้นจะโดน SIGKILL

แผนเป็นเฟส และแต่ละเฟสต้องมีเกณฑ์ออก

1. Assess

ทำ inventory แอป dependency, state, config จัดลำดับความยาก

2. Containerize

เขียน Dockerfile ตั้ง CI build และ scan ทดสอบรันในเครื่องและ staging

3. Verify

เทียบ behavior และ performance กับระบบเดิม ทดสอบ restart, scale, failure

4. Pilot, Cutover, Decommission

รัน parallel กับของเดิม ย้าย traffic ทีละส่วน เก็บของเก่าไว้จนมั่นใจ แล้วค่อยปลด

เกณฑ์ออกของแต่ละเฟสควรเป็นสิ่งที่ตรวจได้ เช่น health check ตอบถูก, ผ่าน load test ที่ตกลงกันไว้, ทดลอง rollback สำเร็จ, มี runbook และทีม on-call อ่านแล้ว การมี “แผนถอย” ที่ลองทำจริงแล้วสำคัญพอ ๆ กับแผนเดินหน้า

Cutover และ rollback

วิธีที่ทำให้ rollback เร็วที่สุดคือเก็บระบบเดิมไว้ให้พร้อมรับ traffic ต่อไปอีกพักหนึ่ง เช่น blue-green ที่สลับ traffic ทั้งก้อนที่ load balancer หรือ canary ที่ค่อย ๆ เพิ่มสัดส่วนไปยังของใหม่ ขณะที่ฐานข้อมูลเป็นจุดที่ถอยยากที่สุด จึงควรเปลี่ยน schema แบบ expand/contract คือเพิ่มของใหม่ให้เข้ากันได้กับทั้งแอปเก่าและใหม่ก่อน แล้วค่อยลบของเก่าหลังย้ายเสร็จ แบบนี้ถอยแอปกลับไปได้โดยไม่ต้อง restore ข้อมูล

ความเสี่ยงที่เจอบ่อยในโครงการจริง

ความเสี่ยงสัญญาณวิธีลด
State ซ่อนอยู่ในดิสก์ใช้ได้ replica เดียว พอเพิ่มเป็นสองตัวผู้ใช้เจอข้อมูลหายตรวจหาไฟล์ที่แอปเขียน ย้ายไป object storage หรือ database
แอปไม่ปิดตัวสุภาพdeploy แล้วมี request ล้มช่วงสั้น ๆ ทุกครั้งจัดการ SIGTERM และตั้ง readiness probe
Resource limit ไม่ตรงกับจริงcontainer โดน OOM kill หรือ CPU ถูก throttleวัดการใช้จริงจาก staging แล้วตั้ง requests และ limits ตามข้อมูล
Config ต่างกันระหว่าง environmentstaging ผ่านแต่ production พังใช้ image เดียวกันทุก environment ต่างกันเฉพาะ config
ทีมยังไม่คุ้นเครื่องมือเหตุการณ์ฉุกเฉินแล้วไม่มีใครรู้จะเริ่ม debug ตรงไหนทำ runbook และซ้อมกับระบบที่ไม่สำคัญก่อน

บทบาทของคนนำโครงการ

นอกจากเรื่องเทคนิค ผู้นำโครงการต้องตกลงขอบเขตและนิยามคำว่าเสร็จกับ stakeholder ตั้งแต่ต้น เลือกแอปนำร่องที่เสี่ยงต่ำแต่ไม่ง่ายจนไม่ได้เรียนรู้อะไร เก็บตัวชี้วัดฐานของระบบเดิมไว้ก่อน (เวลา deploy, error rate, การใช้ resource) เพื่อใช้เทียบหลังย้าย และบอกตรง ๆ ว่าอะไรอยู่นอกขอบเขต เช่น ฐานข้อมูลที่ยังอยู่บน VM เดิมในระยะแรก เพราะ stateful workload เป็นส่วนที่ย้ายยากและเสี่ยงที่สุด การรันมันใน container ไม่ได้ผิด แต่ควรทำเมื่อทีมมีประสบการณ์เรื่อง storage และ backup แล้ว

เรื่อง Compose ไป Kubernetesถ้าระบบมีไม่กี่ service รันบน host เดียวและยอมรับ downtime สั้น ๆ ตอน deploy ได้ Compose อาจพอ แต่ถ้าต้องการ scale หลาย node, self-healing, rolling update และ policy ระดับ cluster ก็ต้องการ orchestrator อย่าง Kubernetes ซึ่งแลกกับความซับซ้อนในการดูแลที่เพิ่มขึ้น ควรตัดสินจากความต้องการจริงของระบบ ไม่ใช่ตามกระแส

ระดับนี้เลิกคิดทีละ container แล้ว คำถามกลายเป็นว่าทั้งองค์กรควรรัน container กันอย่างไรให้เป็นมาตรฐานเดียว จะบังคับใช้นโยบายอย่างไรโดยไม่ทำให้ทีมอื่นทำงานไม่ได้ จะรู้ได้อย่างไรว่าเกิดอะไรขึ้นกับ container หลายร้อยตัว และจะรู้ได้อย่างไรว่า image ที่ปล่อยออกไปปลอดภัยพอ

Policy Enforcement ในระบบ Container

Advance

Competency: ออกแบบชั้นการบังคับใช้นโยบายตั้งแต่ตอนเขียนโค้ดจนถึงตอนรัน และ rollout นโยบายโดยไม่ทำให้ workload เดิมพังพร้อมกันหมด

เอกสารนโยบายไม่ช่วยอะไรถ้าไม่มีกลไกบังคับ

ถ้านโยบายบอกว่า “ห้ามใช้ root” แต่ไม่มีอะไรตรวจ สุดท้ายก็จะมี container ที่รันด้วย root อยู่ใน production สักตัวเสมอ Policy enforcement คือการเอานโยบายที่เขียนเป็นคำพูดไปทำเป็นกฎที่เครื่องตรวจให้ได้ โดยวางไว้หลายจุดตามลำดับของ lifecycle เพราะยิ่งเจอปัญหาเร็ว ยิ่งแก้ถูก

จุดบังคับใช้ตัวอย่างเครื่องมือตรวจอะไรข้อจำกัด
ตอนเขียน (pre-commit / IDE)hadolint, conftestDockerfile ที่ผิดกฎ เช่นไม่ระบุ tag, รัน rootข้ามได้ถ้านักพัฒนาไม่ติดตั้ง ไม่ใช่เส้นสุดท้าย
ใน CITrivy (config, image), conftestmisconfiguration, CVE, secretตรวจได้เฉพาะ pipeline ที่ผ่านทางนี้ ถ้ามีคน deploy ลัดจะไม่เห็น
ที่ registryregistry policy, cosignimmutable tag, signature, retentionขึ้นกับความสามารถของ registry ที่ใช้
ตอน deploy (admission)Pod Security Admission, Kyverno, OPA Gatekeeperspec ของ Pod ก่อนถูกสร้างตรวจเฉพาะสิ่งที่เห็นใน request ไม่เห็นพฤติกรรมตอนรัน
ตอนรัน (runtime)Falco และเครื่องมือจับ syscallพฤติกรรมผิดปกติ เช่นเปิด shell ใน containerเป็นการตรวจจับ ไม่ใช่การป้องกันล่วงหน้า

ไม่ได้แปลว่าต้องมีครบทุกชั้นตั้งแต่วันแรก แต่ควรมี admission ไว้เป็นด่านสุดท้ายก่อนเข้า cluster เพราะเป็นจุดเดียวที่ทุกวิธี deploy ต้องผ่าน

Pod Security Admission (PSA) ใน Kubernetes

Kubernetes มีมาตรฐานกำหนดไว้สามระดับ เรียกว่า Pod Security Standards ได้แก่ privileged (ไม่จำกัด), baseline (กันการตั้งค่าที่ยกระดับสิทธิ์ได้ง่าย) และ restricted (ตามแนวปฏิบัติ hardening เข้มที่สุด) และ PSA เป็นตัวบังคับใช้ผ่าน label ของ namespace โดยมีสามโหมด คือ enforce ปฏิเสธ pod ที่ผิด, audit ให้ผ่านแต่บันทึกลง audit log, และ warn ให้ผ่านแต่แสดงคำเตือนกลับไปหาผู้สั่ง PSA เข้ามาแทน PodSecurityPolicy ที่ถูกถอดออกใน Kubernetes v1.25

apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted

ตัวอย่างนี้บังคับระดับ baseline จริง แต่ audit และ warn ที่ระดับ restricted เพื่อเก็บข้อมูลว่ามี workload ไหนยังไม่ผ่านมาตรฐานที่เป็นเป้าหมาย โดยยังไม่ทำให้ใครถูกบล็อก นี่คือรูปแบบการ rollout ที่ใช้กันบ่อย

Policy engine แบบ custom

PSA ตรวจเฉพาะเรื่อง Pod security เท่านั้น ถ้าต้องการกฎของตัวเอง เช่น image ต้องมาจาก registry ที่อนุมัติ, ห้ามใช้ tag latest, ทุก container ต้องมี resource limit ก็ใช้ policy engine เช่น Kyverno (เขียนนโยบายเป็น YAML) หรือ OPA Gatekeeper (เขียนเป็น Rego) ที่ทำงานเป็น admission controller

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-latest-tag
spec:
  validationFailureAction: Audit    # เปลี่ยนเป็น Enforce เมื่อพร้อม
  background: true
  rules:
  - name: require-image-tag
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "ต้องระบุ tag ของ image"
      pattern:
        spec:
          containers:
          - image: "*:*"
  - name: disallow-latest
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "ห้ามใช้ tag latest"
      pattern:
        spec:
          containers:
          - image: "!*:latest"
ข้อจำกัดเรื่อง versionชื่อ field และรูปแบบของ Kyverno เปลี่ยนไปตามรุ่น (เช่นตำแหน่งของการตั้งโหมด Audit/Enforce) ตัวอย่างข้างบนเป็นรูปแบบประกอบการอธิบาย ก่อนใช้จริงให้เทียบกับเอกสารของ Kyverno ใน version ที่ติดตั้งอยู่

Rollout แบบไม่ทำให้ระบบหยุด

นโยบายใหม่ที่เปิด enforce ทันทีมักทำให้ deploy ของหลายทีมล้มพร้อมกัน แล้วนโยบายก็ถูกเกลียดตั้งแต่วันแรก ลำดับที่ปลอดภัยกว่าคือ (1) เปิดแบบ audit/warn เก็บข้อมูลว่าใครผิดอะไรบ้าง (2) ประกาศ แล้วให้เวลาแก้พร้อมวิธีแก้ที่ชัด (3) เปลี่ยนเป็น enforce ทีละ namespace หรือทีละ environment เริ่มจาก non-production (4) มีทางขอยกเว้นที่ชัดเจน ว่าใครอนุมัติ เหตุผลอะไร หมดอายุเมื่อไร ข้อความที่ policy ตอบกลับควรบอกด้วยว่าผิดกฎข้อไหนและแก้อย่างไร ไม่ใช่แค่ “denied”

จำไว้สอบPSA มี 3 โหมด (enforce / audit / warn) และ 3 ระดับ (privileged / baseline / restricted) • PodSecurityPolicy ถูกถอดใน v1.25 • Admission เป็นด่านที่ทุก deploy ต้องผ่าน • เริ่มจาก audit แล้วค่อย enforce

Logging Standard: Fluentd และ ELK

Advance

Competency: กำหนดมาตรฐาน log ที่ใช้ร่วมกันทั้งองค์กร ออกแบบเส้นทางเก็บ log จาก container ไปยังที่เก็บกลาง และเข้าใจ trade-off เรื่องความน่าเชื่อถือกับ performance

ปัญหาที่ต้องแก้

Container ถูกสร้างและทำลายตลอดเวลา เมื่อ container หายไป log ที่เก็บอยู่ข้างในก็หายไปด้วย ยิ่งมีหลาย replica หลาย node การไล่ docker logs ทีละตัวก็ทำไม่ได้ จึงต้องส่ง log ออกมารวมที่ศูนย์กลาง และถ้าแต่ละทีมเขียน log คนละรูปแบบ การค้นหาข้ามระบบก็ไม่เวิร์กอยู่ดี เลยต้องมีมาตรฐานทั้งสองเรื่อง คือ เส้นทางของ log และ รูปแบบของ log

เส้นทางของ log

แอปเขียน stdout/stderr→ Docker logging driver หรือ node agent→ Fluentd / Fluent Bit→ Elasticsearch→ Kibana

ชุดที่เรียกว่า ELK คือ Elasticsearch (เก็บและค้นหา), Logstash (ประมวลผล log) และ Kibana (ดูผล) ส่วน EFK คือเปลี่ยน Logstash เป็น Fluentd หรือ Fluent Bit ซึ่งเป็น log collector ที่เบากว่าและเป็นที่นิยมใน container เพราะ Fluent Bit ใช้ resource น้อยเหมาะรันเป็น agent บนทุก node

ทางที่ Docker ส่ง log ออกไป

ค่าเริ่มต้นของ Docker คือ driver json-file ที่เก็บ log เป็นไฟล์ JSON บน host และ ค่าเริ่มต้นไม่มีการหมุนไฟล์ log จึงโตไปเรื่อย ๆ จนดิสก์เต็มได้ จึงควรตั้ง max-size กับ max-file ใน /etc/docker/daemon.json (มีผลกับ container ที่สร้างหลังจาก restart daemon เท่านั้น) ส่วน driver local มีการหมุนไฟล์เป็นค่าเริ่มต้นอยู่แล้ว

{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "5"
  }
}

หรือจะส่งตรงเข้า Fluentd ด้วย logging driver ของ Docker ก็ได้ โดยค่า default จะเชื่อมที่ localhost:24224 และเปลี่ยนที่อยู่ได้ด้วย fluentd-address

docker run -d --name api \
  --log-driver=fluentd \
  --log-opt fluentd-address=fluentd.internal:24224 \
  --log-opt tag=docker.{{.Name}} \
  myorg/api:1.4.2

ฝั่ง Fluentd รับ log ด้วย input แบบ forward แล้วส่งต่อไป Elasticsearch ตัวอย่างนี้สมมติว่าติดตั้ง plugin fluent-plugin-elasticsearch แล้ว

<source>
  @type forward
  port 24224
  bind 0.0.0.0
</source>

<filter docker.**>
  @type parser
  key_name log
  reserve_data true
  <parse>
    @type json
  </parse>
</filter>

<match docker.**>
  @type elasticsearch
  host elasticsearch
  port 9200
  logstash_format true
</match>

ตัว filter จะแกะ field log ที่เป็น JSON ให้เป็นฟิลด์แยก ทำให้ค้นด้วย level หรือ trace_id ได้ทันที ถ้าแอปบางตัวยังเขียน log แบบ text ธรรมดา ตรงนี้จะ parse ไม่ผ่านและต้องมีการจัดการ record ที่ผิดรูปแบบไว้ด้วย

Trade-off ที่ต้องตัดสินใจ

ถ้าใช้ Fluentd driver แบบ default ตอน start container แล้วต่อ Fluentd ไม่ได้ container จะสตาร์ตไม่ขึ้น ซึ่งบางองค์กรยอมรับได้เพราะไม่อยากรัน service โดยไม่มี log แต่บางองค์กรรับไม่ได้ ที่ log server ล่มแล้วทั้งระบบหยุด ตัวเลือก fluentd-async ทำให้ Docker เชื่อมต่อใน background และ buffer ข้อความไว้จนกว่าจะเชื่อมได้ ส่วน mode=non-blocking ทำให้แอปไม่ถูกบล็อกตอนเขียน log แต่แลกกับการที่ buffer เต็มแล้วข้อความอาจถูกทิ้ง ต้องเลือกว่าจะยอมเสียอะไรระหว่าง “log หาย” กับ “แอปช้าหรือหยุด”

แบบข้อดีข้อจำกัด
Docker logging driver ส่งตรงตั้งค่าง่าย ไม่ต้องมี agent เพิ่มผูกกับ daemon และพฤติกรรมเมื่อปลายทางล่ม ต้องตั้งให้ถูก
Agent อ่านไฟล์ log บน node (Fluent Bit แบบ DaemonSet)แยกจากแอป ปรับเส้นทาง log ได้โดยไม่ต้อง restart container เป็นรูปแบบทั่วไปบน Kubernetesต้องดูแล agent และต้องแน่ใจว่ามี log rotation บน node
Sidecar ต่อ podจัดการ log ที่เขียนเป็นไฟล์ซึ่งแก้โค้ดไม่ได้เปลืองทรัพยากรต่อ pod และเพิ่มความซับซ้อน

เรื่องคำสั่ง docker logs กับ driver ที่ส่งออกระยะไกล รุ่นเก่าอ่านไม่ได้ แต่ Docker Engine ตั้งแต่ 20.10 มีฟีเจอร์ dual logging ที่เก็บสำเนาไว้ในเครื่องให้ด้วย ทำให้ docker logs ยังใช้งานได้ (ตรวจกับเอกสารของ version ที่ใช้)

มาตรฐานรูปแบบ log

มาตรฐานที่ควรตกลงกันมีไม่กี่ข้อ log ออกที่ stdout/stderr, หนึ่ง event ต่อหนึ่งบรรทัด, เป็น JSON, ใช้ชื่อ field เหมือนกันทุก service และเวลาใช้ ISO 8601 แบบ UTC ถ้าเขียน stack trace เป็นหลายบรรทัด Elasticsearch จะแตกเป็นหลาย event และค้นยาก ให้ใส่ stack trace เป็น field ใน JSON เดียวแทน

{"ts":"2026-11-14T12:03:21.482Z","level":"error","service":"payment-api","version":"1.4.2","env":"prod","trace_id":"4bf92f35","msg":"charge failed","error":"gateway timeout","duration_ms":3021}
Fieldทำไมต้องมี
ts, levelเรียงเหตุการณ์ และกรองตามความรุนแรง
service, version, envบอกว่ามาจากระบบไหน รุ่นไหน สภาพแวดล้อมใด ช่วยเมื่อต้องเทียบว่า bug เริ่มตอน release ไหน
trace_id / correlation idตาม request เดียวกันข้ามหลาย service
msg และ field เฉพาะเหตุการณ์ข้อความที่คนอ่านรู้เรื่อง และข้อมูลที่เครื่องค้นได้
สิ่งที่ห้ามอยู่ใน logpassword, token, ค่า header Authorization ดิบ, เลขบัตร และข้อมูลส่วนบุคคลที่ไม่จำเป็น ควรกำหนดไว้ในมาตรฐานและทำ filter ที่ชั้นเก็บ log ด้วย เพราะ log มักถูกเข้าถึงได้โดยคนมากกว่าฐานข้อมูลหลัก

Retention และต้นทุน

Log เป็นข้อมูลที่โตเร็วและแพง ควรกำหนดอายุการเก็บตามประเภทและกฎหมายที่เกี่ยวข้อง Elasticsearch มี Index Lifecycle Management (ILM) ใช้ย้ายข้อมูลเก่าไปเก็บแบบประหยัดและลบเมื่อครบอายุได้ตามนโยบาย ตัวเลขระยะเวลาที่ควรเก็บเป็นการตัดสินใจของแต่ละองค์กร ไม่มีค่ากลางที่ถูกสำหรับทุกที่

Image Scanning ด้วย Trivy

Advance

Competency: วาง image scanning ให้เป็นส่วนหนึ่งของ pipeline และ lifecycle ตั้ง gate ที่สมเหตุสมผล อ่านผลเป็น และจัดการ exception อย่างมีวินัย

Trivy ตรวจอะไรได้บ้าง

Trivy เป็นเครื่องมือ scan open source ที่ตรวจได้หลายเป้าหมายด้วย CLI เดียว คือ container image, filesystem หรือ repository, และไฟล์ configuration (Dockerfile, Kubernetes manifest, Terraform) และตรวจได้หลายเรื่อง ได้แก่ ช่องโหว่ที่รู้จักของ OS package และ library ของแอป, misconfiguration, secret ที่หลุดเข้าไป และ license การเลือกชนิดของการตรวจใช้ --scanners (ใน Trivy รุ่นเก่าเรียก --security-checks)

trivy image myorg/api:1.4.2                                  # scan image
trivy image --severity HIGH,CRITICAL myorg/api:1.4.2         # เฉพาะระดับสูง
trivy image --ignore-unfixed myorg/api:1.4.2                 # ซ่อนช่องโหว่ที่ยังไม่มี patch
trivy image --scanners vuln,secret myorg/api:1.4.2           # เลือกชนิดการตรวจ
trivy config .                                               # ตรวจ Dockerfile / IaC
trivy fs .                                                   # ตรวจ source และ lockfile
trivy image --format cyclonedx --output sbom.json myorg/api:1.4.2   # สร้าง SBOM

ทำเป็น gate ใน CI

จุดที่คนพลาดบ่อยคือ trivy คืน exit code 0 เสมอตามค่า default แม้เจอช่องโหว่ ผลคือ pipeline ผ่านทั้งที่ scan เจอ CRITICAL เต็มไปหมด ต้องใส่ --exit-code 1 ถึงจะทำให้ pipeline ล้มเมื่อเจอ และควรใช้ร่วมกับ --severity เพื่อบอกว่าระดับไหนที่ยอมให้ล้ม

IMAGE=registry.example.com/shop/api:$GIT_SHA
docker build -t "$IMAGE" .

# 1) สร้างรายงานเก็บไว้เสมอ (exit code ปกติ = 0)
trivy image --format json --output trivy-report.json "$IMAGE"

# 2) gate: ล้มเมื่อเจอ HIGH/CRITICAL ที่มีวิธีแก้แล้ว
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 "$IMAGE"

docker push "$IMAGE"

ทำไมต้อง --ignore-unfixed เพราะช่องโหว่ที่ยังไม่มี patch ทีมแอปแก้เองไม่ได้ การให้ pipeline ล้มเพราะเรื่องนี้ทำให้ทีมเจอ gate ที่ผ่านไม่ได้ และเริ่มหาทางเลี่ยง แต่ก็ไม่ควรมองข้ามไปเลย ต้องมีการดูรายการเหล่านี้เป็นระยะและติดตามว่ามี patch ออกมาเมื่อไร

Scan ครั้งเดียวตอน build ไม่พอ

image ที่ผ่านการ scan วันนี้ อาจมี CVE ใหม่ถูกประกาศเกี่ยวกับ package ในนั้นพรุ่งนี้ โดยตัว image ไม่ได้เปลี่ยนเลย เพราะฐานข้อมูลช่องโหว่ถูกอัปเดตตลอด จึงต้อง scan ซ้ำเป็นระยะกับ image ที่อยู่ใน registry และที่รันอยู่จริง (ตัว Trivy มี Trivy Operator สำหรับตรวจใน Kubernetes cluster) และต้องมีกระบวนการรับมือเมื่อ image ที่ deploy ไปแล้วถูกพบช่องโหว่ใหม่ ว่าใครรับผิดชอบ build ใหม่ภายในเวลาเท่าไร ตามที่องค์กรกำหนด

อ่านผลและ triage

ตารางผลของ Trivy บอกว่า package ไหน เวอร์ชันที่ติดตั้ง เวอร์ชันที่แก้แล้ว (fixed version) รหัส CVE และระดับความรุนแรง สิ่งที่ต้องถามต่อคือ: แก้ได้ด้วยการอัปเดต base image หรือไม่ ช่องโหว่อยู่ใน package ที่แอปใช้จริงหรือเป็นเครื่องมือ build ที่ควรไม่ได้อยู่ใน image สุดท้ายด้วยซ้ำ (ถ้าใช่ แก้ด้วย multi-stage) และการถูกโจมตีเป็นไปได้ในบริบทของเราหรือไม่ ระดับ severity ใน CVE มาจากการประเมินแบบทั่วไป ไม่ได้บอกความเสี่ยงของระบบเราโดยตรง แต่ก็เป็นจุดเริ่มต้นที่ใช้ได้

เมื่อต้องยอมรับความเสี่ยงชั่วคราว ใช้ไฟล์ .trivyignore ระบุรหัส CVE ที่ยกเว้น ควรใส่เหตุผล ผู้รับผิดชอบ และวันที่ต้องกลับมาทบทวน ไม่งั้นรายการยกเว้นจะสะสมและไม่มีใครรู้ว่าทำไมถึงอยู่

สิ่งที่ scan ไม่ได้บอก

ผล scan สะอาดไม่ได้แปลว่า image ปลอดภัย มันแปลว่าไม่พบช่องโหว่ ที่เป็นที่รู้จักและอยู่ในฐานข้อมูลของ scanner เท่านั้น ไม่ครอบคลุม logic bug ในโค้ดของเราเอง การตั้งค่าผิด หรือช่องโหว่ที่ยังไม่มีใครรายงาน ความครอบคลุมยังแตกต่างกันตามชนิดของ image เช่น binary ที่ถูก compile แบบ static ใน image ที่ไม่มี package manager ต้องอาศัยข้อมูลในไฟล์ binary หรือ SBOM ที่ฝังไว้ จึงควรใช้ scan ควบคู่กับมาตรการอื่น ไม่ใช่แทนที่

จำไว้สอบ--exit-code 1 ทำให้ pipeline ล้มเมื่อเจอ (default คือ 0) • --ignore-unfixed ซ่อนที่ยังไม่มี patch • trivy config ตรวจ Dockerfile/IaC • ต้อง rescan image ที่ปล่อยไปแล้วเพราะ CVE ใหม่ออกทุกวัน • ผล scan สะอาด ไม่เท่ากับปลอดภัย

ทำให้ทีมยอมรับ

การนำมาตรฐานใหม่มาใช้ ควรเริ่มด้วยการเลือกสองสามทีมเป็น pilot, เปิดแบบ audit ก่อน, เก็บ feedback แล้วปรับกฎ จึงค่อยขยายและเปลี่ยนเป็น enforce การบันทึกเหตุผลการตัดสินใจของมาตรฐานไว้ใน ADR (Architecture Decision Record) ช่วยให้รู้ว่าทำไมถึงเลือกแบบนี้เมื่อต้องทบทวนในอนาคต และมาตรฐานเองก็ต้องมีรอบทบทวน เพราะ tool และภัยคุกคามเปลี่ยนตลอด

จำไว้สอบมาตรฐานต้องมีกลไกตรวจอัตโนมัติ • Golden image มีเจ้าของและรอบอัปเดต • Tag ไม่แก้ทับและไม่ใช้ latest ใน production • ให้ทางที่ถูกเป็นทางที่ง่ายที่สุด และมีกระบวนการขอยกเว้นที่หมดอายุได้

Part C สถานการณ์ (ลองตอบเองก่อนเปิดดู)

C1. API ใน staging ถูกสตาร์ตใหม่ทุก 2-3 ชั่วโมง docker ps -a เห็น exit code 137 จะหาสาเหตุอย่างไร

137 คือ 128 + 9 แปลว่าโดน SIGKILL ซึ่งมีสาเหตุหลักสองทาง คือมีคนหรือระบบสั่ง kill หรือโดน OOM killer เพราะใช้ memory เกิน limit ผมจะไล่ตามนี้

  1. เช็ก docker inspect api --format '{{.State.OOMKilled}}' ถ้าได้ true จบที่ OOM ได้เลย
  2. เทียบ --memory ที่ตั้งไว้กับการใช้จริงจาก docker stats หรือ metrics ย้อนหลัง ดูว่า memory ไต่ขึ้นเรื่อยๆ ก่อนตาย (สัญญาณ memory leak) หรือพุ่งตอนมีงานบางประเภท
  3. ดู docker events และ log ของ host ว่ามี OOM ระดับ kernel หรือมี process อื่นสั่ง kill หรือไม่
  4. ถ้าเป็น Node.js หรือ JVM ตรวจว่า heap limit ของ runtime ถูกตั้งให้สัมพันธ์กับ memory limit ของ container หรือยัง ไม่งั้น runtime อาจคิดว่ามี memory มากกว่าที่ cgroup ให้จริง

การแก้ขึ้นกับสาเหตุ ถ้า limit ต่ำเกินจริงก็เพิ่มตามข้อมูลที่วัด ถ้ามี leak ก็ต้องแก้ที่แอป การเพิ่ม limit อย่างเดียวแค่ยืดเวลาก่อนตายออกไป

C2. Security สั่งว่า image ที่มี CRITICAL ห้ามขึ้น production แต่ทีมแอปบอกว่า base image ยังไม่มี patch คุณในฐานะ lead จะจัดการอย่างไร

เรื่องนี้คือการหาจุดสมดุลระหว่างนโยบายกับความเป็นจริง ผมจะแยกสถานการณ์ก่อนว่า CRITICAL ที่เจอ มี fixed version หรือยัง

  1. ถ้ามี fix แล้ว นโยบายห้ามผ่านยังถูกต้อง ทีมต้องอัปเดต base หรือ package แล้ว build ใหม่
  2. ถ้ายังไม่มี fix ให้ประเมินว่า package นั้นถูกใช้จริงไหม และถูกโจมตีได้ในบริบทของเราหรือไม่ ถ้าเป็นเครื่องมือที่ไม่จำเป็นตอนรัน ให้ตัดออกด้วย multi-stage หรือเปลี่ยน base เป็นแบบที่เล็กกว่า
  3. ถ้าต้องปล่อยไปก่อน ใช้กระบวนการ exception ที่มีเจ้าของ เหตุผล มาตรการลดความเสี่ยงชั่วคราว (เช่นจำกัด network, ตรวจจับเพิ่ม) และวันหมดอายุ โดย security เป็นผู้อนุมัติ
  4. ตั้งการแจ้งเตือนให้ rescan เมื่อมี patch ออก และบันทึกใน ADR หรือ ticket เพื่อไม่ให้ exception ถูกลืม

สิ่งที่ไม่ควรทำคือปิด gate ของทั้งองค์กรหรือเปลี่ยน exit code เป็น 0 เพราะทำให้นโยบายใช้ไม่ได้กับทุกคน

C3. ต้องย้าย monolith ที่รันบน VM 3 เครื่องเข้า container ภายใน 1 quarter และยอมให้ downtime ได้น้อยมาก จะวางแผนอย่างไร

ผมจะแบ่งเป็นเฟสและกำหนดเกณฑ์ออกของแต่ละเฟสให้ชัด

  1. Assess: ทำ inventory ว่าแอปเขียนไฟล์ที่ไหน เก็บ session ที่ไหน config มาจากไหน ต่อระบบอะไรบ้าง ส่วนไหนผูกกับเครื่องเดิม
  2. Replatform ส่วนที่จำเป็น: ย้าย session ไป Redis, ไฟล์อัปโหลดไป object storage, log ออก stdout, config เป็น environment และเพิ่ม health endpoint กับการจัดการ SIGTERM
  3. Containerize และ CI: เขียน Dockerfile แบบ multi-stage, ตั้ง pipeline build, scan, push แล้วทดสอบรันบน staging ที่มีข้อมูลใกล้เคียงจริง
  4. รันคู่ขนาน: ให้ container ชุดใหม่รับ traffic บางส่วน (canary หรือ weighted routing) ขณะที่ VM เดิมยังทำงาน เทียบ error rate และ latency
  5. Cutover และ rollback: เพิ่มสัดส่วนจนครบ เก็บ VM เดิมไว้พร้อมสลับกลับในช่วงเฝ้าระวัง ฐานข้อมูลเปลี่ยน schema แบบ expand/contract เพื่อให้ถอยแอปได้
  6. Decommission: ปลด VM เมื่อผ่านช่วงเฝ้าระวังและมี runbook ที่ทีม on-call ซ้อมแล้ว

ความเสี่ยงที่ต้องบอก stakeholder ตั้งแต่ต้นคือ state ที่ซ่อนอยู่ในเครื่องเดิม และความพร้อมของทีมกับเครื่องมือใหม่ ซึ่งอาจทำให้ 1 quarter ตึงถ้าแอปมีส่วนที่ผูกกับเครื่องมาก

Part D ลงมือเขียน (แนว hands-on)

D1. Dockerfile นี้มีปัญหาอะไรบ้าง และเขียนใหม่ให้ถูกต้อง 
FROM node:latest
COPY . /app
WORKDIR /app
ENV API_TOKEN=abc123secret
RUN npm install
EXPOSE 3000
CMD npm start

ปัญหาที่ควรเจอ: ใช้ latest ทำให้ build ซ้ำไม่ได้ • COPY . . ก่อนติดตั้ง dependency ทำให้ cache เสียทุกครั้งที่แก้โค้ด และไม่มี .dockerignore จึงอาจมี .env หรือ node_modules เข้าไป • ฝัง token ด้วย ENV ใครได้ image ก็เห็น • ติดตั้ง dev dependency เข้า production • รันด้วย root • CMD npm start เป็น shell form และผ่าน npm ทำให้ signal ไปไม่ถึงแอปโดยตรง

FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --chown=10001:10001 . .
USER 10001:10001
EXPOSE 3000
CMD ["node", "server.js"]

ส่วน token ส่งตอนรันผ่านตัวแปรหรือ secret ของ platform ไม่ใส่ใน image และเพิ่ม .dockerignore ที่ตัด .env, .git, node_modules

D2. เขียน compose สำหรับ api และ redis โดยให้เฉพาะ api เปิด port ออกภายนอก redis ต้องมี healthcheck และเก็บข้อมูลใน volume 
services:
  api:
    image: myorg/api:1.4.2
    ports:
      - "8080:3000"
    environment:
      REDIS_URL: redis://cache:6379
    depends_on:
      cache:
        condition: service_healthy
    networks: [appnet]
  cache:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [appnet]
networks:
  appnet:
volumes:
  redis-data:

จุดที่ต้องเห็น: cache ไม่มี ports จึงเข้าถึงได้เฉพาะจาก service ใน network เดียวกัน, api เรียกด้วยชื่อ service cache, ใช้ service_healthy ไม่ใช่แค่ depends_on ธรรมดา, และ named volume ทำให้ข้อมูลอยู่รอดเมื่อลบ container

D3. เขียนขั้นตอน CI ที่ build image, เก็บรายงาน scan ไว้เสมอ, ล้ม pipeline เมื่อเจอ HIGH หรือ CRITICAL ที่มี patch แล้ว และ push เมื่อผ่านเท่านั้น 
set -euo pipefail
IMAGE="registry.example.com/shop/api:${GIT_SHA}"

docker build -t "$IMAGE" .

# รายงานเก็บเป็น artifact (ไม่ทำให้ pipeline ล้ม)
trivy image --format json --output trivy-report.json "$IMAGE"

# gate
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 "$IMAGE"

# มาถึงตรงนี้ได้เมื่อ gate ผ่าน
docker push "$IMAGE"

เหตุผล: ค่า default ของ --exit-code คือ 0 จึงต้องสั่งเองจึงจะล้ม • แยกรายงานกับ gate เป็นสองคำสั่งเพื่อให้ได้ไฟล์รายงานแม้ gate ล้ม (ใน CI จริงต้องให้ขั้นตอนอัปโหลดรายงานทำงานแม้ขั้นตอนก่อนหน้าล้ม) • set -e ทำให้ docker push ไม่ถูกรันถ้า scan ล้ม • ใช้ git SHA เป็น tag เพื่อให้ย้อนกลับไปหา commit ได้

ข้อสอบรวม ทบทวนทุกหัวข้อ

ชุดนี้สุ่มจากคลังข้อสอบของทุกหัวข้อรวมกับโจทย์สถานการณ์และข้อสอบสไตล์ Deloitte เลือกคำตอบแล้วเฉลยทันทีพร้อมคำอธิบาย กดสุ่มชุดใหม่ได้เรื่อย ๆ ตัวเลือกจะถูกสลับตำแหน่งทุกครั้ง

อ่านทวนสั้น ๆ ก่อนลงมือ

BeginnerContainer ใช้ kernel ของ host ร่วมกัน • Tag ย้ายได้ ส่วน digest ไม่เปลี่ยน • เรียง layer จากของที่เปลี่ยนน้อยไปมาก • EXPOSE ไม่เปิด port • Exit 137 คือ SIGKILL มักเป็น OOM • Compose ใช้ชื่อ service เป็น hostname และต้องมี healthcheck ถ้าต้องรอให้พร้อม
IntermediateDNS ตามชื่ออยู่ใน user-defined network • ไม่ต้อง publish port ถ้าแค่ container คุยกัน • Volume สำหรับข้อมูลที่ต้องอยู่รอด • ปัญหาสิทธิ์ไฟล์มาจาก UID • รันไม่ใช่ root, drop capability, read-only, ไม่ฝัง secret • Migration ต้องมีเกณฑ์ออกและแผน rollback
AdvancePSA มี enforce/audit/warn และ privileged/baseline/restricted • เริ่ม policy จาก audit • json-file ต้องตั้ง max-size • log เป็น JSON หนึ่งบรรทัดต่อ event • Trivy ต้องใส่ --exit-code 1 ถึงจะล้ม • ต้อง rescan image ที่ปล่อยไปแล้ว • มาตรฐานต้องมีกลไกตรวจและทางขอยกเว้น
