เริ่มจากตัวอย่างเดียวกันตลอดทั้งหน้า

สมมติบริษัทมีระบบ Payslip ที่ต้องทำสี่อย่าง คือ Employee Service เก็บข้อมูลพนักงานและสถานะการจ้างงาน, Payslip Service เก็บและแสดงสลิปตามสิทธิ์ของผู้ใช้, Notification Service ส่งอีเมลหรือ push เมื่อสลิปพร้อม และ Tenant Service เก็บค่าตั้งของแต่ละบริษัท เช่น รอบจ่ายเงินกับภาษา

เส้นทึบคือการเรียกกันตรง ๆ ส่วนช่วง Payslip → broker → Notification เป็น event ที่ส่งแบบ asynchronous

การแบ่งแบบนี้เป็นแค่ ตัวอย่าง ไม่ใช่สูตรตายตัว ถ้าทีมเล็กและงานยังไม่เยอะ ทำเป็น Modular Monolith ก้อนเดียวอาจเหมาะกว่า

ลองไล่ลำดับตอน HR กดเผยแพร่ Payslip

  1. HR ส่ง POST /payslips/{id}/publish ไปที่ Payslip Service
  2. Payslip Service ตรวจสิทธิ์ผู้ใช้และสถานะของสลิป
  3. บันทึกสถานะ PUBLISHED ลงฐานข้อมูลของตัวเอง
  4. สร้าง event PayslipPublished เพื่อแจ้ง service อื่น
  5. Notification Service รับ event แล้วส่งอีเมล

Monolith, Modular Monolith และ Microservices

ลองนึกถึงร้านอาหารที่เจ้าของทำเองทุกอย่าง พอลูกค้าเยอะก็ติดคอขวดที่เจ้าของคนเดียว ถ้าแยกเป็นครัว แคชเชียร์ และส่งอาหาร แต่ละฝ่ายก็เก่งขึ้น แต่ถ้าทุกครั้งที่คุยกันต้องเดินส่งกระดาษ งานอาจช้ากว่าเดิม นี่คือทั้งข้อดีและต้นทุนของการแยก service

เรื่องModular MonolithMicroservices
การเรียกข้าม moduleเรียก function หรือ interface ใน process เดียวกันHTTP, gRPC หรือ message ข้าม network
การ deployส่วนใหญ่ deploy พร้อมกันทั้งก้อนdeploy แยกกันได้
ข้อมูลอาจใช้ DB เดียว แยกเป็น module หรือ schemaควรกำหนดว่าใครเป็นเจ้าของข้อมูลแต่ละชุด
การ debugตาม stack trace ได้ง่ายกว่าต้องมี correlation ID และ distributed tracing
ความล้มเหลวเกิดใน process เดียวเป็นหลักมี timeout, partial failure, eventual consistency
เหมาะกับทีมเล็ก โดเมนยังเปลี่ยนบ่อยโดเมนชัด ทีมหลายทีม ต้อง scale หรือ deploy อิสระ
ความเข้าใจผิดที่เจอบ่อยMicroservices ไม่ได้เร็วกว่า monolith เสมอไป การคุยข้าม service ผ่าน network ทำให้ช้าลงและดูแลยากขึ้น ส่วน monolith ที่แบ่ง module ดี ๆ ก็ยังเป็น monolith

Loosely coupled หมายถึงอะไร

Coupling คือการที่ส่วนหนึ่งของระบบต้องรู้รายละเอียดของอีกส่วนมากแค่ไหน ถ้า Notification Service ไปอ่านตารางข้างในของ Payslip Service ตรง ๆ พอ Payslip เปลี่ยน schema ฝั่ง Notification ก็พัง และยังข้ามเส้นความเป็นเจ้าของข้อมูลไปด้วย

// ไม่เหมาะ: Notification Service อ่านตารางภายในของ Payslip Service โดยตรง
const payslip = await payslipDatabase.payslips.findUnique({ where: { id } });

// เหมาะกว่า: รับข้อมูลตามสัญญา (event contract) ที่ตกลงกัน
interface PayslipPublishedV1 {
  eventId: string;
  eventType: 'PayslipPublished';
  occurredAt: string;
  payload: { payslipId: string; employeeId: string; tenantId: string };
}

แบบหลังรู้แค่ว่า event มี field อะไรบ้าง ไม่ต้องรู้ว่าตารางใน DB ของอีกฝั่งหน้าตาเป็นอย่างไร แต่ ใช้ event ไม่ได้แปลว่า loosely coupled เสมอไป ถ้า consumer ไปพึ่ง field ภายในเยอะเกินไป หรือ producer เปลี่ยน schema โดยไม่ดู compatibility สองฝั่งก็ยังผูกกันอยู่ดี

ก่อนเลือก Microservices ให้ตอบสี่คำถามนี้

  1. แบ่งความรับผิดชอบตาม business domain ได้ชัดแล้วหรือยัง
  2. มีเหตุผลให้ deploy หรือ scale แยกกันจริงหรือไม่
  3. ทีมพร้อมเรื่อง CI/CD, monitoring, tracing, security และ incident response หรือยัง
  4. ยอมรับความซับซ้อนของ network, retry, data consistency และการ debug ได้หรือไม่

ถ้าตอบว่า “ยัง” หลายข้อ ให้เริ่มจาก Modular Monolith ก่อน แล้วค่อยแยก service เมื่อมีเหตุผลทางธุรกิจจริง ๆ

ขอบเขตของ service ควรตัดตรงไหน

service หนึ่งตัวควรดูแล business capability ที่มีความหมายในตัวเอง เช่น Payslip ไม่ใช่แยกเป็น GetPayslipService, UpdatePayslipService, DeletePayslipService แค่เพราะ HTTP method ต่างกัน อีกเรื่องคือ service ไม่จำเป็นต้องเขียนคนละภาษา สิ่งที่ควรได้จริงคือ deploy และ scale แยกกันได้ ส่วนจำนวน service ไม่ใช่เป้าหมาย

คำถามสัมภาษณ์: “ทำไมไม่แยกระบบ Payslip เป็น 20 services”คำตอบที่ดีคือ จำนวน service ไม่ใช่เป้าหมาย ต้องดู business boundary, ทีมที่เป็นเจ้าของ, ต้นทุนของ network และการดูแลระบบ, ความสอดคล้องของข้อมูล และความถี่ในการ deploy

// payslips.service.ts  (ข้อมูล in-memory ไว้สอน request flow ไม่ใช่โค้ด production)
import { Injectable, NotFoundException, ForbiddenException } from '@nestjs/common';

type Payslip = { id: string; employeeId: string; netPay: number };

@Injectable()
export class PayslipsService {
  private readonly items: Payslip[] = [
    { id: 'PS-100', employeeId: 'EMP-01', netPay: 35000 },
    { id: 'PS-101', employeeId: 'EMP-02', netPay: 42000 },
  ];

  getForEmployee(id: string, authenticatedEmployeeId: string): Payslip {
    const slip = this.items.find((x) => x.id === id);
    if (!slip) throw new NotFoundException('Payslip not found');
    if (slip.employeeId !== authenticatedEmployeeId) {
      throw new ForbiddenException('Cannot read another employee payslip');
    }
    return slip;
  }
}
// payslips.controller.ts  (โครงสำหรับอธิบายตำแหน่ง Guard ต้องสร้าง JwtAuthGuard จริงเอง)
@Controller('payslips')
export class PayslipsController {
  constructor(private readonly payslips: PayslipsService) {}

  @Get(':id')
  @UseGuards(JwtAuthGuard)
  findOne(@Param('id') id: string, @Req() req: { user: { employeeId: string } }) {
    return this.payslips.getForEmployee(id, req.user.employeeId);
  }
}
อย่าเชื่อ employeeId ที่ client ส่งมาตัวตนของผู้เรียกต้องมาจาก token ที่ server ตรวจแล้ว (req.user) ไม่ใช่จาก query string, body หรือ header ที่ client ตั้งเองได้
GET /payslips/PS-100
   ↓ Auth Guard ตรวจ Bearer token และสร้าง req.user
   ↓ Controller รับ id จาก URL
   ↓ Service ค้นข้อมูลและตรวจเจ้าของสลิป

ถามว่าทำไมแค่ซ่อนปุ่มบน frontend ถึงไม่ใช่ authorization ก็เพราะผู้ใช้ยังยิง HTTP request ตรง ๆ ได้ จึงต้องตรวจสิทธิ์ที่ backend ทุกครั้ง ส่วนการเปลี่ยน ID เป็น UUID แค่ทำให้เดายากขึ้น ไม่ได้แก้ปัญหา (ช่องโหว่แบบนี้เรียกว่า IDOR หรือ BOLA)

async function fetchEmployee(employeeId: string): Promise<EmployeeResponse> {
  const url = `https://employee.internal/v1/employees/${encodeURIComponent(employeeId)}`;
  let response: Response;

  try {
    response = await fetch(url, {
      headers: { Accept: 'application/json' },
      signal: AbortSignal.timeout(3000), // กำหนด timeout เสมอ
    });
  } catch {
    // timeout, DNS, connection reset หรือ network ล้มเหลว
    throw new DependencyUnavailableError('Employee Service unavailable');
  }

  if (response.status === 404) throw new Error('Employee not found');
  if (!response.ok) throw new DependencyUnavailableError(`HTTP ${response.status}`);

  const body: unknown = await response.json();
  if (
    typeof body !== 'object' || body === null ||
    !('id' in body) || !('status' in body) ||
    typeof body.id !== 'string' ||
    (body.status !== 'ACTIVE' && body.status !== 'INACTIVE')
  ) {
    throw new DependencyUnavailableError('Unexpected Employee response');
  }
  return { id: body.id, status: body.status };
}

retry เฉพาะกรณีที่ลองซ้ำแล้วมีโอกาสหายและไม่เสียหาย เช่น GET ที่ timeout หรือ 503 โดยจำกัดจำนวนครั้งและเว้นระยะ อย่า retry 400, 401, 403 เพราะลองกี่ทีผลก็เหมือนเดิม และอย่า retry ธุรกรรมที่ไม่ idempotent ถ้ายังไม่มีวิธีกันข้อมูลซ้ำ

HTTP methodSafeIdempotentหมายเหตุ
GET, HEADใช่ใช่อ่านอย่างเดียว retry ได้
PUT, DELETEไม่ใช่ส่งซ้ำแล้ว state สุดท้ายเหมือนเดิม
POSTไม่ไม่ต้องมี Idempotency-Key ถึงจะ retry ได้อย่างปลอดภัย
PATCHไม่ขึ้นกับวิธีเขียน“ตั้งค่า status = paid” idempotent แต่ “บวกยอดเพิ่ม 100” ไม่ใช่
// retry แบบมีขอบเขต: exponential backoff + jitter (รับ sleep เข้ามาเพื่อให้ test ได้โดยไม่ต้องรอจริง)
async function withRetry<T>(
  fn: () => Promise<T>,
  { attempts = 3, baseMs = 200, sleep = (ms: number) => new Promise((r) => setTimeout(r, ms)) } = {},
): Promise<T> {
  let lastError: unknown;
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      if (!(err instanceof DependencyUnavailableError) || i === attempts - 1) break;
      const delay = baseMs * 2 ** i * (0.5 + Math.random() / 2); // jitter กันทุก client ยิงพร้อมกัน
      await sleep(delay);
    }
  }
  throw lastError;
}

// Middleware เพิ่ม x-request-id (แสดงหลักการ ไม่ใช่ระบบ tracing เต็มรูปแบบ)
@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    // production ควรตรวจรูปแบบและความยาว header จาก client ก่อนเชื่อถือ
    const supplied = req.header('x-request-id');
    const requestId = supplied && /^[a-zA-Z0-9._-]{1,64}$/.test(supplied)
      ? supplied
      : randomUUID();
    res.setHeader('x-request-id', requestId);
    req.headers['x-request-id'] = requestId;
    next();
  }
}

  2. ลอง insert eventId ที่มี unique constraint (INSERT ... ON CONFLICT DO NOTHING)
  3. ถ้าเคยมีแล้ว ข้ามงานและ ACK message
  4. ถ้ายังไม่เคย ทำงานภายใน DB ของตัวเองแล้ว commit
  5. ACK broker หลัง commit สำเร็จเท่านั้น
ข้อจำกัดที่ต้องพูดให้ได้การจดว่าทำแล้วกับการส่งอีเมลไป provider เป็นคนละระบบกัน DB transaction เดียวรับประกัน “ส่งอีเมลครั้งเดียว” ไม่ได้ ต้องใช้ idempotency key ของ provider (ถ้ามี), state machine อย่าง PENDING → SENT และ reconciliation เสริม อย่าอ้างว่า exactly-once แบบ end-to-end ถ้ายังไม่มีมาตรการครบ

Retry, Dead Letter Queue และ Poison Message

การจัดการ error ต้องแยกชนิดก่อน error ชั่วคราว (transient) เช่น provider ตอบ 503 ให้ retry พร้อม backoff และ jitter ส่วน error ถาวร (permanent) เช่น payload ขาด field สำคัญ ลองซ้ำก็ไม่หาย ควรส่งเข้า DLQ (dead letter queue) ซึ่งเป็นที่เก็บ message ที่ประมวลผลไม่สำเร็จหลังลองครบตามนโยบาย เพื่อตรวจสอบภายหลัง ถ้าไม่มี DLQ message ที่ทำให้ consumer ล้มซ้ำ ๆ (poison message) จะขวางคิวทั้งหมด

// โครง consumer ที่ idempotent (แนวคิด ต้องมี DB และ broker client จริง)
async function handle(msg: { eventId: string; payload: PayslipPublishedV1['payload'] }) {
  await db.transaction(async (tx) => {
    const inserted = await tx.insertProcessedEvent('notification-email', msg.eventId); // false ถ้ามีแล้ว
    if (!inserted) return;                       // ซ้ำ: ข้าม
    await tx.createNotification(msg.payload);    // สถานะ PENDING
  });
  // ACK หลัง commit; ส่งอีเมลจริงโดย worker อีกตัวที่ใช้ idempotency key ของ provider
}
คำถามที่ชอบออก: “Queue แก้ปัญหา consistency ทั้งหมดไหม”ไม่ เพราะ consumer มักเห็นข้อมูลช้ากว่า producer และ event อาจซ้ำหรือมาผิดลำดับ ต้องออกแบบให้ระบบรับได้ ไม่ใช่หวังให้ queue ซ่อนปัญหาไว้ให้

หลักสำคัญคือ แต่ละ service เป็นเจ้าของข้อมูลของตัวเอง Employee Service ดูแล employees, Payslip Service ดูแล payslips และ payslip_items, Notification Service ดูแล notifications และ delivery_attempts ถ้า service อื่นอยากได้ข้อมูล ให้ขอผ่าน API หรือ event ไม่ใช่ไปเขียนตารางของคนอื่นตรง ๆ

Database per Serviceประเด็นคือแยก ความเป็นเจ้าของ schema และสิทธิ์เข้าถึง ไม่จำเป็นต้องแยก database server ตั้งแต่วันแรก ช่วงแรกจะใช้ schema หรือ user แยกกันบน PostgreSQL ตัวเดียวก็ได้ แต่ห้ามให้ service อื่นเขียนตารางที่ตัวเองไม่ได้เป็นเจ้าของ

Payslip อยากแสดงชื่อพนักงาน ทำอย่างไร

ทางเลือกข้อดีข้อเสียเหมาะเมื่อ
1. เรียก Employee API ตอนต้องใช้ข้อมูลสดที่สุดเพิ่ม latency และ dependencyต้องการชื่อปัจจุบันเสมอ
2. เก็บ snapshot ชื่อไว้ในสลิปเร็ว ไม่พึ่ง service อื่นไม่ตามชื่อใหม่ชื่อบนสลิปต้องเป็น ณ วันจ่ายเงิน

ทำไม distributed transaction ถึงยาก

1. UPDATE Payslip DB      สำเร็จ
2. POST Notification      ล้มเหลว (network error)
→ สลิป PUBLISHED แล้ว แต่ยังไม่มี notification

ถ้า business ยอมให้ส่งทีหลังได้ ใช้ event + retry ก็พอ ถ้าต้องสำเร็จทั้งชุดหรือย้อนกลับเป็นขั้น ๆ ให้ดู Saga (หัวข้อ 10) ส่วน two-phase commit (2PC) ข้ามหลายระบบมักไม่เหมาะ เพราะล็อกทรัพยากรนานและต้องพึ่ง coordinator ตัวเดียว

Transactional Outbox: กัน “ข้อมูลสำเร็จแต่ event หาย”

ปัญหาคือ ถ้า update DB สำเร็จแล้ว process ล่ม ก่อน publish event จะไม่มีใครรู้ว่าต้องส่งอีเมล แนวคิดของ outbox คือเขียน business data กับ outbox event ลงใน transaction เดียวกัน แล้วให้ worker อีกตัวมาอ่านไปส่งเข้า broker ทีหลัง

// ตัวอย่างแนวคิดด้วย Prisma (สมมติมี model payslip และ outboxEvent)
async function publishPayslip(prisma: PrismaClient, payslipId: string) {
  return prisma.$transaction(async (tx) => {
    const slip = await tx.payslip.update({
      where: { id: payslipId },
      data: { status: 'PUBLISHED' },
    });
    await tx.outboxEvent.create({
      data: {
        id: crypto.randomUUID(),
        eventType: 'PayslipPublished',
        aggregateId: slip.id,
        payload: { payslipId: slip.id, employeeId: slip.employeeId },
        status: 'PENDING',
      },
    });
    return slip;
  });
}

ลองไล่เคสความล้มเหลวทีละจุด ถ้าเขียน payslip สำเร็จแต่เขียน outbox ไม่สำเร็จ transaction จะ rollback ทั้งคู่ ถ้า commit แล้วแต่ relay ยังไม่ได้ส่ง outbox ยังเก็บไว้ให้ retry ได้ ถ้า relay ส่ง event ไปแล้วแต่ล่มก่อน mark ว่าส่งแล้ว event อาจถูกส่งซ้ำ consumer จึงต้อง idempotent อีกวิธีที่ให้ผลคล้ายกันคือ CDC (change data capture) ที่อ่านจาก transaction log ของ DB แล้วส่งเป็น event เช่น Debezium

โค้ดนี้แค่แสดงแนวคิด ก่อนใช้จริงต้องมี schema, import และ business validation เช่น ห้าม publish ซ้ำตาม requirement ถ้ามี relay หลายตัว ต้องมีวิธี claim แถว เช่น FOR UPDATE SKIP LOCKED จะได้ไม่ส่งงานเดียวกันพร้อมกัน

{

Security: OAuth2, JWT, mTLS และ Zero Trust

Intermediate

เกณฑ์: Ensure robust security using advanced authentication/authorization protocols (e.g., OAuth2, JWT, mutual TLS) and zero-trust principles

Authentication ไม่เท่ากับ Authorization

Authentication คือการยืนยันว่าผู้เรียกเป็นใคร ส่วน Authorization คือการเช็กว่าคนนี้ทำสิ่งนี้กับข้อมูลชิ้นนี้ได้ไหม ผู้ใช้ login ผ่านแล้วแต่ขอดู payslip ของคนอื่น ต้องได้ 403 Forbidden (หรือจะซ่อนว่า resource นั้นมีอยู่จริงก็ได้ตามนโยบายของระบบ)

OAuth2, OpenID Connect, JWT, mTLS, Zero Trust

คำใช้ทำอะไรตัวอย่าง
OAuth 2.0framework สำหรับมอบสิทธิ์เข้าถึง resourceClient Credentials ระหว่าง service, Authorization Code + PKCE สำหรับผู้ใช้
OpenID Connectชั้นยืนยันตัวตนบน OAuth2login ผ่าน identity provider ได้ ID token
JWTรูปแบบ token ที่ลงลายเซ็นได้access token ที่มี iss, aud, exp, scope
mTLSให้ทั้ง client และ server แสดง certificate ให้กันเข้ารหัสและยืนยันตัวตนระดับ connection
Zero Trustไม่เชื่อเพียงเพราะอยู่ใน network ภายในตรวจ identity และ permission ทุกการเข้าถึง
สองข้อที่สับสนบ่อยOAuth2 ไม่เท่ากับ JWT เพราะ OAuth2 ใช้ opaque token ก็ได้ และ JWT ที่ลงลายเซ็น (JWS) ไม่ได้ซ่อนเนื้อหา ใครได้ token ไปก็ decode payload อ่านได้ ลายเซ็นกันแค่การแก้ไข ไม่ได้เข้ารหัส

แหล่งอ้างอิง: OAuth 2.0 Security Best Current Practice (RFC 9700, BCP 240, เผยแพร่มกราคม 2025) กำหนดให้ public client ต้องใช้ PKCE กับ authorization code grant และแนะนำให้เลี่ยง implicit grant ที่ส่ง access token กลับมาใน authorization response ส่วน confidential client เอกสารนี้แนะนำให้ใช้ PKCE เช่นกัน

Service-to-service ด้วย Client Credentials

Reporting Service → Authorization Server : ขอ access token (client credentials)
Authorization Server → Reporting Service : access token + scope
Reporting Service → Payslip Service      : GET /reports  + Bearer token
Payslip Service                          : ตรวจ signature, iss, aud, exp, scope
Payslip Service → Reporting Service      : 200 เฉพาะข้อมูลที่มีสิทธิ์

สิ่งที่ resource server ต้องตรวจเมื่อรับ JWT access token มีหกข้อ: (1) ลายเซ็นถูกต้อง จาก key ที่เชื่อถือได้ (2) iss เป็นผู้ออกที่ยอมรับ (3) aud ระบุ API นี้ (4) exp และ nbf อยู่ในช่วงที่ใช้ได้ (5) scope หรือ role ตรงกับ endpoint (6) ตรวจ tenant และ resource-level authorization แยกอีกชั้น

// ตัวอย่างตรวจ JWT ด้วยไลบรารี jose (แนวคิด ปรับตาม identity provider ของจริง)
import { createRemoteJWKSet, jwtVerify } from 'jose';

const JWKS = createRemoteJWKSet(new URL('https://idp.example.com/.well-known/jwks.json'));

export async function verifyAccessToken(token: string) {
  const { payload } = await jwtVerify(token, JWKS, {
    issuer: 'https://idp.example.com/',
    audience: 'payslip-api',
    algorithms: ['RS256'],      // จำกัดอัลกอริทึมที่ยอมรับ
    clockTolerance: 5,          // เผื่อนาฬิกาเคลื่อนเล็กน้อย (วินาที)
  });
  return payload;               // ตรวจ scope และ tenant ต่อใน Guard หรือ policy
}
อย่าทำแค่ decode() JWT แล้วเชื่อ payload เลยโดยไม่ตรวจ signature, ใช้ secret เดียวกันทุก service โดยไม่มีเหตุผล หรือรับ token ที่ aud เป็นของ service อื่น (ลายเซ็นถูกแต่ไม่ได้ออกให้ API นี้ ต้องปฏิเสธ)

mTLS แก้อะไรและยังไม่พอเรื่องอะไร

mTLS คือให้ server ตรวจ certificate ของ client และ client ตรวจ certificate ของ server ช่วยพิสูจน์ตัวตนระดับ transport และกันการดักฟังหรือแอบอ้างได้บางแบบ แต่ถ้า Service A มี certificate ที่ถูกต้อง ไม่ได้แปลว่า A มีสิทธิ์อ่าน payslip ของทุกคน ยังต้องเช็ก authorization อย่าง scope และ tenant policy เพิ่มเสมอ

Zero Trust ในระบบภายใน

ถ้า Notification Service ถูกโจมตีและ token รั่ว แล้วทุก service เชื่อ network ภายในโดยไม่เช็ก token หรือ permission ผู้โจมตีก็ไล่เข้า service อื่นได้ง่าย ๆ หลักปฏิบัติคือ

ในทางปฏิบัติ แต่ละ service ควรมี identity ของตัวเอง และได้สิทธิ์เท่าที่จำเป็น (least privilege) เช่น Notification รับเฉพาะข้อมูลที่ต้องใช้แจ้งเตือน ทุก hop ที่เกี่ยวข้องต้องตรวจ authentication และ authorization โดยไม่เชื่อ header อย่าง x-user-id ที่ client ส่งมาเอง ควรหมุน credential เป็นระยะ ใช้ secret manager จำกัดเส้นทาง network และบันทึก security event โดยไม่ log token หรือข้อมูลส่วนบุคคลเกินจำเป็น

โจทย์ชวนคิด: Gateway ตรวจ JWT แล้ว backend ไม่ต้องตรวจอีกได้ไหมไม่ควร ถ้ายังไม่ได้ออกแบบ trust boundary เพราะอาจมีคนเรียก service ตรง ๆ หรือปลอม header ได้ ต้องระบุตัวตนผู้เรียกและบังคับ authorization ที่ service หรือ resource ที่รับผิดชอบด้วย

API Gateway, BFF, Service Mesh, Discovery และ Versioning

Intermediateเนื้อหาเสริม

เนื้อหาเสริม: ส่วนที่ข้อสอบมักถามต่อจากเรื่อง “well-defined APIs” และ “independently scalable”

Gateway, BFF และ Service Mesh ต่างกันอย่างไร

ตัวช่วยดูแลทราฟฟิกแบบไหนงานหลัก
API Gatewayจาก client เข้ามาในระบบ (north-south)routing, authentication, rate limiting, TLS termination, รวม entry point
BFF (Backend-for-Frontend)ระหว่าง client เฉพาะแบบ (เว็บ, มือถือ) กับ serviceประกอบข้อมูลเป็น view model ที่หน้าจอนั้นต้องการ ลดจำนวน request

ใช้ร่วมกันได้ แต่อย่ายัด business logic ลงใน gateway เพราะมันจะกลายเป็นคอขวดและเป็นจุดที่ล้มแล้วพังทั้งระบบ

Service discovery และ load balancing

instance ของ service เกิดและหายอยู่ตลอด (autoscale, deploy ใหม่) จะเขียน IP ตายตัวไม่ได้ ต้องมีกลไกให้เรียกด้วยชื่อ เช่น DNS ของ Kubernetes Service (http://employee-service) หรือ registry อย่าง Consul ส่วน load balancer จะกระจายคำขอไปเฉพาะ instance ที่ readiness ผ่าน

เลือกเหมาะเมื่อข้อควรระวัง
REST/JSONAPI สาธารณะ หรือเรียกจากเบราว์เซอร์ อ่านง่ายและ debug ง่ายpayload ใหญ่กว่า schema หลวมกว่า

Versioning และ contract testing

การเพิ่ม field ใหม่แบบ optional ถือว่า backward compatible แต่การลบ field เปลี่ยนชนิด หรือเปลี่ยนความหมายเป็น breaking change ต้องออกเวอร์ชันใหม่ (เช่น /v2) และประกาศวันเลิกใช้ เช่นผ่าน header Deprecation และ Sunset ควรใช้ OpenAPI อธิบาย REST และ AsyncAPI อธิบาย event เพื่อให้ contract อยู่ในรูปที่เครื่องอ่านได้ แล้วตรวจ breaking change ใน CI ส่วน consumer-driven contract test (เช่น Pact) ให้ consumer ระบุว่าใช้ field ไหน แล้ว provider ทดสอบว่ายังตอบตามนั้น เร็วกว่า end-to-end และไม่ต้องรัน service ทั้งระบบ

Rate limiting และ idempotency key

ใส่ rate limit ที่ gateway เพื่อกันคนใช้เกินโควตาหรือยิงถล่ม โดยตอบ 429 พร้อม Retry-After ส่วน POST ที่ client อาจ retry (เช่นสั่งจ่ายเงิน) ให้รับ header Idempotency-Key แล้วจำผลของ key นั้นไว้ ถ้าได้ key เดิมมาอีกก็คืนผลเดิม ไม่ทำซ้ำ

CQRS: แยกทางเขียนออกจากทางอ่าน

CQRS (Command Query Responsibility Segregation) คือการแยกทาง “เปลี่ยนข้อมูล” (command/write) ออกจากทาง “อ่านข้อมูล” (query/read) สมมติ HR Dashboard ต้องโชว์จำนวน payslip ที่ publish แล้ว จำนวนพนักงานที่ได้รับเงิน และจำนวน notification ที่ส่งสำเร็จ ถ้าทุกครั้งต้องไป join ผ่าน API ของสามระบบ หน้าจะช้า และถ้า service ไหนล่ม ข้อมูลก็ไม่ครบ

HR Admin → Write API (Publish Payslip) → Payslip DB
                       ↓ event PayslipPublished
                 Read Model Projector → Dashboard Read DB
HR Dashboard → Query API → Dashboard Read DB   (อ่านข้อมูลสรุปที่เตรียมไว้แล้ว)

ข้อแลกเปลี่ยน: dashboard อาจช้าไปหลายวินาที ต้องรับมือ event ซ้ำหรือมาผิดลำดับ และมีภาระดูแล read model เพิ่ม CQRS ไม่จำเป็นต้องแยก database หรือใช้ Event Sourcing เสมอไป แค่แยก command handler กับ query handler ใน monolith ก็นับเป็น CQRS แบบหนึ่งแล้ว

Saga: ธุรกรรมที่ต้องผ่านหลาย service

สมมติระบบจ่ายเงินทำงานตามลำดับ Payroll ยืนยันรายการ → Payment สั่งโอน → Payslip เผยแพร่ → Notification แจ้งพนักงาน ถ้าขั้น Payslip ล้มเหลวหลังโอนเงินสำเร็จไปแล้ว เราจะ ROLLBACK เงินที่ออกจากธนาคารด้วย SQL transaction ของ Payslip DB ไม่ได้ Saga คือการออกแบบกระบวนการหลายขั้นที่แต่ละขั้นมี compensating action (ธุรกรรมใหม่ที่ทำเพื่อแก้ผลของขั้นก่อนหน้า) ตามกฎธุรกิจ

Confirm Payroll → Request Payment → [สำเร็จ?]
   ไม่สำเร็จ → Mark Payment Failed
   สำเร็จ    → Publish Payslip → [สำเร็จ?]
       สำเร็จ    → Notify Employee → COMPLETED
       ไม่สำเร็จ → Retry / Manual Reconcile (ไม่ย้อนโอนเงินเองโดยไม่มีกฎธุรกิจ)

Circuit Breaker: ถ้า downstream ล้มอยู่ จะหยุดเรียกอย่างไร?

ถ้า Payslip Service เรียก Employee Service แล้ว timeout ทุกครั้ง ขณะที่รับ 1,000 request ต่อวินาที และแต่ละอันรอ 5 วินาที connection, memory และ thread จะถูกกินจนหมด Payslip Service ก็ล่มตามไปด้วย circuit breaker มีสามสถานะ

Closed เรียก downstream ตามปกติและนับความล้มเหลว Open ปฏิเสธคำขอที่จะส่งไป downstream ไปเลยชั่วคราว ไม่ต้องรอ timeout ทุกครั้ง Half-open ปล่อยคำขอทดลอง (probe) ผ่านไปไม่กี่ตัวเพื่อดูว่า downstream ฟื้นหรือยัง ต้องใช้ร่วมกับ timeout, retry budget, bulkhead, rate limiting และ observability ไม่ใช่ใส่ circuit breaker ตัวเดียวแล้วระบบจะทนทาน และต้องตกลงให้ชัดว่าตอน Open จะ fail fast หรือใช้ fallback ที่ถูกต้องทางธุรกิจ

API Composition: ถ้าหน้าจอต้องใช้ข้อมูลจากหลาย service

หน้า Payslip ต้องมีชื่อพนักงาน รายการรายได้/หักเงิน และค่าตั้งของ tenant BFF จึงเรียกสามระบบ พร้อมกัน แล้วประกอบเป็น view model ส่งให้ frontend

async function getPayslipView(payslipId: string, employeeId: string) {
  const [employee, payslip, tenant] = await Promise.all([
    getEmployee(employeeId),
    getPayslip(payslipId),
    getTenantConfigForPayslip(payslipId),
  ]);
  return { employee, payslip, tenant };
}

มีสี่เรื่องที่ต้องตัดสินใจ ข้อแรก Promise.all() จะ reject เมื่อมีตัวใดตัวหนึ่ง reject ถ้าธุรกิจยอมให้ตอบเท่าที่ได้ ให้ใช้ Promise.allSettled พร้อม partial response ข้อสอง ตรวจ authorization ทั้งใน BFF และ downstream ตาม trust boundary ข้อสาม จำกัด timeout และ concurrency ไม่ให้การเรียกแตกออกหลายสาย (fan-out) จนระบบล่ม ข้อสุดท้าย การเรียกพร้อมกันไม่ได้การันตีว่าข้อมูลทั้งหมดเป็น snapshot ณ เวลาเดียวกัน ถ้าต้องการแบบนั้นต้องออกแบบเพิ่ม

Expand-Contract: ตัวอย่างเปลี่ยนชื่อ column

สมมติต้องเปลี่ยน employee_name เป็น display_name ในขณะที่ service เวอร์ชันเก่ายังรันอยู่

  1. Expand: เพิ่ม display_name เข้ามา โดยยังเก็บ employee_name ไว้
  2. ปรับแอปให้อ่านและเขียนได้ทั้งสอง field (หรือ dual-write อย่างระวัง)
  3. Backfill ข้อมูลเก่าแล้วตรวจว่าถูกต้อง
  4. deploy consumer และ producer จนทุกตัวใช้ field ใหม่
  5. Contract: ลบ field เก่าเมื่อมั่นใจแล้วว่าไม่มีใครใช้
-- 1) Expand (deploy ได้โดยแอปเวอร์ชันเก่าไม่พัง)
ALTER TABLE employees ADD COLUMN display_name TEXT;
-- 3) Backfill เป็นชุดเล็ก ๆ ไม่ให้ล็อกตารางนาน
UPDATE employees SET display_name = employee_name WHERE display_name IS NULL AND id BETWEEN 1 AND 10000;
-- 5) Contract (หลังทุกเวอร์ชันเลิกอ่านคอลัมน์เก่าแล้วเท่านั้น)
ALTER TABLE employees DROP COLUMN employee_name;
ข้อผิดพลาดยอดนิยมลบหรือเปลี่ยนชื่อ column ใน deploy เดียว ทั้งที่ pod เวอร์ชันเก่ายังอ่านอยู่ จะพังทันทีระหว่าง rolling deploy

ใช้ตัวชี้วัด DORA สี่ตัว ได้แก่ deployment frequency, lead time for changes, change failure rate และ time to restore service สองตัวแรกวัดความเร็ว สองตัวหลังวัดความเสถียร ต้องดูคู่กัน ไม่ใช่เร่งอย่างเดียว อีกอย่างคือควรทำ pipeline เป็นโค้ด (pipeline as code), infrastructure as code และ GitOps เพื่อให้ทุก environment สร้างซ้ำได้

Bulkhead และ load shedding

Bulkhead คือการแบ่งทรัพยากร (connection pool, thread, queue) เป็นช่อง ๆ เหมือนผนังกั้นห้องในเรือ ไม่ให้ dependency ตัวเดียวที่ช้ากินทรัพยากรไปทั้งหมด เช่นแยก pool ที่เรียก Employee ออกจาก pool ที่เรียก Tenant ส่วน load shedding คือเมื่อรับไม่ไหวให้ปฏิเสธงานที่สำคัญน้อยก่อน (เช่นตอบ 503 พร้อม Retry-After) ดีกว่าปล่อยให้ทุก request ช้าจนล่มทั้งระบบ

Timeout budget

สมมติหน้า Payslip ต้องตอบภายใน 2 วินาที แต่ต้องเรียก 3 service ต่อกัน

Gateway          100 ms
Tenant API       400 ms
Employee API     700 ms
Payslip API      600 ms
------------------------
รวม             1800 ms   (ยังไม่รวม network และ serialization)

ถ้าแต่ละ service ตั้ง timeout 5 วินาทีเท่ากันหมด จะคุม latency รวมไม่ได้เลย ต้องวาง deadline หรือ timeout budget แล้วส่งเวลาที่เหลือต่อให้ downstream และเรียกพร้อมกันเมื่อไม่ได้พึ่งกัน

// ส่ง deadline ต่อ ๆ กันไป: downstream ได้เวลาที่เหลือ ไม่ใช่ timeout ตายตัว
async function callWithDeadline(url: string, deadlineAt: number): Promise<Response> {
  const remaining = deadlineAt - Date.now();
  if (remaining <= 0) throw new Error('Deadline exceeded');
  return fetch(url, { signal: AbortSignal.timeout(remaining), headers: { 'x-deadline': String(deadlineAt) } });
}

99.9%ประมาณ 43.2 นาที

ถ้า error budget ใกล้หมด ทีมอาจชะลอฟีเจอร์เสี่ยงสูงแล้วหันมาเน้นความเสถียรก่อน (เป็นแนวทางบริหาร ไม่ใช่สูตรตายตัวของทุกองค์กร) อีกเรื่องที่ควรรู้คือ ความพร้อมใช้ของ service ที่เรียกต่อกันเป็นทอดจะต่ำลง ถ้า A, B, C พร้อม 99.9% เท่ากัน และต้องสำเร็จทั้งสามตัว ความพร้อมรวมจะเหลือประมาณ 0.999³ ≈ 99.7% จึงต้องลด dependency ในเส้นทางหลัก ใช้ fallback และเรียกแบบ asynchronous เท่าที่ทำได้

จุดเสี่ยงของช่วงเปลี่ยนผ่านdual-write หรือการ sync ข้อมูลระหว่างระบบเก่ากับใหม่ซับซ้อนและทำให้ข้อมูลเพี้ยนได้ ต้องมี reconciliation ตรวจว่าข้อมูลตรงกัน และอาจใช้ anti-corruption layer คั่นไว้ ไม่ให้โมเดลของ monolith รั่วมาปนใน service ใหม่

กำหนด boundary ด้วย DDD และ Bounded Context

อย่าแบ่ง service ตามชื่อ table อย่างเดียว ให้ถามว่า ใครเป็นเจ้าของ business rule, ธุรกรรมไหนต้องสอดคล้องกันทันที, ทีมไหนดูแลฟีเจอร์นี้ และอะไรที่เปลี่ยนพร้อมกันบ่อย ถ้า PayslipCalculation กับ PayslipPublish ต้องเปลี่ยนและ deploy ด้วยกันตลอด การแยกเป็นสอง service อาจแค่เพิ่ม coupling โดยไม่จำเป็น เทคนิคหนึ่งที่ช่วยหา boundary คือ event storming ให้ผู้เชี่ยวชาญธุรกิจกับ dev นั่งไล่เหตุการณ์สำคัญของระบบด้วยกัน

L1 (Beginner). เขียน getEmployeeState(result) แปลงผลของ Employee API เป็นสถานะ

รับ ApiResult ที่เป็น 200 พร้อม active, 404 หรือ 503 แล้วคืน 'ACTIVE' | 'INACTIVE' | 'NOT_FOUND' | 'UNAVAILABLE' โดยเป็น pure function (ไม่มี side effect)

โค้ดเฉลย

type ApiResult =
  | { status: 200; body: { id: string; active: boolean } }
  | { status: 404 }
  | { status: 503 };

type EmployeeState = 'ACTIVE' | 'INACTIVE' | 'NOT_FOUND' | 'UNAVAILABLE';

function getEmployeeState(result: ApiResult): EmployeeState {
  switch (result.status) {
    case 200:
      return result.body.active ? 'ACTIVE' : 'INACTIVE';
    case 404:
      return 'NOT_FOUND';
    case 503:
      return 'UNAVAILABLE';
  }
}

ใช้ discriminated union ของ TypeScript ให้ status บอกว่า body มีหรือไม่ ได้แยกกรณีครบตามชนิดที่โจทย์กำหนด เวลา O(1) พื้นที่ O(1)

  assert.equal(getEmployeeState({ status: 200, body: { id: 'E1', active: true } }), 'ACTIVE');
  assert.equal(getEmployeeState({ status: 200, body: { id: 'E1', active: false } }), 'INACTIVE');
  assert.equal(getEmployeeState({ status: 404 }), 'NOT_FOUND');

L2 (Intermediate). เขียน HTTP client ที่ปลอดภัย getEmployeeStatus(fetcher, id)

เรียก GET /employees/:id เมื่อได้ 200 body ต้องเป็น { status: 'ACTIVE' | 'INACTIVE' } ถ้า status อื่นให้ throw HTTP {status} ถ้า 200 แต่รูปแบบ JSON ผิดให้ throw Invalid response และ ID ต้องผ่าน encodeURIComponent

โค้ดเฉลย

type ApiFetch = (url: string, init?: RequestInit) => Promise<Response>;

async function getEmployeeStatus(
  fetcher: ApiFetch,
  id: string,
): Promise<'ACTIVE' | 'INACTIVE'> {
  const response = await fetcher(`/employees/${encodeURIComponent(id)}`, {
    method: 'GET',
    headers: { Accept: 'application/json' },
  });

  if (!response.ok) throw new Error(`HTTP ${response.status}`);

  let value: unknown;
  try {
    value = await response.json();
  } catch {
    throw new Error('Invalid response');
  }

  if (
    typeof value !== 'object' || value === null ||
    !('status' in value) ||
    (value.status !== 'ACTIVE' && value.status !== 'INACTIVE')
  ) {
    throw new Error('Invalid response');
  }
  return value.status;
}

ทำไมต้องเช็ก JSON ด้วย เพราะ server อาจตอบ 200 แต่ body ผิด schema ได้ และ TypeScript type ไม่ได้ตรวจตอนรัน ส่วน network error หรือ timeout ปล่อยให้ผู้เรียกจัดการต่อ ไม่กลืนเงียบ ๆ (ฟังก์ชันรับ fetcher เข้ามา เลยเทสต์ได้โดยไม่ต้องมี server)

L3 (Intermediate). เขียน Idempotent Event Processor createProcessor(send)

ส่งไม่เกินหนึ่งครั้งต่อ eventId และถ้า send() โยน error ห้าม mark ว่าสำเร็จ เพื่อให้ retry รอบถัดไปได้

โค้ดเฉลย

type NotificationEvent = { eventId: string; employeeId: string };

function createProcessor(send: (employeeId: string) => void) {
  const processed = new Set<string>();
  return (event: NotificationEvent): void => {
    if (processed.has(event.eventId)) return;
    send(event.employeeId);        // ถ้าโยน Error จะไม่ถึงบรรทัดถัดไป
    processed.add(event.eventId);  // mark หลังส่งสำเร็จเท่านั้น
  };
}
ข้อจำกัดที่ต้องพูดให้ได้Set หายเมื่อ restart และไม่แชร์ข้าม instance ถ้า process ล่มหลังส่งอีเมลแต่ก่อนบันทึกลง Set ก็ยังส่งซ้ำได้ ของจริงต้องใช้ idempotency แบบ durable (ตาราง processed_events ที่มี unique constraint), วางขอบเขต transaction ให้ถูก และจัดการ side effect ภายนอกตามที่ provider รองรับ เช่น idempotency key

Test case (รันด้วย node --test)

import test from 'node:test';
import assert from 'node:assert/strict';

test('ส่งไม่เกินหนึ่งครั้งต่อ eventId', () => {
  const sent: string[] = [];
  const handle = createProcessor((id) => sent.push(id));
  handle({ eventId: 'event-1', employeeId: 'E1' });
  handle({ eventId: 'event-1', employeeId: 'E1' });
  handle({ eventId: 'event-2', employeeId: 'E2' });
  assert.deepEqual(sent, ['E1', 'E2']);
});

test('send โยน error แล้ว retry ได้', () => {
  let calls = 0;
  const handle = createProcessor(() => { if (++calls === 1) throw new Error('provider down'); });
  assert.throws(() => handle({ eventId: 'event-3', employeeId: 'E3' }), /provider down/);
  handle({ eventId: 'event-3', employeeId: 'E3' }); // ครั้งที่สองต้องลองส่งใหม่
  assert.equal(calls, 2);
  handle({ eventId: 'event-3', employeeId: 'E3' }); // สำเร็จแล้ว ไม่ส่งซ้ำ
  assert.equal(calls, 2);
});
L4 (Intermediate). เขียน deduplicateEvents(events) เลือก event แรกของแต่ละ eventId

รักษาลำดับเดิมของ event ที่พบครั้งแรก เพิ่มเคสสำหรับ array ว่าง, มีตัวเดียว และซ้ำทั้งหมด แล้ววิเคราะห์ complexity

โค้ดเฉลย

type Event = { eventId: string; type: string };

function deduplicateEvents(events: Event[]): Event[] {
  const seen = new Set<string>();
  const result: Event[] = [];

  for (const event of events) {
    if (seen.has(event.eventId)) continue;
    seen.add(event.eventId);
    result.push(event);
  }
  return result;
}

เวลา O(n) โดยเฉลี่ย (ค้นใน Set เฉลี่ย O(1)) พื้นที่ O(n) ผลลัพธ์เรียงตามที่เจอครั้งแรก และไม่แก้ array เดิม

Test case (รันด้วย node --test)

import test from 'node:test';
import assert from 'node:assert/strict';

test('เลือกตัวแรกของแต่ละ eventId และรักษาลำดับ', () => {
  const input = [
    { eventId: 'a', type: 'PUBLISHED' },
    { eventId: 'b', type: 'UPDATED' },
    { eventId: 'a', type: 'PUBLISHED' },
    { eventId: 'c', type: 'DELETED' },
  ];
  assert.deepEqual(deduplicateEvents(input), [input[0], input[1], input[3]]);

  assert.deepEqual(deduplicateEvents([{ eventId: 'x', type: 'T' }]), [{ eventId: 'x', type: 'T' }]);

L5 (Intermediate เสริม). เขียน withRetry ที่มี exponential backoff + jitter และ test ได้โดยไม่ต้องรอจริง

retry เฉพาะ DependencyUnavailableError สูงสุด attempts ครั้ง รอ baseMs × 2^i × (0.5 + random/2) ไม่รอหลังครั้งสุดท้าย และ error ถาวรห้าม retry ให้ฟังก์ชันรับ sleep กับ random เข้ามาเป็นพารามิเตอร์ test จะได้คุมเวลาได้

โค้ดเฉลย

class DependencyUnavailableError extends Error {}

async function withRetry<T>(
  fn: () => Promise<T>,
  opts: { attempts?: number; baseMs?: number; sleep?: (ms: number) => Promise<void>; random?: () => number } = {},
): Promise<T> {
  const { attempts = 3, baseMs = 200, sleep = (ms) => new Promise((r) => setTimeout(r, ms)), random = Math.random } = opts;
  let lastError: unknown;
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      // retry เฉพาะ error ชั่วคราว และไม่รอหลังครั้งสุดท้าย
      if (!(err instanceof DependencyUnavailableError) || i === attempts - 1) break;
      await sleep(baseMs * 2 ** i * (0.5 + random() / 2)); // exponential backoff + jitter
    }
  }
  throw lastError;
}

backoff ทำให้ลองห่างขึ้นเรื่อย ๆ ส่วน jitter ทำให้ client หลายตัวไม่ยิงพร้อมกันตอน downstream ฟื้น (thundering herd) ใน test ใช้ random: () => 1 เพื่อให้เวลารอออกมาตายตัวเป็น 200 แล้ว 400

L6 (Advance). เขียน state machine ของ Circuit Breaker: recordResult และ allowProbe

เริ่ม CLOSED failures=0, ใน CLOSED ล้มเหลวครบ 3 ครั้งติดต่อกันเป็น OPEN และถ้าสำเร็จ reset เป็น 0, เมื่อระบบภายนอกอนุญาตให้ probe (allowProbe) เปลี่ยน OPEN เป็น HALF_OPEN, ใน HALF_OPEN probe สำเร็จเป็น CLOSED (reset) และล้มเหลวเป็น OPEN (failures=3)

โค้ดเฉลย

type State = 'CLOSED' | 'OPEN' | 'HALF_OPEN';
type Breaker = { state: State; failures: number };

function recordResult(current: Breaker, success: boolean): Breaker {
  if (current.state === 'OPEN') return { ...current };

  if (current.state === 'HALF_OPEN') {
    return success
      ? { state: 'CLOSED', failures: 0 }
      : { state: 'OPEN', failures: 3 };
  }

  if (success) return { state: 'CLOSED', failures: 0 };
  const failures = current.failures + 1;
  return { state: failures >= 3 ? 'OPEN' : 'CLOSED', failures };
}

function allowProbe(current: Breaker): Breaker {
  return current.state === 'OPEN'
    ? { ...current, state: 'HALF_OPEN' }
    : { ...current };
}

เวลา O(1) พื้นที่ O(1) ต่อการเรียก ตัวอย่างนี้ยังไม่ใช่ circuit breaker สำหรับ production เพราะไม่มีนาฬิกาจับเวลาพัก, sliding window ของความล้มเหลว, ตัวจำกัดจำนวน probe และการจัดการหลาย request พร้อมกัน (shared state ข้าม instance)

type PayslipRow = { id: string; tenantId: string; netPay: number; status: string };
type PayslipPage = {
  page: number;
  per_page: number;
  total: number;
  total_pages: number;

};
type FetchPage = (tenantId: string, page: number) => Promise<PayslipPage>;

async function totalPublishedNetPay(fetchPage: FetchPage, tenantId: string): Promise<number> {
  const first = await fetchPage(tenantId, 1);
  // หน้าที่เหลือเรียกพร้อมกัน (ถ้า total_pages เยอะมาก ควรจำกัด concurrency)
  const rest: Promise<PayslipPage>[] = [];
  for (let p = 2; p <= first.total_pages; p++) rest.push(fetchPage(tenantId, p));
  const pages = [first, ...(await Promise.all(rest))];

  let sum = 0;
  for (const page of pages) {
    for (const row of page.data) {
      if (row.status === 'PUBLISHED') sum += row.netPay;
    }
  }
  return sum;
}

H2 · Coding: ลำดับการสตาร์ต service

Problem

ระบบมีหลาย service และบางตัวต้องรอให้อีกตัวสตาร์ตก่อน (เช่น payslip ต้องรอ db) ให้หาลำดับสตาร์ตที่ถูกต้อง ถ้ามีหลายลำดับที่ใช้ได้ ให้เลือกลำดับที่น้อยที่สุดตามตัวอักษร (เลือกตัวที่ชื่อน้อยสุดก่อนในแต่ละขั้น) ถ้ามีวงจรรอกันเองให้คืน null

Function Description

เติมฟังก์ชัน startOrder(services, deps)

  • string[] services รายชื่อ service ทั้งหมด (ไม่ซ้ำกัน)
  • [string, string][] deps แต่ละคู่ [a, b] แปลว่า a ต้องรอ b สตาร์ตก่อน
Returns

string[] | null ลำดับสตาร์ต หรือ null ถ้าเป็นไปไม่ได้

Constraints
  • 1 ≤ services.length ≤ 104, 0 ≤ deps.length ≤ 105
  • ชื่อใน deps อยู่ใน services ทุกตัว และไม่มีคู่ซ้ำ

        ["payslip","db"], ["notify","payslip"]]

Explanation 0: มีแค่ db ที่ไม่ต้องรอใคร จึงสตาร์ตก่อน หลังจากนั้น auth กับ payslip พร้อมสตาร์ตทั้งคู่ เลือก auth ก่อนเพราะชื่อน้อยกว่า ต่อด้วย payslip พอ payslip เสร็จ api กับ notify ก็พร้อม เลือก api ก่อน

โค้ดเฉลย

function startOrder(services: string[], deps: [string, string][]): string[] | null {
  const waiting = new Map<string, number>();        // service นี้ยังรอ dependency อีกกี่ตัว
  const dependents = new Map<string, string[]>();   // ใครรอ service นี้อยู่บ้าง
  for (const s of services) {
    waiting.set(s, 0);
    dependents.set(s, []);
  }
  for (const [a, b] of deps) {                      // a ต้องรอ b
    waiting.set(a, waiting.get(a)! + 1);
    dependents.get(b)!.push(a);
  }

  const ready = services.filter((s) => waiting.get(s) === 0).sort();
  const order: string[] = [];
  while (ready.length > 0) {
    const s = ready.shift()!;                       // เลือกตัวที่ชื่อน้อยที่สุดก่อนเสมอ
    order.push(s);
    for (const d of dependents.get(s)!) {
      waiting.set(d, waiting.get(d)! - 1);
      if (waiting.get(d) === 0) {
        ready.push(d);
        ready.sort();
      }
    }
  }
  return order.length === services.length ? order : null; // ไม่ครบ = มีวงจร
}

นี่คือ topological sort แบบ Kahn ถ้าเลือกจนหมดแล้วยังได้ไม่ครบทุก service แปลว่ามีวงจร ตัวอย่างนี้เรียง ready ใหม่ทุกครั้งเพื่อความอ่านง่าย ถ้า services ถึง 104 ตัวและต้องเร็วกว่านี้ ให้เปลี่ยนเป็น min-heap จะเหลือประมาณ O((V+E) log V)

function createRateLimiter(limit: number, windowMs: number) {
  const hits = new Map<string, number[]>();         // เวลาของคำขอที่ "ผ่าน" ของแต่ละ client

  return function allow(clientId: string, nowMs: number): boolean {
    const recent = (hits.get(clientId) ?? []).filter((t) => t > nowMs - windowMs);
    if (recent.length >= limit) {
      hits.set(clientId, recent);                   // คำขอที่ถูกปฏิเสธไม่นับรวม
      return false;
    }
    recent.push(nowMs);
    hits.set(clientId, recent);
    return true;
  };
}

เก็บเวลาของคำขอที่ผ่านไว้ต่อ client แล้วตัดอันที่หลุดหน้าต่างทิ้งทุกครั้งที่ถูกเรียก ต่อครั้งใช้เวลาประมาณ O(k) เมื่อ k คือจำนวนคำขอในหน้าต่าง ข้อเสียคือ Map โตตามจำนวน client ในงานจริงต้องมีวิธีลบ client ที่เงียบไปนาน ๆ และถ้ามีหลาย instance ก็ต้องย้ายสถานะไปเก็บที่กลาง เช่น Redis

  1. Begin transaction
  2. UPDATE payslip และ INSERT outbox (PENDING) ใน transaction เดียว
  3. COMMIT
  4. Relay worker อ่าน outbox โดย claim แถวให้เหมาะกับหลาย worker (เช่น SKIP LOCKED)
  5. Publish ไป broker พร้อม event ID และจัดการ publish acknowledgement
  6. Mark outbox เป็น sent เมื่อยืนยันการส่งได้ตามที่ broker รองรับ
  7. Consumer ใช้ event ID ใน durable store เพื่อ dedup และ commit ผลในฐานข้อมูลของตัวเอง
  8. ACK หลัง commit ถ้าล้มเหลวใช้ bounded retry, backoff และ DLQ

จุดที่ยังซ้ำได้: relay ส่ง broker สำเร็จแต่ล่มก่อน mark sent, consumer ทำสำเร็จแต่ล่มก่อน ACK, email provider รับคำสั่งแล้วแต่ผู้เรียก timeout

  3. Data ownership และการจัดชั้น PII
  4. Authentication/authorization และการหมุนเวียน secret/certificate
  5. Structured log, trace, metric และ correlation ID
  6. SLI/SLO และนโยบาย alert
  7. CI/CD gate: test, security scan, contract test
  8. มาตรฐาน rollback, canary และ DB migration
  9. Runbook, ช่องทางยกระดับ incident และการซ้อม DR
  10. ADR, architecture review และกรอบเวลา deprecation
M10. Payment โอนสำเร็จไปแล้วแต่ Payslip publish ล้มเหลว ออกแบบ recovery plan แยกสิ่งที่ retry ได้, ต้อง reconcile และห้ามทำอัตโนมัติ
  • Retry ได้: publish payslip แบบ idempotent พร้อม audit trail
  • ต้อง reconcile: สถานะ PAID ต้องบันทึกให้ถูก ไม่สั่งโอนซ้ำโดยไม่มี idempotency และตรวจผลจริงกับ payment provider
  • ถ้า retry หมดแล้วยังไม่สำเร็จ: เข้า NEEDS_REVIEW พร้อม alert และ runbook
  • ห้ามอัตโนมัติ: refund หรือ reverse transfer ถ้ายังไม่มีกฎธุรกิจรองรับและ provider ยังไม่รองรับ

                                                  ↓ Outbox Relay

  1. Job submission: HR ส่งคำขอแล้วได้ jobId เช่น HTTP 202 Accepted
  2. Workers: ทำงานเป็น batch มี concurrency limit และรายงานความคืบหน้า
  3. Data ownership: job, payslip, notification เป็นเจ้าของฐานข้อมูลของตัวเอง
  4. Outbox: บันทึก business data พร้อม event ใน transaction เดียว
  5. Idempotency: กัน publish และ notification ซ้ำด้วย business key และ event ID
  6. Security: HR มี role สำหรับ publish, employee อ่านเฉพาะสลิปตัวเอง, คุม tenant scope ทุก query
  7. Observability: throughput, failed jobs, queue lag, p95, trace และ alert พร้อม runbook
  8. Failure policy: bounded retry, DLQ, reconciliation หรือ manual intervention
  9. Trade-off: queue เพิ่ม eventual consistency, progress อาจช้ากว่าความจริง, worker parallel สูงเกินไปอาจกด DB หรือ provider

BeginnerMicroservices แบ่งตาม business capability ไม่ใช่ตามจำนวน container ทีมเล็กและโดเมนยังไม่ชัดให้เริ่มจาก modular monolith fetch() ไม่ throw เมื่อได้ 4xx/5xx ต้องเช็ก response.ok เอง ตั้ง timeout เสมอ ตรวจสิทธิ์ที่ backend ไม่ใช่แค่ซ่อนปุ่ม และ retry เฉพาะ error ชั่วคราวที่ idempotent
IntermediateGuard เช็กสิทธิ์ Middleware ใส่ request ID Interceptor จับเวลา Pipe ตรวจ DTO Filter แปลง error ใช้ HTTP กับงานที่ต้องได้คำตอบทันที ใช้ event กับงานเบื้องหลัง queue ไม่ได้การันตี exactly-once consumer ต้อง idempotent ใช้ outbox กัน event หาย ให้แต่ละ service เป็นเจ้าของข้อมูลตัวเอง JWT ต้องตรวจ signature, iss, aud, exp, scope และ mTLS ไม่ใช่ authorization
AdvanceCQRS แยก read/write ไม่ต้องใช้ Event Sourcing เสมอ Saga ใช้ compensation ไม่ใช่ rollback ของ DB circuit breaker มี Closed, Open, Half-open และต้องใช้คู่กับ timeout กับ retry budget เปลี่ยน schema แบบ expand-contract ย้ายระบบด้วย Strangler Fig และดูแลด้วย catalog, SLO, runbook, ADR
