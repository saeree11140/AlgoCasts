OWASP Top 10 คืออะไร และไม่ใช่อะไร

OWASP Top 10 เป็นเอกสารสร้างความตระหนักรู้ (awareness document) ว่าความเสี่ยงของ web application กลุ่มไหนเจอบ่อยและกระทบหนักตามข้อมูลที่ OWASP รวบรวมมา ตัวมันไม่ใช่ checklist ที่ผ่านครบสิบข้อแล้วแปลว่าระบบปลอดภัย และบางหมวดอย่าง Insecure Design เป็นเรื่องของการออกแบบ สแกนด้วยเครื่องมือตรง ๆ ไม่ได้ ข้อสอบมักถามสองอย่างคู่กัน คือโค้ดแบบนี้อยู่หมวดไหน และแก้ด้วยอะไร เลยต้องจำเป็นคู่ ไม่ใช่จำแค่ชื่อ

OWASP Top 10 ตั้งใจให้เป็นภาพรวม แต่ละหมวดรวมช่องโหว่หลายชนิดไว้ใต้ชื่อเดียว (ฉบับ 2025 รวม CWE 248 รายการไว้ใน 10 หมวด) พอจะใช้ตรวจจริงจังจึงต้องไปใช้ OWASP ASVS (Application Security Verification Standard) ซึ่งเป็นรายการข้อกำหนดที่แบ่งเป็นระดับ ตรวจได้เป็นข้อ ๆ ส่วนวิธีเขียนโค้ดให้ถูกต้องรายเรื่อง เช่น Password Storage, Session Management, SQL Injection Prevention ให้ดูใน OWASP Cheat Sheet Series

อีกเรื่องที่ควรสังเกตคือ OWASP ค่อย ๆ เปลี่ยนชื่อหมวดจากอาการไปเป็นต้นเหตุ เช่น Sensitive Data Exposure เปลี่ยนเป็น Cryptographic Failures เพราะต้นเหตุจริงคือการเข้ารหัสที่อ่อนหรือไม่มี ไม่ใช่การที่ข้อมูลรั่วเฉย ๆ เวลาตอบข้อสอบประเภท "ช่องโหว่นี้อยู่หมวดไหน" ให้ถามตัวเองก่อนว่าต้นเหตุคืออะไร ไม่ใช่ดูแค่ผลที่เกิดขึ้น

Secure Coding: Validate Input, Encode Output และ Injection

Beginner

Follow secure coding guidelines. Apply common vulnerabilities (OWASP Top 10) using secure coding guideline (e.g., validate input, sanitize output).

Validate กับ Encode เป็นคนละงานกัน

มือใหม่มักเอาสองอย่างนี้มาปนกัน Validate คือเช็กว่าข้อมูลที่เข้ามาหน้าตาถูกตามที่ระบบคาดหวังไหม ทำที่ขอบระบบ (boundary) แล้วปฏิเสธตั้งแต่ต้นถ้าไม่ผ่าน ส่วน Encode หรือ parameterize คือทำให้ข้อมูลไม่ถูกตีความเป็นคำสั่งตอนส่งต่อไปยังปลายทาง เช่น SQL, HTML หรือ shell ปลายทางแต่ละแบบมีกฎ escape ไม่เหมือนกัน การ "ล้างข้อมูลทีเดียวตอนรับเข้ามา" จึงกันได้ไม่ครบ

วิธี validate ที่ดีคือ allowlist บอกว่าอะไรยอมรับได้ แล้วปฏิเสธที่เหลือทั้งหมด การไล่ปิดคำอย่าง DROP หรือ <script> (blocklist) พลาดง่าย เพราะผู้โจมตีเปลี่ยนรูปแบบการเขียนได้ไม่จำกัด ส่วนการตรวจที่ฝั่ง browser ช่วยแค่เรื่องประสบการณ์ใช้งาน ใครก็ยิง request ตรงเข้า API ข้ามหน้าเว็บได้

const ORDER_ID = /^[A-Z]{2}\d{6}$/;

app.get('/orders/:orderId', async (req, res) => {
  if (!ORDER_ID.test(req.params.orderId)) {
    return res.status(400).json({ error: 'invalid_order_id' });
  }
  // รูปแบบถูกแล้ว แต่ยังต้องเช็กว่า user คนนี้เป็นเจ้าของ order จริง
  const order = await orders.findForUser(req.params.orderId, req.user.id);
  if (!order) return res.sendStatus(404);
  res.json(order);
});

สังเกตว่า validate ผ่านแล้วยังไม่พอ เพราะรูปแบบถูกไม่ได้แปลว่า user มีสิทธิ์ดู order นั้น ข้อสอบชอบหยิบจุดนี้มาทำเป็นตัวหลอก

SQL Injection: แยกคำสั่งออกจากค่า

ถ้าต่อ string เข้าไปในคำสั่ง SQL ค่าที่ผู้ใช้ส่งมาจะกลายเป็นส่วนหนึ่งของ query ได้ วิธีแก้คือส่งโครงสร้างของคำสั่งไปก่อน แล้วส่งค่าตามไปทีหลังเป็น parameter driver จะไม่ตีความค่าเป็น SQL ไม่ว่าข้างในจะมีอักขระอะไร

// มีช่องโหว่: email ที่เป็น  ' OR '1'='1  จะเปลี่ยนความหมายของ query
const bad = "SELECT id, name FROM users WHERE email = '" + email + "'";

// ปลอดภัย: ค่าไปทาง parameter ($1) ไม่ปนกับตัวคำสั่ง
const { rows } = await db.query(
  'SELECT id, name FROM users WHERE email = $1',
  [email]
);

จุดที่ parameterize ไม่ได้คือชื่อตารางหรือชื่อคอลัมน์ที่มาจากผู้ใช้ เช่น ORDER BY กรณีนี้ใช้ allowlist ของชื่อคอลัมน์ที่อนุญาต แล้ว map ค่าที่รับมาเป็นชื่อจริงในโค้ดเอง ส่วน ORM ช่วยได้เมื่อใช้ API ปกติ แต่พอเขียน raw query แล้วต่อ string ปัญหาก็กลับมาเหมือนเดิม

XSS: encode ตาม context ของ output

XSS เกิดเมื่อข้อมูลจากผู้ใช้ถูกใส่ลงหน้าเว็บในรูปที่ browser ตีความเป็น HTML หรือ JavaScript วิธีแก้ที่ถูกจุดคือเลือก API ที่มองข้อมูลเป็นข้อความตั้งแต่แรก

const li = document.createElement('li');

li.innerHTML = comment.text;    // ถ้า text เป็น <img src=x onerror=...> โค้ดจะรัน
li.textContent = comment.text;  // browser มองเป็นข้อความธรรมดา ไม่ parse เป็น HTML

list.appendChild(li);

Framework อย่าง React, Vue หรือ Angular encode ให้อัตโนมัติเมื่อใช้ binding ปกติ ความเสี่ยงกลับมาตอนใช้ช่องทางที่ข้ามกลไกนั้น เช่น dangerouslySetInnerHTML หรือ v-html ถ้าจำเป็นต้องแสดง HTML ที่ผู้ใช้เขียนจริง ให้ผ่าน sanitizer ที่ดูแลต่อเนื่องอย่าง DOMPurify อย่าเขียน regex ลบแท็กเอง และ Content-Security-Policy ช่วยลดความเสียหายได้อีกชั้น แต่ไม่ได้แทนการ encode

Command Injection: อย่าส่งข้อมูลผู้ใช้เข้า shell

import { exec, execFile } from 'node:child_process';

// host = "8.8.8.8; cat /etc/passwd" แล้ว shell จะรันสองคำสั่ง
exec('ping -c 1 ' + host, callback);

// ไม่ผ่าน shell: host ถูกส่งเป็น argument เดียวเสมอ
if (!/^[a-zA-Z0-9.-]{1,253}$/.test(host)) throw new Error('invalid_host');
execFile('ping', ['-c', '1', host], callback);

execFile ไม่เรียก shell จึงไม่มีความหมายพิเศษของ ; หรือ | แต่ยังต้อง validate เพราะค่าที่ขึ้นต้นด้วย - อาจถูกโปรแกรมปลายทางตีความเป็น option (argument injection)

CSRF และ IDOR ที่ต้องรู้ตั้งแต่ระดับนี้

CSRF ใช้นิสัยของ browser ที่แนบ cookie ไปให้อัตโนมัติทุกครั้งที่มี request ไปยังโดเมนนั้น ผู้ใช้ login ธนาคารค้างไว้แล้วไปเปิดเว็บอื่นที่ซ่อน form ส่งไปที่ bank.com/transfer browser ก็แนบ cookie ให้ ธนาคารเห็นว่า cookie ถูกต้องก็ทำรายการให้ ทางป้องกันที่ตรงที่สุดคือ CSRF token ที่ผูกกับ session และ cookie แบบ SameSite=Lax หรือ Strict พร้อมไม่ใช้ GET เปลี่ยนข้อมูล

IDOR (หรือ BOLA) คือเปลี่ยนเลขใน URL จาก /invoices/1001 เป็น 1002 แล้วเห็นของคนอื่น ต้นเหตุคือ server เช็กแค่ว่า login แล้ว แต่ไม่เช็กว่าข้อมูลชิ้นนั้นเป็นของคนที่ขอ วิธีแก้คือใส่เงื่อนไขเจ้าของลงไปในทุก query โดยใช้รหัสผู้ใช้ที่ได้จาก session หรือ token ไม่ใช่ค่าที่ client ส่งมา

เพิ่มเติมเชิงลึก: Path Traversal และ Open Redirect

สองช่องโหว่นี้เกิดจากหลักเดียวกัน คือเอาค่าที่ผู้ใช้ส่งมาไปใช้เป็นเส้นทางโดยไม่ตรวจ Path Traversal คือส่งชื่อไฟล์เป็น ../../etc/passwd เพื่อหลุดออกจากโฟลเดอร์ที่ตั้งใจ วิธีกันคือ resolve เป็น path เต็มแล้วเช็กว่ายังอยู่ใต้โฟลเดอร์ฐานจริง

import path from 'node:path';

const BASE = path.resolve('/srv/uploads');

export function safePath(name) {
  const full = path.resolve(BASE, name);           // '../x' หรือ '/etc/passwd' จะหลุดออกนอก BASE
  if (!full.startsWith(BASE + path.sep)) throw new Error('invalid_path');
  return full;
}

ข้อควรระวังคือ symbolic link ที่ชี้ออกนอกโฟลเดอร์ยังผ่านการเช็กนี้ได้ ถ้าระบบอนุญาตให้ผู้ใช้สร้าง link ต้องใช้ fs.realpath ก่อนเช็ก ส่วน Open Redirect คือพารามิเตอร์อย่าง ?next= ที่ถูกใช้ redirect โดยไม่ตรวจ ผู้โจมตีส่งลิงก์เว็บจริงที่ลงท้ายด้วยเว็บปลอมให้เหยื่อ โจทย์ใน Coding Lab ให้ลองเขียนตัวตรวจเอง

กับดักที่ข้อสอบชอบใช้ตัวเลือกที่ว่า "ลบอักขระอันตรายออก" หรือ "เปลี่ยน ' เป็น ''" มักเป็นข้อผิด เพราะพลาดง่ายและขึ้นกับ database กับ encoding คำตอบที่ถูกเกือบทุกครั้งคือแยกข้อมูลออกจากคำสั่งตั้งแต่ต้น (parameterize, execFile, textContent)

Authentication กับ Authorization

เริ่มจากแยกสองคำนี้ให้ชัด Authentication ตอบว่า "คุณคือใคร" ส่วน Authorization ตอบว่า "คุณทำอะไรได้บ้าง" ระบบที่ login ได้แล้วยังไม่ได้แปลว่าตรวจสิทธิ์ถูก ช่องโหว่ Broken Access Control เกิดบ่อยตรงที่ทีมทำ authentication เสร็จแล้วลืมว่ายังมี authorization อีกชั้น

เก็บ password ยังไงให้ถูก

Password ต้องเก็บเป็น hash ด้วยฟังก์ชันที่ออกแบบให้ช้าและกินหน่วยความจำ เช่น Argon2id หรือ bcrypt ซึ่งมี salt แยกรายบุคคลและปรับ cost factor ขึ้นได้เมื่อ hardware เร็วขึ้น ฟังก์ชัน hash ทั่วไปอย่าง SHA-256 เร็วเกินไป ผู้โจมตีที่ได้ database ไปลองเดา password ได้เร็วมากบน GPU ส่วนการเข้ารหัสแบบถอดกลับได้อย่าง AES ก็ไม่เหมาะ เพราะ key รั่วเมื่อไรก็ถอดได้ทั้งตาราง

import bcrypt from 'bcrypt';

const COST = 12; // ปรับตาม hardware ของ server ที่ใช้งานจริง

export const hashPassword = (plain) => bcrypt.hash(plain, COST);
export const verifyPassword = (plain, hash) => bcrypt.compare(plain, hash);

ข้อจำกัดที่ควรรู้ bcrypt อ่าน password ได้แค่ 72 ไบต์แรก ถ้าอนุญาตให้ตั้ง passphrase ยาวมากต้องคิดเรื่องนี้ OWASP Password Storage Cheat Sheet แนะนำ Argon2id เป็นตัวเลือกแรก และ bcrypt เมื่อใช้ Argon2id ไม่ได้ ตัวเลขพารามิเตอร์ล่าสุดให้เปิดดูจาก cheat sheet ตอนตั้งค่า

Session token ผ่าน cookie

หลัง login ระบบออก session id ที่สุ่มจนเดาไม่ได้แล้วส่งกลับใน cookie flag สามตัวที่ต้องตั้งคือ HttpOnly (JavaScript อ่านไม่ได้ ลดผลของ XSS), Secure (ส่งเฉพาะ HTTPS) และ SameSite (ลดโอกาสเกิด CSRF) อีกเรื่องที่ลืมกันบ่อยคือออก session id ใหม่ทุกครั้งหลัง login สำเร็จ เพื่อกัน session fixation ซึ่งผู้โจมตีเอา session id ที่รู้ล่วงหน้าไปให้เหยื่อใช้ แล้วรอจนเหยื่อ login

import session from 'express-session';

app.use(session({
  name: 'sid',
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 30 * 60 * 1000 },
}));

app.post('/login', async (req, res) => {
  const user = await authenticate(req.body.email, req.body.password);
  if (!user) return res.status(401).json({ error: 'invalid_credentials' });
  req.session.regenerate((err) => {          // ออก session id ใหม่หลัง login
    if (err) return res.sendStatus(500);
    req.session.userId = user.id;
    res.sendStatus(204);
  });
});
ข้อความ error ตอน login ต้องเหมือนกันทุกกรณีอย่าตอบว่า "ไม่พบอีเมลนี้" กับ "รหัสผ่านผิด" แยกกัน ไม่งั้นผู้โจมตีใช้เช็กได้ว่าอีเมลไหนมีบัญชีอยู่ในระบบ (user enumeration)

OAuth 2.0: Authorization Code + PKCE

OAuth 2.0 เป็น framework สำหรับ การมอบสิทธิ์ ให้แอปหนึ่งเข้าถึงทรัพยากรแทนผู้ใช้ โดยไม่ต้องให้ password กับแอปนั้น ตัวมันเองไม่ได้บอกว่าผู้ใช้คือใคร ถ้าต้องการยืนยันตัวตนก็ใช้ OpenID Connect (OIDC) ซึ่งต่อยอดบน OAuth 2.0 และเพิ่ม ID Token เข้ามา

สำหรับ SPA และ mobile app flow ที่ควรใช้คือ Authorization Code ร่วมกับ PKCE (RFC 7636) แอปสร้างค่าสุ่ม code_verifier เก็บไว้เอง ส่ง code_challenge ที่เป็น hash ของค่านั้นไปตอนขอ authorization แล้วค่อยส่ง verifier ตัวจริงตอนแลก code เป็น token ถึงผู้โจมตีดัก code ได้ก็แลก token ไม่ได้ เพราะไม่มี verifier ส่วน Implicit flow กับ Resource Owner Password Credentials ไม่ควรใช้กับแอปใหม่ แนวทางด้านความปลอดภัยของ OAuth และ draft ของ OAuth 2.1 ตัดสอง flow นี้ออก

import { randomBytes, createHash } from 'node:crypto';

const codeVerifier  = randomBytes(32).toString('base64url');
const codeChallenge = createHash('sha256').update(codeVerifier).digest('base64url');
const state         = randomBytes(16).toString('base64url');  // กัน CSRF ตอน callback

const url = new URL('https://auth.example.com/authorize');
url.search = new URLSearchParams({
  response_type: 'code',
  client_id: 'my-spa',
  redirect_uri: 'https://app.example.com/callback',
  scope: 'openid profile',
  state,
  code_challenge: codeChallenge,
  code_challenge_method: 'S256',
}).toString();
Flowใช้เมื่อหมายเหตุ
Authorization Code + PKCESPA, mobile, web ที่มี user loginแนะนำเป็นค่าเริ่มต้น ทั้ง public และ confidential client
Client Credentialsservice เรียก service ไม่มีผู้ใช้ไม่ใช่การ login ของคน
Implicitไม่ควรใช้กับแอปใหม่token โผล่ใน URL fragment เสี่ยงรั่ว
Resource Owner Passwordไม่ควรใช้กับแอปใหม่ให้แอปเห็น password ของผู้ใช้ ขัดกับเหตุผลที่มี OAuth

ตอน callback ต้องเช็กว่า state ที่ได้กลับมาตรงกับที่ส่งไป และฝั่ง Authorization Server ต้องจับคู่ redirect_uri แบบตรงตัวกับที่ลงทะเบียนไว้ ถ้าอนุญาตแบบ wildcard จะเปิดช่องให้ code ถูกส่งไปที่อื่นได้ และอย่าส่ง token ผ่าน query string เพราะไปค้างอยู่ใน log และ history

Data Privacy พื้นฐาน: PII, Consent และการเข้ารหัส

Beginner

Understand data privacy regulations basics (e.g., collect consent, anonymize PII, enable encryption in transit and at rest).

กฎหมายกว้าง ๆ และสิ่งที่ developer ต้องลงมือทำ

GDPR ของ EU และ PDPA ของไทย (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562) ใช้แนวคิดใกล้กัน ระดับนี้ไม่ต้องจำตัวบท แต่ต้องรู้หลักที่ลงมือทำในโค้ดได้เลย ส่วนรายละเอียดทางกฎหมายควรถามฝ่ายกฎหมายหรือ DPO เนื้อหานี้ไม่ใช่คำปรึกษาทางกฎหมาย

PII คือข้อมูลที่ระบุตัวบุคคลได้ ทั้งทางตรง (ชื่อ เลขบัตรประชาชน เบอร์โทร อีเมล) และทางอ้อมเมื่อรวมกัน (วันเกิด + รหัสไปรษณีย์ + เพศ) Consent คือความยินยอมที่ต้องชัดเจน ระบุวัตถุประสงค์ และถอนได้ แต่ consent ไม่ใช่ฐานทางกฎหมายเพียงอย่างเดียว ข้อมูลบางประเภทประมวลผลได้ตามสัญญา ตามหน้าที่ที่กฎหมายกำหนด หรือตามประโยชน์โดยชอบด้วยกฎหมาย ทีมต้องระบุให้ชัดว่าใช้ฐานไหนกับข้อมูลชุดไหน

หลักที่ลงมือได้ทันทีมีสี่เรื่อง เก็บเท่าที่จำเป็น (data minimization), กำหนดระยะเวลาเก็บแล้วลบเมื่อครบ, ไม่ใส่ PII ลง log และเข้ารหัสทั้งตอนส่งและตอนเก็บ

Anonymize ไม่เท่ากับ hash

ข้อมูลที่ anonymize จริงต้องย้อนกลับไประบุตัวบุคคลไม่ได้อีก ส่วนการแทนค่าด้วย token หรือ hash คือ pseudonymization ซึ่งยังถือเป็นข้อมูลส่วนบุคคลภายใต้ GDPR เพราะเมื่อมีข้อมูลเสริม หรือผู้โจมตีลอง hash อีเมลทั้งรายการมาเทียบ ก็โยงกลับได้ ข้อสอบชอบใช้จุดนี้เป็นตัวหลอก

เทคนิคย้อนกลับได้ไหมตัวอย่างใช้เมื่อ
Maskingไม่ย้อนที่ค่าที่แสดง (ต้นฉบับยังเก็บอยู่ที่อื่น)s*****i@example.comแสดงบนหน้าจอ และเขียน log
Pseudonymizationย้อนได้ถ้ามีข้อมูลเสริม (ตารางจับคู่ หรือ key)แทนอีเมลด้วย user_8812, HMAC ของอีเมลวิเคราะห์ข้อมูลที่ยังต้องโยงกลับในบางกรณี
Anonymizationย้อนไม่ได้จริงรวมเป็นสถิติ, ตัดตัวระบุทิ้งแล้วประเมินความเสี่ยงการระบุตัวเผยแพร่หรือแชร์ข้อมูลเชิงสถิติ
Encryptionถอดได้ถ้ามี keyAES-GCM, disk encryptionปกป้องข้อมูลที่ยังต้องใช้งานจริง
// mask ก่อนเขียน log: somchai@example.com -> s*****i@example.com
export function maskEmail(email) {
  const [local, domain] = email.split('@');
  if (!domain || local.length < 2) return '***';
  return local[0] + '*'.repeat(local.length - 2) + local.at(-1) + '@' + domain;
}

logger.info({ event: 'signup', email: maskEmail(user.email), userId: user.id });

Encryption in transit และ at rest

In transit คือข้อมูลระหว่างทาง ใช้ TLS (1.2 ขึ้นไป และควรเปิด 1.3 เมื่อรองรับ) ทั้งระหว่าง browser กับ server และระหว่าง service กับ database เสริมด้วย HSTS ให้ browser ไม่ยอมคุยด้วย HTTP At rest คือข้อมูลที่นอนอยู่ใน disk, database หรือ backup ใช้การเข้ารหัสระดับ volume หรือ database และสำหรับ field ที่อ่อนไหวมากอาจเข้ารหัสระดับ application เพิ่ม เป้าหมายคือถ้า snapshot หรือ backup หลุด ผู้ที่ได้ไฟล์ไปต้องยังอ่านเนื้อหาไม่ได้

Key ต้องไม่อยู่ที่เดียวกับข้อมูลถ้าเก็บ key ไว้ใน repository หรือไฟล์ข้าง ๆ snapshot ก็เท่ากับไม่ได้เข้ารหัส ใช้ KMS หรือ secret manager แล้วแยกสิทธิ์การใช้ key ออกจากสิทธิ์อ่านข้อมูล

เพิ่มเติมเชิงลึก: Retention, การลบ และการแจ้งเหตุ

หลักการจำกัดระยะเวลาเก็บ (storage limitation) แปลว่าต้องมีนโยบายว่าข้อมูลแต่ละประเภทเก็บนานเท่าไรและลบอย่างไร ฝั่งโค้ดทำได้ด้วยการเก็บวันที่ลงฐานข้อมูล แล้วมี job ลบหรือ anonymize ตามรอบ อย่าลืมว่า backup และ log ก็ถือเป็นที่เก็บข้อมูลด้วย ถ้าเจ้าของข้อมูลขอลบ ต้องวางแผนว่า backup จัดการอย่างไร เช่น ให้หมดอายุตามรอบแทนการแก้ไฟล์ backup ย้อนหลัง

เมื่อเกิดเหตุข้อมูลรั่ว ทั้ง PDPA และ GDPR กำหนดให้แจ้งหน่วยงานกำกับดูแลภายใน 72 ชั่วโมงนับจากที่รู้เหตุ ในกรณีที่เหตุนั้นมีความเสี่ยงต่อสิทธิของเจ้าของข้อมูล ซึ่งเป็นเหตุผลที่ audit log และกระบวนการ incident response ต้องพร้อมก่อนเกิดเหตุ ไม่ใช่เพิ่งมาคิดหลังรั่ว รายละเอียดเงื่อนไขให้ตรวจกับฝ่ายกฎหมาย

import { randomBytes, createCipheriv, createDecipheriv } from 'node:crypto';

// key ต้องยาว 32 ไบต์ และมาจาก KMS / secret manager ไม่ใช่ค่าที่ hardcode
export function encrypt(plain, key) {
  const iv = randomBytes(12);                       // GCM ใช้ nonce 12 ไบต์ และห้ามซ้ำกับ key เดิม
  const c = createCipheriv('aes-256-gcm', key, iv);
  const data = Buffer.concat([c.update(plain, 'utf8'), c.final()]);
  return Buffer.concat([iv, c.getAuthTag(), data]); // เก็บ iv + tag ไปพร้อม ciphertext
}

export function decrypt(blob, key) {
  const iv = blob.subarray(0, 12), tag = blob.subarray(12, 28), data = blob.subarray(28);
  const d = createDecipheriv('aes-256-gcm', key, iv);
  d.setAuthTag(tag);                                // ถ้าข้อมูลถูกแก้ final() จะ throw
  return Buffer.concat([d.update(data), d.final()]).toString('utf8');
}

ประเด็นที่ข้อสอบชอบถามคือ nonce ซ้ำกับ key เดิมใน GCM ทำให้ความปลอดภัยพังทั้งระบบ ไม่ใช่แค่ลดลง และ AES-ECB ไม่ควรใช้เพราะข้อมูลที่เหมือนกันได้ ciphertext เหมือนกัน เห็นรูปแบบออกมา

สำหรับระบบที่มีข้อมูลเยอะ ใช้ envelope encryption สร้าง data key ไว้เข้ารหัสข้อมูล แล้วให้ KMS เข้ารหัส data key อีกชั้น ข้อดีคือหมุน master key ได้โดยไม่ต้องเข้ารหัสข้อมูลทั้งหมดใหม่ และสิทธิ์เรียก KMS แยกควบคุมได้

JWT (JSON Web Token) ประกอบด้วย header, payload และ signature แบบ base64url สิ่งที่คนเข้าใจผิดบ่อยที่สุดคือ payload ไม่ได้ถูกเข้ารหัส ใครได้ token ไปก็อ่านได้ signature แค่รับประกันว่าไม่ถูกแก้ ดังนั้นห้ามใส่ข้อมูลลับลงไป

การ verify ที่ถูกต้องต้องตรวจครบทุกข้อ ไม่ใช่แค่ decode มาอ่านค่า

import { jwtVerify, createRemoteJWKSet } from 'jose';

const JWKS = createRemoteJWKSet(new URL('https://auth.example.com/.well-known/jwks.json'));

export async function verifyAccessToken(token) {
  const { payload } = await jwtVerify(token, JWKS, {
    issuer: 'https://auth.example.com',
    audience: 'orders-api',
    algorithms: ['RS256'],        // allowlist ไม่รับ none และไม่รับ HS256
    clockTolerance: 5,            // ยอมเหลื่อมของนาฬิกา 5 วินาที
  });
  return payload;
}

เรื่อง lifetime: access token ควรอายุสั้น (หลักนาทีถึงหลักสิบนาที) เพราะ JWT แบบ stateless เพิกถอนกลางทางยาก ส่วน refresh token อายุยาวกว่า เก็บฝั่ง server แล้วทำ rotation คือออกตัวใหม่ทุกครั้งที่ใช้และเพิกถอนตัวเก่า ถ้ามีคนเอา refresh token ที่ใช้ไปแล้วมาใช้ซ้ำ ให้เพิกถอนทั้งชุดของ session นั้น เพราะแปลว่ามี token รั่ว

เก็บ token ไว้ที่ไหนใน browserถ้าเก็บใน localStorage สคริปต์ XSS อ่านได้ทันที ตัวเลือกที่ปลอดภัยกว่าสำหรับเว็บคือ cookie แบบ HttpOnly; Secure; SameSite ซึ่งต้องมีมาตรการ CSRF คู่ไปด้วย ไม่มีที่เก็บฝั่ง browser ที่ปลอดภัยจาก XSS ได้สมบูรณ์ การกัน XSS จึงยังสำคัญที่สุด

RBAC และสิ่งที่มันแก้ไม่ได้

RBAC (Role-Based Access Control) ผูกสิทธิ์เข้ากับ role แล้วกำหนด role ให้ผู้ใช้ ข้อดีคือบริหารง่าย เพิ่มคนใหม่ก็แค่ให้ role ข้อจำกัดคือ role บอกได้แค่ว่าทำประเภทนี้ได้ ไม่ได้บอกว่าทำกับชิ้นไหน ได้ เช่น role support อ่าน ticket ได้ แต่ถ้า ticket ของลูกค้าคนอื่นล่ะ ต้องมีการตรวจความเป็นเจ้าของ (ownership) หรือ attribute เพิ่ม ซึ่งเป็นที่มาของ ABAC

จัดลำดับความรุนแรง: CVSS ไม่ใช่คำตอบเดียว

CVSS ให้คะแนน 0.0 ถึง 10.0 จากลักษณะของช่องโหว่ เช่น เจาะผ่านเครือข่ายได้ไหม ต้องมีสิทธิ์ก่อนไหม กระทบความลับ ความถูกต้อง และความพร้อมใช้ แต่คะแนนนี้ไม่รู้บริบทองค์กรเรา ช่องโหว่ 9.8 บนระบบภายในที่แยกจากเครือข่ายอาจเร่งด่วนน้อยกว่า 7.5 บนระบบที่เปิดออกอินเทอร์เน็ตและมี exploit แพร่หลาย ทีมจึงนิยมดูร่วมกับสัญญาณอื่น เช่น มีรายการอยู่ใน CISA KEV (Known Exploited Vulnerabilities) หรือไม่ และค่า EPSS ที่ประเมินโอกาสถูกโจมตี รวมถึงความสำคัญของระบบนั้นต่อธุรกิจ

ตัวเลือกที่ถูกในข้อสอบ prioritizationมักเป็นแบบ "พิจารณาความรุนแรง ความสามารถในการถูกโจมตี และผลกระทบต่อธุรกิจร่วมกัน" ส่วนตัวเลือกที่ตัดสินจากคะแนน CVSS อย่างเดียว หรือแก้ตามลำดับที่เจอ มักเป็นตัวหลอก

Security test ที่เขียนเป็น automated test ได้

ช่องโหว่ที่เคยแก้แล้วควรมี test กันย้อนกลับ ไม่งั้นมีคนแก้โค้ดใหม่แล้วช่องโหว่เดิมกลับมาโดยไม่มีใครรู้ ตัวอย่างนี้ทดสอบว่า user A เปิด order ของ user B ไม่ได้

import { test } from 'node:test';
import assert from 'node:assert/strict';

test('user A เปิด order ของ user B ไม่ได้ (BOLA)', async () => {
  const orderOfB = await createOrder({ owner: userB });
  const res = await api.get(`/orders/${orderOfB.id}`, { as: userA });
  assert.equal(res.status, 404);          // ไม่เปิดเผยแม้แต่ว่ามี order นี้อยู่
});

test('บัญชีธรรมดาส่ง role=admin มาเองไม่ได้ (mass assignment)', async () => {
  const res = await api.patch('/me', { body: { name: 'x', role: 'admin' }, as: userA });
  const me = await api.get('/me', { as: userA });
  assert.notEqual(me.body.role, 'admin');
});

เพิ่มเติมเชิงลึก: Rules of Engagement ก่อนทดสอบ

งานทดสอบเจาะระบบมืออาชีพเริ่มจากเอกสารที่ตกลงกันก่อน ระบุ scope (ระบบ ช่วงเวลา IP ที่ยิงได้), สิ่งที่ห้ามทำ (เช่น DoS, social engineering กับพนักงานจริงถ้าไม่ได้ตกลง), ช่องทางติดต่อฉุกเฉิน และวิธีจัดการข้อมูลที่พบระหว่างทดสอบ ฝั่งทีม developer ก็ควรเตรียม environment ที่แยกจาก production และมีข้อมูลจำลอง เพราะการสแกนแบบ active บางครั้งสร้างข้อมูลขยะหรือทำให้ระบบช้า

Secure API: Validation, Rate Limiting, Token Auth และ API Gateway + WAF

Intermediate

Design secure APIs (e.g., input validation, rate limiting, token-based authentication, API Gateway with WAF).

API ต้องไม่เชื่อ client

ช่องโหว่ของ API ไม่เหมือนเว็บทั่วไปตรงที่ผู้โจมตีไม่ต้องผ่านหน้าจอ ยิง request ตรงด้วยสคริปต์ได้เลย OWASP มีรายการแยกคือ OWASP API Security Top 10 (ฉบับ 2023) อันดับต้นคือ API1 Broken Object Level Authorization (BOLA), API2 Broken Authentication, API3 Broken Object Property Level Authorization (รวม excessive data exposure และ mass assignment เข้าด้วยกัน), API4 Unrestricted Resource Consumption และ API5 Broken Function Level Authorization

มาตรการที่ใช้ซ้อนกันมีสี่ชั้น

ชั้นทำอะไรกันอะไร
API Gatewayจุดเข้าเดียว ตรวจ token เบื้องต้น, rate limit, routing, loggingการเข้าถึงโดยไม่ผ่านตัวควบคุมกลาง
WAFกรอง request ที่ตรง signature การโจมตีที่รู้จักการโจมตีพื้นฐานจำนวนมาก, บอทบางส่วน
Service เองvalidate schema, ตรวจสิทธิ์ระดับ object และ functionตรรกะธุรกิจที่ผิด ซึ่ง gateway ไม่รู้
Responseส่งเฉพาะฟิลด์ที่จำเป็นข้อมูลเกินจำเป็นรั่ว (excessive data exposure)
WAF ไม่ใช่เหตุผลให้ข้ามการแก้โค้ดWAF ตรวจจาก pattern ของ request และไม่เข้าใจตรรกะของแอป เช่น มันไม่รู้ว่า user A ไม่ควรเห็น order ของ user B การเปลี่ยนเลข id ใน URL เป็น request ที่หน้าตาปกติทุกประการ จึงต้องแก้ที่การตรวจสิทธิ์ในโค้ด

Input validation แบบ schema ที่เข้มงวด

import { z } from 'zod';

const CreateOrder = z.object({
  productId: z.string().regex(/^P\d{6}$/),
  quantity: z.number().int().min(1).max(100),
  note: z.string().max(200).optional(),
}).strict();                       // ปฏิเสธฟิลด์ที่ไม่รู้จัก กัน mass assignment

app.post('/orders', requireAuth, (req, res) => {
  const parsed = CreateOrder.safeParse(req.body);
  if (!parsed.success) return res.status(400).json({ error: 'invalid_request' });
  // ใช้ parsed.data เท่านั้น ไม่ใช้ req.body ต่อ
});

จำกัดขนาดของ body, จำนวนรายการใน array และความลึกของ JSON ด้วย ไม่งั้นส่งก้อนใหญ่มาให้ server กินหน่วยความจำได้ (API4 Unrestricted Resource Consumption) ถ้าเป็น GraphQL ให้จำกัดความลึกและความซับซ้อนของ query

Rate limiting: เลือกอัลกอริทึมและกุญแจนับ

Rate limiting กัน brute force, credential stuffing และการใช้ทรัพยากรเกินควร อัลกอริทึมที่พบบ่อยคือ token bucket (อนุญาต burst ได้ในขอบเขต) และ sliding window (นับตามหน้าต่างเวลาที่เลื่อนไปเรื่อย ๆ) การเลือก key ที่ใช้นับสำคัญพอกัน ถ้านับตาม IP อย่างเดียว คนหลัง NAT เดียวกันจะโดนจำกัดพร้อมกัน และผู้โจมตีที่มีหลาย IP ก็ผ่านได้ ควรนับหลายแบบพร้อมกัน เช่น ตาม user, ตาม API key และตาม IP

export class TokenBucket {
  constructor(capacity, refillPerSec, now = () => Date.now()) {
    this.capacity = capacity; this.refillPerSec = refillPerSec;
    this.tokens = capacity; this.last = now(); this.now = now;
  }
  allow(cost = 1) {
    const t = this.now();
    this.tokens = Math.min(this.capacity, this.tokens + ((t - this.last) / 1000) * this.refillPerSec);
    this.last = t;
    if (this.tokens < cost) return false;   // ตอบ 429 Too Many Requests พร้อม Retry-After
    this.tokens -= cost;
    return true;
  }
}

ตัวอย่างนี้เก็บสถานะในหน่วยความจำของ process เดียว ถ้ามีหลาย instance ต้องเก็บตัวนับไว้ที่กลาง เช่น Redis ไม่งั้นแต่ละเครื่องนับแยกกัน และ endpoint อย่าง login กับ reset password ควรจำกัดเข้มกว่า endpoint ทั่วไป

Token-based authentication ใน API

ใช้ Bearer token ใน header Authorization ไม่ใส่ใน URL เพราะค้างอยู่ใน log ของ proxy และ browser history ตรวจ scope ของ token ด้วยว่าอนุญาตให้ทำสิ่งที่เรียกมาหรือไม่ และใช้ HTTPS เท่านั้น ระหว่าง service ภายในก็ควรใช้ mTLS หรือ token ที่ออกให้ service นั้นโดยเฉพาะ ไม่ใช้ shared secret ตัวเดียวทั้งระบบ

เพิ่มเติมเชิงลึก: ปัญหาที่ gateway ช่วยไม่ได้

Gateway ตรวจ token ได้ว่าถูกต้องและยังไม่หมดอายุ แต่การตัดสินว่า token นี้เข้าถึง /orders/1002 ได้ไหมต้องรู้ว่า order นั้นของใคร ซึ่งข้อมูลนี้อยู่ใน service ถ้าย้ายการตรวจไปไว้ที่ gateway ทั้งหมดจะผูกตรรกะธุรกิจไว้ผิดที่ แนวปฏิบัติที่นิยมคือ gateway ทำ authentication, rate limit และตรวจ schema คร่าว ๆ แล้ว service แต่ละตัวทำ authorization เอง เพราะ service เป็นที่เดียวที่รู้ความสัมพันธ์ของข้อมูลจริง

Security Monitoring และ Incident Response

Intermediate

Monitor security events and respond to incidents (e.g., detect suspicious activity, execute incident response plan).

ตรวจจับอะไร และจะรู้ได้อย่างไรว่ามีเหตุ

Monitoring มีประโยชน์เมื่อรู้ว่าต้องมองหาอะไร สัญญาณที่เป็นตัวอย่างได้แก่ login ล้มเหลวจำนวนมากจาก IP หรือบัญชีเดียวกัน (brute force) หรือล้มเหลวกับหลายบัญชีจากแหล่งเดียว (credential stuffing/password spraying), login สำเร็จจากสถานที่หรืออุปกรณ์ที่ไม่เคยเห็น, การเปลี่ยนสิทธิ์ผู้ใช้, การดึงข้อมูลปริมาณมากผิดปกติ, การเข้าถึง endpoint ที่ปกติไม่มีใครเรียก และ error 5xx พุ่งหลังมี request รูปแบบแปลก

ข้อสังเกตจาก OWASP A09 คือ log เฉย ๆ ไม่พอ ต้องมี alert ที่ถูกส่งถึงคนที่ลงมือได้ และมีเกณฑ์ที่ไม่ดังจนคนเมินทิ้ง ถ้า alert มาวันละร้อยตัวแล้วไม่มีใครอ่าน ก็เท่ากับไม่มี

วงจร Incident Response

NIST SP 800-61 (ฉบับ Rev. 2 แบ่งสี่ช่วง ฉบับ Rev. 3 ปรับให้สอดคล้องกับ NIST Cybersecurity Framework 2.0) กรอบที่ข้อสอบหยิบมาใช้บ่อยคือแบบสี่ช่วงของ Rev. 2 ส่วนตำราหลายเล่มแตกเป็นหกขั้นตอน (Preparation, Identification, Containment, Eradication, Recovery, Lessons Learned) ควรรู้ทั้งสองมุม

ช่วงทำอะไรตัวอย่าง
Preparationเตรียมทีม แผน เครื่องมือ และฝึกซ้อมกำหนดผู้ติดต่อ, เตรียม playbook, ตั้ง log ส่วนกลาง
Detection & Analysisยืนยันว่าเป็นเหตุจริง ประเมินขอบเขตและความรุนแรงดู log, หาบัญชีและเครื่องที่ได้รับผลกระทบ, เก็บหลักฐาน
Containment, Eradication & Recoveryจำกัดความเสียหาย กำจัดต้นเหตุ แล้วกู้ระบบตัดเครื่องออกจากเครือข่าย, เพิกถอน token, แพตช์ช่องโหว่, restore จาก backup ที่สะอาด
Post-Incident Activityทบทวนหลังเหตุ ปรับปรุงกระบวนการblameless post-mortem, เพิ่ม detection rule, แก้ที่ต้นเหตุ
ลำดับที่ข้อสอบชอบถามเจอเหตุแล้วอย่าเพิ่งรีบปิดหรือลบเครื่อง เพราะอาจทำลายหลักฐาน (volatile data) ให้จำกัดความเสียหายก่อนโดยแยกเครื่องออกจากเครือข่าย เก็บหลักฐาน แล้วจึงกำจัดต้นเหตุ และอย่า restore ระบบกลับขึ้นมาก่อนปิดช่องที่ผู้โจมตีใช้เข้ามา ไม่งั้นโดนซ้ำ

ตัวอย่างสถานการณ์: token รั่ว

ทีมพบว่า API key ของ production หลุดเข้า public repository ลำดับที่เหมาะสมคือ เพิกถอน (revoke) key ทันทีและออกตัวใหม่, ตรวจ log การใช้ key นั้นย้อนหลังว่ามีการเรียกที่ไม่ใช่ของเรา, ประเมินว่าข้อมูลอะไรถูกเข้าถึง ถ้ามีข้อมูลส่วนบุคคลต้องแจ้งตามกำหนดเวลาของกฎหมาย, จากนั้นค่อยล้างประวัติใน repository และเพิ่ม secret scanning ไม่ใช่เริ่มจากการลบ commit แล้วคิดว่าจบ

เพิ่มเติมเชิงลึก: ตัวชี้วัดและการซ้อม

ทีมที่จริงจังจะวัด MTTD (mean time to detect) และ MTTR (mean time to respond/recover) เพื่อดูว่าตรวจจับและรับมือเร็วขึ้นหรือช้าลง และซ้อมด้วย tabletop exercise คือนั่งคุยตามสถานการณ์สมมุติ เพื่อดูว่าแผนที่เขียนไว้ใช้ได้จริงไหม ใครติดต่อใคร ใครมีอำนาจตัดสินใจปิดระบบ ซึ่งเป็นเรื่องที่ไม่มีใครรู้จนกว่าจะซ้อม

ระดับ Advance

ระดับนี้ไม่ได้ถามว่า "ช่องโหว่นี้แก้ยังไง" แต่ถามว่า "ระบบทั้งระบบควรออกแบบยังไง และจะพาองค์กรไปถึงตรงนั้นยังไง" ครอบคลุม Zero Trust ที่ใช้ identity เป็นศูนย์กลาง, การนำ DevSecOps และความปลอดภัยของ CI/CD pipeline, และ threat modeling กับการประเมินความเสี่ยงขั้นสูง

คำตอบที่ดีในระดับนี้มักเป็นการชั่งน้ำหนัก (trade-off) ไม่ใช่คำตอบตายตัว ข้อสอบจึงมักมีตัวเลือกที่ "ถูกบางส่วน" หลายตัว ให้เลือกตัวที่ตรงกับสถานการณ์ที่สุด

11

Zero Trust Architecture และ Identity-first Access Control

Advance

Architect zero-trust security architecture with identity-first access control.

Zero Trust ไม่ใช่ผลิตภัณฑ์ที่ซื้อมาติด

โมเดลเดิมสร้างกำแพงรอบเครือข่ายภายในแล้วเชื่อใจทุกอย่างที่อยู่ข้างใน ปัญหาคือผู้โจมตีที่เข้ามาได้แล้ว (เช่น ผ่านเครื่องพนักงานที่ติด malware) เคลื่อนที่ไปทั่วเครือข่ายได้ง่าย (lateral movement) Zero Trust เปลี่ยนสมมติฐานเป็น "ไม่มีที่ไหนที่เชื่อใจโดยอัตโนมัติ" ทุก request ต้องถูกพิสูจน์ตัวตนและตรวจสิทธิ์ ไม่ว่ามาจากในหรือนอกเครือข่าย

เอกสารอ้างอิงหลักคือ NIST SP 800-207 Zero Trust Architecture ซึ่งบอกชัดว่า Zero Trust เป็นชุดแนวคิดและสถาปัตยกรรม ไม่ใช่เทคโนโลยีเดียว ข้ออ้างของผู้ขายที่ว่า "ซื้อตัวนี้แล้วได้ Zero Trust" จึงเป็นข้อควรระวัง หลักที่ใช้อธิบายได้สามข้อ

หลักความหมายตัวอย่างการทำจริง
Verify explicitlyตัดสินจากข้อมูลที่มีทั้งหมดทุกครั้ง ไม่ใช่แค่ตำแหน่งเครือข่ายตรวจ identity, MFA, สถานะอุปกรณ์, ตำแหน่ง, ความเสี่ยงของ session
Least privilegeให้สิทธิ์น้อยที่สุดและเฉพาะช่วงเวลาที่ต้องใช้just-in-time access, credential อายุสั้น, แยกสิทธิ์ตามหน้าที่
Assume breachออกแบบโดยถือว่าส่วนหนึ่งถูกเจาะไปแล้วmicrosegmentation, เข้ารหัสทุกเส้นทาง, log และตรวจจับต่อเนื่อง

องค์ประกอบตาม NIST SP 800-207

หัวใจคือแยก "คนตัดสินใจ" ออกจาก "คนบังคับใช้" Policy Decision Point (PDP) ประกอบด้วย Policy Engine (PE) ที่ตัดสินใจว่าอนุญาตหรือไม่ และ Policy Administrator (PA) ที่สั่งให้เปิดหรือปิดเส้นทางการเชื่อมต่อ ส่วน Policy Enforcement Point (PEP) อยู่หน้าทรัพยากรและทำตามคำตัดสินนั้น PE รับข้อมูลประกอบจากหลายแหล่ง เช่น identity provider, ระบบจัดการอุปกรณ์, threat intelligence และ log

ผู้ใช้/service ──request──▶ [ PEP ] ──ถามคำตัดสิน──▶ [ PDP: Policy Engine + Policy Administrator ]
                              │                                   ▲
                              │ อนุญาต → เปิดเส้นทางไป              │ ข้อมูลประกอบ: identity, device posture,
                              ▼                                   │ risk score, log, threat intel
                         [ ทรัพยากร ]                              │

Identity-first: ทำให้ identity เป็นขอบเขตความปลอดภัยใหม่

เมื่อไม่ใช้เครือข่ายเป็นเส้นแบ่ง identity จึงกลายเป็นจุดควบคุมหลัก ทั้งของคน (employee, customer) และของ workload (service, pipeline, container) สิ่งที่ต้องมี ได้แก่ IdP กลางพร้อม MFA ที่ทน phishing สำหรับบัญชีสำคัญ, อัตลักษณ์ของ service ที่ออกให้แบบอายุสั้นและหมุนอัตโนมัติ (เช่น workload identity, SPIFFE/SPIRE หรือ OIDC federation ของ cloud), การตรวจสถานะอุปกรณ์ก่อนอนุญาต และ conditional access ที่ปรับตามความเสี่ยง

ข้อควรระวังคือการรวมศูนย์ identity ทำให้ IdP เป็นเป้าที่ค่าความเสียหายสูงมาก ต้องป้องกันเป็นพิเศษ มีบัญชี break-glass ที่เก็บแยกและมีการเฝ้าระวัง และมีแผนรับมือตอน IdP ล่ม เพราะถ้าทุกอย่างพึ่ง IdP และ policy ไม่ตอบ ระบบจะเข้าไม่ได้เลย

ตัวอย่าง policy as code และ fail closed

นโยบายที่เขียนเป็นโค้ดรีวิวและทดสอบได้ ตัวอย่างนี้ใช้ภาษา Rego ของ Open Policy Agent (OPA) ใช้ default allow := false เพื่อให้ผลเริ่มต้นเป็นปฏิเสธ (deny by default) และถ้าเรียก PDP ไม่ได้ฝั่ง PEP ต้องปฏิเสธเช่นกัน (fail closed)

package authz
import rego.v1

default allow := false

allow if {
  input.user.mfa == true                       # ผ่าน MFA แล้ว
  input.device.compliant == true               # อุปกรณ์ผ่านเกณฑ์
  input.action == "read"
  input.user.role in {"support", "admin"}
  input.resource.tenant == input.user.tenant   # ตรวจขอบเขตข้อมูลด้วย ไม่ใช่แค่ role
}
Fail open เป็นความผิดพลาดที่เจอบ่อยทีมที่กลัวระบบล่มมักตั้งให้ "ถ้าเรียก policy service ไม่ได้ ให้ผ่านไปก่อน" ซึ่งเท่ากับผู้โจมตีทำให้ policy service ล่มแล้วผ่านได้ทุกอย่าง ทางที่ถูกคือ fail closed คู่กับการออกแบบให้ PDP พร้อมใช้สูง และ cache คำตัดสินช่วงสั้น ๆ

วิธีเริ่มย้ายไปสู่ Zero Trust

ไม่มีใครเปลี่ยนทั้งองค์กรในครั้งเดียว ลำดับที่ใช้ได้จริงคือ สำรวจว่ามี identity, อุปกรณ์, แอป และข้อมูลอะไรบ้าง, เริ่มจากทรัพยากรที่มีค่าที่สุด (protect surface) แทนที่จะพยายามป้องกันทุกอย่าง, บังคับ MFA และรวม IdP, ลดสิทธิ์ที่กว้างเกินจำเป็น, แบ่งเครือข่ายย่อย (microsegmentation) ตามความสำคัญ, เก็บ log ให้ครบ แล้ววัดผลก่อนขยายขอบเขต

เพิ่มเติมเชิงลึก: VPN, Service Mesh และ trade-off

VPN แบบเดิมให้สิทธิ์เข้าถึงทั้งเครือข่ายเมื่อ login สำเร็จ ซึ่งขัดกับหลัก least privilege ทางเลือกคือ Zero Trust Network Access (ZTNA) ที่ให้เข้าถึงเป็นรายแอป ตามผลการตรวจ identity และอุปกรณ์ ส่วนระหว่าง service ภายใน mTLS ผ่าน service mesh ช่วยให้ทุกการเชื่อมต่อถูกเข้ารหัสและมี identity ของ service ที่ตรวจได้ แต่แลกกับความซับซ้อนในการดูแล certificate และ latency ที่เพิ่มขึ้น การเลือกว่าจะทำถึงระดับไหนจึงต้องเทียบกับความเสี่ยงและต้นทุนของระบบนั้น ไม่ใช่ทำให้สุดทุกที่

Advance

Lead security transformation initiatives (e.g., implementing DevSecOps, securing CI/CD pipelines).

DevSecOps คือการย้ายความปลอดภัยให้อยู่ในงานประจำวัน

แนวคิด shift-left คือเอาการตรวจความปลอดภัยไปไว้ใกล้ตอนเขียนโค้ดให้มากที่สุด เพราะแก้ตอนต้นถูกกว่าและเร็วกว่าไปเจอบน production แต่ shift-left ไม่ได้แปลว่าตรวจแค่ต้นทาง ยังต้องมี shift-right ด้วย คือเฝ้าระวังและตรวจจับตอนระบบรันจริง การเปลี่ยนวัฒนธรรมสำคัญพอกับการติดตั้งเครื่องมือ ถ้าทีมความปลอดภัยเป็นด่านที่ขวางตอนท้าย ทีมพัฒนาจะหาทางเลี่ยง

ตัว pipeline เองก็เป็นเป้าโจมตี

CI/CD runner มักมีสิทธิ์สูงมาก เข้าถึง secret, deploy ขึ้น production และเขียน artifact ได้ ผู้โจมตีจึงสนใจเจาะ pipeline มากกว่าเจาะแอปตรง ๆ OWASP ปี 2025 สะท้อนเรื่องนี้ด้วยหมวด A03 Software Supply Chain Failures มาตรการหลักได้แก่

ความเสี่ยงมาตรการ
token ของ pipeline มีสิทธิ์กว้างเกินไปกำหนด permissions ขั้นต่ำต่อ job, ใช้ token อายุสั้น
เก็บ cloud credential แบบ long-lived เป็น secretใช้ OIDC federation ให้ pipeline ขอ credential ชั่วคราวจาก cloud
action หรือ dependency ของบุคคลที่สามถูกแก้pin เวอร์ชันด้วย commit SHA เต็ม, ตรวจด้วย SCA, ใช้ lockfile
โค้ดจาก pull request ของคนนอกรันด้วยสิทธิ์สูงแยก workflow สำหรับ PR ภายนอกให้ไม่มี secret, ระวัง pull_request_target
artifact ถูกสลับระหว่างทางลงนาม artifact และตรวจ provenance ตอน deploy (เช่น cosign, SLSA)
push ตรงเข้า main โดยไม่มีคนรีวิวbranch protection, ต้องมี review และ status check ผ่าน
name: ci
on:
  pull_request:

permissions:
  contents: read              # ค่าเริ่มต้นของทั้ง workflow: อ่านอย่างเดียว

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      # pin ด้วย commit SHA เต็ม (ตัวอย่างนี้ใช้ค่าสมมุติ ให้ใช้ SHA จริงของเวอร์ชันที่ตรวจแล้ว)
      - uses: actions/checkout@0000000000000000000000000000000000000000
      - run: npm ci
      - run: npm audit --audit-level=high
      - run: npm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write         # ขอ OIDC token เพื่อแลก credential ชั่วคราวจาก cloud
    steps:
      - uses: actions/checkout@0000000000000000000000000000000000000000
      - run: ./scripts/deploy.sh   # ไม่มี long-lived secret เก็บไว้ใน repository
pull_request_target เป็นกับดักที่เจอบ่อยtrigger นี้รันใน context ของ repository ปลายทางและเข้าถึง secret ได้ ถ้า workflow เช็กเอาโค้ดของ PR (ซึ่งมาจากคนนอก) ไปรันด้วย ผู้โจมตีส่ง PR ที่มีสคริปต์อันตรายแล้วขโมย secret ได้ ถ้าต้องใช้ ให้รันเฉพาะโค้ดจาก base branch หรือไม่ checkout โค้ดจาก PR

นำการเปลี่ยนแปลงให้ได้ผล: Lead Transformation

ข้อสอบระดับนี้มักถามว่า "ทีมต่อต้านเครื่องมือใหม่ ควรทำอะไรก่อน" คำตอบที่ถูกมักเน้นให้ความปลอดภัยเป็นเรื่องที่ทีมเข้าใจและได้ประโยชน์ ไม่ใช่การบังคับจากข้างบน

แนวทางรายละเอียด
Paved roadทำทางที่ปลอดภัยให้เป็นทางที่ง่ายที่สุด เช่น template ของ pipeline ที่มีการสแกนอยู่แล้ว ทีมใช้แล้วได้ความปลอดภัยโดยไม่ต้องตั้งค่าเอง
Security championsตั้งตัวแทนในแต่ละทีมพัฒนา ช่วยกระจายความรู้และเป็นสะพานกับทีมความปลอดภัย
เริ่มเล็กและวัดผลนำร่องกับทีมหรือบริการหนึ่ง ปรับ rule ลด false positive แล้วค่อยขยาย
Guardrail มากกว่า gateบล็อกเฉพาะสิ่งที่รุนแรงและแน่ชัด ส่วนที่เหลือรายงานและมีกำหนดแก้
กระบวนการยกเว้นมีทางขอ risk acceptance ที่มีผู้อนุมัติ เหตุผล และวันหมดอายุ ไม่ใช่ปิด rule แบบเงียบ ๆ

ตัวชี้วัดที่ใช้ดูความคืบหน้า เช่น เวลาเฉลี่ยในการแก้ช่องโหว่ระดับสูง, สัดส่วนบริการที่มีการสแกนครบ, จำนวนช่องโหว่ที่หลุดไปถึง production และความถี่ของการ deploy ซึ่งต้องไม่ลดลงจนทีมรู้สึกว่าความปลอดภัยทำให้ช้า ไม่ควรวัดความสำเร็จจากจำนวน finding ที่เจอ เพราะตัวเลขนั้นขึ้นลงตามเครื่องมือมากกว่าตามความปลอดภัยจริง

เพิ่มเติมเชิงลึก: SBOM, SLSA และ artifact signing

SBOM (Software Bill of Materials) คือรายการส่วนประกอบของซอฟต์แวร์ ทำให้ตอบได้เร็วเมื่อมีช่องโหว่ใหม่ว่าระบบไหนใช้ library นั้นอยู่ รูปแบบที่พบบ่อยคือ SPDX และ CycloneDX SLSA (Supply-chain Levels for Software Artifacts) เป็นกรอบที่ระบุระดับความน่าเชื่อถือของกระบวนการ build และ provenance ว่า artifact นี้สร้างจากโค้ดไหน ด้วยกระบวนการอะไร ส่วนการลงนามด้วยเครื่องมืออย่าง cosign (Sigstore) ช่วยให้ตอน deploy ตรวจได้ว่า image มาจาก pipeline ของเราจริง ไม่ได้ถูกสลับ สามอย่างนี้ตอบปัญหาคนละมุม SBOM บอกว่ามีอะไรอยู่ข้างใน, provenance บอกว่าสร้างมาจากอะไรอย่างไร และ signature บอกว่าไม่ถูกแก้หลังจากนั้น

Threat Modeling และ Risk Assessment ขั้นสูง

Advance

Perform advanced threat modeling and risk assessment.

Threat modeling ตอบสี่คำถาม

กรอบที่ใช้กันแพร่หลาย (จาก Threat Modeling Manifesto) ถามสี่ข้อ ได้แก่ เรากำลังสร้างอะไร, อะไรผิดพลาดได้บ้าง, เราจะทำอะไรกับมัน และเราทำดีพอหรือยัง การทำตั้งแต่ขั้น design ได้ผลที่สุด เพราะช่องโหว่ระดับการออกแบบ (A06 Insecure Design) แก้ด้วยการสแกนโค้ดไม่ได้

ขั้นตอนทั่วไป

ขั้นทำอะไรผลลัพธ์
1. กำหนดขอบเขตและ assetบอกว่าปกป้องอะไร ข้อมูลอะไรมีค่ารายการ asset และข้อกำหนดด้านความปลอดภัย
2. วาด Data Flow Diagram (DFD)แสดง actor, process, data store, data flowแผนภาพที่ทีมเห็นตรงกัน
3. ระบุ trust boundaryเส้นที่ระดับความเชื่อใจเปลี่ยน เช่น internet → API, API → databaseจุดที่ต้องตรวจสอบเป็นพิเศษ
4. หาภัยคุกคามใช้ STRIDE หรือ attack tree ไล่ทุก flow ที่ข้าม boundaryรายการภัยคุกคาม
5. ประเมินและเลือกมาตรการจัดลำดับตามความเสี่ยง ตัดสินใจจัดการมาตรการ พร้อมผู้รับผิดชอบ
6. ตรวจสอบและทบทวนทดสอบว่ามาตรการทำงานจริง ทบทวนเมื่อ design เปลี่ยนthreat model ที่เป็นปัจจุบัน

STRIDE: จับคู่ภัยคุกคามกับคุณสมบัติที่ถูกละเมิด

ตัวอักษรภัยคุณสมบัติที่ถูกละเมิดตัวอย่างมาตรการ
SSpoofingAuthenticationปลอมเป็นผู้ใช้อื่นด้วย token ที่ขโมยมาMFA, token ผูกกับ client, mTLS
TTamperingIntegrityแก้ราคาใน request ก่อนส่งคำนวณฝั่ง server, signature, validation
RRepudiationNon-repudiationผู้ใช้ปฏิเสธว่าไม่ได้กดอนุมัติaudit log ที่แก้ไม่ได้, การลงนามธุรกรรม
IInformation disclosureConfidentialityerror message เผยโครงสร้าง databaseเข้ารหัส, ควบคุมสิทธิ์, error ทั่วไป
DDenial of serviceAvailabilityส่ง request หนักจนระบบช้าrate limit, quota, autoscale, timeout
EElevation of privilegeAuthorizationผู้ใช้ทั่วไปเรียก endpoint ของ admin ได้ตรวจสิทธิ์ทุก function, least privilege

STRIDE ใช้กับแต่ละองค์ประกอบใน DFD ได้ตรง ๆ ตัวอย่างเช่น data store เสี่ยง T, I, D ส่วน process เสี่ยงครบทั้งหก และ data flow ที่ข้าม trust boundary เสี่ยง T, I, D โดยเฉพาะ ส่วน attack tree ใช้เมื่อต้องการมองจากเป้าหมายของผู้โจมตีย้อนกลับไป เช่น "ขโมยข้อมูลลูกค้า" แล้วแตกเป็นเส้นทางที่เป็นไปได้ทั้งหมด ซึ่งช่วยเห็นเส้นทางที่ง่ายที่สุดสำหรับผู้โจมตี

ระวังการจับคู่ผิดในข้อสอบข้อสอบชอบให้สถานการณ์แล้วถามว่าเป็นภัยแบบไหนใน STRIDE ให้ถามตัวเองว่าคุณสมบัติข้อไหนถูกละเมิด ผู้ใช้ปฏิเสธว่าไม่ได้ทำรายการคือ Repudiation ไม่ใช่ Spoofing และ Spoofing คือการปลอมเป็นคนอื่น ไม่ใช่การเดารหัส

จาก threat สู่ risk: ประเมินและตัดสินใจ

ความเสี่ยงเกิดจากโอกาสที่จะเกิด (likelihood) คูณผลกระทบ (impact) ได้ทั้งแบบเชิงคุณภาพ (สูง กลาง ต่ำ) และเชิงปริมาณ (ประเมินเป็นมูลค่าความเสียหาย) แต่ตัวเลขที่ประเมินโดยไม่มีข้อมูลรองรับให้ความรู้สึกแม่นยำเกินจริง ทีมควรบันทึกสมมติฐานไว้ด้วย สิ่งที่ต้องตัดสินใจหลังประเมินมีสี่ทาง

ทางเลือกความหมายตัวอย่าง
Mitigateลดโอกาสหรือผลกระทบเพิ่ม MFA, เข้ารหัสข้อมูล
Transferย้ายความเสี่ยงไปให้ผู้อื่นรับบางส่วนประกันภัยไซเบอร์, ใช้ผู้ให้บริการที่รับผิดชอบส่วนนั้น
Avoidเลิกกิจกรรมที่ก่อความเสี่ยงไม่เก็บข้อมูลบัตรเอง ใช้ payment gateway
Acceptยอมรับโดยรู้ตัว มีผู้อนุมัติและวันทบทวนความเสี่ยงต่ำและแก้แพงเกินมูลค่าความเสียหาย

การ transfer ไม่ได้ลบความรับผิดชอบทั้งหมด เช่น ข้อมูลส่วนบุคคลของลูกค้ายังเป็นหน้าที่ของผู้ควบคุมข้อมูลอยู่ดี และหลังจัดการแล้วจะมี residual risk เหลืออยู่เสมอ ต้องบันทึกไว้ใน risk register พร้อมเจ้าของความเสี่ยง

แล็บ 1 safeRedirect: กัน Open Redirect

วิธีที่ปลอดภัยคือ parse ด้วย URL parser แล้วตรวจ origin ไม่ใช่ตรวจ string ด้วยตา โดยบังคับให้ค่าเป็น path ภายในเท่านั้น

// safe-redirect.mjs
export function safeRedirect(next, fallback = '/') {
  if (typeof next !== 'string' || next.length === 0 || next.length > 2048) return fallback;
  // ต้องขึ้นต้นด้วย / ตัวเดียว ห้าม // หรือ /\ (browser บางตัวตีความเป็น protocol-relative)
  if (!next.startsWith('/') || next.startsWith('//') || next.startsWith('/\\')) return fallback;
  // ห้ามอักขระควบคุม (กัน header injection และการแทรกบรรทัดใหม่)
  if (/[\u0000-\u001f\u007f]/.test(next)) return fallback;
  try {
    const base = 'http://placeholder.invalid';
    const u = new URL(next, base);
    if (u.origin !== base) return fallback;   // parse แล้วต้องยังอยู่ origin เดิม
    return u.pathname + u.search + u.hash;
  } catch {
    return fallback;
  }
}

แล็บ 2 ตรวจ Webhook Signature ด้วย HMAC

ระบบภายนอก (เช่น payment gateway) ส่ง webhook มาพร้อม signature ที่คำนวณด้วย HMAC ฝั่งเรา ต้องคำนวณใหม่แล้วเทียบ มีสองเรื่องที่พลาดบ่อย เทียบด้วย === ธรรมดาซึ่งเสี่ยง timing attack (เวลาเปรียบเทียบเปลี่ยนตามจำนวนตัวอักษรที่ตรง) ต้องใช้ timingSafeEqual และต้องคำนวณจาก raw body ไม่ใช่ JSON ที่ parse แล้วเอามา stringify ใหม่ เพราะลำดับ key และช่องว่างอาจต่างไป นอกจากนี้ควรตรวจ timestamp กัน replay

// webhook.mjs
import { createHmac, timingSafeEqual } from 'node:crypto';

export function verifyWebhook({ rawBody, signatureHex, timestamp, secret, now = Date.now(), toleranceSec = 300 }) {
  if (!/^[0-9a-f]{64}$/i.test(signatureHex ?? '')) return false;
  const ts = Number(timestamp);
  if (!Number.isFinite(ts) || Math.abs(now / 1000 - ts) > toleranceSec) return false;   // กัน replay

  const expected = createHmac('sha256', secret).update(`${ts}.${rawBody}`).digest();
  const given = Buffer.from(signatureHex, 'hex');
  return given.length === expected.length && timingSafeEqual(given, expected);
}

แล็บ 4 สร้าง Query ที่รับค่า Sort จากผู้ใช้

parameter ใช้กับ "ค่า" ได้ แต่ใช้กับชื่อคอลัมน์หรือทิศทาง ASC/DESC ไม่ได้ ต้อง map ค่าที่รับมาไปยังชื่อที่เรากำหนดไว้เองเท่านั้น

// order-query.mjs
const SORTABLE = { created: 'created_at', total: 'total_amount', status: 'status' };
const DIRECTIONS = { asc: 'ASC', desc: 'DESC' };

export function buildOrderQuery({ userId, sort = 'created', dir = 'desc', limit = 20 }) {
  const column = SORTABLE[sort];
  const direction = DIRECTIONS[String(dir).toLowerCase()];
  if (!column || !direction) throw new Error('invalid_sort');
  const n = Math.min(Math.max(Number.parseInt(limit, 10) || 20, 1), 100);   // จำกัดช่วง 1-100

  return {
    // ชื่อคอลัมน์มาจาก allowlist ในโค้ดเท่านั้น ส่วนค่าไปทาง parameter
    text: `SELECT id, status, total_amount FROM orders WHERE user_id = $1 ORDER BY ${column} ${direction} LIMIT $2`,
    values: [userId, n],
  };
}

C4. ผู้บริหารถามว่า “อยากทำ Zero Trust ต้องซื้อผลิตภัณฑ์ตัวไหน จบเลยไหม” ควรตอบและวางแผนอย่างไร

ตอบตรง ๆ ได้ว่าไม่มีผลิตภัณฑ์เดียวที่ทำให้ได้ Zero Trust เพราะตาม NIST SP 800-207 มันเป็นสถาปัตยกรรมและแนวทาง ครอบคลุม identity, อุปกรณ์, เครือข่าย, แอป และข้อมูล เครื่องมือเป็นส่วนหนึ่งของการลงมือ แต่ต้องปรับกระบวนการและนโยบายควบคู่กัน

  1. สำรวจก่อนว่ามีอะไรบ้าง ทั้ง identity, อุปกรณ์, แอป, ข้อมูล และเส้นทางที่เข้าถึงกัน
  2. เลือก protect surface คือทรัพยากรที่มีค่าที่สุดก่อน (เช่น ระบบเงินเดือน, ข้อมูลลูกค้า) ไม่ทำทั้งองค์กรพร้อมกัน
  3. รวม identity เข้า IdP กลาง บังคับ MFA (ทน phishing สำหรับบัญชีสิทธิ์สูง) และลดสิทธิ์ที่กว้างเกินจำเป็น
  4. เพิ่มการตรวจสถานะอุปกรณ์ และ conditional access ตามความเสี่ยง
  5. แบ่งส่วนเครือข่าย (microsegmentation) และเข้ารหัสการเชื่อมต่อภายในให้ไม่เชื่อใจจากตำแหน่งเครือข่าย
  6. เก็บ log และเฝ้าระวังต่อเนื่อง กำหนดตัวชี้วัด แล้วทบทวนก่อนขยายขอบเขต
  7. เตรียมความพร้อมกรณี policy service หรือ IdP ล่ม (พร้อมใช้สูง, break-glass, fail closed)

D1. เขียน redactSecrets(obj) สำหรับเตรียม object ก่อนเขียน log ให้ซ่อนค่าของ key ที่เป็น password, token, authorization, secret ไม่ว่าอยู่ลึกแค่ไหน (รวมใน array) โดยไม่แก้ object เดิม พร้อม test case 
// redact.mjs
const SENSITIVE = /^(password|passwd|token|access_?token|refresh_?token|authorization|secret|api_?key|cookie)$/i;

export function redactSecrets(value, seen = new WeakSet()) {
  if (value === null || typeof value !== 'object') return value;
  if (seen.has(value)) return '[Circular]';           // กัน object ที่อ้างวนกลับมาที่ตัวเอง
  seen.add(value);
  let out;
  if (Array.isArray(value)) {
    out = value.map((v) => redactSecrets(v, seen));
  } else {
    out = {};
    for (const [k, v] of Object.entries(value)) {
      out[k] = SENSITIVE.test(k) ? '[REDACTED]' : redactSecrets(v, seen);
    }
  }
  seen.delete(value);   // เก็บเฉพาะเส้นทางปัจจุบัน object ที่ถูกอ้างซ้ำแบบไม่วนจะได้ไม่ถูกมองเป็น Circular
  return out;
}

export function requireRole(...allowed) {
  const allow = new Set(allowed);
  return (req, res, next) => {
    if (!req.user) return res.sendStatus(401);                     // ยังไม่ยืนยันตัวตน
    if (!allow.has(req.user.role)) return res.sendStatus(403);     // ยืนยันแล้วแต่ไม่มีสิทธิ์
    next();
  };
}

test('ไม่มี user -> 401 และไม่เรียก next', () => {
  assert.deepEqual(run(requireRole('admin'), {}), { status: 401, called: false });
});
test('role ไม่อยู่ในรายการ -> 403', () => {
  assert.deepEqual(run(requireRole('admin'), { user: { role: 'viewer' } }), { status: 403, called: false });
});
test('role ตรง -> เรียก next', () => {
  assert.deepEqual(run(requireRole('admin', 'support'), { user: { role: 'support' } }), { status: null, called: true });
});
test('ไม่ได้ระบุ role เลย -> ปฏิเสธทุกคน (deny by default)', () => {
  assert.equal(run(requireRole(), { user: { role: 'admin' } }).status, 403);
});
test('role เป็น undefined -> ปฏิเสธ', () => {
  assert.equal(run(requireRole('admin'), { user: {} }).status, 403);
});

คู่ที่ชื่อคล้ายกันและชอบโผล่มาเป็นตัวลวง

ข้อสอบแบบตัวเลือกชอบเอาของที่ชื่อคล้ายกันมาวางคู่กัน ตารางนี้สรุปความต่างไว้ในบรรทัดเดียว

คำถามคำตอบย่อพร้อมหลักคิด
Authentication vs Authorizationคุณคือใคร / คุณทำอะไรได้ ล็อกอินได้แล้วยังต้องตรวจสิทธิ์
401 vs 403ยังไม่ยืนยันตัวตนหรือ token ผิด / รู้ว่าเป็นใครแต่ไม่มีสิทธิ์
Hash vs Encryption vs Signatureทางเดียว ใช้กับ password / ถอดกลับได้ถ้ามี key / พิสูจน์ผู้ลงนามและว่าไม่ถูกแก้
Hash vs HMACใครก็คำนวณซ้ำได้ / ต้องมี secret key จึงใช้ยืนยันผู้ส่งได้
Anonymization vs Pseudonymizationย้อนระบุตัวไม่ได้จริง / แทนค่าแต่ยังโยงกลับได้ ยังเป็นข้อมูลส่วนบุคคล
Validation vs Sanitization vs Encodingปฏิเสธข้อมูลผิดรูปแบบ / ตัดส่วนอันตรายออก / แปลงอักขระตาม context ตอนแสดงผล
XSS vs CSRFรันโค้ดของผู้โจมตีในเว็บเรา (encode, CSP) / ใช้ cookie ของเหยื่อส่ง request (token, SameSite)
IDOR/BOLA vs Function-levelเปลี่ยน id เห็นของคนอื่น / เรียก endpoint ของ admin ที่ลืมตรวจ role
OAuth 2.0 vs OIDC vs SAMLมอบสิทธิ์เข้าถึง API / ยืนยันตัวตนบน OAuth (ID token) / SSO องค์กรแบบ XML
Access token vs Refresh tokenอายุสั้น ใช้เรียก API / อายุยาว เก็บฝั่ง server แลกตัวใหม่และ rotate
SAST vs DAST vs SCA vs IASTอ่านโค้ด / ยิงแอปที่รัน / เทียบ dependency กับช่องโหว่ที่รู้ / agent ในแอปตอนรัน test
Vulnerability assessment vs Pentestหาช่องโหว่ให้ครบและจัดลำดับ / พิสูจน์ผลกระทบด้วยการโจมตีจริงภายใต้ขอบเขตที่อนุญาต
CVSS vs KEV vs EPSSความรุนแรงของช่องโหว่ / รายการที่ถูกโจมตีจริงแล้ว / โอกาสที่จะถูกโจมตี
WAF vs API Gatewayกรอง request ที่ตรง signature การโจมตี / จุดเข้าเดียว ตรวจ token, rate limit, routing
Fail open vs Fail closedระบบตรวจพังแล้วปล่อยผ่าน / พังแล้วปฏิเสธ ระบบความปลอดภัยควรเป็นแบบหลัง
PDP vs PEP (Zero Trust)ตัดสินใจว่าอนุญาตหรือไม่ / บังคับใช้คำตัดสินที่หน้าทรัพยากร
SBOM vs Provenance vs Signatureมีอะไรอยู่ข้างใน / สร้างมาจากอะไรอย่างไร / ไม่ถูกแก้หลังสร้าง
Mitigate vs Transfer vs Avoid vs Acceptลดความเสี่ยง / ย้ายบางส่วนให้ผู้อื่น / เลิกกิจกรรม / ยอมรับโดยมีผู้อนุมัติ
Spoofing vs Repudiationปลอมเป็นผู้อื่น (Authentication) / ปฏิเสธว่าไม่ได้ทำ (Non-repudiation)
Containment vs Eradication vs Recoveryจำกัดความเสียหาย / กำจัดต้นเหตุ / กู้ระบบกลับมาใช้งาน
