เริ่มจากปัญหาจริง

สมมติมีฟังก์ชัน calculateTotal คิดยอดตะกร้าสินค้า รอบแรกมีแค่ราคารวม พอฝ่ายการตลาดขอคูปอง SAVE10 ต่อมาขอคูปองอีกใบที่ต้องซื้อขั้นต่ำ 1,000 บาท ทุกครั้งที่แก้ เรามีทางเดียวที่จะรู้ว่าของเดิมยังไม่พัง คือเปิดหน้าเว็บมากดเอง unit test คือการเขียนโค้ดไปตรวจโค้ดแทนการกดเอง และรันได้ในเวลาไม่กี่วินาทีทุกครั้งที่แก้

“Unit” คือหน่วยแค่ไหน

ไม่มีนิยามตายตัว ส่วนใหญ่หมายถึง function, method หรือ class ที่มีพฤติกรรมชัดเจน ทีมส่วนใหญ่ตกลงกันว่า unit test ควรรันเร็วระดับมิลลิวินาที ไม่แตะ network, database หรือ file system จริง และไม่ขึ้นกับเวลาปัจจุบันหรือค่าสุ่ม ถ้าข้อใดข้อหนึ่งหลุด test นั้นกลายเป็น integration test ไปแล้ว ซึ่งไม่ได้ผิดอะไร แต่ต้องรู้ตัว เพราะความเร็ว ความเสถียร และวิธีไล่หาสาเหตุเวลาพังไม่เหมือนกัน

มีสองสำนักที่ตีความคำว่า unit ต่างกัน สำนัก solitary แยก class ออกจาก collaborator ทุกตัวด้วย test double ส่วนสำนัก sociable ยอมให้ class คุยกับ collaborator จริงที่เป็นโค้ดล้วน ๆ ในหน่วยความจำ ทั้งสองแบบใช้ได้ ต่างกันที่ trade-off คือแบบแรกชี้จุดที่พังได้แม่นกว่าแต่ test ผูกกับโครงสร้างภายในมากกว่า

ระดับทดสอบอะไรdependencyความเร็วเจอปัญหาแบบไหน
Unitfunction / class ตัวเดียวใช้ test double แทนมิลลิวินาทีlogic ผิด, edge case หลุด
Integrationหลาย component ต่อกัน เช่น service + databaseจริงบางส่วนวินาทีSQL ผิด, mapping ผิด, config ผิด
Functional / APIพฤติกรรมตาม requirement ผ่านช่องทางที่ client เห็น เช่น HTTP endpointแล้วแต่การออกแบบวินาทีstatus/format ผิด, requirement ไม่ครบ
End-to-Endทั้งระบบผ่าน UI หรือ API ภายนอกจริงทั้งหมดวินาทีถึงนาทีflow ข้ามระบบพัง, deploy หรือ config ผิด
คำว่า “functional testing” มีสองความหมายความหมายแรกคือการทดสอบว่าระบบทำงานตาม functional requirement (ทำอะไรได้) ตรงข้ามกับ non-functional ที่ว่าด้วย performance, security, usability ความหมายที่สองคือบางทีมใช้เรียก test ที่ยิงเข้า API หรือ component ทั้งก้อนแบบ black-box ในข้อสอบให้ดูบริบทของโจทย์ว่าถามความหมายไหน

ทำไมถึงเป็นรูปปิรามิด

แนวคิด test pyramid (Mike Cohn) บอกว่าควรมี unit test จำนวนมากที่ฐาน มี integration/functional test รองลงมา และมี end-to-end น้อยที่สุดที่ยอดปิรามิด เหตุผลคือยิ่งขึ้นไปข้างบน test ยิ่งช้า ยิ่งแพงต่อการดูแล และยิ่งพังเองง่ายโดยโค้ดไม่ได้ผิด แต่นี่ไม่ใช่กฎตายตัว งาน frontend หรือ service ที่เป็นแค่ตัวต่อระหว่างระบบอื่น หลายทีมเลือกลงน้ำหนักที่ integration test มากกว่า (เรียกกันว่า testing trophy) เพราะ bug ส่วนใหญ่อยู่ตรงรอยต่อ ไม่ได้อยู่ในฟังก์ชันเดี่ยว ๆ วิธีเลือกคือดูว่า bug ที่เคยหลุดไปถึง production ของระบบเราเกิดที่ชั้นไหน

โครง Arrange – Act – Assert

test ที่อ่านง่ายแบ่งเป็นสามช่วง ตั้งข้อมูล (Arrange) เรียกสิ่งที่ทดสอบ (Act) แล้วตรวจผล (Assert) ลองดูตัวอย่างนี้ ซึ่งรันผ่านบน Jest 30.5.2

const { calculateTotal } = require('../src/pricing');

test('SAVE10 ลด 10% และปัดทศนิยม 2 ตำแหน่ง', () => {
  // Arrange
  const items = [{ price: 199.5, qty: 2 }, { price: 50, qty: 1 }];

  // Act
  const total = calculateTotal(items, 'SAVE10');

  // Assert: subtotal 449 × 0.9 = 404.1
  expect(total).toBeCloseTo(404.1, 2);
});

ช่วง Act ควรเป็นบรรทัดเดียว ถ้าต้องเรียกสองสามบรรทัดเพื่อทดสอบเรื่องเดียว มักเป็นสัญญาณว่า API ของโค้ดใช้ยาก หรือ test กำลังตรวจหลายเรื่องพร้อมกัน ส่วนชื่อ test ให้เขียนเป็น behavior ที่คาดหวังพร้อมเงื่อนไข เช่น “ตะกร้าว่างต้อง throw” แทนที่จะเป็น testCalculateTotal1 เพราะตอน test ล้มใน CI ชื่อคือสิ่งเดียวที่คนเห็นก่อนจะเปิดโค้ด

F.I.R.S.T. ลักษณะของ unit test ที่ดี

Fast รันเร็วจนไม่มีใครขี้เกียจรัน Independent แต่ละ test ไม่พึ่งผลของ test อื่น สลับลำดับแล้วต้องผ่านเหมือนเดิม Repeatable รันกี่ครั้งในเครื่องไหนก็ได้ผลเดิม จึงห้ามพึ่งเวลาจริงหรือข้อมูลที่เหลือจากรอบก่อน Self-validating ผ่านหรือไม่ผ่านชัดเจนโดยไม่ต้องให้คนอ่าน log แล้วตีความ Timely เขียนใกล้เวลาที่เขียนโค้ด ไม่ใช่ทิ้งไปเขียนตอนใกล้ปล่อย

ข้อผิดพลาดที่เจอบ่อยตอนเริ่มเขียน

แบบแรกคือ test ที่ไม่มี assertion เลย รันผ่านและทำให้ coverage ขึ้น แต่ไม่ได้ตรวจอะไร แบบที่สองคือใส่หลายเรื่องไว้ใน test เดียว พอล้มก็ไม่รู้ว่าเรื่องไหนพัง แบบที่สามคือคำนวณค่าที่คาดหวังด้วยสูตรเดียวกับโค้ดจริง เช่น expect(total).toBe(subtotal * 0.9) ถ้าสูตรในโค้ดผิด สูตรใน test ก็ผิดตามกัน test จึงผ่านอย่างสบายใจ วิธีที่ปลอดภัยกว่าคือคำนวณค่าที่คาดหวังจาก requirement แล้วเขียนเป็นตัวเลขตรง ๆ

เลือก framework ตามภาษา แต่หลักการเหมือนกัน

ฝั่ง JavaScript/TypeScript ที่ใช้กันมากคือ Jest, Vitest และ Mocha ฝั่ง Python คือ pytest กับ unittest (อยู่ใน standard library) ฝั่ง Java คือ JUnit ซึ่งขึ้น major version เป็น 6 แล้ว (6.0.0 ออกวันที่ 30 กันยายน 2025 ต้องใช้ Java 17 ขึ้นไป และเลขเวอร์ชันของ Platform, Jupiter, Vintage ใช้ตัวเดียวกัน) annotation ที่ใช้เขียน test ทั่วไปอย่าง @Test และ @BeforeEach ยังเหมือนกับ JUnit 5 ส่วนฝั่ง .NET มี xUnit และ NUnit ทุกตัวมีของสามอย่างเหมือนกัน คือวิธีประกาศ test, assertion และ setup/teardown

Assertion ที่ต้องแยกให้ออก

ข้อสอบชอบถามว่า assertion ตัวไหนเทียบอะไรแบบไหน ตารางนี้ตรวจกับ Jest 30.5.2 และ pytest 9.1.1 แล้ว

เรื่อง Promise มีของจริงให้ดู ผมลองเขียน expect(Promise.resolve(1)).resolves.toBe(2) โดยไม่ใส่ await ใน Jest 30.5.2 บน Node 22 ผลคือ assertion ล้มหลัง test จบ แล้วหลุดออกมาเป็น unhandled rejection จนโปรเซสของ Jest ล่ม ไม่ได้แสดงเป็น test ที่ fail ตามปกติ พฤติกรรมตรงนี้ขึ้นกับเวอร์ชันของ Jest และ Node บางสภาพแวดล้อมอาจรายงานว่าผ่านโดยไม่เห็น error จึงเป็นเหตุผลที่ต้อง await ทุกครั้ง

Setup, teardown และการแยก state ระหว่าง test

ใช้ beforeEach / afterEach (Jest) หรือ fixture (pytest) เพื่อสร้างของใหม่ให้ทุก test ปัญหาคลาสสิกคือประกาศ array หรือ object ไว้ระดับไฟล์แล้วให้ test หลายตัวแก้ค่าร่วมกัน ผลคือ test ผ่านเมื่อรันทีละตัวแต่ล้มเมื่อรันทั้งชุด หรือล้มเมื่อสลับลำดับ ถ้าต้องแชร์ของที่สร้างแพง เช่น connection ให้แชร์เฉพาะของที่ไม่เปลี่ยนค่า (read-only) และล้างข้อมูลหลังจบแต่ละ test

ออกแบบ test case ด้วย equivalence partitioning และ boundary value

เราทดสอบทุก input ไม่ได้ จึงแบ่ง input เป็นกลุ่มที่โค้ดน่าจะปฏิบัติเหมือนกัน (equivalence partition) แล้วเลือกตัวแทนมาหนึ่งค่าต่อกลุ่ม จากนั้นเพิ่มค่ารอบ ๆ รอยต่อระหว่างกลุ่ม (boundary value) เพราะ bug ชอบอยู่ตรง > กับ >= ลองดูกับกติกา “คูปอง FREE100 ลด 100 บาท เมื่อยอดรวมตั้งแต่ 1,000 บาทขึ้นไป”

กลุ่มค่าที่ควรลองผลที่คาดหวัง
ต่ำกว่าเกณฑ์999.99ไม่ลด คืน 999.99
พอดีเกณฑ์ (boundary)1000ลด 100 คืน 900
เกินเกณฑ์นิดเดียว1000.01ลด 100 คืน 900.01
input ผิดปกติตะกร้าว่าง, ราคาติดลบ, จำนวนเป็น 0throw error ตามที่กำหนด

เขียนเป็น test แบบ parameterized จะไม่ต้องก๊อปปี้ test สามชุด ตัวอย่างนี้รันผ่านแล้ว

test.each([
  [999.99, 999.99],
  [1000, 900],
  [1000.01, 900.01],
])('FREE100 ต้อง subtotal >= 1000 (subtotal=%p → %p)', (subtotal, expected) => {
  expect(calculateTotal([{ price: subtotal, qty: 1 }], 'FREE100')).toBe(expected);
});

เวอร์ชัน Python หน้าตาแบบเดียวกัน ใช้ @pytest.mark.parametrize และ pytest.approx ตอนเทียบทศนิยม

@pytest.mark.parametrize(
    "total, tier, expected",
    [(1000, "basic", 1000.0), (1000, "silver", 950.0), (1000, "gold", 900.0), (99.99, "silver", 94.99)],
)
def test_member_discount(total, tier, expected):
    assert member_discount(total, tier) == pytest.approx(expected)

Test double มี 5 แบบ

ชื่อชุดนี้มาจากหนังสือ xUnit Test Patterns ของ Gerard Meszaros ใช้กันแพร่หลาย แต่ library แต่ละตัวเรียกชื่อไม่ตรงกันเป๊ะ ตารางนี้ใช้ความหมายแบบดั้งเดิม

ชนิดหน้าที่ตัวอย่างการใช้
Dummyส่งไปให้ครบ parameter แต่ไม่ถูกใช้จริงส่ง logger เปล่า ๆ เข้า constructor ที่บังคับให้ใส่
Stubตอบค่าที่กำหนดไว้ล่วงหน้า เพื่อให้โค้ดเดินไปในเส้นทางที่ต้องการpayment.charge คืน { ok: false } เพื่อทดสอบเส้นทางจ่ายไม่ผ่าน
Spyของจริงหรือ stub ที่แอบจดไว้ว่าถูกเรียกอย่างไรบ้างjest.spyOn(Math, 'random')

Fakeของที่ทำงานได้จริงแต่แบบง่าย ไม่เหมาะกับ productionrepository ที่เก็บข้อมูลใน array แทน database

ในทางปฏิบัติ jest.fn() เป็น “mock function” ตัวเดียวที่ทำได้ทั้ง stub (ตั้งค่าที่คืน) และ spy (จดการเรียก) ส่วน Mockito.mock() ในฝั่ง Java ก็คล้ายกัน จึงไม่ต้องกังวลถ้าเอกสารของ library เรียกทุกอย่างว่า mock สิ่งที่ต้องจำคือความต่างของ “ตรวจผลลัพธ์ที่ออกมา” (state verification) กับ “ตรวจว่าโค้ดเรียกใครอย่างไร” (behavior verification) เพราะสองแบบนี้ทำให้ test ผูกกับ implementation ในระดับต่างกัน

ทำให้โค้ดเปลี่ยน dependency ได้ด้วยการ inject

test ของ OrderService ด้านล่างทำได้ง่ายเพราะ class รับ repository, payment และ clock ผ่าน constructor ไม่ได้ require ของจริงไว้ข้างใน เวลาจึง inject เข้าไปได้ด้วย ทำให้ค่า createdAt คาดเดาได้

class OrderService {
  constructor({ orderRepo, payment, clock = () => new Date() }) {
    this.orderRepo = orderRepo;
    this.payment = payment;
    this.clock = clock;
  }

  async checkout(userId, amount) {
    if (amount <= 0) throw new Error('amount must be positive');
    const charge = await this.payment.charge(userId, amount);
    if (!charge.ok) return { status: 'FAILED', reason: charge.reason };
    const order = await this.orderRepo.save({
      userId, amount, chargeId: charge.id, createdAt: this.clock().toISOString(),
    });
    return { status: 'PAID', orderId: order.id };
  }
}
function setup(chargeResult) {
  const orderRepo = { save: jest.fn().mockResolvedValue({ id: 'ORD-1' }) };   // stub + spy
  const payment = { charge: jest.fn().mockResolvedValue(chargeResult) };
  const clock = () => new Date('2026-01-15T10:00:00.000Z');                    // เวลาคงที่
  return { orderRepo, payment, service: new OrderService({ orderRepo, payment, clock }) };
}

test('ตัดเงินไม่ผ่าน → ไม่ต้องบันทึก order', async () => {
  const { service, orderRepo } = setup({ ok: false, reason: 'INSUFFICIENT_FUNDS' });

  const result = await service.checkout('u1', 500);

  expect(result).toEqual({ status: 'FAILED', reason: 'INSUFFICIENT_FUNDS' });
  expect(orderRepo.save).not.toHaveBeenCalled();
});

สังเกตว่า test นี้ตรวจทั้งผลลัพธ์ (state) และตรวจว่า save ไม่ถูกเรียก (behavior) เพราะ requirement ของเคสนี้คือ “ห้ามบันทึก” ซึ่งมองเห็นได้จากการเรียกเท่านั้น ถ้าตรวจแค่ผลลัพธ์ เราจะไม่รู้ว่ามีออเดอร์หลุดเข้า database หรือเปล่า

mock ที่ชื่อที่โค้ดใช้ ไม่ใช่ที่ต้นทาง (Python)

กับดักที่คนเจอบ่อยใน unittest.mock.patch คือ patch ผิดชื่อ ถ้า user_service.py เขียน from mailer import send_email ชื่อ send_email จะถูกคัดลอกเข้า namespace ของ user_service ไปแล้ว การ patch mailer.send_email จึงไม่มีผลกับโค้ดที่เรียกผ่านชื่อใน user_service ต้อง patch ที่ user_service.send_email ตัวอย่างนี้รันผ่านบน pytest 9.1.1 ทั้งสองกรณี

@patch("user_service.send_email")          # ถูก: patch ที่ชื่อซึ่งโค้ดใช้อยู่

def test_patching_wrong_target_does_not_stop_real_call():

Functional test ต่างจาก unit test ตรงไหน

unit test ถามว่า “โค้ดชิ้นนี้ทำงานถูกไหม” ส่วน functional test ถามว่า “ระบบทำสิ่งที่ requirement บอกไหม” ผู้เขียน test ไม่ต้องสนใจว่าข้างในแบ่ง class อย่างไร สนใจแค่ input ที่ส่งเข้าไปกับผลที่ออกมา (black-box) ดังนั้น functional test จึงมีอายุยืนกว่า เพราะถึงจะ refactor โครงสร้างภายใน test ก็ยังใช้ได้ตราบที่พฤติกรรมไม่เปลี่ยน

Coverage วัดอะไรบ้าง

coverage คือสัดส่วนของโค้ดที่ถูกรันระหว่างที่ test ทำงาน แต่คำว่า “โค้ด” นับได้หลายแบบ ซึ่งให้ภาพไม่เท่ากัน

ชนิดนับอะไรจุดที่ต้องระวัง
Statement / Lineคำสั่งหรือบรรทัดที่ถูกรันif ที่ไม่มี else ให้ line ครบได้ แม้ฝั่ง false ไม่เคยถูกเดิน

Condition (คำที่ SonarQube ใช้)แต่ละนิพจน์ boolean ถูกประเมินเป็นทั้ง true และ false หรือยังเป็นองค์ประกอบหนึ่งของค่า Coverage รวมของ SonarQube

File             | % Stmts | % Branch | % Funcs | % Lines
 pricing.js      |     100 |      100 |     100 |     100
 retry.js        |     100 |       40 |     100 |     100

ทุกบรรทัดถูกรัน แต่ branch ได้แค่ 40% เพราะฟังก์ชันประกาศ { retries = 3, delayMs = 1000 } = {} ซึ่งมีค่า default สามจุด และมี if (attempt < retries) อีกหนึ่งจุด test ที่เขียนไว้ส่ง option ครบทุกครั้ง ค่า default จึงไม่เคยถูกใช้ ถ้าดูแค่ line coverage เราจะเห็นว่า “ครบแล้ว” ทั้งที่ยังมีเส้นทางที่ไม่เคยถูกทดสอบ

SonarQube ไม่ได้รัน test และไม่ได้วัด coverage เอง มันอ่านไฟล์รายงานที่เครื่องมือ coverage สร้างไว้แล้ว นำมาจับคู่กับไฟล์ source แล้วคำนวณ metric ของตัวเอง ดังนั้นขั้นตอนใน CI ต้องเรียงเป็น รัน test พร้อมสร้างรายงาน แล้วค่อยรัน scanner ชื่อ property ที่ใช้ชี้ไปยังรายงานต่างกันตามภาษา (ตรวจชื่อกับเอกสาร “Test coverage parameters” ของเวอร์ชันที่ใช้ เพราะชื่ออาจเปลี่ยนได้)

ภาษารูปแบบรายงานตัวอย่าง property

ค่า Coverage ที่ SonarQube แสดงเป็นการรวม line กับ condition เข้าด้วยกัน ตามสูตรในเอกสารของ Sonar

Coverage           = (CT + CF + LC) / (2*B + EL)
Line coverage      = LC / EL
Condition coverage = (CT + CF) / (2*B)

CT = เงื่อนไขที่เคยประเมินเป็น true อย่างน้อยหนึ่งครั้ง   CF = เคยเป็น false
B  = จำนวนเงื่อนไขทั้งหมด   LC = บรรทัดที่ถูกรัน   EL = บรรทัดที่ต้องครอบคลุม (lines to cover)

ลองแทนค่าตัวอย่าง (ตัวเลขสมมติ เพื่อฝึกคำนวณ) EL = 100, LC = 90, B = 10, CT = 8, CF = 6 จะได้ Coverage = (8 + 6 + 90) / (20 + 100) = 104 / 120 ≈ 86.7% ขณะที่ line coverage คือ 90% และ condition coverage คือ 14 / 20 = 70% นี่คือเหตุผลหนึ่งที่ตัวเลขใน SonarQube ไม่ตรงกับที่เครื่องมือ coverage ตัวเดิมแสดง เพราะเทียบกันคนละ metric ได้ อีกเหตุผลคือ SonarQube นับ “บรรทัดที่ต้องครอบคลุม” ตามการวิเคราะห์ของมันเอง ซึ่งอาจไม่เท่ากับของเครื่องมือเดิม

Quality gate และ “new code”

quality gate ใน SonarQube คือชุดเงื่อนไขที่ถ้าไม่ผ่านจะถือว่า analysis ล้ม ตัวเริ่มต้นชื่อ Sonar way เน้นที่ new code คือโค้ดที่เพิ่งเพิ่มหรือแก้ตามนิยาม new code ของโปรเจกต์ เงื่อนไขของมันตามเอกสารของ SonarQube Server เวอร์ชัน 10.4 เป็นดังนี้ ไม่มี issue ใหม่ Security Hotspot ใหม่ถูกรีวิวครบ coverage ของ new code ตั้งแต่ 80.0% ขึ้นไป และโค้ดซ้ำใน new code ไม่เกิน 3.0% โดยเงื่อนไข coverage กับ duplication ปรับค่าเองได้ ตัวเลข 80% จึงเป็นค่าตั้งต้นของเครื่องมือ ไม่ใช่มาตรฐานสากล แต่ละทีมกำหนดเองได้ตามความเสี่ยง

เวลา analysis เป็น pull request จะใช้เฉพาะเงื่อนไขที่ผูกกับ new code นอกจากนี้มี “fudge factor” คือกลไกข้ามเงื่อนไข coverage และ duplication เมื่อโค้ดใหม่น้อยเกินไป เอกสารของ SonarQube Cloud ระบุว่าจะข้ามจนกว่าจะมีบรรทัดใหม่อย่างน้อย 20 บรรทัด ส่วน Server ให้ดูเอกสารของเวอร์ชันที่ใช้

ถ้า new code coverage ว่างหรือไม่ขึ้น ให้เช็กตามลำดับนี้หา report ไม่เจอเพราะ path ใน property ผิด (ใน CI แบบ Docker path ของไฟล์อาจต่างจากตอนรัน test) หรือไม่มีบรรทัดใหม่ในช่วง new code จริง ๆ และเคสที่พบบ่อยอีกอย่างคือ CI ใช้ shallow clone ทำให้ scanner หาบรรทัดที่เปลี่ยนจาก SCM ไม่ได้ ซึ่งแก้ด้วยการ clone เต็ม (เช่นตั้ง fetch-depth: 0 ใน actions/checkout) ส่วน coverage ที่ไม่อยากนับ เช่น โค้ดที่ generate ขึ้นมา ใช้ sonar.coverage.exclusions ได้ แต่ควรให้ทีมรีวิวรายการ exclusion เป็นระยะ ไม่เช่นนั้นจะกลายเป็นที่ซ่อนโค้ดที่ไม่มี test

test('calculateTotal รันได้', () => {

test นี้ทำให้บรรทัดในฟังก์ชันเป็นสีเขียว แต่ถ้า logic ผิด มันก็ผ่านต่อไป เครื่องมือที่ตอบคำถามว่า test ตรวจผลจริงไหมคือ mutation testing เช่น Stryker (JavaScript/TypeScript), PIT (Java) และ mutmut (Python) หลักการคือแก้โค้ดให้ผิดทีละจุด (mutant) แล้วรัน test ถ้า test ล้มแปลว่าจับ mutant นั้นได้ สัดส่วน mutant ที่ถูกจับเรียกว่า mutation score ข้อเสียคือรันช้า จึงมักใช้กับโมดูลสำคัญหรือรันเฉพาะไฟล์ที่เปลี่ยน

ปิดช่องจริง: จาก branch 40% เป็น 100%

กลับไปที่ retry.js ที่ branch ได้ 40% ช่องที่หายไปคือค่า default เราเขียน test ที่เรียก retry(fn) โดยไม่ส่ง option และตรวจว่าค่า default ทำงานตามที่ตั้งใจจริง คือรอ 1,000 มิลลิวินาทีก่อนลองใหม่

test('เรียกโดยไม่ส่ง options → ใช้ retries=3 และ delay 1000ms', async () => {
  const fn = jest.fn().mockRejectedValueOnce(new Error('e1')).mockResolvedValue('ok');

  const promise = retry(fn);
  await jest.advanceTimersByTimeAsync(999);
  expect(fn).toHaveBeenCalledTimes(1);   // ยังไม่ครบ 1000ms จึงยังไม่ลองใหม่
  await jest.advanceTimersByTimeAsync(1);

  await expect(promise).resolves.toBe('ok');
  expect(fn).toHaveBeenCalledTimes(2);
});

หลังเพิ่ม test ตัวนี้ (รันจริงบน Jest 30.5.2) retry.js ได้ branch 100% และ branch ของทั้งโปรเจกต์ทดลองขยับจาก 84.37% เป็น 93.75% จุดที่ควรสังเกตคือ test นี้ไม่ได้เขียนเพื่อดันตัวเลข มันตรวจพฤติกรรมที่ใครสักคนอาจแก้โดยไม่ตั้งใจ ถ้ามีคนเปลี่ยน default จาก 1000 เป็น 100 test นี้ล้มทันที

โค้ดเก่าที่ยังไม่มี test เลย

เริ่มจาก characterization test (แนวคิดจากหนังสือ Working Effectively with Legacy Code ของ Michael Feathers) คือเขียน test ที่บันทึกพฤติกรรมปัจจุบันของโค้ดตามที่เป็นอยู่ ไม่ว่าตอนนี้จะถูกหรือผิด แล้วใช้มันเป็นตาข่ายนิรภัยตอนแก้ ถ้าโค้ดรันยากเพราะฝัง new Date(), การเรียก HTTP หรือ singleton ไว้ข้างใน ให้หา seam คือจุดที่เปลี่ยนพฤติกรรมได้โดยไม่แก้ตรรกะ เช่น รับ clock หรือ client เป็น parameter ที่มีค่า default เป็นของจริง จากนั้นค่อยแยกส่วนที่เป็น logic ล้วน ๆ ออกจากส่วนที่ติด I/O เพื่อให้ส่วนแรกทดสอบแบบ unit ได้ง่าย

// ก่อน: ทดสอบยากเพราะผูกกับเวลาจริง
function createToken(userId) {
  return { userId, expiresAt: new Date(Date.now() + 3600 * 1000) };
}

// หลัง: seam คือพารามิเตอร์ now ที่มีค่า default เป็นของจริง
function createToken(userId, now = Date.now()) {
  return { userId, expiresAt: new Date(now + 3600 * 1000) };
}

อย่าไล่เลข

ถ้าผลักทีมด้วยตัวเลขอย่างเดียว จะเจอ test ที่เขียนให้บรรทัดเป็นสีเขียวโดยไม่มี assertion หรือการ exclude ไฟล์เพื่อให้ผ่านเกณฑ์ คำถามที่ควรถามกับ test ทุกตัวคือ “ถ้าโค้ดตรงนี้ผิด test จะล้มไหม” วิธีตรวจเร็ว ๆ ด้วยมือคือแก้โค้ดจริงให้ผิดนิดเดียว เช่น เปลี่ยน >= เป็น > แล้วรัน test ถ้ายังผ่านก็แปลว่า test ยังไม่ได้ปกป้องจุดนั้น ซึ่งเป็นแนวคิดเดียวกับ mutation testing ที่ทำด้วยมือ

# clock_demo.py
import time

def is_expired(created_at: float, ttl_seconds: int) -> bool:
    return time.time() - created_at > ttl_seconds

# test_clock_demo.py
def test_expired_boundary(monkeypatch):
    monkeypatch.setattr("clock_demo.time.time", lambda: 1000.0)
    assert is_expired(created_at=900.0, ttl_seconds=100) is False   # เท่ากับ ttl ยังไม่หมดอายุ
    assert is_expired(created_at=899.0, ttl_seconds=100) is True

จะ mock ที่ชั้นไหน

กับ HTTP API ภายนอก มีสองทางเลือกหลัก ทางแรกคือ mock adapter ของเรา เช่น paymentGateway.charge ทำง่ายและเร็ว แต่ไม่ได้ตรวจว่าเราส่ง URL, header และ body ถูกหรือเปล่า รวมถึงการ parse response ทางที่สองคือจำลองที่ชั้น HTTP ซึ่ง library จริงของเรายังทำงานครบ จึงจับความผิดพลาดพวกนี้ได้ แลกกับ setup ที่มากกว่า หลายทีมเลือกใช้ทั้งสองแบบ คือ mock adapter ใน unit test ของ service และใช้ชั้น HTTP ทดสอบตัว adapter เอง

mock ที่ไม่ตรงความจริง (mock drift)

ปัญหาที่เจ็บที่สุดของการ mock คือ test ผ่านหมดแต่ production พัง เพราะ mock ตั้งไว้ว่า API คืน { id } แต่ของจริงคืน { orderId } วิธีลดความเสี่ยงคือทดสอบกับ contract จริง เช่น contract test (Pact เป็นตัวอย่างหนึ่ง) หรือตรวจ response ที่ใช้ใน mock เทียบกับ OpenAPI schema และมี integration test ของเส้นทางหลักกับ sandbox ของผู้ให้บริการ ฝั่ง Python มีเครื่องมือเล็ก ๆ ที่ช่วยได้คือ autospec=True ทำให้ mock มี signature เหมือนของจริง เรียกผิดจำนวน argument จะ error ทันที (ตรวจกับ Python 3.13 แล้ว ส่วน mock ธรรมดารับ argument อะไรก็ได้)

with patch("user_service.send_email", autospec=True) as m:
    with pytest.raises(TypeError):
        m("only-one-arg")      # send_email จริงรับ 2 argument

Mockito ฝั่ง Java (ตัวอย่าง API ไม่ได้รันในชุดนี้)

หลักการเดียวกัน คือ stub ด้วย when(...).thenReturn(...) และตรวจด้วย verify เมื่อใช้ MockitoExtension จะเปิด strict stubs ไว้ ถ้าตั้ง stub แล้ว test ไม่ได้ใช้ จะเกิด UnnecessaryStubbingException ซึ่งช่วยเตือนให้ลบ stub ที่ไม่จำเป็น

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
  @Mock PaymentGateway payment;
  @Mock OrderRepo repo;
  @InjectMocks OrderService service;

  @Test
  void doesNotSaveWhenChargeFails() {
    when(payment.charge("u1", 500)).thenReturn(ChargeResult.failed("INSUFFICIENT_FUNDS"));

    var result = service.checkout("u1", 500);

    assertEquals("FAILED", result.status());
    verify(repo, never()).save(any());
  }
}

ใช้ mock แค่ไหนถึงพอดี

แนวทางที่หลายทีมใช้คือ stub ของที่ “ถามค่า” (query) เพื่อให้โค้ดเดินต่อได้ และ verify เฉพาะผลข้างเคียงที่เป็นหัวใจของ requirement เช่น การบันทึกออเดอร์หรือการส่งอีเมล ส่วนการ verify ทุกการเรียกภายในจะทำให้ test พังทุกครั้งที่ refactor ถึงพฤติกรรมภายนอกจะไม่เปลี่ยน

ทักษะที่คาดหวัง: กำหนดกลยุทธ์และเป้าหมาย coverage · วางมาตรฐาน · ปรับประสิทธิภาพ · กำกับด้วยเมตริก · ผลักดันวัฒนธรรมและโค้ช

9

กลยุทธ์ unit testing และเป้าหมาย coverage ระดับหลายทีม

Advance

Define and evolve unit testing strategy and coverage goals across teams or projects

กลยุทธ์ไม่ใช่ตัวเลข coverage ตัวเดียว

ก่อนตั้งเลขใด ๆ ให้ตอบสามข้อ bug ที่หลุดไป production ของเราเกิดจากอะไรบ้าง ระบบแบ่งเป็นชั้นอย่างไร และ test ชั้นไหนในตอนนี้เปราะหรือช้าที่สุด คำตอบจะบอกว่าควรลงน้ำหนักที่ไหน แนวคิดทั้ง test pyramid และ testing trophy เป็นแค่จุดเริ่มต้นให้คิด ไม่มีรูปทรงไหนถูกเสมอไป

ลักษณะงานน้ำหนักที่ควรลงข้อควรระวัง
Domain logic หนัก (คิดราคา, ค่าธรรมเนียม, กฎสิทธิ์)unit test หนาแน่น อาจเสริม property-based test หรือ mutation testing ในโมดูลสำคัญtest ที่ผูกกับโครงสร้างภายใน refactor แล้วพังตาม
CRUD บาง ๆ บน frameworkintegration/API test กับ DB จริงมักคุ้มกว่า unit test ของ controllerunit test ที่ mock ทุกอย่างแทบไม่ตรวจอะไร
หลาย microserviceunit ในแต่ละ service + contract test ระหว่าง service + E2E น้อยตัวที่ครอบ journey สำคัญE2E จำนวนมากช้าและ flaky
Frontendcomponent test ที่ทดสอบพฤติกรรมที่ผู้ใช้เห็น + unit ของ logic ที่แยกออกมาsnapshot ที่ไม่มีใครอ่านตอนอัปเดต
Legacy ที่ไม่มี testcharacterization test เฉพาะจุดที่กำลังแก้ + gate ที่ new codeอย่ารอเขียนทั้งระบบก่อนค่อยเริ่ม

ตั้งเป้า coverage เป็นชั้น ๆ

เป้าหมายเดียวทั้งองค์กรมักไม่เวิร์ก ทางที่ใช้ได้จริงคือแยกเป็นหลายชั้น ชั้นแรกคือ gate ที่ new code ซึ่ง SonarQube ตั้งต้นไว้ที่ 80% ชั้นที่สองคือ ratchet คือ coverage รวมห้ามต่ำกว่าค่าปัจจุบัน แล้วขยับเป้าขึ้นเป็นช่วง ๆ ชั้นที่สามคือโมดูลที่เสี่ยงสูงตั้งเกณฑ์เข้มกว่า (เช่น โมดูลที่เกี่ยวกับเงินหรือสิทธิ์) และชั้นที่สี่คือข้อยกเว้นต้องบันทึกเหตุผล เจ้าของ และวันที่ทบทวน ตัวเลขทั้งหมดนี้ทีมต้องกำหนดเองจากบริบท ไม่มีตัวเลขสากลที่ถูกเสมอ

เหตุผลที่เริ่มที่ new code คือ ระบบเก่าที่ coverage 20% ปรับเป็น 80% ในไม่กี่เดือนไม่ได้ ถ้าตั้งเกณฑ์กับ coverage รวมทันที ทุก PR จะถูกบล็อกจากเรื่องที่ผู้เขียนไม่ได้ก่อ ทีมจะเริ่มหาทางเลี่ยง ส่วนการ gate ที่ new code ทำให้ของใหม่มีคุณภาพตามเกณฑ์ และตัวเลขรวมค่อย ๆ ดีขึ้นตามธรรมชาติ

ขยายไปหลายทีมอย่างไรไม่ให้เกิดแรงต้าน

เริ่มจากวัดสถานะปัจจุบันของแต่ละทีม (baseline) แล้วตกลงนิยามร่วมกัน เช่น อะไรนับเป็น unit test อะไรเป็น integration จากนั้นทำ template ของ pipeline กลางที่ตั้ง coverage report และ SonarQube ให้เรียบร้อย ทีมที่เริ่มทีหลังจะได้ไม่ต้องตั้งเอง ทดลองกับหนึ่งถึงสองทีมก่อน (pilot) เก็บปัญหาจริง แล้วค่อยขยาย ทบทวนกลยุทธ์เป็นรอบ เช่น ทุกไตรมาส โดยดูจากเมตริกและ incident ที่เกิด trade-off ของมาตรฐานกลางคือความสม่ำเสมอแลกกับความยืดหยุ่น ทางออกที่ใช้บ่อยคือให้ override ได้เมื่อมีเหตุผลที่บันทึกไว้

สิ่งที่ตั้งใจไม่ทดสอบก็ได้ แต่ต้องตัดสินใจอย่างเปิดเผย

getter/setter ธรรมดา โค้ดที่ generate จากเครื่องมือ (เช่น client ที่สร้างจาก OpenAPI spec) และ glue code ของ framework มีมูลค่าต่อการทดสอบต่ำ ให้ exclude แบบที่ทบทวนได้และมีเหตุผลกำกับ แล้วไปทดสอบที่ต้นทางแทน เช่น ทดสอบ spec หรือตัว generator ถ้า exclude แบบเงียบ ๆ รายการจะโตจนกลายเป็นที่ซ่อนโค้ดเสี่ยง

10

มาตรฐานการเขียนโค้ดและ test ที่ขยายได้

Advance

Establish coding and testing guidelines to ensure consistency and scalability of unit tests

มาตรฐานที่ควรเขียนไว้

ข้อกำหนดที่ดีสั้นและตรวจได้ ตารางนี้เป็นตัวอย่างหมวดที่ทีมส่วนใหญ่ควรตกลงกัน แต่ละข้อควรมีเหตุผลกำกับ เพื่อให้คนที่เห็นต่างเถียงกับเหตุผลได้ ไม่ใช่เถียงกับคนเขียน

หมวดตัวอย่างข้อกำหนดเหตุผล
ชื่อและโครงสร้างชื่อ test บอกพฤติกรรมและเงื่อนไข ใช้โครง Arrange–Act–Assertล้มใน CI แล้วอ่านชื่อก็รู้ว่าอะไรพัง
ขอบเขต unitunit test ห้ามแตะ network, database, เวลาจริง ถ้าแตะต้องติด tag integrationรักษาความเร็วและความเสถียรของ suite หลัก
นโยบาย mockmock ที่ขอบระบบ (HTTP, DB, เวลา) ส่วนคลาสภายในใช้ของจริงหรือ fake กลางลดความเปราะเวลา refactor
ข้อมูลทดสอบสร้างผ่าน builder ต่อ test ไม่แชร์ object ที่แก้ค่าได้test ไม่เหยียบกัน รันขนานได้
Assertionทุก test ต้องมี assertion ที่ตรวจผล ไม่มี if/loop ใน testกัน test ที่ผ่านโดยไม่ได้ตรวจอะไร
Definition of Doneโค้ดใหม่และ bug fix ต้องมี test และ new-code coverage ผ่าน gateทำให้ test เป็นส่วนหนึ่งของงาน

anti-pattern ที่ควรรู้จักชื่อ

Anti-patternปัญหาทางแก้
Assertion-free testรันผ่านแต่ไม่ตรวจอะไร ดัน coverage ปลอมบังคับด้วย lint rule และรีวิว
Logic ใน test (loop, if)test ซับซ้อนและอาจมี bug เอง บาง assertion อาจไม่ถูกรันใช้ test.each / parametrize
Shared mutable fixturetest ผูกกัน ผ่านหรือล้มตามลำดับสร้างข้อมูลใหม่ต่อ test
ทดสอบ private method หรือรายละเอียดภายในrefactor โดยพฤติกรรมเดิมก็ทำให้ test ล้มทดสอบผ่านพฤติกรรมสาธารณะ
Over-mockingtest ผูกกับวิธีทำ ไม่ใช่ผลที่ต้องได้mock เฉพาะที่ขอบระบบ
Skip หรือคอมเมนต์ test ทิ้งโดยไม่มีร่องรอยช่องว่างที่ไม่มีใครรู้กติกา: skip ต้องมี ticket เจ้าของ และวันหมดอายุ

บังคับด้วยเครื่องมือ ไม่ใช่ด้วยเอกสารอย่างเดียว

กติกาที่ต้องจำเอง ไม่นานก็ถูกลืม ถ้าตรวจอัตโนมัติได้ให้ตรวจใน CI ตัวอย่างนี้เปิดกฎของ eslint-plugin-jest ผมลองรันกับ ESLint 10.15.0 และ eslint-plugin-jest 29.17.0 กับไฟล์ที่มี test ไม่มี assertion, test ที่ถูก skip และ expect ใต้ if ซึ่งทั้งสามถูกจับครบ

// eslint.config.mjs
import jest from 'eslint-plugin-jest';

export default [
  {
    files: ['**/*.test.js'],
    plugins: { jest },
    rules: {
      'jest/expect-expect': 'error',          // test ต้องมี assertion
      'jest/no-conditional-expect': 'error',  // ห้าม expect ใต้ if/catch
      'jest/no-disabled-tests': 'warn',       // เตือนเมื่อมี test.skip
      'jest/no-focused-tests': 'error',       // ห้าม test.only หลุดเข้า main
      'jest/valid-expect': 'error',
    },
  },
];

ส่วนฝั่ง Python ใช้ marker และ --strict-markers เพื่อกันชื่อ marker ที่พิมพ์ผิด และฝั่ง Java ใช้ tag ของ JUnit (@Tag("integration")) แยกชั้นของ test เพื่อรันคนละจังหวะใน pipeline

ทำให้มาตรฐานขยายได้

หลักการที่ไม่ขึ้นกับภาษา เช่น Arrange–Act–Assert, test ต้อง independent, นโยบาย mock ควรแยกจากตัวอย่างและ config เฉพาะภาษา เพื่อให้ทีมที่ใช้ภาษาต่างกันใช้เอกสารเดียวกันได้ จากนั้นให้มี shared test utility (builder, fake ที่ใช้ซ้ำ) ใน package กลาง, template โปรเจกต์ที่ตั้ง lint, coverage และ CI ไว้ให้, PR template ที่มี checklist เรื่อง test และตัวอย่าง “test ที่ดี” จริงใน repo เอกสารควรมีเจ้าของและเวอร์ชัน บอกวันที่แก้และเหตุผล เพื่อให้เป็นเอกสารที่เปลี่ยนตามบทเรียน ไม่ใช่ประกาศที่ตายตัว

11

ปรับประสิทธิภาพ test: ลดความซ้ำ เร็วขึ้น ดูแลง่าย

Advance

Optimize test efficiency by reducing redundancy, improving runtime, and ensuring maintainability

วัดก่อนปรับ

suite ที่ช้ามักไม่ได้ช้าทั้งหมด แต่ช้าที่ไม่กี่จุด ใช้เครื่องมือบอกก่อนเดา ฝั่ง pytest ใช้ pytest --durations=10 แสดง test ที่ช้าที่สุดสิบตัว ฝั่ง Jest ใช้ --verbose ดูเวลาของแต่ละ test แล้วดูว่าเวลาหมดไปกับขั้นตอนไหน เป็น setup, การรอ, หรือ I/O จริงที่หลุดเข้ามา การเพิ่ม worker เป็นสองเท่าโดยไม่รู้สาเหตุอาจทำให้ปัญหา flaky เพิ่มขึ้นแทนที่จะเร็วขึ้น

ลดความซ้ำซ้อน

ความซ้ำที่เจอบ่อยคือกฎเดียวกันถูกทดสอบครบทุกกรณีทั้งในชั้น unit, API และ E2E ซึ่งแปลว่าเสียเวลารันและเสียเวลาแก้สามที่เมื่อกฎเปลี่ยน แนวทางคือเก็บรายละเอียดทุกกรณีไว้ที่ชั้นล่างสุดที่จับได้ แล้วให้ชั้นบนมีเคสตัวแทนไม่กี่เคสเพื่อยืนยันว่าชิ้นส่วนต่อกันถูก test ที่คล้ายกันหลายตัวให้รวมเป็น parameterized test ส่วน test ที่ไม่มีใครรู้ว่าปกป้องอะไร ให้ตรวจก่อนลบ ด้วย mutation testing หรือด้วยการแก้โค้ดให้ผิดแล้วดูว่ามี test ล้มหรือไม่ pytest-cov มีตัวเลือก --cov-context=test ที่บันทึกว่า test ไหนรันบรรทัดไหน ใช้หา test ที่ครอบคลุมเท่ากันได้

ลดเวลารัน

เทคนิคตัวอย่างเงื่อนไข / trade-off
รันขนานJest แยก worker ตามไฟล์ (ปรับด้วย --maxWorkers), pytest-xdist (-n auto), JUnit parallel executiontest ต้อง independent ถ้าแชร์ port, ไฟล์ หรือ schema จะ flaky
แบ่ง shard ใน CIjest --shard=1/3ต้องรวมรายงาน coverage จากทุก shard ก่อนตรวจ threshold หรือส่งเข้า SonarQube
รันเฉพาะที่เกี่ยวข้องjest --changedSince=origin/main, --onlyChangedเหมาะกับ feedback ระหว่างพัฒนา ควรรันครบอีกรอบก่อน merge
ตัดการรอเปล่าแทน sleep ด้วย fake timers หรือรอ eventต้องออกแบบโค้ดให้ควบคุมเวลาได้
ย้าย setup ที่แพงไปครั้งเดียวbeforeAll หรือ fixture scope แบบ moduleใช้ได้เมื่อของที่สร้างเป็น read-only และล้างข้อมูลหลังจบ
แยก suite เร็วและช้าtag unit กับ integration แล้วรันคนละจังหวะsuite เร็วรันทุก commit suite ช้ารันทุก PR หรือรายคืน

ดูแลง่าย: DRY กับ DAMP

ในโค้ดปกติเรากำจัดความซ้ำ แต่ใน test มีแนวคิดที่เรียกว่า DAMP (Descriptive And Meaningful Phrases) คือยอมให้ซ้ำบ้างถ้าทำให้ test แต่ละตัวอ่านจบในที่เดียวและเห็นเจตนาชัด helper ที่ซ่อนข้อมูลสำคัญไว้ลึกเกินไปบังคับให้คนต้องกระโดดไปมาระหว่างไฟล์เพื่อรู้ว่า test ตัวนี้ใช้ข้อมูลอะไร builder ที่ให้ระบุเฉพาะฟิลด์ที่เกี่ยวข้องกับ test เป็นจุดสมดุลที่ใช้ได้ดี และเพราะ test เป็นโค้ด จึงควรได้รับการรีวิวและ refactor เหมือนโค้ดหลัก รวมถึงลบ test ที่ปกป้องพฤติกรรมที่ requirement ยกเลิกไปแล้ว

หนึ่ง property แทนหลายตัวอย่าง

property-based testing (fast-check ใน JavaScript, Hypothesis ใน Python) ให้เราเขียนคุณสมบัติที่ต้องเป็นจริงเสมอ เช่น “ยอดรวมหลังลดต้องไม่เกินยอดก่อนลด” แล้วให้เครื่องมือสุ่มข้อมูลจำนวนมากมาทดสอบ ช่วยเจอกรณีที่ไม่ได้คิดถึง แลกกับความซับซ้อนในการเขียน property และต้องกำหนด seed เพื่อให้ทำซ้ำได้เมื่อล้ม

Quality governance ด้วยตัวชี้วัด

Advance

Establish metrics-driven quality governance (e.g., coverage %, defect leakage, test pass/fail trends)

ตัวชี้วัดที่ใช้บ่อย และกับดักของแต่ละตัว

ตัวชี้วัดบอกอะไรกับดัก
Coverage บน new code / รวม / branchสัดส่วนโค้ดที่ test รันไม่บอกว่าตรวจผลหรือเปล่า ดันตัวเลขได้ด้วย test ที่ไม่มี assertion
Mutation scoreสัดส่วน mutant ที่ test จับได้ สะท้อนคุณภาพ assertionรันช้า ใช้กับโมดูลสำคัญหรือไฟล์ที่เปลี่ยน
Pass/fail trendแนวโน้มความเขียวของ buildเขียวตลอดอาจเพราะ test ถูก skip หรือ retry ปิดปัญหา
Flaky rateสัดส่วนครั้งที่ test เปลี่ยนผลโดยไม่มีการเปลี่ยนโค้ดต้องนิยามและเก็บข้อมูลรันซ้ำให้ได้ก่อน
Suite duration (เช่น p50/p95)ความเร็วของ feedbackเฉลี่ยอย่างเดียวซ่อนรอบที่ช้ามาก
Defect leakage / escaped defectsdefect ที่หลุดไปหลังปล่อยต้องนิยามช่วงเวลาและชนิดของ defect ให้ตรงกัน
Change failure rate (กลุ่ม DORA)สัดส่วนการ deploy ที่ต้องแก้ด่วนหรือ rollbackเป็นผลรวมของหลายปัจจัย ไม่ใช่เฉพาะ test

Defect leakage: คิดอย่างไร

นิยามที่ใช้กันบ่อยคือ defect ที่พบหลังปล่อย หารด้วย defect ทั้งหมดที่พบก่อนและหลังปล่อย ตัวเลขด้านล่างเป็นตัวอย่างสมมติเพื่อฝึกคำนวณ ไม่ใช่ข้อมูลจริงหรือเกณฑ์อ้างอิง

ก่อนปล่อยพบ 36 รายการ, หลังปล่อยพบ 4 รายการ
Defect leakage = 4 / (36 + 4) = 10%
Defect Removal Efficiency (DRE) = 36 / (36 + 4) = 90%

ทีมต้องตกลงให้ชัดว่านับ defect ช่วงเวลาไหนหลังปล่อย (เช่นภายใน 30 วัน) และไม่นับ requirement ที่เปลี่ยนภายหลังเป็น defect ไม่งั้นตัวเลขของทีมต่าง ๆ เทียบกันไม่ได้

อ่านเทรนด์ให้เป็น

ตัวเลขเดียวหลอกได้ง่าย การอ่านคู่กันบอกเรื่องราวมากกว่า ถ้า coverage ขึ้นจาก 60% เป็น 85% แต่ defect ที่หลุดไม่ลดเลย แสดงว่า test ที่เพิ่มอาจไม่ได้ตรวจอะไร ให้ตรวจด้วย mutation score และดูว่า defect หลุดจากโมดูลไหน ถ้า pass rate คงที่ที่ 98% แต่ flaky rate สูงขึ้น ความเชื่อมั่นต่อ pipeline กำลังลดลงทั้งที่ตัวเลขดูปกติ ถ้า suite duration เพิ่มขึ้นเรื่อย ๆ feedback ช้าลง คนจะรันน้อยลงและ commit ก้อนใหญ่ขึ้น และถ้า defect ซ้ำที่โมดูลเดิม แปลว่ามีช่องว่างของ test เฉพาะจุดที่ควรปิด

วางกลไกกำกับ

เมตริกที่คำนวณอัตโนมัติได้ (coverage บน new code, ผลของ test, ความซ้ำของโค้ด) ให้ใส่ใน quality gate ของ CI เพื่อไม่ต้องพึ่งการตามเตือนด้วยคน เมตริกที่ต้องตีความ (leakage, flaky rate, เทรนด์) ให้มีเจ้าของและจังหวะทบทวนที่ทีมตกลง พร้อมกระบวนการยกเว้นที่บันทึกเหตุผลและวันหมดอายุ การตั้งเกณฑ์ให้เริ่มจากค่าจริงของวันนี้แล้วบังคับว่าห้ามแย่ลง จากนั้นขยับขึ้นเป็นช่วง ๆ ตามข้อมูล จะได้รับการยอมรับมากกว่าการประกาศเกณฑ์สูงลิ่วในวันแรก

Goodhart’s lawเมื่อตัวชี้วัดถูกใช้เป็นเป้าหมายเดียว คนจะปรับพฤติกรรมเพื่อให้ตัวเลขดี จนตัวเลขไม่สะท้อนคุณภาพจริง เช่น เขียน test ไม่มี assertion ให้ coverage ผ่าน หรือ exclude ไฟล์ วิธีลดความเสี่ยงคือดูหลายตัวคู่กัน (coverage คู่กับ mutation score และ leakage) และไม่ใช้เมตริกเหล่านี้ประเมินผลงานรายบุคคล

L1. เขียน test ให้ calculateTotal ให้ครบตามสเปก (Jest)

สเปก: รับ items (array ของ { price, qty }) และ coupon ถ้า items ไม่ใช่ array หรือว่างให้ throw Error ถ้า price < 0 หรือ qty <= 0 ให้ throw RangeError คูปอง SAVE10 ลด 10% คูปอง FREE100 ลด 100 บาทเมื่อยอดรวมตั้งแต่ 1,000 ขึ้นไป ผลปัดเป็นทศนิยม 2 ตำแหน่ง ให้เขียน test ที่ครอบคลุม partition และ boundary ทั้งหมด

function calculateTotal(items, coupon) {
  if (!Array.isArray(items) || items.length === 0) throw new Error('items must be a non-empty array');
  let subtotal = 0;
  for (const { price, qty } of items) {
    if (price < 0 || qty <= 0) throw new RangeError('invalid price or qty');
    subtotal += price * qty;
  }
  let total = subtotal;
  if (coupon === 'SAVE10') total = subtotal * 0.9;
  else if (coupon === 'FREE100' && subtotal >= 1000) total = subtotal - 100;
  return Math.round(total * 100) / 100;
}

    }
  }
  throw lastError;
}

แนวคิด: ช่องที่ขาดคือค่า default ทั้งสามจุด test เดิมส่ง option ครบทุกครั้ง ให้เรียก retry(fn) โดยไม่ส่ง option และตรวจว่า delay ที่ใช้คือ 1,000 ms จริง

describe('retry: ค่า default', () => {
  beforeEach(() => jest.useFakeTimers());
  afterEach(() => jest.useRealTimers());

  test('เรียกโดยไม่ส่ง options → ใช้ retries=3 และ delay 1000ms', async () => {
    const fn = jest.fn().mockRejectedValueOnce(new Error('e1')).mockResolvedValue('ok');

    const promise = retry(fn);
    await jest.advanceTimersByTimeAsync(999);
    expect(fn).toHaveBeenCalledTimes(1);
    await jest.advanceTimersByTimeAsync(1);

    await expect(promise).resolves.toBe('ok');
    expect(fn).toHaveBeenCalledTimes(2);
  });
});

L6. สอง test นี้มีปัญหาคนละแบบ หาให้เจอและแก้ (Jest) 
// (ก) ล้มทั้งที่ค่าดูเหมือนกัน
test('โหลด user', async () => {
  const user = await loadUser(1);                       // คืน { id: 1, name: 'A', tags: [] }
  expect(user).toBe({ id: 1, name: 'A', tags: [] });
});

// (ข) ผ่านหรือล้มไม่แน่นอน ผลไม่น่าเชื่อถือ
test('reject เมื่อ id ไม่ถูกต้อง', () => {
  expect(loadUser(-1)).rejects.toThrow('invalid id');
});

(ก) toBe เทียบ reference ด้วย Object.is object สองก้อนจึงไม่เท่ากันแม้ค่าตรงกัน ให้ใช้ toEqual (ข) ไม่มี await หรือ return ทำให้ test จบก่อนที่ assertion จะทำงาน ผมลองกับ Jest 30.5.2 บน Node 22 แบบที่ assertion ล้ม ผลคือเกิด unhandled rejection จนโปรเซสของ Jest ล่ม ส่วนบางสภาพแวดล้อมอาจรายงานว่าผ่านโดยไม่เห็นความผิดพลาด จึงต้อง await หรือ return เสมอ

test('โหลด user', async () => {
  const user = await loadUser(1);
  expect(user).toEqual({ id: 1, name: 'A', tags: [] });
});

test('reject เมื่อ id ไม่ถูกต้อง', async () => {
  await expect(loadUser(-1)).rejects.toThrow('invalid id');
});
