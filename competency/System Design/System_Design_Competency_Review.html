Skill Definition: Designing systems to meet specified requirements and agreed systems architectures

เริ่มจากโจทย์เดียวกันตลอดทั้งหน้า

สมมติเราต้องทำระบบ Payslip ที่หลายบริษัทใช้ร่วมกัน (multi-tenant) HR ของแต่ละบริษัทเลือกรอบเงินเดือนแล้วกดเผยแพร่ พนักงานเข้ามาดูสลิปของตัวเอง ระบบต้องส่งแจ้งเตือน และฝ่ายซัพพอร์ตต้องตามหา error ได้โดยไม่ต้องเห็นตัวเลขเงินเดือนของใคร

สิ่งที่ระบบต้องทำ (functional requirement)

  1. HR เลือกบริษัท (tenant) กับรอบเงินเดือน แล้ว publish payslip ได้
  2. พนักงานดูได้เฉพาะ payslip ของตัวเอง และเลือกเดือนได้
  3. ผู้ที่มีสิทธิ์ดาวน์โหลดเป็น PDF ได้
  4. publish สำเร็จแล้วระบบส่งแจ้งเตือน โดย HR ไม่ต้องรอส่งอีเมลเสร็จ
  5. ซัพพอร์ตเปิดดู log เพื่อหาสาเหตุ error ได้ โดย log ไม่มีข้อมูลเงินเดือน

คุณภาพที่ต้องได้ (non-functional requirement) ตัวเลขด้านล่างเป็นค่าสมมติสำหรับฝึกออกแบบ ไม่ใช่ของระบบจริง

ประเด็นเป้าหมายสมมติทำไมต้องถามก่อนออกแบบ
จำนวนพนักงาน40,000 คนบอกขนาดข้อมูลและจำนวนผู้ใช้
ช่วง peak300 request/วินาที ตอนวันจ่ายเงินเดือนใช้คิด capacity และวางแผน load test
latencyp95 ของ GET /payslips ไม่เกิน 400 msบอกว่าเร็วพอสำหรับผู้ใช้หรือยัง
availability99.9% ต่อเดือนกำหนดว่าต้องมี monitoring และ redundancy แค่ไหน
securityทุก request ตรวจ tenant และความเป็นเจ้าของกันข้อมูลเงินเดือนรั่วข้ามบริษัทหรือข้ามคน
auditเก็บว่าใคร publish และ download เมื่อไรไว้ตรวจย้อนหลัง แต่ไม่ log ตัวเลขเงินเดือน
Functional คือ “ทำอะไรได้” ส่วน non-functional คือ “ทำได้ดีแค่ไหนภายใต้ข้อจำกัดอะไร”ถ้าไม่ถามเรื่อง non-functional ก่อน เราอาจเขียนฟีเจอร์ครบทุกข้อแล้วเลือกสถาปัตยกรรมผิดทั้งที่ไม่มีใครจับได้ เพราะ requirement ไม่เคยบอกว่าต้องรองรับ 300 request ต่อวินาที

requirement ที่ดีต้อง “วัดได้”

คำว่า “เร็ว” “ปลอดภัย” “ดูแลง่าย” ฟังดูดีแต่ตรวจไม่ได้ ใครจะบอกว่าผ่านก็ได้ ลองเปรียบเทียบดู

เขียนแบบนี้ยังใช้ไม่ได้เขียนใหม่ให้วัดได้
ระบบต้องเร็วp95 ของ GET /payslips ≤ 400 ms ที่ 300 request/วินาที
ระบบต้องปลอดภัยrequest ข้าม tenant หรือข้ามพนักงานต้องถูกปฏิเสธ 100% ในชุด authorization test
ระบบต้องไม่ล่มavailability 99.9% ต่อเดือน วัดจาก health check ของ load balancer
ดูแลง่ายแก้สูตรคำนวณภาษีแล้วกระทบไม่เกิน 1 module และ test ผ่านใน CI ภายใน 10 นาที
ผู้ใช้ใช้งานง่ายพนักงานใหม่หา payslip เดือนล่าสุดเจอภายใน 3 คลิก (วัดจาก usability test 5 คน)

วาด flowchart ของ user flow ก่อน จะเห็นช่องโหว่เร็ว

flowchart ที่ดีไม่ได้มีแค่ทางที่สำเร็จ ทุกเงื่อนไข (ข้าวหลามตัด) ต้องมีทางออกที่ชัดทั้งสองฝั่ง ลองไล่ตามภาพว่ามีกรณีไหนที่ผู้ใช้ถูกปล่อยค้างโดยไม่มีผลลัพธ์หรือเปล่า

สี่เหลี่ยมคือขั้นตอน ข้าวหลามตัดคือเงื่อนไข วงรีคือจุดเริ่มกับจุดจบ ทุกเส้นออกจากเงื่อนไขต้องไปจบที่ผลลัพธ์ที่ผู้ใช้เห็นได้ เช่น หน้า login, ข้อความไม่มีสิทธิ์ หรือหน้าว่างที่อธิบายว่ายังไม่มีสลิป

คำถามที่ควรถามก่อนวาดกล่อง

  • ใครใช้ พนักงาน HR และซัพพอร์ตมีสิทธิ์ต่างกันตรงไหน
  • ปริมาณและช่วงเวลา ใช้พร้อมกันหมดวันจ่ายเงินเดือน หรือกระจายทั้งเดือน
  • ข้อมูลอ่อนไหวแค่ไหน payslip เป็นทั้งข้อมูลส่วนบุคคลและข้อมูลการเงิน
  • “สำเร็จ” หมายถึงอะไร publish สำเร็จตอนบันทึกลงฐานข้อมูล หรือตอนอีเมลส่งออกไปแล้ว
  • ข้อจำกัด เวลา ทีม งบ cloud ที่องค์กรอนุมัติ หรือ API เดิมที่ต้องต่อด้วย
  • มีระบบเดิมไหม ต้องย้ายข้อมูลโดยไม่หยุดระบบหรือเปล่า

System Design กับ Software Architecture ต่างกันอย่างไร

System design เริ่มจากโจทย์ที่ต้องทำให้สำเร็จ เช่น “พนักงาน 40,000 คนเปิดดูสลิปพร้อมกันได้อย่างไร” แล้วไล่แยก requirement, component, data flow, เส้นทาง error และ performance ส่วน software architecture เน้นการตัดสินใจเชิงโครงสร้างที่ส่งผลระยะยาว เช่น แยก service หรือไม่ วาง trust boundary ตรงไหน ใครเป็นเจ้าของข้อมูลชุดไหน ในงานจริงสองคำนี้ทับกันมาก อย่าเสียเวลาแบ่งให้เด็ดขาด ข้อสอบมักวัดว่าเราอธิบายเหตุผลได้ไหมมากกว่าตั้งชื่อให้ถูก

คุณภาพของระบบมีมิติอะไรบ้าง

ถ้านึกไม่ออกว่า non-functional requirement ควรมีหัวข้ออะไร ลองหยิบรายการจาก ISO/IEC 25010 มาเป็นเช็กลิสต์ ฉบับ 2011 มี 8 characteristic ส่วนฉบับปรับปรุง 2023 มี 9 โดยเปลี่ยนชื่อ usability เป็น interaction capability เปลี่ยน portability เป็น flexibility และเพิ่ม safety เข้ามา ในข้อสอบอาจเจอทั้งชื่อเก่าและชื่อใหม่ ตารางข้างล่างใส่ทั้งสองไว้

สมมติเราเขียนหน้า Payslip เป็น React component ตัวเดียวที่ทำทุกอย่าง ทั้ง fetch API กรองข้อมูล จัดรูปแบบเงิน ตรวจสิทธิ์ export PDF และแสดง error พอมีฟีเจอร์ใหม่ก็ต้องแก้ไฟล์เดิมซ้ำแล้วซ้ำอีก เขียน test ก็ยากเพราะทุกอย่างพันกัน แนวคิดแก้ปัญหานี้ง่ายมาก คือ แยกส่วนที่มีเหตุผลเปลี่ยนต่างกันออกจากกัน

อ่านภาพ: ลูกศรคือ “ใครเรียกใคร” ส่วนที่ติดต่อ backend ถูกกั้นไว้ใน PayslipApiClient ที่เดียว ถ้า API เปลี่ยน เราแก้จุดเดียว UI ไม่ต้องรู้ว่าข้างหลังเป็นอะไร

ตัวอย่าง interface ที่ช่วยแยกหน้าที่

export interface PayslipSummary {
  employeeId: string;
  period: string;
  netPay: number;
}

export interface PayslipRepository {
  findByEmployeeAndPeriod(
    employeeId: string,
    period: string
  ): Promise<PayslipSummary | null>;
}

export class PayslipReader {
  constructor(private readonly repository: PayslipRepository) {}

  async execute(employeeId: string, period: string) {
    return this.repository.findByEmployeeAndPeriod(employeeId, period);
  }
}
  • PayslipRepository บอกว่า “ต้องทำอะไรได้” แต่ไม่ผูกว่าเก็บใน PostgreSQL หรือเป็นข้อมูลปลอมตอนเทสต์
  • PayslipReader เปลี่ยนวิธีอ่านข้อมูลได้โดยไม่ต้องแก้ตัวเอง
  • ถ้าใช้ NestJS จริง ต้องกำหนด injection token ให้ interface ด้วย เพราะ interface ของ TypeScript หายไปตอน runtime

Beginner

สองคำนี้ต่างกันอย่างไร

Reliability คือระบบทำงานได้ตามที่คาดไว้อย่างต่อเนื่อง แม้บางส่วนจะผิดพลาด ส่วน usability คือผู้ใช้เข้าใจว่าเกิดอะไรขึ้นและทำงานต่อได้ถูก สองเรื่องนี้ชนกันบ่อยที่หน้าจอ error เพราะระบบจะ “ไม่พัง” ก็ต่อเมื่อผู้ใช้รู้ว่าต้องทำอะไรต่อ

สถานการณ์ควรออกแบบอย่างไรถ้าลืมจะเกิดอะไร
กำลังโหลดแสดง loading หรือ skeletonผู้ใช้คิดว่าหน้าค้าง แล้วกดซ้ำ
ไม่มีข้อมูลเดือนนี้แสดงหน้าว่างพร้อมอธิบายผู้ใช้คิดว่าระบบพัง
API ตอบ 401พาไป login หรือ refresh ตาม flow ที่กำหนดวนยิง request ซ้ำหรือค้างเงียบ ๆ
API ตอบ 403บอกว่าไม่มีสิทธิ์ และไม่แสดงข้อมูลเสี่ยงข้อมูลรั่ว และผู้ใช้งง
network timeoutแสดงปุ่มลองใหม่ที่ควบคุมได้spinner หมุนไม่จบ
กด export ซ้ำปิดปุ่มระหว่างทำงาน หรือกันงานซ้ำสร้างไฟล์ซ้ำหลายชุด
401, 403, 404 และ 5xx ไม่ใช่ “โหลดไม่สำเร็จ” เหมือนกันหมดแต่ละตัวบอกว่าใครต้องแก้และผู้ใช้ควรทำอะไรต่อ ถ้าเหมารวมเป็น toast ว่า “เกิดข้อผิดพลาด” ผู้ใช้จะไม่รู้ว่าต้อง login ใหม่ ขอสิทธิ์ หรือรอแล้วลองอีกครั้ง

แต่ละรหัสควรทำให้เกิดอะไร

รหัสความหมายฝั่ง UIฝั่ง backend
400ข้อมูลที่ส่งมาไม่ถูกรูปแบบชี้ให้แก้ input ที่ผิดตรวจ input และตอบ error ที่อ่านรู้เรื่อง
401ยังไม่ได้ยืนยันตัวตนไป login หรือ refresh sessionไม่ส่งข้อมูลใด ๆ
403รู้ว่าเป็นใคร แต่ไม่มีสิทธิ์บอกว่าไม่มีสิทธิ์ ไม่ retryตรวจสิทธิ์ที่ server เสมอ
404ไม่พบ resourceหน้าว่างหรือข้อความไม่พบระวังอย่าบอกเกินว่ามีอยู่จริงหรือไม่
429ยิงถี่เกินกำหนดรอแล้วลองใหม่ตามเวลาที่บอกส่ง Retry-After ถ้าทำได้
5xxฝั่งระบบมีปัญหาปุ่มลองใหม่ + ข้อความที่ไม่ตำหนิผู้ใช้log พร้อม requestId ไม่เปิดเผยรายละเอียดภายใน

เรื่องที่คนชอบถาม: ตอบ 404 แทน 403 เพื่อไม่ให้คนนอกรู้ว่า resource นั้นมีอยู่ ทำได้และเป็นแนวปฏิบัติที่ใช้กันจริง แต่ต้อง ตรวจสิทธิ์ก่อนแล้วค่อยเลือกรหัสที่จะตอบ ไม่ใช่ข้ามการตรวจสิทธิ์ไป

วาด state diagram ให้ทุกคนเห็นตรงกัน

เวลาบอกทีมว่า “ถ้า error ก็ขึ้น toast” มันคลุมเครือเกินไป state diagram บังคับให้เราตอบว่า มีสถานะอะไรได้บ้าง และเปลี่ยนจากสถานะไหนไปสถานะไหนเมื่อเกิดอะไร ทั้ง UI, QA และ backend จะอ่านภาพเดียวกันแล้วเขียน test case ได้ครบกว่าเดิมมาก

กรณีที่เจอบ่อย: ผู้ใช้เปลี่ยนเดือนเร็ว ๆ แล้วข้อมูลเก่ากลับมาทับของใหม่

ลองนึกภาพว่าผู้ใช้เลือกเดือน ก.ย. แล้วรีบเปลี่ยนเป็น ต.ค. request ของ ก.ย. ออกไปก่อน แต่บังเอิญตอบกลับมาช้ากว่า ถ้าโค้ดเขียนว่า “ตอบกลับมาเมื่อไรก็ใส่เข้า state เลย” หน้าจอจะโชว์ ก.ย. ทั้งที่ผู้ใช้เลือก ต.ค. อยู่ เรียกว่า race condition วิธีแก้ที่ตรงจุดคือยกเลิกคำขอเก่า (หรือเทียบว่าคำตอบนี้เป็นของคำขอล่าสุดไหม) และตั้ง timeout ไปด้วยเพื่อไม่ให้ spinner ค้าง

type Result<T> = { ok: true; data: T } | { ok: false; status: number };

export async function loadPayslip(
  period: string,
  signal: AbortSignal
): Promise<Result<{ netPay: number }>> {
  const res = await fetch(`/api/v1/payslips?period=${encodeURIComponent(period)}`, { signal });
  if (!res.ok) return { ok: false, status: res.status };
  return { ok: true, data: await res.json() };
}

// ฝั่ง UI: ทุกครั้งที่เปลี่ยนเดือน ให้ยกเลิกคำขอเก่า และตั้ง timeout
let current: AbortController | null = null;

export function requestPeriod(period: string, onDone: (r: Result<{ netPay: number }>) => void) {
  current?.abort();
  const ctrl = new AbortController();
  current = ctrl;
  const timer = setTimeout(() => ctrl.abort(), 10_000);
  loadPayslip(period, ctrl.signal)
    .then(r => { if (current === ctrl) onDone(r); })
    .catch(() => { if (current === ctrl) onDone({ ok: false, status: 0 }); })
    .finally(() => clearTimeout(timer));
}

ตรงนี้ปิดสองปัญหาในครั้งเดียว: คำตอบเก่าไม่ทับของใหม่ (current === ctrl) และ request ที่ค้างเกิน 10 วินาทีถูกตัดแล้วขึ้น error แทน spinner ไม่จบ ฝั่ง backend ก็ต้องช่วยกันด้วย เช่น ไม่ปล่อยให้ผู้ใช้กด refresh รัว ๆ จนระบบรับ request ซ้ำเกินจำเป็น

guideline ที่ทีมมักตกลงกันไว้

  • endpoint ขึ้นต้นด้วย /api/v1/... และตั้งชื่อ resource เป็นคำนาม
  • ตรวจ input ด้วย schema หรือ DTO ที่ทีมใช้ร่วมกัน
  • error response มีรูปแบบเดียวกัน เช่น code, message, requestId
  • ใช้ component จาก design system ถ้ารองรับ requirement นั้นอยู่แล้ว
  • ทุก API ต้องมี authentication, log ที่ไม่เผยข้อมูลส่วนบุคคล และ automated test ตามระดับความเสี่ยง

ประโยชน์ของ guideline ไม่ได้อยู่ที่ “กฎเยอะ” แต่อยู่ที่ คนใหม่เปิดโค้ดแล้วเดาถูกว่าอะไรอยู่ตรงไหน และ code review ไม่ต้องเสียเวลาเถียงเรื่องรสนิยม

ถ้ากฎใช้ไม่ได้กับโจทย์เรา ต้องทำอย่างไร

สมมติ vendor ส่งข้อมูลมาเป็นไฟล์ CSV เพราะยังไม่มี API สิ่งที่ไม่ควรทำคือแอบทำทางลัดเงียบ ๆ แล้วปล่อยให้คนต่อไปมาเจอเอง ให้ลำดับแบบนี้

  1. ลองทำตามกฎก่อน ดูว่าแปลงข้อมูลที่ขอบ (adapter) ให้ตรงกติกาได้ไหม
  2. ถ้าไม่ได้จริง ให้ถามคนที่ดูแลมาตรฐาน เช่น tech lead หรือ architect พร้อมเหตุผลและทางเลือกที่คิดไว้
  3. บันทึกการตัดสินใจ ด้วย ADR สั้น ๆ ว่าเบี่ยงเพราะอะไร มีความเสี่ยงอะไร จะกลับมาทบทวนเมื่อไร
  4. ใส่ test ที่ครอบเรื่องนี้ เพื่อให้ถ้ามีคนแก้ภายหลังจะรู้ว่าพังตรงไหน

ประเมิน concurrency ด้วยกฎของ Little

กฎของ Little บอกว่า จำนวน request ที่กำลังทำงานอยู่ ≈ throughput × เวลาตอบเฉลี่ย เมื่อระบบอยู่ในสภาวะค่อนข้างคงที่ ถ้า 300 RPS และเวลาตอบเฉลี่ย 0.2 วินาที จะมี request ค้างอยู่ในระบบเฉลี่ยราว 60 ตัวพร้อมกัน

ตัวเลข 60 ยังเอาไปกำหนดจำนวน instance ตรง ๆ ไม่ได้เพราะไม่รู้ว่า request หนึ่งใช้ CPU เท่าไร รอ I/O เท่าไร memory และ GC เป็นอย่างไร และต้องเผื่อ traffic ที่พุ่งกะทันหันกับเวลาที่ autoscaling ใช้ตื่น อีกอย่าง p95 ไม่ใช่ค่าเฉลี่ย อย่าเอา p95 มาแทนในสูตรแล้วเรียกว่าคำนวณแม่น

ตัวอย่างที่ใช้ได้จริงกว่าคือคิดเรื่อง connection pool ถ้าแต่ละ request ถือ connection ของฐานข้อมูลเฉลี่ย 30 ms ที่ 300 RPS จะมี connection ถูกใช้เฉลี่ย 300 × 0.03 = 9 ตัว ถ้า traffic พุ่งเป็นสองเท่าก็ 18 ตัว ซึ่งใกล้เต็มถ้า pool ตั้งไว้ 20 แบบนี้ปัญหาจะโผล่ที่ฐานข้อมูลก่อนที่ API จะเต็มด้วยซ้ำ

วาดภาพรวมของระบบแบบมีขอบเขต

API มีอย่างน้อยสองตัวเพื่อเพิ่ม capacity และกันกรณีตัวเดียวล่ม แต่ฐานข้อมูลยังเป็นจุดเดียวที่ต้องออกแบบ HA และ recovery แยกต่างหาก การมี API สองตัวไม่ได้ทำให้ทั้งระบบ highly available เอง

scale ขึ้นด้วยวิธีไหน

วิธีทำอย่างไรข้อดีข้อจำกัด
vertical scalingเพิ่ม CPU/RAM ให้เครื่องเดิมง่าย ไม่ต้องแก้โค้ดมีเพดาน และยังเป็นจุดล่มจุดเดียว
horizontal scalingเพิ่มจำนวน instance หลัง load balancerขยายต่อได้ และกันตัวเดียวล่มต้องออกแบบให้ stateless และจัดการ session ให้ดี
read replicaแยกการอ่านไปยังฐานข้อมูลสำเนาลดภาระ primaryอาจเห็นข้อมูลเก่าตาม replication lag
cacheเก็บผลที่อ่านบ่อยไว้ใกล้ผู้ใช้ลดภาระ DB ได้มากต้องออกแบบ key, ความสดของข้อมูล และสิทธิ์
async workerย้ายงานหนัก (PDF, email) ไปทำเบื้องหลังAPI ตอบเร็ว scale worker แยกได้ต้องมี queue, retry และ monitoring เพิ่ม

ข้อควรจำ: การ scale ที่ได้ผลคือ scale จุดที่เป็นคอขวดจริง ถ้าคอขวดอยู่ที่ query ช้า การเพิ่ม API จาก 2 เป็น 8 ตัวอาจทำให้ฐานข้อมูลโดนยิงหนักขึ้นและแย่กว่าเดิม

cache ข้อมูลเงินเดือนอย่างปลอดภัย

payslip อ่านบ่อยแต่เปลี่ยนไม่กี่ครั้งต่อเดือน cache จึงน่าสนใจ แต่ข้อมูลนี้อ่อนไหว ต้องระวังเป็นพิเศษ

  • key ต้องรวม tenantId, employeeId, period ไม่ใช่แค่ period
  • cache hit ไม่ใช่เหตุผลให้ข้ามการตรวจสิทธิ์ ตรวจสิทธิ์ก่อนแล้วค่อยอ่าน cache
  • ต้องมีวิธีลบ cache เมื่อมีการแก้ไข payslip หรือสิทธิ์เปลี่ยน และตั้ง TTL ไว้เป็นตาข่ายรองรับ
  • cache ไม่ได้ช่วย query ที่ช้าเสมอไป ต้องวัดก่อนว่าช้าเพราะอะไร

ความพร้อมใช้งานของระบบที่ต่อกันเป็นลูกโซ่

ถ้าบริการหนึ่งมี availability 99.9% และมันต้องพึ่งฐานข้อมูลที่มี 99.9% เหมือนกัน ผลรวมของสองตัวต่อกันเป็นอนุกรมจะเหลือประมาณ 0.999 × 0.999 ≈ 99.8% หรือ downtime ราว 86 นาทีต่อเดือน ยิ่งพึ่งพากันหลายชั้น ตัวเลขยิ่งลดลง ส่วนการวางสำรองแบบขนานจะดีขึ้นเฉพาะเมื่อความล้มเหลวของสองตัว เป็นอิสระต่อกันจริง ซึ่งแทบไม่จริงถ้าใช้ฐานข้อมูล ตัว deploy หรือ config ร่วมกัน

มาตรฐานพื้นฐานที่ระบบหลาย component ควรตกลงกันก่อน

  • service ไม่เก็บสถานะผู้ใช้ไว้ในหน่วยความจำ (stateless) เพื่อเพิ่ม instance ได้โดยไม่เสียข้อมูล
  • มี health endpoint แยก “ยังมีชีวิต” (liveness) กับ “พร้อมรับ traffic” (readiness)
  • ค่า config และ secret มาจาก environment ไม่ฝังในโค้ด
  • log เป็นโครงสร้าง มี requestId ผูกข้ามทุก component และไม่มีข้อมูลอ่อนไหว
  • ทุกการเรียกข้ามเครือข่ายมี timeout และนโยบาย retry ที่กำหนดไว้ชัด

type Option = { name: string; scores: number[] };

export function weightedScore(weights: number[], option: Option): number {
  if (weights.length !== option.scores.length) throw new Error('Mismatched lengths');
  const total = weights.reduce((a, b) => a + b, 0);
  if (Math.abs(total - 1) > 1e-9) throw new Error('Weights must sum to 1');
  return option.scores.reduce((sum, s, i) => sum + s * weights[i], 0);
}

type Status = 'draft' | 'validated' | 'published' | 'archived';
type Action = 'validate' | 'publish' | 'archive';

const allowedTransitions: Record<Status, Partial<Record<Action, Status>>> = {
  draft: { validate: 'validated' },
  validated: { publish: 'published' },
  published: { archive: 'archived' },
  archived: {},
};

export function transition(status: Status, action: Action): Status {
  const next = allowedTransitions[status][action];
  if (!next) throw new Error(`Invalid transition: ${status} -> ${action}`);
  return next;
}

transition('draft', 'validate');   // validated
// transition('published', 'publish'); // โยน Error
import { describe, it, expect } from 'vitest';
import { transition } from './state-machine';

describe('Payslip publishing lifecycle', () => {
  it('allows validation before publishing', () => {
    expect(transition('draft', 'validate')).toBe('validated');
  });

  it('rejects publishing twice', () => {
    expect(() => transition('published', 'publish')).toThrow('Invalid transition');
  });
});

  6. บันทึกการตัดสินใจ ผลทดสอบก่อน/หลัง และแผน rollback

Data, API และ async design ที่ระบบหลาย component ต้องมี

Intermediateเนื้อหาเสริม

เนื้อหาเสริม: ส่วนนี้เติมเข้ามาเพราะเกณฑ์ “ระบบหลาย component” ต้องใช้เรื่องข้อมูล สัญญา API และงานเบื้องหลังเสมอ

ออกแบบข้อมูลของระบบหลายบริษัท

  • ใส่ tenant_id ในทุกตารางที่เป็นข้อมูลของบริษัท และให้เป็นส่วนหนึ่งของ key หรือ index เพื่อให้ query ที่ลืมใส่เงื่อนไข tenant หาง่าย
  • เก็บจำนวนเงินอย่าใช้ float ใช้ NUMERIC หรือเก็บเป็นหน่วยย่อยสุด (เช่น สตางค์เป็นจำนวนเต็ม) พร้อมสกุลเงิน เพราะ 0.1 + 0.2 ไม่เท่ากับ 0.3 ใน float
  • ระบุเจ้าของข้อมูลชัด ตารางนี้ใคร “เขียน” ได้ ใคร “อ่าน” ได้ ถ้าหลาย component เขียนตารางเดียวกันโดยไม่มีกติกา schema จะเปลี่ยนไม่ได้
  • เก็บสถานะแบบมีประวัติ สำหรับข้อมูลที่ต้อง audit เช่น ใคร publish เมื่อไร แทนการ update ทับ

ให้งานหนักทำเบื้องหลังโดยไม่ให้ event หาย

ปัญหาคลาสสิกคือ บันทึกสถานะ publish ลงฐานข้อมูลสำเร็จแล้ว แต่ระบบล่มก่อนส่ง event ไปบอก notification ทำให้ไม่มีใครรู้ วิธีที่ใช้กันคือ transactional outbox บันทึกสถานะกับรายการ “event ที่ต้องส่ง” ลงฐานข้อมูลใน transaction เดียวกัน แล้วให้ตัวส่งแยกไปอ่านแล้วส่งต่อ

  • นิยามว่า “publish สำเร็จ” คือเมื่อไร ในที่นี้คือเมื่อสถานะถูก commit และมีหลักฐานว่า event จะถูกส่งต่อ (outbox commit) ส่งอีเมลไม่สำเร็จไม่ทำให้ publish ย้อนกลับ เว้นแต่ requirement จะบอกไว้ต่างจากนี้
  • ตัวส่งอาจส่ง event ซ้ำได้ ฝั่งรับต้องออกแบบให้ทำซ้ำแล้วไม่เกิดผลซ้ำ (idempotent consumer)
  • queue ส่วนใหญ่รับประกันแค่ “อย่างน้อยหนึ่งครั้ง” ไม่ใช่ “ครั้งเดียวพอดี” อย่าสัญญาเกินกว่านี้

cache แบบ cache-aside และการสร้าง key ที่ปลอดภัย

รูปแบบที่ใช้บ่อยที่สุดคือ cache-aside: อ่าน cache ก่อน ถ้าไม่มีค่อยอ่านฐานข้อมูลแล้วใส่ลง cache ส่วนตอนเขียนให้ลบหรืออัปเดต cache ส่วนที่เกี่ยวข้อง ความเสี่ยงอันดับหนึ่งของข้อมูลหลาย tenant คือ key ไม่ครบ ทำให้คนหนึ่งอ่านค่าของอีกคน

const SAFE = /^[A-Za-z0-9_-]+$/;

export function payslipCacheKey(tenantId: string, employeeId: string, period: string): string {
  for (const part of [tenantId, employeeId, period]) {
    if (!SAFE.test(part)) throw new Error('Invalid key part');
  }
  return `payslip:v1:${tenantId}:${employeeId}:${period}`;
}

ตรวจอักขระของแต่ละส่วนด้วย เพื่อกันคนใส่ตัวคั่นแล้วทำให้ key ของสองคนชนกัน และใส่เวอร์ชัน (v1) ไว้เผื่อเปลี่ยนรูปแบบข้อมูลภายหลังจะได้ไม่ต้องล้าง cache ทั้งหมดด้วยมือ

ป้องกันระบบตัวเองด้วยการจำกัดอัตรา

  • rate limit ต่อผู้ใช้หรือ tenant เพื่อไม่ให้รายเดียวกินทรัพยากรทั้งระบบ (noisy neighbor)
  • backpressure เมื่อ queue ยาวเกินกำหนด ให้รับงานช้าลงหรือปฏิเสธชั่วคราวแทนที่จะสะสมจนล่ม
  • bulkhead แยก pool หรือทรัพยากรของงานหนัก (เช่น export) ออกจากงานที่ต้องตอบเร็ว (เช่น ดู payslip) งานหนักจะได้ไม่ลากงานเบาล่มไปด้วย

ระดับ Advance

ระดับนี้ไม่ได้ถามว่าเรารู้จักเครื่องมือกี่ตัว แต่ถามว่าเรากล้าตัดสินใจเมื่อทุกทางต้องเสียอะไรบางอย่างไหม ออกแบบระบบหลายทีมหลายภูมิภาคให้สมดุลได้ไหม บริหารความเสี่ยงด้วยหลักฐานได้ไหม และวางกติกาให้หลายทีมออกแบบไปทางเดียวกันโดยไม่ทำให้ทุกคนช้าลงได้ไหม

คำถามที่ต้องตอบให้ได้: ยอมเสียอะไรเมื่อระบบมีปัญหา พิสูจน์ได้อย่างไรว่าแผนใช้ได้จริง และใครเป็นเจ้าของการตัดสินใจ

Advance

เกณฑ์: Architect enterprise-scale distributed systems balancing performance, reliability, security, and maintainability

เมื่อระบบใหญ่ขึ้น คำถามเปลี่ยนไป

ในระบบที่มีหลายประเทศ หลายทีม หลาย cloud region สิ่งที่ยากไม่ใช่ “สร้าง service เพิ่มอีกตัว” แต่คือ เลือกว่ายอมเสียอะไรเมื่อระบบมีปัญหา ต้องชั่งน้ำหนักสี่เรื่องพร้อมกัน และทุกเรื่องดึงกันเอง

มิติถามว่าตัวอย่างที่ชนกับมิติอื่น
performancelatency, throughput, capacity เป็นอย่างไรเขียนข้อมูลลงสอง region พร้อมกันให้ปลอดภัย แต่ช้าลง
reliabilityavailability, recovery, ความคงทนของข้อมูลทำซ้ำข้อมูลหลายที่เพื่อกันล่ม แต่ต้นทุนและความซับซ้อนเพิ่ม
securityidentity, สิทธิ์, การแบ่งเครือข่าย, audit, encryptionห้ามข้อมูลข้ามประเทศ ทำให้ failover ข้าม region ไม่ได้
maintainabilityเปลี่ยน สังเกต ทดสอบ และแบ่งทีมดูแลได้ไหมแยก service มากเพื่อความเป็นอิสระ แต่ทีมต้อง on-call และ trace ข้ามระบบมากขึ้น

ตัวอย่างแนวคิด multi-region (ไม่ใช่ blueprint สำหรับ production)

ก่อนเลือกแบบนี้ ต้องตอบคำถามเหล่านี้ให้ได้

  • ถ้า region A ล่ม region B รับ เขียน ได้ทันทีไหม หรือแค่อ่านได้
  • replica ตามหลัง primary นานแค่ไหน (replication lag) และถ้า failover จะเสียข้อมูลช่วงนั้นไหม
  • จะเกิดข้อมูลซ้ำหรือสองฝั่งต่างเขียนจนขัดกัน (split-brain) ได้ไหม และแก้อย่างไร
  • ข้อมูลเงินเดือนของแต่ละประเทศอยู่ที่ไหนได้บ้างตามกฎหมาย (data residency)
  • เปลี่ยน region แล้ว session และการจัดการ key เข้ารหัสยังใช้งานได้ไหม
“มีสอง region” ไม่เท่ากับ active-active และไม่รับประกัน RPO = 0ต้องกำหนดเรื่อง replication, failover, consistency และ runbook ให้สอดคล้องกัน การเขียนในภาพว่ามี replica ไม่ได้แปลว่าเรากู้ได้จริง ต้องมีการซ้อมพิสูจน์

RTO และ RPO

  • RTO (Recovery Time Objective) หลังระบบล่ม ต้องกลับมาให้บริการภายในเวลาที่ตกลง เช่น ไม่เกิน 30 นาที
  • RPO (Recovery Point Objective) ยอมสูญเสียข้อมูลย้อนหลังได้มากสุดเท่าไร เช่น ไม่เกิน 5 นาที
  • ถ้าทำ backup วันละครั้ง จะยืนยัน RPO 5 นาทีไม่ได้ ต้องมี replication หรือ log archiving เพิ่ม

เมื่อ business ตั้ง RTO/RPO แล้ว เราเลือกกลยุทธ์ DR ที่ตอบเป้านั้นในต้นทุนที่รับได้ ชื่อกลยุทธ์สี่แบบในตารางนี้ตามเอกสาร AWS “Disaster recovery options in the cloud” (ลิงก์อยู่ท้ายหน้า) โดยทั่วไปยิ่งเป้า RTO/RPO เข้มยิ่งแพงและซับซ้อนขึ้น

กลยุทธ์หน้าตาRTO / RPO เทียบกันต้นทุนและความซับซ้อน
backup and restoreสำรองข้อมูลแล้วสร้างระบบใหม่เมื่อเกิดเหตุRTO/RPO ยาวที่สุดในสี่แบบต่ำสุด
pilot lightเก็บข้อมูลและแกนหลักไว้ที่ region สำรอง ส่วนที่เหลือเปิดเมื่อจำเป็นสั้นกว่า backup and restoreต่ำถึงกลาง

ตารางเทียบแค่ลำดับสั้น–ยาว ไม่ได้ให้ตัวเลข ค่าจริงขึ้นกับการออกแบบ ปริมาณข้อมูล และ runbook ที่ซ้อมแล้ว ต้องวัดจากการซ้อมของเราเอง

consistency กับ availability: ตัวอย่างที่เจอจริง

สมมติ HR กด publish แล้วพนักงานเปิดอ่านทันที แต่ read replica ตามหลัง primary อยู่ 10 วินาที พนักงานเลยเห็นข้อมูลเก่า ทางเลือกต้องตัดสินใจชัด ๆ

  1. read-after-write จาก primary สำหรับ HR หลัง publish (ผู้ที่เพิ่งเขียนอ่านจากที่ที่ข้อมูลล่าสุดแน่นอน)
  2. ใช้ version token หรือ marker ให้ client รอจนกว่า replica ตามถึง version นั้น
  3. ยอม eventual consistency สำหรับเรื่องที่รอได้ เช่น การแจ้งเตือน แต่ไม่ยอมสำหรับเรื่องที่ผิดแล้วเสียหาย เช่น การแก้ยอดจ่ายเงิน
CAP ไม่ได้แปลว่า “เลือก 2 จาก 3” ตลอดเวลาCAP พูดถึงการแลกระหว่าง consistency กับ availability ตอนเกิด network partition เท่านั้น ส่วนตอนปกติ ยังมีการแลกอีกแบบ คือ latency กับ consistency (ซึ่งโมเดล PACELC อธิบายไว้) ระบบที่ “เลือก consistency” ก็ไม่ได้แปลว่าไม่ต้องสนใจ availability ตอนที่ทุกอย่างปกติ

แบ่งข้อมูลและจำกัดความเสียหาย

  • partition key เลือกให้กระจายภาระเท่ากันและตอบ query หลักได้ในพาร์ติชันเดียว เช่น tenant_id หรือประเทศ ระวัง tenant ใหญ่รายเดียวกลายเป็น hot partition
  • failure domain / blast radius ออกแบบให้ความผิดพลาดหนึ่งจุดกระทบแค่ส่วนเล็ก ๆ เช่น แยก cell ต่อกลุ่ม tenant เพื่อให้ปัญหาของบริษัทหนึ่งไม่ลามไปทุกบริษัท
  • graceful degradation ถ้าบริการเสริมล่ม ระบบหลักยังทำงานต่อได้ในรูปแบบที่ลดความสามารถ เช่น ดูสลิปได้แต่ปุ่ม PDF ขึ้นว่าชั่วคราวใช้ไม่ได้
  • exactly-once ข้ามระบบส่วนใหญ่ไม่มีให้ ออกแบบเป็น at-least-once + idempotent จะตรงกับโลกจริงกว่า

งบเวลา (latency budget) ข้ามหลายขั้น

เป้า p95 400 ms ต้องแบ่งให้แต่ละขั้นก่อน เช่น edge/LB 30 ms, API logic 70 ms, authorization 40 ms, ฐานข้อมูล 150 ms, เผื่อเครือข่ายและ serialization 110 ms (ตัวเลขสมมติ) ถ้าเพิ่มบริการที่ต้องเรียกข้าม region อีกหนึ่งขั้นที่กินครั้งละ 120 ms งบก็ล้นทันที การแบ่งงบแบบนี้ช่วยให้คุยกับหลายทีมได้ว่า “ส่วนของคุณมีกี่ ms”

ทำให้มาตรฐานตรวจได้เอง ด้วย fitness function

กฎที่เขียนไว้ในเอกสารมักถูกลืม กฎที่ถูกตรวจใน CI จะอยู่ได้นานกว่า ตัวอย่างกฎ “service ห้าม import โค้ดของ service อื่นโดยตรง” ตรวจได้ด้วยฟังก์ชันสั้น ๆ

type Dep = { from: string; to: string };
type Rule = { from: string; mustNotDependOn: string };

export function findViolations(deps: Dep[], rules: Rule[]): Dep[] {
  return deps.filter(d =>
    rules.some(r => r.from === d.from && r.mustNotDependOn === d.to)
  );
}

const rules: Rule[] = [{ from: 'notification', mustNotDependOn: 'payslip-db' }];
findViolations([{ from: 'notification', to: 'payslip-db' }], rules); // 1 รายการ

ของจริงจะดึงรายการ dependency จากโค้ด (ด้วยเครื่องมืออย่าง dependency-cruiser หรือ ArchUnit) แล้วใช้หลักเดียวกัน ข้อดีคือกฎถูกตรวจทุกครั้งที่ commit โดยไม่ต้องรอ review ของคน

  • technology radar จัดเทคโนโลยีเป็น adopt / trial / assess / hold ให้ทุกทีมเห็นทิศทางร่วมกัน

รูปแบบหน้าตาข้อดีข้อเสีย

security by design: คิดตั้งแต่ขีดเส้นบนภาพ

  • ขีด trust boundary บน diagram ว่าจุดไหนข้อมูลข้ามจากฝั่งที่ไม่ไว้ใจมาฝั่งที่ไว้ใจ ทุกเส้นที่ข้ามต้องมีการตรวจ
  • แยก authentication กับ authorization รู้ว่าเป็นใคร ไม่เท่ากับรู้ว่าทำอะไรกับข้อมูลชิ้นนี้ได้ โดยเฉพาะ object-level authorization ที่ต้องตรวจทุกครั้งที่เปิดข้อมูลรายชิ้น (ช่องโหว่ยอดฮิตของ API คือคนเปลี่ยน ID แล้วเห็นข้อมูลคนอื่น)
  • least privilege ให้สิทธิ์เท่าที่จำเป็น รวมถึงสิทธิ์ของ service ต่อ service และต่อฐานข้อมูล
  • ปกป้องข้อมูลระหว่างเดินทางและตอนเก็บ เข้ารหัสทั้งสองแบบ และจัดการ key แยกจากข้อมูล
  • ไม่ใส่ข้อมูลอ่อนไหวใน log กำหนดว่า field ไหนต้องปิด และตรวจใน test
  • audit เก็บว่าใครทำอะไรกับข้อมูลสำคัญเมื่อไร แก้ย้อนหลังไม่ได้

SLI, SLO, SLA และ error budget

คำคืออะไรตัวอย่าง
SLIตัวชี้วัดที่วัดจริงสัดส่วน request ที่สำเร็จและตอบภายใน 400 ms
SLOเป้าหมายภายในของ SLI99.9% ของ request ใน 30 วันต้องสำเร็จและเร็วตามเกณฑ์
SLAสัญญากับลูกค้า ถ้าผิดมีผลทางการเงินหรือกฎหมายถ้าต่ำกว่า 99.5% คืนค่าบริการ
error budgetส่วนที่ยอมให้พลาดได้ = 1 − SLOSLO 99.9% → พลาดได้ 0.1% ของเวลา/request

error budget ทำให้การคุยเรื่องความเสี่ยงเป็นตัวเลข: ถ้าเดือนนี้ใช้งบไปแล้ว 80% ก็ชะลอการปล่อยฟีเจอร์เสี่ยงแล้วไปเสริมความเสถียรก่อน ถ้าเหลือเยอะก็กล้าปล่อยเร็วขึ้น และอย่าลืมว่า SLO ต้องผูกกับสิ่งที่ผู้ใช้รู้สึกจริง ไม่ใช่แค่ CPU

สัญญาณสี่อย่างที่ควรเฝ้า (golden signals) คือ latency, traffic, errors และ saturation ถ้าเฝ้าครบสี่ตัวต่อทุก service สำคัญ จะเจอปัญหาส่วนใหญ่ก่อนผู้ใช้

L1 (Beginner). เขียน mapHttpStatusToUI(status) แปลงรหัส HTTP เป็นสถานะของหน้าจอCoding Challenge

Function Description

function mapHttpStatusToUI(status: number): UIState

เป็น pure function (ไม่มี side effect) ตามกติกา: 200 → success, 401 → login-required, 403 → forbidden, 404 → not-found, 500–599 → server-error, ค่าอื่น → unexpected-error

ParameterTypeความหมาย
statusnumberรหัส HTTP ของ response

Returns UIState: 'success' | 'login-required' | 'forbidden' | 'not-found' | 'server-error' | 'unexpected-error'

Constraints

  • status เป็นจำนวนเต็ม
  • ต้องเป็น pure function ไม่อ่านหรือเขียนสถานะนอกฟังก์ชัน

Sample Input / Output

InputOutputคำอธิบาย

503'server-error'ช่วง 500–599 ถือเป็นข้อผิดพลาดฝั่ง server
204'unexpected-error'ไม่อยู่ในกติกาที่กำหนด จึงถือว่าไม่คาดคิด

Edge Cases ที่ควรคิดถึง

  • 599 ยังเป็น server-error ส่วน 600 ไม่ใช่
  • รหัสที่ไม่รู้จัก เช่น 418 ต้องไม่ทำให้โปรแกรมล้ม

โค้ดเฉลย (TypeScript strict)

type UIState =
  | 'success' | 'login-required' | 'forbidden'
  | 'not-found' | 'server-error' | 'unexpected-error';

export function mapHttpStatusToUI(status: number): UIState {
  if (status === 200) return 'success';
  if (status === 401) return 'login-required';
  if (status === 403) return 'forbidden';
  if (status === 404) return 'not-found';
  if (status >= 500 && status <= 599) return 'server-error';
  return 'unexpected-error';
}

type ResponseUIState = 'success' | 'empty' | 'forbidden' | 'error';
type ResponseInfo = { status: number; hasData: boolean };

export function mapResponseToUI(input: ResponseInfo): ResponseUIState {

  if (input.status === 200) return input.hasData ? 'success' : 'empty';
  return 'error';
}

type Level = 'low' | 'medium' | 'high' | 'critical';
type Risk = { name: string; likelihood: Exclude<Level, 'critical'>; impact: Level };

const RANK: Record<Level, number> = { low: 1, medium: 2, high: 3, critical: 4 };

export function prioritizeRisks(risks: Risk[]): Risk[] {
  const score = (r: Risk) => RANK[r.likelihood] * RANK[r.impact];
  return [...risks].sort((a, b) => {
    const ca = a.impact === 'critical' ? 1 : 0;
    const cb = b.impact === 'critical' ? 1 : 0;
    if (ca !== cb) return cb - ca;
    if (score(a) !== score(b)) return score(b) - score(a);
    return a.name.localeCompare(b.name);
  });
}

LEFT JOIN payslips p
  ON  p.employee_id = e.id
  AND p.tenant_id   = e.tenant_id
  AND p.period      = '2026-10'
  AND p.status      = 'published'
WHERE e.tenant_id = 'T1'
  AND p.id IS NULL
ORDER BY e.id;

เงื่อนไขของตาราง payslips ต้องอยู่ใน ON ไม่ใช่ WHERE ถ้าย้ายไปไว้ใน WHERE เงื่อนไข p.status = 'published' จะตัดแถวที่ไม่มีคู่ (ค่า NULL) ทิ้ง ทำให้ LEFT JOIN กลายเป็น INNER JOIN และผลที่ควรได้หายไปหมด คำสั่ง NOT EXISTS ใช้ได้เช่นกันและบางทีอ่านง่ายกว่า

A05. ระบบ Payslip ให้บริการ 3 ประเทศ มี data residency และ peak ต่างกัน และแต่ละ region อาจล่ม เลือกแนวทาง partition/replication/failover อย่างไร ระบุ trade-off อย่างน้อย 4 ข้อ
  • ถามก่อน: ข้อกำหนด residency/retention ของแต่ละประเทศ, RTO/RPO, pattern การเขียน, ใครมี on-call
  • แบ่งตาม tenant/ประเทศ ช่วยเรื่องกฎหมายแต่เพิ่มความซับซ้อนของ routing และการทำรายงานรวม
  • replicate แบบ async ข้าม region ลด latency ของการเขียน แต่เสี่ยง replication lag และ RPO ไม่เป็นศูนย์
  • active-active write เพิ่ม availability บางกรณี แต่ต้องแก้ conflict และ consistency ซึ่งซับซ้อนมาก
  • global failover ช่วย availability แต่ต้องกำหนดว่า failover แล้วรับเขียนได้หรือไม่ และข้อมูลที่ห้ามข้ามประเทศจะกู้อย่างไร
  • แยก key และ identity ต่อ region เพิ่ม security boundary แต่งาน operate ยุ่งขึ้น
  • ต้องพิสูจน์ด้วย DR drill, load/latency test และ compliance review ก่อนอนุมัติ

failure และ securityลืมพูดกว้าง ๆออกแบบ error, authorization, reliability ได้เหมาะกับโจทย์
validation และการสื่อสารไม่มีบอกว่าจะทดสอบมี test, metric, acceptance criteria, ADR และเจ้าของ

ข้อสอบรวม ทบทวนทั้งหัวข้อ

ชุดนี้สุ่ม 40 ข้อจากคลังที่รวมแนวข้อสอบท้ายทุกหัวข้อ โจทย์สถานการณ์ และ Mock Exam ตัวเลือกจะสลับใหม่ทุกครั้ง ตอบข้อไหนก็เฉลยข้อนั้นทันที บางข้อเลือกได้หลายคำตอบ (มีป้าย “เลือกทุกข้อที่ถูก” บอก และกด “ตรวจคำตอบ” เมื่อเลือกครบ) และต้องเลือกให้ครบทุกข้อที่ถูก ทุกข้อมีป้ายระดับกำกับ ทำเสร็จแล้วกดส่ง จะเห็นคะแนนแยกตามระดับ เฉลย และหัวข้อที่ควรย้อนกลับไปอ่านซ้ำ

อ่านทวนสั้น ๆ ก่อนลงมือ

Beginnerแยก functional กับ non-functional และเขียนให้วัดได้ แยก component ตามเหตุผลที่เปลี่ยน พึ่ง interface ไม่พึ่งตัว implementation จำให้ได้ว่า 401, 403, 404, 5xx ต้องตอบสนองต่างกัน ระวัง response เก่าทับใหม่ ทำตาม guideline และบันทึก ADR เมื่อต้องเบี่ยง เอกสารต้องมี input/output, flow ปกติและ error, เกณฑ์ผ่าน
Intermediatep95 ไม่ใช่ค่าเฉลี่ย in-flight ≈ RPS × เวลาตอบเฉลี่ย แต่ยังไม่ใช่จำนวน pod เพิ่ม instance ไม่ช่วยถ้าคอขวดอยู่ที่ DB เทียบ architecture ด้วย decision matrix แล้วทำ sensitivity ทำหลาย view ให้ตรงกัน (structural, sequence, interface, state) พิสูจน์ด้วย prototype ที่มีเกณฑ์ตั้งก่อน เขียน spec ให้มี error, สิทธิ์, performance, และคำถามที่ยังเปิดอยู่ ใช้ outbox และ idempotency กับงานเบื้องหลัง
Advanceต้องตอบได้ว่ายอมเสียอะไรเมื่อระบบมีปัญหา RTO คือเวลากู้ RPO คือข้อมูลที่ยอมเสีย สอง region ไม่ใช่ active-active และไม่ใช่ RPO ศูนย์ CAP พูดถึงตอน partition ความเสี่ยงวิกฤตต้องมีแผนก่อนเสมอ ซ้อม restore และ failover จึงเชื่อได้ framework ช่วยตั้งคำถามไม่ใช่เลือกแทน governance ต้องเข้มตามความเสี่ยงและมี exception ที่มีเจ้าของกับวันหมดอายุ

สรุป 1 หน้า ก่อนเข้าสอบ

ไว้อ่านทวนหลังเรียนครบทุกหัวข้อ ก่อนเข้าห้องสอบสักสิบห้านาทีก็พอ

ถ้าโจทย์บอกแบบนี้ ให้นึกถึงอะไร

สถานการณ์แนวทางที่พิจารณาข้อควรระวัง
ได้ requirement มาคลุม ๆถามจนแปลงเป็นตัวเลขและเงื่อนไขที่วัดได้“เร็ว” “ปลอดภัย” ไม่ใช่ requirement
component ทำหลายเรื่องปนกันแยกตามเหตุผลที่เปลี่ยน + interfaceอย่ากระโดดไปหา microservices
ต้องต่อระบบที่ format ไม่ตรงมาตรฐานadapter ที่ขอบ + ADR/exceptionอย่าแอบเบี่ยงเงียบ ๆ
ผู้ใช้เปลี่ยนค่าเร็วแล้วข้อมูลเก่าทับใหม่ยกเลิกคำขอเก่า / เช็ก request IDต้องมี test ที่ response กลับด้านลำดับ
API ช้า p95 สูงtrace → หาคอขวด → แก้ → load test ซ้ำเพิ่ม instance หรือ cache ก่อนวัดอาจแย่ลง
ต้องเทียบหลายทางเลือกdecision matrix + sensitivity + prototypeคะแนนเสมอต้องดูความเสี่ยงและการย้อนกลับ
งานหนักทำให้ API ช้าasync job + worker + status endpointต้องคุม retry, ซ้ำ, สิทธิ์ และ retention
บันทึกสถานะแล้ว event หายtransactional outboxตัวส่งส่งซ้ำได้ ฝั่งรับต้อง idempotent
อ่านจาก replica เห็นข้อมูลเก่าread-after-write จาก primary / version tokenเพิ่ม replica ไม่ลด lag
ต้องกู้ระบบเมื่อ region ล่มเลือก DR ตาม RTO/RPO และซ้อมbackup ที่ไม่เคย restore ไม่ใช่หลักฐาน
เปลี่ยน API ที่มี consumer ภายนอกadditive/v2 + contract test + deprecationอย่าลบ field ก่อนมีหลักฐานว่าย้ายครบ
หลายทีมออกแบบไม่ไปทางเดียวกันมาตรฐานแบบผลลัพธ์ + golden path + review ตามความเสี่ยงgate ทุกอย่างทำให้ทีมเลี่ยง

แม่แบบตอบข้อสอบออกแบบ (ใช้ได้กับ Intermediate และ Advance)

  1. ถามให้ชัด ผู้ใช้ใคร use case อะไร ข้อจำกัด ข้อสมมติ
  2. requirement functional + non-functional ที่มีตัวเลข
  3. ภาพใหญ่ component, data flow, ระบบภายนอก
  4. ข้อมูลและ interface schema, API, event, ใครเป็นเจ้าของข้อมูล, authorization
  5. ทางเลือก อย่างน้อยสองแบบพร้อม trade-off
  6. ล้มเหลวและ scale คอขวด, retry, idempotency, monitoring, DR
  7. พิสูจน์ prototype, test, หลักฐาน, acceptance criteria
  8. ตัดสินใจ เหตุผล ความเสี่ยง ADR แผน rollout และ rollback

สิ่งที่มักทำให้เสียคะแนน

  • วาดกล่อง 10 อัน แต่บอกไม่ได้ว่าแต่ละอันทำอะไร
  • บอกว่า “scalable” โดยไม่มี throughput, latency หรือคอขวด
  • เลือกเทคโนโลยีก่อนถาม requirement
  • ส่งมอบแค่ภาพกล่อง ไม่มี sequence, เส้นทาง error หรือ API contract
  • ตอบว่า “ล่มก็ retry” โดยไม่พูดถึง timeout, retry storm, ข้อมูลซ้ำ และ fallback
  • บอกว่า “มี backup” แต่ไม่เคยซ้อม restore และไม่กำหนด RPO/RTO
  • เชื่อข้อมูลจาก JWT หรือ query โดยไม่ตรวจ tenant และความเป็นเจ้าของที่ server
  • ไม่บันทึกการตัดสินใจและสมมติฐานที่เปลี่ยนไปหลังได้ feedback

Checklist ความพร้อมตาม Competency

คำถามทบทวนเร็ว 10 ข้อ (ปิดหน้าจอแล้วตอบออกเสียง)

  1. ต้องรู้อะไรบ้างก่อนวาด architecture
  2. ทำไม functional requirement อย่างเดียวไม่พอสำหรับระบบจริง
  3. class diagram กับ sequence diagram ต่างกันอย่างไร
  4. API ตอบ 403 แล้ว UI กับ backend ต้องทำอะไรบ้าง
  5. p95 สูงขึ้นและเพิ่ม API instance แล้วไม่ดีขึ้น ควรตรวจอะไร
  6. เลือก modular monolith แทน microservices ได้ในสถานการณ์ใด
  7. จะใช้ prototype พิสูจน์ว่า design ใหม่เหมาะสมได้อย่างไร
  8. detailed spec ที่ดีต้องมีอะไรนอกจากชื่อ endpoint
  9. RTO กับ RPO ต่างกันอย่างไร และพิสูจน์ว่า DR plan ใช้ได้อย่างไร
  10. governance ช่วยลดความเสี่ยงอะไร และทำอย่างไรไม่ให้ทีมช้าลง
