เขียน pipeline แรก: build, test, publish artifact และ deploy

Beginner

Write CI/CD pipelines for build and deploy automation using tools for simple build-deploy tasks

โครง YAML ขั้นต่ำของ Azure Pipelines

สมมติมีเว็บ Node.js ที่มี script lint, test, build อยู่ใน package.json แล้ว pipeline แรกที่ใช้งานได้ควรหน้าตาประมาณนี้ (ตัวอย่างนี้สร้างขึ้นเพื่ออธิบาย ไม่ได้มาจากโปรเจกต์จริง)

trigger:
  branches:
    include:
      - main

pool:
  vmImage: ubuntu-latest

variables:
  nodeVersion: 20.x

steps:
  - task: NodeTool@0
    displayName: ติดตั้ง Node.js
    inputs:
      versionSpec: $(nodeVersion)

  - script: npm ci
    displayName: ติดตั้ง dependency

  - script: npm run lint
    displayName: Lint

  - script: npm test -- --ci --reporters=default --reporters=jest-junit
    displayName: Unit test

  - task: PublishTestResults@2
    displayName: แสดงผล test ในหน้า pipeline
    condition: succeededOrFailed()
    inputs:
      testResultsFormat: JUnit
      testResultsFiles: junit.xml

  - script: npm run build
    displayName: Build

  - publish: dist
    artifact: web-dist
    displayName: เก็บ artifact

อ่านทีละส่วน trigger บอกว่า push เข้า main แล้วให้รัน ส่วน pool.vmImage เลือก agent ที่ Microsoft ดูแลให้ script คือสั่ง shell ตรง ๆ ส่วน task คือชุดคำสั่งสำเร็จรูปที่ระบุเวอร์ชันหลักไว้หลัง @ เช่น PublishTestResults@2 ส่วนบรรทัด publish เป็นชื่อย่อของ task ที่อัปโหลด pipeline artifact

สังเกต condition: succeededOrFailed() ที่ขั้น publish ผล test ค่า default ของทุก step คือรันเมื่อ step ก่อนหน้าสำเร็จ ถ้า test ล้มแล้วไม่ใส่เงื่อนไขนี้ ขั้น publish จะถูกข้าม ผลคือหน้า pipeline ไม่มีแท็บ Tests ในรอบที่เราอยากดูมันที่สุด

เพิ่ม stage สำหรับ deploy

พอมี artifact แล้ว ให้แยกเป็นสอง stage เพื่อให้ deploy เป็นงานของมันเอง

trigger:
  branches:
    include:
      - main

stages:
  - stage: Build
    jobs:
      - job: BuildAndTest
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: |
              npm ci
              npm test -- --ci
              npm run build
            displayName: Build และ test
          - publish: dist
            artifact: web-dist

  - stage: DeployDev
    dependsOn: Build
    condition: succeeded()
    jobs:
      - deployment: DeployWeb
        pool:
          vmImage: ubuntu-latest
        environment: dev
        strategy:
          runOnce:
            deploy:
              steps:
                - script: ls -R $(Pipeline.Workspace)/web-dist
                  displayName: ตรวจไฟล์ที่ได้รับ
                - task: AzureWebApp@1
                  inputs:
                    azureSubscription: my-azure-connection
                    appType: webApp
                    appName: demo-web-dev
                    package: $(Pipeline.Workspace)/web-dist

deployment เป็นชนิด job พิเศษที่ผูกกับ environment ทำให้ Azure DevOps เก็บประวัติว่าอะไรถูก deploy ไปที่ไหนเมื่อไร และใช้ approval ได้ (ดูหัวข้อ 5) สิ่งที่ควรรู้ตั้งแต่ตอนนี้คือ deployment job จะดาวน์โหลด artifact ของ run เดียวกันมาไว้ที่ $(Pipeline.Workspace) ให้เอง ไม่ต้องสั่ง download ซ้ำ และมันไม่ได้ checkout โค้ดมาให้ ถ้าต้องใช้ source ต้องสั่ง checkout: self เอง ส่วนชื่อ my-azure-connection เป็น service connection ที่ต้องสร้างไว้ใน Project settings ก่อน

ถ้าใช้ GitHub Actions จะต่างกันแค่ไหน

แนวคิดเหมือนกัน ต่างที่ชื่อและวิธีเขียน

name: ci
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: web-dist
          path: dist

จุดที่ต่างจนทำให้คนพลาดบ่อยคือ Azure Pipelines checkout โค้ดให้อัตโนมัติใน job ปกติ ส่วน GitHub Actions ต้องใส่ actions/checkout เอง และเวอร์ชันของ action (@v4) เปลี่ยนตามเวลา ควรเช็ก major ล่าสุดก่อนคัดลอกไปใช้

trigger กับ pr ไม่ใช่เรื่องเดียวกันtrigger ทำงานเมื่อมี push เข้า branch ส่วน pr ทำงานเมื่อมี pull request ใน Azure Pipelines คีย์ pr ใช้ได้กับ repo ที่อยู่บน GitHub และ Bitbucket Cloud เป็นต้น ถ้าโค้ดอยู่ใน Azure Repos ต้องตั้ง build validation ที่ branch policy แทน

Script สำหรับ compile, test, package ให้รันซ้ำได้

Beginner

Manage scripts for compile, test, package

ใส่ logic ไว้ใน repo ไม่ใช่ใน YAML

ถ้าทุก step เป็น one-liner ยาว ๆ ใน YAML ปัญหาจะมาตอนต้องแก้ เพราะต้อง push แล้วรอ pipeline รันถึงจะรู้ว่าพิมพ์ผิด วิธีที่ทีมส่วนใหญ่เลือกคือให้ pipeline เรียก script ที่อยู่ใน repo (scripts/ci.sh, Makefile, npm run, mvn, dotnet) แล้วให้นักพัฒนารัน script ตัวเดียวกันบนเครื่องตัวเองได้ pipeline จึงเหลือหน้าที่แค่จัดลำดับและส่งค่าเข้าไป

#!/usr/bin/env bash
set -euo pipefail

VERSION="${1:?usage: ci.sh <version>}"

npm ci
npm run lint
npm test -- --ci
npm run build

mkdir -p out
tar -czf "out/web-${VERSION}.tgz" -C dist .
sha256sum "out/web-${VERSION}.tgz" > "out/web-${VERSION}.tgz.sha256"
echo "packaged web-${VERSION}.tgz"

เรียกจาก pipeline ได้เป็นบรรทัดเดียว เช่น ./scripts/ci.sh $(Build.BuildId) และรันในเครื่องด้วย ./scripts/ci.sh local ได้เลย

สามตัวเลือกของ set ใน bash ที่ควรตั้งทุกครั้ง

set -e ให้ script หยุดเมื่อคำสั่งใดคืน exit code ที่ไม่ใช่ 0 set -u ให้หยุดเมื่อใช้ตัวแปรที่ยังไม่ได้ตั้งค่า (กันกรณี rm -rf "$DIR/" ตอน DIR ว่าง) set -o pipefail ให้ผลของ pipe เป็น exit code ของคำสั่งที่ล้มตัวแรก ไม่ใช่ตัวสุดท้าย ลองดูเคสนี้

# ไม่มี pipefail: test ล้ม แต่ tee สำเร็จ ทั้งบรรทัดจึงนับว่าผ่าน
npm test | tee test.log
echo "exit code = $?"

# มี pipefail: ได้ exit code ของ npm test
set -o pipefail
npm test | tee test.log

ข้อควรระวังคือ set -e ไม่มีผลกับคำสั่งที่อยู่ในเงื่อนไข เช่น if cmd; then หรือ cmd || true การเติม || true ต่อท้ายเพื่อให้ pipeline เขียวเป็นวิธีที่ทำให้ build ที่พังจริงไม่มีใครรู้

Build ให้ได้ผลเหมือนเดิมทุกครั้ง

reproducible build คือรัน commit เดิมวันนี้กับเดือนหน้าแล้วได้ผลเหมือนกัน สิ่งที่มักทำให้ไม่เหมือนคือ dependency ที่ไม่ได้ล็อกเวอร์ชัน และ tool ที่ติดตั้งเป็น “ล่าสุด” ทุกครั้ง

ทำแบบนี้แทนแบบนี้เหตุผล
npm cinpm installci ติดตั้งตาม lockfile เป๊ะ ลบ node_modules เดิมทิ้ง และล้มถ้า lockfile ไม่ตรงกับ package.json
FROM node:20.11-alpine (หรือ pin ด้วย digest)FROM node:latesttag ที่ชี้ไปที่ image ใหม่เรื่อย ๆ ทำให้ build วันนี้ไม่เท่ากับเมื่อวาน
tag artifact ด้วย build number หรือ commit SHAเขียนทับ latestย้อนไปหา commit ต้นทางได้ และ rollback ไปเวอร์ชันที่แน่นอนได้
ระบุ version ของ tool ใน pipelineพึ่งของที่ติดมากับ agentimage ของ agent ถูกอัปเดตเป็นระยะ เวอร์ชันของ tool เปลี่ยนได้โดยไม่มีใครแตะโค้ด

Package ได้หลายรูป

รูปแบบขึ้นกับสิ่งที่ปลายทางต้องการ จะเป็น zip หรือ tarball สำหรับ web app ธรรมดา, NuGet หรือ npm package สำหรับ library, Docker image สำหรับ container หรือ Helm chart สำหรับ Kubernetes ถ้าเป็น image ใน Azure Pipelines มักใช้ task Docker@2 ที่มี command: buildAndPush พร้อม tag เป็นค่าที่ไล่ย้อนกลับได้ เช่น $(Build.BuildId)

แถมไฟล์ checksum ไปกับ artifactไฟล์ .sha256 ช่วยให้ขั้น deploy ตรวจได้ว่าไฟล์ที่ดาวน์โหลดมาตรงกับที่ build ไว้ ไม่ถูกแก้ระหว่างทาง ไม่ใช่เครื่องมือ security ครบชุด แต่เป็นการตรวจที่ถูกและทำได้ทันที

อ่าน log จากจุดที่ล้มจริง ไม่ใช่บรรทัดสุดท้าย

log ของ step ที่ล้มมักจบด้วยข้อความกว้าง ๆ เช่น Bash exited with code '1' ซึ่งบอกแค่ว่ามีอะไรสักอย่างคืน exit code ไม่ใช่ 0 สาเหตุจริงอยู่เหนือบรรทัดนั้นขึ้นไป ให้เปิด step ที่แดง แล้วหา error ตัวแรก (ตัวหลัง ๆ มักเป็นผลต่อเนื่อง) ใน Azure Pipelines บรรทัดที่เป็น error จะขึ้นต้นด้วย ##[error] ส่วนถ้า test ล้ม แท็บ Tests จะบอกชื่อ test กับ assertion ที่ไม่ตรงชัดกว่าอ่านจาก log ยาว ๆ

แยกให้ออกก่อนว่าพังเพราะอะไรประเภทไหน

ประเภทหน้าตาเริ่มตรวจจาก
YAML ผิดrun ไม่เริ่มเลย หรือขึ้น error ตั้งแต่ตอน parse เช่น mapping ไม่ถูกที่indentation, ช่องว่างหลัง :, ชื่อ key สะกดผิด ใช้ปุ่ม Validate ใน editor
โค้ดหรือ test พังstep build/test แดง และรันซ้ำแล้วแดงเหมือนเดิมerror ตัวแรกใน log, แท็บ Tests, ลองรัน script เดียวกันในเครื่อง
Environment ไม่ตรงcommand not found, Cannot find module, เวอร์ชันของ tool ไม่ตรงเทียบเวอร์ชัน tool กับเครื่องเรา ดูว่า install step ครบไหม
ตัวแปรหรือ secretค่าว่าง, authentication ล้มชื่อตัวแปรสะกดตรงไหม, secret ถูกส่งเข้า env ของ step หรือยัง
สิทธิ์ข้อความว่า pipeline ต้องได้รับอนุญาตให้ใช้ resource ก่อนจึงจะไปต่อผู้ดูแล resource (service connection, environment) ต้องกดอนุญาตให้ pipeline นั้น
Infrastructureงานค้างสถานะ queued, agent offline, disk เต็ม, network timeoutสถานะ pool, จำนวน parallel job ที่เหลือ, demands ที่ระบุไว้ตรงกับ agent ไหม

  branches:

    parameters:
      envName: dev

      dependsOn: Build

# templates/deploy-stage.yml
parameters:
  - name: envName
    type: string
  - name: appName
    type: string
  - name: dependsOn
    type: string

stages:
  - stage: Deploy_${{ parameters.envName }}
    displayName: Deploy ${{ parameters.envName }}
    dependsOn: ${{ parameters.dependsOn }}
    variables:
      - group: web-${{ parameters.envName }}
    jobs:
      - deployment: Web
        pool: { vmImage: ubuntu-latest }
        environment: ${{ parameters.envName }}
        strategy:
          runOnce:
            deploy:
              steps:
                - script: echo "deploy to ${{ parameters.appName }} (API=$(apiBaseUrl))"

ตัวอย่างนี้ใช้ template ตัวเดียวสร้าง stage ของทุก environment ส่วนที่ต่างกันส่งเข้าไปเป็น parameter และค่า config ต่อ environment มาจาก variable group ชื่อ web-dev, web-staging, web-prod เมื่อเพิ่ม environment ใหม่ก็เพิ่มแค่การเรียก template อีกหนึ่งบล็อก ${{ parameters.envName }} เป็น template expression ที่ถูกขยายตอน compile ก่อน pipeline เริ่มรัน ต่างจาก $(var) ที่ถูกแทนค่าตอน runtime ก่อนส่งให้ task และ $[ ] ที่ประเมินตอน runtime เช่นกันแต่ใช้ใน condition และตำแหน่งที่รองรับ ข้อสอบชอบถามความต่างสามแบบนี้ และต้องจำไว้ว่า template expression อ่านค่าที่เพิ่งมีตอน runtime ไม่ได้

แยกให้ชัดว่าอะไรอยู่ที่ไหน

เรื่องเก็บไว้ที่เหตุผล

ใครอนุมัติ production, เวลาที่ deploy ได้, branch ที่อนุญาตApprovals and checks ของ environmentแก้ผ่าน YAML ไม่ได้ จึงเป็นกลไกป้องกันที่ไม่ขึ้นกับผู้เขียน pipeline
ค่าที่ต่างกันตาม environmentvariable group หรือไฟล์ config ต่อ environmentartifact ยังเป็นชิ้นเดียวกัน
credential ของปลายทางservice connection ที่จำกัดสิทธิ์ต่อ environmentdev กับ prod ไม่ควรใช้ identity เดียวกัน

deployment job และ strategy

deployment job รองรับ strategy สามแบบคือ runOnce, rolling และ canary โดยมี lifecycle hook ให้ใส่ขั้นตอนตามช่วง ได้แก่ preDeploy, deploy, routeTraffic, postRouteTraffic และ on: failure หรือ on: success สำหรับ cleanup หรือ rollback แต่ผลของ hook เหล่านี้ไม่ได้ทำให้เกิด rollback เอง ต้องเขียนขั้นตอนใน on: failure เอง เรื่อง rolling ในเอกสารจำกัดไว้กับ resource ประเภท VM

- deployment: Web
  environment: production
  strategy:
    runOnce:
      preDeploy:
        steps:
          - script: ./scripts/backup-config.sh
      deploy:
        steps:
          - script: ./scripts/release.sh
      routeTraffic:
        steps:
          - script: ./scripts/switch-traffic.sh
      postRouteTraffic:
        steps:
          - script: ./scripts/smoke-test.sh
      on:
        failure:
          steps:
            - script: ./scripts/rollback.sh

ตัวแปรสามรูปแบบใน Azure Pipelines

รูปแบบถูกแทนค่าเมื่อไรถ้าตัวแปรยังไม่มีค่า
${{ variables.x }} (template expression)ตอน compile YAML ก่อน runกลายเป็นสตริงว่าง
$(x) (macro)ตอน runtime ก่อนส่งให้ task หรือ scriptเหลือเป็นข้อความ $(x) ตามเดิม
$[ variables.x ] (runtime expression)ตอน runtime ใช้ได้ใน condition และตำแหน่งที่รองรับกลายเป็นสตริงว่าง

เคสที่เจอบ่อยคือเอา $(x) ไปใช้เป็นเงื่อนไข compile-time เช่น ${{ if eq($(x), 'prod') }} ซึ่งไม่ทำงาน เพราะตอนนั้นยังไม่มีค่า ถ้าค่ามาจาก parameter ให้ใช้ parameters.x ในเงื่อนไข compile-time

variable group และ Key Vault

variable group เก็บชุดค่าไว้ที่ Library แล้วให้หลาย pipeline อ้างถึงได้ ตั้งสิทธิ์ได้ และเชื่อมกับ Azure Key Vault เพื่อดึง secret สดตอนรัน (เลือกชื่อ secret ที่จะดึง) ข้อดีคือค่าที่ต่างกันต่อ environment ไม่อยู่ใน repo และ secret หมุนเวียนได้โดยไม่แก้ pipeline

stages:
  - stage: DeployProd
    variables:
      - group: web-prod
      - name: replicas
        value: 4
    jobs:
      - deployment: Web
        environment: production
        strategy:
          runOnce:
            deploy:
              steps:
                - script: ./scripts/deploy.sh
                  env:
                    DB_PASSWORD: $(dbPassword)
                    API_BASE_URL: $(apiBaseUrl)

ค่า config ต้องไม่ฝังอยู่ใน artifact

หลักคือ artifact เหมือนกันทุก environment ค่าที่ต่างกันเข้ามาตอน deploy ผ่าน environment variable, app setting ของ App Service, ConfigMap/Secret ของ Kubernetes หรือไฟล์ config ที่ถูกแทนค่าตอนปล่อย การ build ใหม่ทีละ environment เพื่อ “ฝัง” ค่าเข้าไปเป็นสาเหตุที่ staging ผ่านแต่ production ล้ม

ให้ pipeline พิสูจน์ตัวตนโดยไม่เก็บ secret

วิธีเดิมคือสร้าง service principal แล้วเก็บ secret ไว้ใน service connection ซึ่งหมดอายุและรั่วได้ วิธีที่ Microsoft แนะนำสำหรับ Azure คือ workload identity federation บน Azure Resource Manager service connection ใช้ OIDC แลก token อายุสั้นต่อรัน ไม่มี secret ให้หมุนเวียน ข้อควรรู้คือ token ของ Azure DevOps ผูกกับ service connection และ project ไม่ได้พก claim ของ branch หรือ environment ไปให้ฝั่ง Azure ตรวจ การจำกัดว่า pipeline ไหนใช้ connection ไหนได้จึงต้องทำที่ Azure DevOps (permission ของ service connection, environment checks, branch policy) และต้องให้ role บน Azure แค่เท่าที่จำเป็นด้วย เพราะ federation เปลี่ยนวิธีพิสูจน์ตัวตน ไม่ได้ลดสิทธิ์ให้เอง

แยก identity ของ dev กับ prodถ้า dev ใช้ service connection ตัวเดียวกับ prod ใครก็ตามที่แก้ pipeline แล้วชี้ไป dev ก็ได้สิทธิ์ production ไปด้วย ตั้งสอง connection ที่ role ต่างกัน และให้ connection ของ prod ใช้ได้เฉพาะ pipeline ที่ผ่าน check

SonarQube และ Quality Gate ใน pipeline

Intermediate

Integrate automated security and quality scanning into the pipeline using SonarQube and security scans ZAP in the pipeline

SonarQube ตรวจอะไร

SonarQube วิเคราะห์โค้ดแบบ static (SAST) หา bug, code smell, vulnerability, security hotspot และ duplication แล้วสรุปเป็นค่าต่อ project ถ้ามีรายงาน test coverage ส่งเข้าไป ก็แสดง coverage ด้วย จุดที่ต้องจำคือมันไม่ได้รันโค้ด และ ไม่ได้คำนวณ coverage เอง ต้องให้เครื่องมือ test สร้างรายงาน (เช่น lcov, Cobertura, JaCoCo) แล้วบอก path ให้ scanner

ลำดับ task ใน Azure Pipelines

extension ของ SonarQube มีสาม task และลำดับสำคัญ: Prepare ก่อน build, Analyze หลัง build และ test, Publish ท้ายสุด ตามเอกสารของ SonarQube ตอนนี้ major ล่าสุดของ task คือ @8 (เวอร์ชัน 7 ถูกระบุว่า deprecated) ดังนั้นตัวเลขหลัง @ ต้องตรงกับเวอร์ชัน extension ที่ติดตั้งในองค์กร

steps:
  - task: SonarQubePrepare@8
    inputs:
      SonarQube: sonarqube-connection
      scannerMode: cli
      configMode: manual
      cliProjectKey: demo-web
      cliSources: src
      extraProperties: |
        sonar.javascript.lcov.reportPaths=coverage/lcov.info
        sonar.qualitygate.wait=true

  - script: |
      npm ci
      npm test -- --ci --coverage
    displayName: Test พร้อม coverage

  - task: SonarQubeAnalyze@8

  - task: SonarQubePublish@8
    inputs:
      pollingTimeoutSec: '300'

SonarQubePublish รอให้ server ประมวลผลจนเสร็จ (poll) แล้วแสดง quality gate ในหน้าสรุป build ตามเอกสารมันทำให้เวลา build เพิ่มได้ชัด ส่วน property sonar.qualitygate.wait=true ทำให้ scanner รอผล gate และล้มเมื่อ gate ไม่ผ่าน ใช้ร่วมกับ sonar.qualitygate.timeout เพื่อกำหนดเวลาสูงสุด (ควรตรวจชื่อ property และค่า default กับเอกสารของเวอร์ชัน SonarQube ที่ใช้)

Quality gate และ “new code”

quality gate คือชุดเงื่อนไขที่ตอบว่า ผ่าน หรือ ไม่ผ่าน ส่วน gate ค่าตั้งต้นชื่อ Sonar way ตั้งเงื่อนไขบนโค้ดใหม่ เช่น ห้ามมี issue ใหม่ coverage ของโค้ดใหม่ไม่ต่ำกว่าเกณฑ์ และ duplication ของโค้ดใหม่ไม่เกินเกณฑ์ (ค่าตัวเลขขึ้นกับเวอร์ชัน ตรวจจากหน้า Quality Gates ของ server ที่ใช้) แนวคิด “clean as you code” คือไม่บังคับให้แก้ของเก่าทั้งหมดก่อน แต่ห้ามเพิ่มหนี้ใหม่ ซึ่งทำให้ทีมที่มีระบบเก่าเริ่มใช้ได้จริง

ตัวชี้วัดหมายถึงข้อควรระวัง
Bugโค้ดที่น่าจะทำงานผิดต้องดูทีละรายการ มี false positive ได้
Vulnerabilityช่องโหว่ด้านความปลอดภัยที่เครื่องมือยืนยันได้ไม่ใช่ทุก vulnerability ที่ถูกตรวจเจอด้วย static analysis
Security hotspotจุดที่ละเอียดอ่อนต้องให้คนตรวจไม่นับเป็นช่องโหว่จนกว่าคนจะตัดสิน
Coverageสัดส่วนบรรทัด/เงื่อนไขที่ถูก test รันบอกว่าโค้ดถูกรัน ไม่ได้บอกว่ามีการตรวจผลลัพธ์
Duplicationสัดส่วนโค้ดที่ซ้ำซ้ำเพราะบังเอิญเหมือนกับซ้ำเพราะ copy ต่างกัน

ปัญหาที่เจอบ่อย

coverage ขึ้น 0% มักเป็นเพราะ path ของรายงานผิดหรือรายงานถูกสร้างหลัง Analyze ส่วนผลวิเคราะห์ PR ไม่ขึ้นหรือ “new code” ผิดเพี้ยน มักมาจาก clone แบบตื้นที่ไม่มีประวัติ git พอให้เทียบ ใน Azure Pipelines ให้ตั้ง fetchDepth: 0 ที่ขั้น checkout และถ้า gate ค้างรอนานให้ดูว่า background task ของ server ประมวลผลช้าหรือ timeout สั้นเกินไป

  displayName: ZAP baseline scan

- publish: zap-out
  artifact: zap-report
  condition: succeededOrFailed()

โฟลเดอร์ที่ mount ไปที่ /zap/wrk ใน container คือที่ที่ ZAP เขียนรายงานและอ่านไฟล์ config ของเรา จึงต้อง copy ไฟล์ config เข้าไปและเปิดสิทธิ์เขียน เพราะ process ใน container ไม่ได้รันด้วยผู้ใช้เดียวกับ agent -r สร้างรายงาน HTML, -J สร้าง JSON และ -c ชี้ไฟล์กำหนดว่ากฎไหนให้ IGNORE, WARN หรือ FAIL

exit code ของ ZAP baseline0 คือสำเร็จ, 1 คือมีอย่างน้อยหนึ่ง FAIL, 2 คือมีอย่างน้อยหนึ่ง WARN โดยไม่มี FAIL และ 3 คือความล้มเหลวอื่น ๆ ค่าเริ่มต้นแจ้งทุก alert เป็น WARN ดังนั้นถ้าไม่ตั้งไฟล์ config สคริปต์จะออก 2 เมื่อเจออะไรก็ตาม ซึ่ง pipeline ถือว่า step ล้ม ต้องเลือกเองว่าจะรับ 2 ได้ไหม และกำหนดกฎที่ถือเป็น FAIL ให้ชัด ZAP ไม่ได้ตัดสินแทนว่า build ควรล้มเมื่อไร

ควรทำให้ pipeline ล้มเมื่อไร

ถ้าให้ล้มทุก alert ทีมจะหาทางปิด scan เอง ทางที่ใช้งานได้จริงคือเริ่มจากรายงานอย่างเดียว คัดกฎที่เป็นความเสี่ยงจริงให้เป็น FAIL ทีละกลุ่ม ปล่อยที่เหลือเป็น WARN และบันทึกข้อยกเว้นพร้อมเหตุผลกับวันหมดอายุ การสแกนแบบ authenticated ต้องตั้ง context ให้ ZAP ล็อกอินได้ ไม่เช่นนั้นจะเห็นแค่หน้าที่ไม่ต้องล็อกอิน

สแกนเฉพาะระบบที่เราเป็นเจ้าของหรือได้รับอนุญาตfull scan ส่ง request ที่ดูเหมือนการโจมตีจริง ใช้กับ environment ทดสอบที่แยกไว้ และแจ้งทีมที่ดูแล WAF หรือ monitoring ล่วงหน้าเพื่อไม่ให้ถูกนับเป็นเหตุการณ์จริง

Deployment validation: ปล่อยแล้ว ต้องตรวจว่าใช้ได้

pipeline ที่จบแค่ “deploy สำเร็จ” บอกได้เพียงว่า script ไม่ error แต่ไม่ได้บอกว่าแอปทำงาน ขั้น validation ที่พบบ่อยมีสามระดับ health check (endpoint ตอบ 200 และ dependency พร้อม), smoke test (เรียก flow สำคัญไม่กี่อัน เช่น login, สร้างรายการ) และตรวจสถานะของ platform เช่น kubectl rollout status ที่รอจน Deployment พร้อม หรือถ้าไม่พร้อมตามเวลาก็คืนค่าล้ม

#!/usr/bin/env bash
set -euo pipefail
URL="${1:?usage: smoke.sh <base-url>}"

for i in $(seq 1 12); do
  code=$(curl -s -o /dev/null -w '%{http_code}' "$URL/health" || true)
  if [ "$code" = "200" ]; then
    echo "health ok after $i tries"
    curl -fsS "$URL/api/version"
    exit 0
  fi
  echo "attempt $i: status $code, retry in 10s"
  sleep 10
done
echo "health check failed" >&2
exit 1

สังเกตว่า script นี้รอและลองใหม่ เพราะแอปที่เพิ่งเริ่มมักยังไม่พร้อมทันที และจบด้วย exit 1 เมื่อหมดเวลาเพื่อให้ stage นั้นล้มจริง ถ้า deploy ไปที่ production ควรผูกกับขั้น rollback หรือหยุดการปล่อยในขั้นต่อไป

ทำให้การ deploy ทำซ้ำได้

repeatable deployment หมายถึงรันซ้ำกับ artifact เดิมแล้วได้สถานะปลายทางเดิม ไม่ใช่ว่าครั้งที่สองพังเพราะครั้งแรกทำไปครึ่งทาง script ที่ทำให้เป็น idempotent (เช่น mkdir -p, kubectl apply, การสร้างทรัพยากรแบบ declarative) ปลอดภัยกว่าคำสั่งที่สร้างทับหรือเพิ่มต่อท้ายทุกครั้ง และเก็บ log ของ deployment ไว้ผูกกับ artifact เพื่อสืบย้อน

ระดับ Advance

ระดับนี้เปลี่ยนมุมจาก “pipeline ส่งของขึ้นระบบ” เป็น “สถานะที่ต้องการอยู่ใน Git และมีตัวควบคุมดึงระบบให้ตรงตามนั้น” รวมถึงดูแลหลาย service หลาย cluster ปล่อยแบบค่อยเป็นค่อยไป ป้องกันตัว pipeline เอง และใช้ข้อมูลจริงย้อนกลับมาปรับวิธีทำงานของทีม

ทักษะที่คาดหวัง: GitOps pipeline แบบ declarative ข้ามหลาย service และ cluster · ดูแลความปลอดภัย scalability และ monitoring ของ pipeline · นำ DevOps lifecycle ครบวงจรด้วย feedback loop แบบ real-time

Argo CD: Application

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/config.git
    targetRevision: main
    path: apps/web/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: web
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

source บอกว่าอ่านจาก repo ไหน revision ไหน path ไหน ส่วน destination บอกว่าลง cluster และ namespace ไหน ถ้าไม่ใส่ syncPolicy.automated Argo CD จะแสดงสถานะ OutOfSync แต่รอคนกด sync เอง prune: true ลบ resource ที่หายไปจาก Git และ selfHeal: true แก้กลับเมื่อมีคนแก้ cluster ตรง ๆ (drift) สองตัวนี้ควรเปิดโดยเข้าใจผลก่อน เพราะ prune ลบของจริง และ selfHeal จะย้อนการแก้ฉุกเฉินที่ทำด้วยมือโดยไม่ถามใคร

generator มีหลายแบบ เช่น list (ระบุเอง), cluster (วนตาม cluster ที่ลงทะเบียนกับ Argo CD), git (วนตามโฟลเดอร์หรือไฟล์ใน repo) และตัวผสม ประโยชน์คือเพิ่ม cluster หรือ service ใหม่โดยไม่ต้องเขียน Application ทีละไฟล์ ความเสี่ยงคือการแก้ template หนึ่งครั้งกระทบทุก cluster พร้อมกัน จึงควรมี sync แบบ progressive หรือแยก ApplicationSet ตามระดับความเสี่ยง

อีกรูปแบบคือ app-of-apps: Application ตัวหนึ่งชี้ไปยังโฟลเดอร์ที่เก็บ Application ตัวอื่น ใช้ bootstrap cluster ใหม่ทั้งชุดได้จากจุดเดียว

หลาย cluster และสิทธิ์

Hub-and-spoke (Argo CD กลาง)

มีจุดดูแลเดียวและเห็นทุก cluster ใน UI เดียว แต่ถือ credential เข้าทุก cluster จึงเป็นเป้าหมายสำคัญ ต้องจำกัดด้วย AppProject และป้องกัน control plane ให้เข้มงวด

ต่อ cluster (Flux ในแต่ละ cluster)

แต่ละ cluster ดึงของตัวเอง ไม่ต้องเปิดทางเข้าจากข้างนอก ขอบเขตผลกระทบ (blast radius)เล็กกว่า แต่ต้องมีวิธีมองภาพรวมและอัปเกรด controller หลายที่

ไม่มีแบบที่ดีกว่าเสมอไป ขึ้นกับจำนวน cluster, ทีมที่ดูแล, ข้อกำหนดด้านเครือข่าย (cluster ที่ไม่ยอมให้ inbound) และว่าอยากได้ UI กลางหรือไม่

ลำดับและการพึ่งพาระหว่าง service

บางชุดต้องขึ้นตามลำดับ เช่น CRD ก่อน แล้วค่อยทรัพยากรที่ใช้ CRD นั้น ใน Argo CD ใช้ sync waves (annotation argocd.argoproj.io/sync-wave) และ hook ส่วน Flux ใช้ dependsOn ใน Kustomization ถ้าไม่จัดลำดับ จะเห็น error ช่วงแรกว่าไม่รู้จัก kind ซึ่งมักหายเองเมื่อ reconcile รอบถัดไป แต่ทำให้ health ผิดพลาดชั่วคราว

ปล่อยทีละน้อย แล้วให้ข้อมูลตัดสิน

Kubernetes Deployment ทำ rolling update ได้ แต่ไม่มีแนวคิด “ปล่อยให้ผู้ใช้ 10% ก่อนแล้วดูตัวชี้วัด” Argo Rollouts เพิ่ม resource ชื่อ Rollout ที่ใช้แทน Deployment เพื่อรองรับ canary และ blue-green พร้อมวิเคราะห์ metric อัตโนมัติ (Flagger ของ Flux เป็นอีกตัวเลือกที่แนวคิดคล้ายกัน)

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: web
spec:
  replicas: 5
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.8.3
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - analysis:
            templates:
              - templateName: success-rate
        - setWeight: 50
        - pause: { duration: 10m }
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
    - name: success-rate
      interval: 1m
      count: 5
      successCondition: result[0] >= 0.99
      failureLimit: 1
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{app="web",code!~"5.."}[2m]))
            /
            sum(rate(http_requests_total{app="web"}[2m]))

ถ้า analysis ไม่ผ่านตามเงื่อนไข Rollout จะถูก abort และย้อน traffic กลับเวอร์ชันเสถียร โดยไม่ต้องมีคนตื่นมากด การจะน่าเชื่อถือได้ ตัวชี้วัดต้องสะท้อนประสบการณ์ผู้ใช้จริง (อัตรา error, latency) และต้องมี traffic พอให้ตัวเลขมีความหมาย ถ้า canary ได้ request แค่ไม่กี่ครั้งต่อนาที ผลวิเคราะห์ก็สุ่มเกินจะไว้ใจ

ย้อน image กลับเวอร์ชันเก่าทำได้ในไม่กี่นาที แต่ถ้าเวอร์ชันใหม่เปลี่ยน schema ของฐานข้อมูลไปแล้ว โค้ดเก่าอาจใช้ schema ใหม่ไม่ได้ รูปแบบที่ลดความเสี่ยงคือ expand/contract (หรือ parallel change) แบ่งการเปลี่ยนเป็นหลายรอบที่แต่ละรอบเข้ากันได้กับโค้ดทั้งเวอร์ชันเก่าและใหม่

1 Expandเพิ่ม column ใหม่ (nullable)
→
2 Dual writeโค้ดใหม่เขียนทั้งสองที่
→
3 Backfill + switch readย้ายข้อมูลเก่า แล้วอ่านจากที่ใหม่

Security, scalability และ monitoring ของตัว pipeline

Advance

Ensure security, scalability, and monitoring of CI/CD pipelines

pipeline คือเป้าโจมตี

pipeline มักถือสิทธิ์สูงกว่านักพัฒนาคนใดคนหนึ่ง (เข้า registry, cluster, secret) การเจาะ pipeline จึงคุ้มกว่าการเจาะแอป OWASP มีรายการ Top 10 CI/CD Security Risks ซึ่งรวมความเสี่ยง เช่น การควบคุม flow ไม่เพียงพอ (ใครก็ push โค้ดเข้า production โดยไม่มี review), pipeline ที่รันโค้ดอันตรายจาก PR ภายนอก (poisoned pipeline execution), สิทธิ์ของ pipeline เกินจำเป็น, การจัดการ credential ไม่ดี และ dependency ที่ไม่ผ่านการตรวจ ควรตรวจชื่อและลำดับของแต่ละข้อกับเอกสารฉบับล่าสุดก่อนอ้างอิง

ความเสี่ยงตัวอย่างที่เกิดจริงได้มาตรการ
โค้ดจาก PR ภายนอกรันใน pipeline ที่มี secretfork ส่ง PR แก้สคริปต์ build แล้วอ่าน secret ออกไปไม่ให้ PR จาก fork เข้าถึง secret, ใช้ approval ก่อนรัน, แยก pipeline ที่มีสิทธิ์สูงไว้ใน branch ที่ป้องกัน
สิทธิ์เกินจำเป็นservice connection เดียวเข้าได้ทุก subscriptionแยกต่อ environment, ให้ role น้อยที่สุด, ใช้ OIDC/federation อายุสั้น
dependency และ action จากภายนอกใช้ uses: some/action@main ที่เจ้าของแก้ภายหลังpin เวอร์ชันหรือ commit SHA, ใช้ lockfile, ตรวจ SCA
artifact ถูกแก้ระหว่างทางimage ที่ deploy ไม่ใช่อันที่ builddeploy ด้วย digest, ลงนาม (เช่น cosign), เก็บ SBOM และ provenance (SLSA)
ไม่มีร่องรอยให้ตรวจแก้ pipeline แล้วไม่รู้ใครทำเมื่อไรaudit log, branch protection, pipeline เป็นโค้ดผ่าน review

ใน Azure DevOps การบังคับให้ pipeline ต้องใช้ template ที่ผ่านการอนุมัติ (required template check ที่ environment หรือ service connection) ช่วยให้ทีมแพลตฟอร์มฝังขั้นตอนบังคับ เช่น scan และ sign ไว้ใน extends template ที่ทีมแอปไม่ข้ามได้ ใน GitHub Actions ให้จำกัด permissions: ของ GITHUB_TOKEN ระดับ workflow

# GitHub Actions: จำกัดสิทธิ์ token และ pin action ด้วย commit SHA
permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<full-commit-sha>   # แทนด้วย SHA จริงของเวอร์ชันที่ตรวจแล้ว
      - run: npm ci && npm test

Scalability: ทำให้ pipeline ไม่เป็นคอขวด

เมื่อทีมโตขึ้น คิว build ยาวและเวลา build บวมคือสัญญาณแรก ทางที่ใช้บ่อย: self-hosted agent ที่ปรับขนาดอัตโนมัติ (Azure DevOps มี Virtual Machine Scale Set agents, GitHub มี runner scale set), cache dependency และ layer ของ image, แบ่ง test เป็นชุดขนานด้วย strategy: matrix หรือ parallel, ให้ job ที่ไม่ขึ้นต่อกันรันพร้อมกัน และรันเฉพาะส่วนที่เปลี่ยนใน monorepo (path filter) ข้อแลกเปลี่ยนคือ self-hosted agent ต้องดูแลความปลอดภัยและการอัปเดตเอง และต้องไม่ใช้ agent ที่คงสถานะข้าม job ร่วมกับงานที่ไม่ไว้ใจกัน

strategy:
  matrix:
    shard1: { SHARD: "1/4" }
    shard2: { SHARD: "2/4" }
    shard3: { SHARD: "3/4" }
    shard4: { SHARD: "4/4" }
  maxParallel: 4
steps:
  - script: npx jest --shard=$(SHARD)

Monitoring: วัดตัว pipeline เหมือนวัดบริการ

สิ่งที่ควรเก็บมี เวลา build (p50/p95) แยกตามขั้น, อัตราล้ม และสาเหตุ, อัตรา flaky test, เวลารอคิว, ค่าใช้จ่ายต่อ build และ ความใหม่ของ agent image แล้วตั้งแจ้งเตือนเมื่อค่าผิดปกติ ไม่ใช่รอให้คนบ่น ส่วนตัวชี้วัดด้านการส่งมอบที่ DORA ใช้ คือ deployment frequency, lead time for changes, change failure rate, failed deployment recovery time และ (เพิ่มในรายงานปี 2024) rework rate ให้ใช้เป็นเครื่องมือดูแนวโน้มของทีม ไม่ใช่เกณฑ์เปรียบเทียบคนหรือทีม เพราะเมื่อตัวเลขกลายเป็นเป้า คนจะปรับพฤติกรรมให้ตัวเลขสวย

Advance

วงจรจริงมีหลาย loop ซ้อนกัน

lifecycle มักวาดเป็นรูปเลขแปดแนวนอน ไม่ใช่เส้นตรง: plan → code → build → test → release → deploy → operate → monitor แล้ววนกลับ plan สิ่งที่ทำให้เรียกว่า “feedback loop” คือแต่ละช่วงส่งข้อมูลย้อนกลับไปช่วงก่อนหน้า และความเร็วของการย้อนกลับสำคัญพอกับขนาดของข้อมูล

loopเวลาที่ควรได้คำตอบข้อมูลที่ไหลกลับ
IDE / pre-commitวินาทีlint, type error, secret ที่เผลอใส่
PR validationไม่กี่นาทีbuild, unit test, quality gate
หลัง deploy ไป stagingนาทีถึงสิบนาทีsmoke test, DAST, integration test
progressive delivery ใน productionนาทีถึงชั่วโมงerror rate, latency, ผลของ canary analysis

หลักคือย้ายการตรวจไปทางซ้าย (shift left) เมื่อทำได้ถูกกว่า แต่ไม่ใช่ทุกอย่างตรวจได้ก่อนปล่อย ปัญหาบางแบบเห็นได้เฉพาะใน production จึงต้องมีทางขวาด้วย (shift right): observability, canary, feature flag และ runbook ที่ซ้อมจริง

Observability ที่ผูกกับ release

เมื่อเห็นว่า error พุ่ง คำถามแรกคือ “เปลี่ยนอะไรไปเมื่อสักครู่” ถ้า deployment แต่ละครั้งถูกบันทึกเป็น event ที่วางทับบนกราฟ (annotation ใน Grafana, release marker ในเครื่องมือ APM) พร้อมเวอร์ชัน และ commit การหาสาเหตุเร็วขึ้นมาก การติด label เวอร์ชันบน metric และ log ก็ให้ผลคล้ายกัน

SLO และ error budget เป็นตัวตัดสินจังหวะการปล่อย

SLO คือเป้าหมายระดับบริการ เช่น 99.9% ของ request สำเร็จในช่วง 30 วัน ส่วนที่เหลือ (0.1%) คือ error budget ถ้าใช้หมดเร็ว ทีมชะลอการปล่อยฟีเจอร์และเอาเวลาไปแก้ความเสถียร ถ้ายังเหลือมาก ก็ปล่อยได้ถี่ขึ้นหรือรับความเสี่ยงมากขึ้น วิธีนี้เปลี่ยนการถกเถียงเรื่อง “ปล่อยเร็วหรือปล่อยปลอดภัย” เป็นตัวเลขที่ตกลงกันล่วงหน้า

# ตัวอย่างกฎ alert แบบ burn rate (Prometheus) — ตัวเลขและ window ต้องปรับตาม SLO จริงของบริการ
groups:
  - name: web-slo
    rules:
      - alert: WebErrorBudgetFastBurn
        expr: |
          (
            sum(rate(http_requests_total{app="web",code=~"5.."}[5m]))
            /
            sum(rate(http_requests_total{app="web"}[5m]))
          ) > (14.4 * 0.001)
        for: 2m
        labels:
          severity: page
        annotations:
          summary: "web กำลังใช้ error budget เร็วกว่าปกติมาก"

ตัวคูณ 14.4 มาจากแนวทาง multi-window burn rate ในหนังสือ SRE Workbook ของ Google ซึ่งหมายถึงใช้ budget 2% ของเดือนในหนึ่งชั่วโมง ควรอ่านที่มาก่อนนำไปตั้งค่าจริง และมักใช้สองหน้าต่างเวลาร่วมกัน (สั้นกับยาว) เพื่อลด alert หลอก

หลังเหตุการณ์: postmortem ที่ไม่หาคนผิด

incident ที่เกี่ยวกับ pipeline หรือ release ควรจบด้วยบันทึกที่ตอบสี่เรื่อง: เกิดอะไรขึ้นตามลำดับเวลา, ตรวจพบได้ด้วยวิธีใด (และทำไมไม่เร็วกว่านี้), อะไรทำให้เหตุการณ์ใหญ่ขึ้น และ action ที่ต้องทำพร้อมเจ้าของกับกำหนดเวลา ที่สำคัญคือ action ต้องเปลี่ยนระบบ (เพิ่ม test, เพิ่ม gate, ปรับ alert) ไม่ใช่แค่ “ระวังให้มากขึ้น”

สิ่งที่ผู้นำ lifecycle ต้องตอบได้ตอนนี้ไหลช้าตรงไหน (lead time แตกเป็นขั้นอะไรบ้าง), ปล่อยพลาดแล้วฟื้นได้เร็วแค่ไหน, ทีมไว้ใจ pipeline พอจะปล่อยบ่อยหรือไม่ และตัวชี้วัดที่ใช้ถูกใช้เพื่อเรียนรู้หรือเพื่อกดดัน

Lab 2: เขียน pipeline จากโจทย์

โจทย์: repo เป็น Node.js มี npm test และ npm run build (ได้โฟลเดอร์ dist) ต้องการ (1) รันบน push เข้า main และ PR (2) cache dependency (3) publish ผล test (4) publish dist เป็น artifact (5) deploy ไป staging อัตโนมัติ และ production เมื่อมีคนอนุมัติ

แนวคำตอบ 
trigger: [main]
pr: [main]

stages:
  - stage: Build
    jobs:
      - job: BuildAndTest
        pool: { vmImage: ubuntu-latest }
        steps:
          - task: Cache@2
            inputs:
              key: 'npm | "$(Agent.OS)" | package-lock.json'
              path: $(Pipeline.Workspace)/.npm
          - script: npm ci --cache $(Pipeline.Workspace)/.npm
          - script: npm test -- --ci
          - task: PublishTestResults@2
            condition: succeededOrFailed()
            inputs:
              testResultsFormat: JUnit
              testResultsFiles: junit.xml
          - script: npm run build
          - publish: dist
            artifact: web-dist

  - stage: Staging
    dependsOn: Build
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: Web
        pool: { vmImage: ubuntu-latest }
        environment: staging
        strategy:
          runOnce:
            deploy:
              steps:
                - script: ls $(Pipeline.Workspace)/web-dist

  - stage: Production
    dependsOn: Staging
    jobs:
      - deployment: Web
        pool: { vmImage: ubuntu-latest }
        environment: production   # ตั้ง approval ที่ environment นี้
        strategy:
          runOnce:
            deploy:
              steps:
                - script: ls $(Pipeline.Workspace)/web-dist

ขั้น deploy ในตัวอย่างใช้ ls แทนการ deploy จริง ให้เปลี่ยนเป็น task หรือ script ของปลายทางที่ใช้ ส่วน approval ตั้งที่หน้า Environments ของ production ไม่ได้อยู่ในไฟล์นี้

Lab 3: เขียน health check script

โจทย์: เขียน wait-healthy.sh <url> [max_tries] ที่เรียก <url>/health ทุก 5 วินาที สำเร็จเมื่อได้ HTTP 200 (exit 0) ถ้าครบจำนวนครั้ง (ค่าเริ่มต้น 10) แล้วยังไม่ได้ ให้ exit 1 พร้อมข้อความที่ stderr

แนวคำตอบ 
#!/usr/bin/env bash
set -euo pipefail

url="${1:?usage: wait-healthy.sh <url> [max_tries]}"
max="${2:-10}"

for ((i = 1; i <= max; i++)); do
  code=$(curl -s -o /dev/null -w '%{http_code}' "$url/health" || true)
  if [ "$code" = "200" ]; then
    echo "healthy after $i tries"
    exit 0
  fi
  echo "try $i/$max: status ${code:-none}"
  sleep 5
done

echo "not healthy after $max tries" >&2
exit 1

จุดที่ตรวจ: || true ทำให้ curl ที่เชื่อมต่อไม่ได้ไม่ฆ่า script ตอนที่เปิด set -e (script ต้องลองใหม่) ค่า default ของ argument และ exit code ที่ถูกต้องทั้งสองทาง

Lab 4: อ่าน Application ของ Argo CD

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/config.git
    targetRevision: main

ตอบให้ได้: (1) ถ้ามีคนลดจำนวน replica ใน cluster ด้วย kubectl scale จะเกิดอะไร (2) ถ้าลบไฟล์ service.yaml ออกจาก path นี้ใน Git จะเกิดอะไรกับ Service ใน cluster (3) ถ้า namespace web ยังไม่มี การ sync จะเป็นอย่างไร

เฉลย Lab 4
  1. selfHeal ตรวจพบ drift และปรับ replica กลับตามค่าใน Git (ถ้า replica ถูกควบคุมด้วย HPA ต้องกันไม่ให้สองฝ่ายแย่งกัน เช่น ไม่ระบุ replicas ใน manifest หรือใช้ ignoreDifferences)
  2. prune ลบ Service ออกจาก cluster เพราะไม่อยู่ใน Git แล้ว
  3. sync ล้มด้วย error ว่าไม่พบ namespace จนกว่าจะสร้างก่อน หรือเพิ่ม syncOptions: [CreateNamespace=true]
